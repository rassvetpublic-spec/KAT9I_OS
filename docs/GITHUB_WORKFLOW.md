# GitHub Workflow KAT9I_OS — рабочая памятка

Это короткая практическая инструкция. Она не заменяет каноническую политику `docs/spec/24_GITHUB_PROJECT_MANAGEMENT.md`, архитектурный Gate в Issue #62 или конкретные требования рабочих Issues.

## 1. Что это?

GitHub Project — главный визуальный экран работы. Issue — каноническая карточка конкретной задачи. Branch — отдельная рабочая ветка. Pull Request (PR) — запрос на принятие изменения. Actions / CI — автоматические проверки. Review / QA — проверка результата. Merge — принятие изменения в `main`.

## 2. Зачем это нужно?

Чтобы в любой момент было видно:

`что появилось → что нужно разобрать → что можно брать → что сейчас делается → что проверяется → что заблокировано → что готово`.

GitHub Project показывает состояние, но не заменяет Issue и не становится вторым источником требований.

## 3. Где это видно в KAT9I_OS?

- Project `KAT9I_OS — разработка` — общий экран управления.
- Issue #62 — порядок Gate G0→G4 и условия перехода между этапами.
- Issue #1 — настройка GitHub как Control Plane (управляющего контура).
- `docs/spec/24_GITHUB_PROJECT_MANAGEMENT.md` — канонические правила GitHub-процесса.
- `AGENTS.md` — обязательные правила для AI-агентов.
- `.github/PULL_REQUEST_TEMPLATE.md` — единый шаблон PR.
- `.github/ISSUE_TEMPLATE/` — простые формы создания задач.

## 4. Что происходит автоматически?

То, что уже реализовано репозиторием:

- GitHub Actions запускает контроль качества;
- отдельный workflow публикует Pages;
- triage помогает разобрать новые обращения;
- Dependabot следит за поддерживаемыми зависимостями;
- связанные PR и Issues сохраняют историю работы и Evidence.

Защита `main` через GitHub Ruleset и настройка Project v2 пока имеют инфраструктурный статус `PROVISIONAL`: их фактическое платформенное состояние отслеживается в Issue #1 и должно подтверждаться отдельным Evidence. До такой проверки нельзя считать, что прямые изменения, удаление или force push уже технически заблокированы.

Автоматизация не имеет права превращать факт merge в QA PASS или Gate PASS.

## 5. Автоматическая настройка Project

Для первоначального развёртывания и повторной проверки Project используется `scripts/configure_project.ps1`.

Настройщик рассчитан на Project #2 `KAT9I_OS — разработка` и работает повторяемо: уже существующие канонические поля не дублируются, стандартные значения `Todo / In Progress / Done` переименовываются с сохранением их идентичности, а неизвестные значения вызывают безопасную остановку вместо удаления данных.

Он настраивает:

- связь Project с каноническим репозиторием;
- `Status`, `Gate`, `Priority`, `Work Type`, `Область`, `Размер`;
- `Implementation Worker`, `QA Worker`, `Claim`, `Target`, `Risk`, `Evidence`;
- недельное поле `Итерация`;
- добавление актуальных открытых Issues и PR, а также управляющей Issue #62;
- канонические представления Control Tower, Architecture G1, Ready Queue, Active Workers, QA Queue, Blocked, v0.1 Roadmap, Security, Evidence / Compliance и Unclassified, если API GitHub позволяет создать их для текущего типа токена.

Для доступа к пользовательскому Project GitHub CLI должен быть авторизован с правом `project`. Сам настройщик не хранит токены и не добавляет секреты в репозиторий.

Встроенные Project Workflows не объявляются настроенными, пока их фактическое состояние не подтверждено Evidence. Если GitHub API не позволяет создать нужное правило программно, это остаётся отдельным минимальным платформенным шагом.

Настройщик никогда автоматически не выполняет merge, не выставляет `QA PASS` и не объявляет Gate пройденным.

## 6. Что нужно делать руками?

Минимальный рабочий цикл:

1. Открыть Project и выбрать понятную Issue.
2. Проверить Gate, зависимости и Scope.
3. Исполнитель оставляет `FAST-CLAIM`.
4. Создать ветку от свежего `main`.
5. Работать только в Scope Issue.
6. Открыть Draft PR и связать его с Issue.
7. Дождаться зелёного CI.
8. Перевести PR в Ready for review и пройти Review / независимый QA, если он требуется.
9. Исправить обоснованные замечания и разрешить threads только после исправления.
10. Даже после полного PASS **не выполнять merge**, пока владелец проекта явно не напишет `mtd`, `MTD` или `мтд`.
11. После `mtd` выполнить merge и проверить фактическое состояние `main`, Issue и Project.

## Главное правило

> **Merge разрешён только после явной команды владельца `mtd` / `MTD` / `мтд`.**

Зелёный CI, approved review, QA PASS и доступная кнопка Merge означают только «изменение готово к возможному принятию». Они не заменяют `mtd`.

## Статусы Project

KAT9I_OS уже использует более строгую Gate/QA-модель. Канонические значения поля `Status` нужно использовать дословно:

- `Входящие` — новая работа;
- `Нужно разобрать` — нужно определить Gate, приоритет, Scope и зависимости;
- `Готово к работе` — задачу можно брать;
- `В работе` — есть активный исполнитель;
- `Проверка QA` — результат проверяется;
- `Заблокировано` — продолжать нельзя до устранения блокера;
- `Готово` — работа действительно завершена по правилам проекта.

Не сокращать эту модель только ради более простой доски: отдельные `Проверка QA` и `Заблокировано` нужны для доказуемого процесса KAT9I_OS.

## Приоритет

- `P0` — критично, блокирует ключевой этап или безопасность;
- `P1` — важно;
- `P2` — полезно;
- `P3` — позже.

Приоритет не заменяет Gate: задача может быть P0, но всё равно оставаться LOCKED более ранним Gate.

## Если что-то сломалось

Сначала ответить на четыре вопроса:

1. Что именно упало?
2. Почему это произошло?
3. Где это видно: Issue, PR, Actions, Review или Project?
4. Что нужно исправить, чтобы получить проверяемый PASS?

Не скрывать красные проверки и не закрывать Issue только потому, что PR был merged.
