# GitHub Workflow KAT9I_OS — рабочая памятка

Это короткая практическая инструкция. Она не заменяет каноническую политику `docs/spec/24_GITHUB_PROJECT_MANAGEMENT.md`, архитектурный Gate в Issue #62 или конкретные требования рабочих Issues.

## 1. Что это?

GitHub Project — главный визуальный экран работы. Issue — каноническая карточка конкретной задачи. Branch — отдельная рабочая ветка. Pull Request (PR) — запрос на принятие изменения. Actions / CI — автоматические проверки. Review / QA — проверка результата. Merge — принятие изменения в `main`.

## 2. Зачем это нужно?

Чтобы в любой момент было видно:

`что появилось → что нужно разобрать → что можно брать → что сейчас делается → что проверяется → что заблокировано → что готово`.

GitHub Project показывает состояние, но не заменяет Issue и не становится вторым источником требований.

## 3. Где это видно в KAT9I_OS?

- Project `KAT9I_OS — разработка` — общий экран управления.
- Issue #62 — порядок Gate G0→G4 и условия перехода между этапами.
- Issue #1 — настройка GitHub как центра управления.
- `docs/spec/24_GITHUB_PROJECT_MANAGEMENT.md` — канонические правила GitHub-процесса.
- `AGENTS.md` — обязательные правила для AI-агентов.
- `.github/PULL_REQUEST_TEMPLATE.md` — единый шаблон PR.
- `.github/ISSUE_TEMPLATE/` — простые формы создания задач.

## 4. Что происходит автоматически?

То, что уже реализовано репозиторием:

- GitHub Actions запускает контроль качества;
- отдельный workflow публикует Pages;
- triage помогает разобрать новые обращения;
- Dependabot следит за поддерживаемыми зависимостями;
- связанные PR и Issues сохраняют историю работы и доказательства.

Защита `main` через GitHub Ruleset и настройка Project v2 пока имеют инфраструктурный статус `PROVISIONAL`: их фактическое платформенное состояние отслеживается в Issue #1 и должно подтверждаться отдельным доказательством. До такой проверки нельзя считать, что прямые изменения, удаление или force push уже технически заблокированы.

Автоматизация не имеет права превращать факт merge в прохождение проверки качества или этапа.

## 5. Автоматическая настройка Project

Для первоначального развёртывания и повторной проверки Project используется `scripts/configure_project.ps1`.

Настройщик рассчитан на Project #2 `KAT9I_OS — разработка` и работает повторяемо. Уже существующие канонические поля не дублируются. Известные старые английские названия распознаются как миграционные алиасы, но если безопасное переименование значения потребовало бы заменить option ID и нельзя доказать сохранение привязок Items, настройщик останавливается без изменения данных и требует явной миграции. Неизвестные значения также вызывают безопасную остановку вместо удаления или скрытой замены данных.

Он настраивает видимые пользовательские поля:

- `Статус`;
- `Этап`;
- `Приоритет`;
- `Тип`;
- `Область`;
- `Размер`;
- `Итерация`;
- `Исполнитель`;
- `Проверяющий`;
- `Исполнение`;
- `Цель`;
- `Риск`;
- `Доказательство`.

Итерация длится **3 дня**. Если существующее поле `Итерация` имеет другую длительность, настройщик не сбрасывает существующие периоды и привязки, а останавливается для явной безопасной миграции.

Настройщик также:

- связывает Project с каноническим репозиторием;
- добавляет актуальные открытые Issues и PR, а также управляющую Issue #62; ошибка получения полного списка является блокером, а не тихо пропускается;
- поддерживает **ровно восемь** основных рабочих представлений: `00 — Dashboard`, `01 — Queue`, `02 — Active Work`, `03 — QA Gate`, `04 — Release Flow`, `05 — Roadmap`, `06 — Blocked / Parking`, `07 — Agent KPI`;
- Roadmap и Agent KPI имеют отдельные представления по принятой владельцем Issue #150; технический контракт находится в `config/project_views.json`;
- после успешного создания восьми канонических представлений удаляет только заранее известные старые/сверхлимитные представления; неизвестные пользовательские представления автоматически не удаляет и при их обнаружении останавливается для ручного разбора;
- имена восьми канонических представлений проверяет с учётом регистра и не принимает дубли;
- не хранит токены и секреты;
- никогда автоматически не выполняет merge, не выставляет прохождение проверки качества и не объявляет этап пройденным.

Для доступа к пользовательскому Project GitHub CLI должен быть авторизован с правом `project`.

## 6. Что нужно делать руками?

Минимальный рабочий цикл:

1. Открыть Project и выбрать понятную Issue.
2. Проверить этап, зависимости и границы работы.
3. Исполнитель оставляет `FAST-CLAIM`.
4. Создать ветку от свежего `main`.
5. Работать только в рамках Issue.
6. Открыть Draft PR и связать его с Issue.
7. Дождаться зелёного CI.
8. Перевести PR в Ready for review и пройти Review / независимую проверку качества, если она требуется.
9. Исправить обоснованные замечания и разрешить threads только после исправления.
10. Даже после полного PASS **не выполнять merge**, пока владелец проекта явно не напишет `mtd`, `MTD` или `мтд`.
11. После `mtd` выполнить merge и проверить фактическое состояние `main`, Issue и Project.

## Главное правило

> **Merge разрешён только после явной команды владельца `mtd` / `MTD` / `мтд`.**

Зелёный CI, approved review, QA PASS и доступная кнопка Merge означают только «изменение готово к возможному принятию». Они не заменяют `mtd`.

## Статусы Project

Канонические значения поля `Статус`:

- `Входящие` — новая работа;
- `Нужно разобрать` — нужно определить этап, приоритет, границы работы и зависимости;
- `Готово к работе` — задачу можно брать;
- `В работе` — есть активный исполнитель;
- `Проверка QA` — результат проходит review / независимую проверку качества;
- `Заблокировано` — продолжать нельзя до устранения блокера;
- `Готово` — работа действительно завершена по правилам проекта.

Поле `Исполнение` отдельно показывает состояние захвата работы:

- `Свободно`;
- `В очереди`;
- `Активно`;
- `На проверке`;
- `Заблокировано`;
- `Освобождено`.

## Приоритет

- `P0` — критично, блокирует ключевой этап или безопасность;
- `P1` — важно;
- `P2` — полезно;
- `P3` — позже.

Приоритет не заменяет этап: задача может быть P0, но всё равно оставаться заблокированной более ранним этапом.

## Если что-то сломалось

Сначала ответить на четыре вопроса:

1. Что именно упало?
2. Почему это произошло?
3. Где это видно: Issue, PR, Actions, Review или Project?
4. Что нужно исправить, чтобы получить проверяемый PASS?

Не скрывать красные проверки и не закрывать Issue только потому, что PR был merged.

## Для новичка

Если термин непонятен, используйте `docs/guides/GITHUB_FOR_COWORKERS.md` и `docs/GLOSSARY.md`. Английские названия GitHub допустимы, но рядом должно быть простое русское объяснение.


## Миграция Project по #150

Владелец принял переход от пяти к восьми представлениям. Подробное соответствие и границы находятся в `docs/spec/24_GITHUB_PROJECT_MANAGEMENT.md`, машинный набор — в `config/project_views.json`.

После CI, независимого QA и разрешённого merge workflow `Project — миграция восьми представлений` запускается владельцем из Actions на main или точным управляющим комментарием в #150. Вторая строка комментария фиксирует `expected_head=<полный SHA main>`; первая — `KAT9I-CONTROL/1 | PROJECT-VIEWS-APPLY`. Ввод комментария проверяется как данные, не исполняется оболочкой.

Workflow получает только проверенную main, использует существующий KAT9I_PROJECT_TOKEN, сохраняет снимок до изменения и итоговый аудит в Actions artifacts. Новые представления проверяются до удаления прежних. Неизвестные представления и несовместимые поля останавливают настройщик. При частичной ошибке снимок сохраняется; автоматического отката или объявления PASS нет. Полный аудит может оставаться FAIL из-за отдельного drift карточек — это не скрывается.

Наличие восьми вкладок не означает завершения всей #150: проекция дополнительных стадий QUEUE-GUARD, Parent Roadmap, время в статусе и реальные KPI требуют своих источников данных и отдельного Evidence. GitHub API настройки visibleFieldIds не позволяет настроить все параметры группировки и карточек UI. До их проверки полное UX acceptance не заявляется.
