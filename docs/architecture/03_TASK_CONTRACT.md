# 3. Контракты и модель задачи

## Схема

```text
Запрос пользователя
        ↓
TaskContract (контракт задачи)
        │
        ├── цель
        ├── область разрешённых действий
        ├── ссылки на контекст
        ├── ссылка на действующие правила
        ├── требования к возможностям исполнителя
        ├── требования к уровню ИИ
        ├── требования к результату
        ├── место сохранения результата
        ├── требования QA (независимой проверки)
        └── идентификаторы для метрик
        ↓
   Core / Context / Inference / Coworker
        ↓
     Execution
        ↓
     TaskResult
        ↓
     ResultRef
```

## 3.1. Назначение

`TaskContract (контракт задачи)` — универсальный паспорт работы KAT9I_OS.

Он отвечает на вопросы:

- что нужно сделать;
- в какой области разрешена работа;
- где находится необходимый контекст;
- какие правила действуют;
- какие возможности нужны исполнителю;
- какой результат считается правильным;
- куда записать результат;
- требуется ли независимый QA (контроль качества).

Контракт не должен содержать весь репозиторий, всю историю диалога, всю базу знаний, полный набор навыков или всю историю метрик. По умолчанию используются ссылки на источники и результаты.

## 3.2. Четыре отдельные сущности

KAT9I_OS разделяет описание задачи, текущее состояние, результат и зависимости:

```text
TaskContract
Что должно быть сделано

TaskRuntimeState
Что происходит сейчас

TaskResult
Чем закончилась задача

TaskGraph
Как задача связана с другими задачами
```

Это предотвращает превращение одного контракта в перегруженный объект, содержащий требования, исполнение, историю и результат одновременно.

## 3.3. TaskContract — требования задачи

Минимально контракт должен содержать:

- `task_id` — идентификатор задачи;
- `parent_task_id` — идентификатор родительской задачи, если это подзадача;
- источник задачи;
- цель;
- проект / Workspace (рабочее пространство);
- основной Domain (домен — тип работы);
- Scope (область разрешённых действий);
- `ContextRefs` — ссылки на контекст;
- `RulesRef` — ссылку на итоговый набор правил;
- требования к возможностям исполнителя;
- требования к уровню ИИ;
- `OutputContract` — требования к результату;
- `ResultSink` — место сохранения результата;
- требования QA;
- идентификаторы, необходимые системе метрик.

## 3.4. Scope — область разрешённых действий

Исполнитель не имеет права самостоятельно расширять Scope (разрешённую область работы).

Если во время выполнения требуется действие вне разрешённой области, задача должна перейти в состояние запроса расширения области или блокировки, а не продолжать работу самовольно.

Scope может задавать:

- репозиторий;
- разрешённые пути;
- запрещённые пути;
- допустимые типы изменений;
- ограничения на создание веток, PR (запросов на внесение изменений) и merge (слияние изменений);
- разрешённые внешние системы.

## 3.5. ContextRefs — ссылки на контекст

Контекст передаётся по принципу `Reference-first (сначала ссылка)`.

Контракт может ссылаться на:

- GitHub repository (репозиторий);
- Issue (задачу GitHub);
- PR (запрос на внесение изменений);
- Google Drive;
- личную базу знаний;
- локальный файл;
- MCP resource (ресурс через MCP);
- другой поддерживаемый источник.

Если исполнитель способен сам получить источник через Connector (подключаемый источник), KAT9I_OS не должна без необходимости переносить его содержимое через собственный контекст.

## 3.6. RulesRef — ссылка на правила

TaskContract не содержит всю базу правил.

Он ссылается на конкретный `Effective Ruleset (итоговый набор действующих правил)`.

Для воспроизводимости необходимо сохранять:

- версию;
- контрольный отпечаток;
- статус разрешения правил;
- источник происхождения.

Это позволяет доказать, какие именно правила действовали во время выполнения задачи.

## 3.7. Требования к возможностям исполнителя

Core описывает не конкретного исполнителя, а необходимые возможности.

Например:

- чтение GitHub;
- запись в репозиторий;
- запуск Python;
- работа на Windows;
- создание PR;
- доступ к определённому Connector.

`Coworker (модуль распределённой работы)` выбирает конкретного исполнителя позже.

## 3.8. Требования к ИИ

TaskContract не должен быть привязан к конкретному названию модели.

Он задаёт требования, например:

- минимальный уровень качества;
- сложность рассуждения;
- требования приватности;
- допустимость локального выполнения;
- возможность повышения уровня модели;
- требуемые мультимодальные или инструментальные способности.

`Inference (модуль выбора ИИ)` выбирает конкретный маршрут выполнения позже.

## 3.9. OutputContract — контракт результата

Задача заранее определяет, что считается правильным результатом.

Примеры:

- для разработки — PR с изменениями и тестами;
- для исследования — документ с источниками и выводами;
- для Suno — доменный пакет результата;
- для QA — вердикт и доказательства проверки.

Доменные детали результата принадлежат соответствующему Domain, а не Core.

## 3.10. ResultSink и ResultRef

`ResultSink (место сохранения результата)` определяет, куда исполнитель должен записать результат.

Примеры:

- GitHub PR;
- GitHub Issue или комментарий;
- Google Drive;
- локальный файл;
- артефакт;
- личная база знаний.

После выполнения KAT9I_OS по возможности получает `ResultRef (ссылку на результат)`, а не копию всего результата.

## 3.11. QA — требования независимой проверки

TaskContract должен уметь задавать:

- требуется ли QA;
- должен ли QA быть независимым;
- какие проверки обязательны;
- какие доказательства должны быть получены.

Если политика требует независимого QA:

```text
Implementation Worker != QA Worker
```

Это системное ограничение, а не рекомендация в тексте задания.

## 3.12. Метрики

TaskContract не содержит историю метрик.

Он передаёт только идентификаторы, необходимые для последующей агрегации, например:

- тип задачи;
- домен;
- проект;
- идентификатор эксперимента;
- идентификатор базовой линии.

Историю и агрегаты хранит отдельный модуль Metrics (метрики).

## 3.13. TaskRuntimeState — текущее состояние

Состояние выполнения хранится отдельно от требований задачи.

Оно может содержать:

- текущий статус;
- выбранного Worker (исполнителя);
- выбранного Provider (провайдера ИИ);
- lease (временное право владения задачей);
- номер попытки;
- временные отметки;
- ссылку на промежуточный или итоговый результат;
- статус QA.

## 3.14. TaskResult — результат

TaskResult фиксирует итог выполнения:

- статус;
- ResultRef;
- доказательства;
- сведения о проверке;
- причины ошибки или блокировки;
- метаданные, необходимые для метрик и самообучения.

## 3.15. TaskGraph — граф задач

Сложная работа разбивается на несколько связанных TaskContract.

```text
Parent Task
    ├── Subtask A
    ├── Subtask B
    └── QA Task
```

Каждая подзадача остаётся самостоятельной задачей со своим Scope, RulesRef, исполнителем и результатом.

Сложность последовательности и зависимостей хранится в TaskGraph, а не внутри одного перегруженного TaskContract.

## 3.16. Единственный источник истины

Внутри KAT9I_OS каноническое состояние исполнения формируют:

```text
TaskContract + TaskRuntimeState + TaskResult + TaskGraph
```

При этом внешние системы сохраняют собственную область истины.

Например GitHub Issue остаётся источником истины для самого Issue, а KAT9I_OS хранит своё исполнительное представление и ссылки на него.

## 3.17. Что запрещено помещать в TaskContract

По умолчанию в контракт не должны попадать:

- полная история диалога;
- полный репозиторий;
- вся личная база знаний;
- полный каталог Skills (навыков);
- полный каталог Tools (инструментов);
- история Metrics;
- внутренние рассуждения модели;
- секретные данные без необходимости;
- большие результаты предыдущих исполнителей, если на них можно передать ссылку.

## 3.18. Основные принципы

1. TaskContract описывает требования, а не историю выполнения.
2. Runtime-состояние хранится отдельно.
3. Результат хранится отдельно.
4. Зависимости задач хранятся в TaskGraph.
5. Большие данные передаются ссылками по принципу Reference-first.
6. Исполнитель не может самостоятельно расширить Scope.
7. TaskContract не привязан к конкретному Worker или конкретной модели ИИ.
8. QA задаётся как формальное требование.
9. История метрик не передаётся через контракт.
10. Подзадача создаётся как отдельный TaskContract, а не как изменение исходной цели родительской задачи.
