# 4. Правила и приоритет исполняемого кода

## Схема

```text
Задача
  ↓
Системные ограничения
+ личные правила
+ правила проекта
+ правила домена
+ правила конкретной задачи
  ↓
Rule Manager (менеджер правил)
  ↓
Проверка применимости и Scope (области действия)
  ↓
DENY (запрет) выше ALLOW (разрешения)
  ↓
Effective Ruleset (итоговый набор действующих правил)
  ↓
RESOLVED (разрешено) / BLOCKED (заблокировано)
  ↓
RulesRef (ссылка на набор правил)
  ↓
TaskContract (контракт задачи)
  ↓
Исполнение по приоритету:
Executable-first → Local-first → внешние провайдеры
```

## 4.1. Назначение Rule Manager

Rule Manager (менеджер правил) — единая подсистема KAT9I_OS, которая определяет, какие обязательные правила действуют для конкретной задачи.

В системе должен существовать один канонический механизм разрешения правил. Домены, Skills (навыки), Workers (исполнители) и внешние агенты не должны создавать собственные альтернативные механизмы определения приоритетов правил.

## 4.2. Главный принцип конфликтов

Запрет имеет приоритет над разрешением.

Если к одному действию одновременно применимы ALLOW (разрешить) и DENY (запретить), итогом является DENY.

Пример: работа с GitHub разрешена, но использование fork (форка — копии репозитория) запрещено. Итог: GitHub разрешён, fork запрещён.

## 4.3. Область действия правил

Rule Manager обязан учитывать Scope (область действия правила). Запрет более узкого действия не должен автоматически блокировать всю более широкую область.

Пример: разрешено работать с репозиторием, но запрещено напрямую изменять main. Следовательно, можно создавать ветку и PR (запрос на внесение изменений), но нельзя напрямую менять main.

Порядок обработки:

1. Собрать применимые правила.
2. Определить Scope каждого правила.
3. Определить конкретное действие.
4. Применить все запреты.
5. Применить разрешения, которые не конфликтуют с запретами.
6. Неразрешимая неоднозначность приводит к BLOCKED.

## 4.4. Источники правил

Правила могут поступать из нескольких источников:

- системные ограничения KAT9I_OS;
- Personal Rules (личные обязательные правила владельца);
- Workspace Rules (правила рабочего пространства или проекта);
- Domain Rules (правила домена);
- Task Rules (правила конкретной задачи).

Не используется простая схема «личное всегда выше проектного». Сначала определяется применимость и область действия, затем при конфликте применяется принцип «запрет выше разрешения».

## 4.5. Fail-closed — безопасная блокировка

Если система не может доказать, что потенциально опасное действие разрешено, оно не выполняется.

Причинами BLOCKED могут быть:

- неизвестная версия правил;
- повреждённый RulesRef;
- конфликт обязательных ограничений;
- неизвестный канонический репозиторий;
- отсутствие обязательного правила безопасности.

## 4.6. Effective Ruleset

Rule Manager формирует Effective Ruleset (итоговый набор правил) только для конкретной задачи. Исполнитель не должен получать всю базу правил пользователя или проекта.

Это уменьшает:

- объём контекста;
- расход токенов;
- число конфликтов;
- вероятность неправильной интерпретации.

TaskContract должен ссылаться на итоговый набор через RulesRef, содержащий как минимум версию, контрольный отпечаток, источник и статус RESOLVED или BLOCKED.

## 4.7. Rules и Preferences

Rule (правило) — обязательное требование. Нарушение приводит к блокировке или ошибке.

Preference (предпочтение) — мягкое пожелание. Оно не может отменять обязательное правило.

## 4.8. Executable-first — сначала исполняемый код

Фундаментальный принцип KAT9I_OS:

> Любой повторяемый, формализуемый и проверяемый шаг Skill (навыка), Workflow (процесса) или Domain (домена) должен по возможности выполняться локальным исполняемым кодом. ИИ используется только для остаточной части, требующей интерпретации, генерации или сложного рассуждения.

Skill не должен автоматически означать текстовый промпт. Целевая структура навыка:

```text
Skill
├── Executable Core (исполняемое ядро)
├── Model Logic (логика, требующая ИИ)
├── Rules (правила)
├── Tests (тесты)
└── Metrics (метрики)
```

## 4.9. Классы навыков

### CODE — полностью исполняемый код

ИИ не требуется. Примеры:

- Git diff;
- проверка Scope;
- SHA и контрольные суммы;
- проверка JSON/YAML;
- поиск файлов;
- проверка длины;
- статические проверки;
- сбор метрик;
- проверка формата;
- запуск тестов.

### HYBRID — код + ИИ

Код выполняет все детерминированные этапы, ИИ получает только остаточную интеллектуальную задачу и минимальный релевантный контекст.

### MODEL — преимущественно интеллектуальная задача

Используется для архитектуры, драматургии, сложного анализа, исследования и других задач, где требуется содержательное рассуждение. Даже в таких навыках получение данных, фильтрация, валидация и проверка результата по возможности остаются кодом.

## 4.10. Local-first — сначала локально

Если операция может быть выполнена локально достаточно качественно, безопасно, быстро и без платного внешнего вызова, локальный способ имеет приоритет.

Порядок предпочтений:

1. локальный детерминированный код;
2. локальные алгоритмы, индекс, поиск и БД;
3. локальный ИИ;
4. уже оплаченный подписочный ИИ;
5. платный API (программный интерфейс).

Каждый следующий уровень используется только для той части задачи, которую предыдущий уровень не может решить с требуемым качеством и безопасностью.

Local-first применяется поэтапно, а не ко всей задаче целиком.

## 4.11. Skill Compiler — перевод навыков в код

KAT9I_OS должна иметь механизм постепенного переноса повторяемых частей Skills и Workflows из промптов в исполняемый код.

Цикл:

```text
наблюдение повторяемого шага
  ↓
Learning (самообучение)
  ↓
предложение детерминировать шаг
  ↓
локальная реализация
  ↓
тесты
  ↓
независимый QA (контроль качества)
  ↓
новая версия Skill или Workflow
```

Одна из целей самообучения: искать не только способы улучшить промпт, но и части работы, которые ИИ больше не должен выполнять вообще.

## 4.12. Метрики зрелости

Для контроля перехода от ИИ к коду используются как минимум:

- Determinization Rate (доля работы, переведённой в детерминированный код);
- LLM Avoidance Rate (доля операций без ИИ);
- доля локального ИИ;
- доля подписочного ИИ;
- доля платного API;
- экономия внешних токенов;
- влияние локализации на время и качество;
- количество повторных работ после неверного выбора локального пути.

## 4.13. Исполняемые Workflows

Повторяемые процессы должны по возможности становиться исполняемыми Workflow (процессами), а не длинными инструкциями для модели.

Пример для разработки:

```text
Issue (задача GitHub)
→ проверка контракта кодом
→ подготовка Worktree (изолированной рабочей копии)
→ получение ссылок на контекст
→ модель выполняет только интеллектуальную часть
→ тесты кодом
→ Scope Guard (проверка области изменений) кодом
→ создание PR через GitHub
→ независимый QA
→ финальные проверки кодом
```

ИИ является одним из вычислительных компонентов Workflow Engine (движка процессов), а не самим движком.

## 4.14. Базовая триада KAT9I_OS

Три взаимосвязанных принципа:

1. Executable-first — сначала исполняемый код.
2. Local-first — если нужен интеллектуальный анализ, сначала локальный путь.
3. Reference-first — данные по возможности передаются ссылками, а не копируются целиком.

Эта триада является базовой политикой экономии, повторяемости и управляемости KAT9I_OS.
