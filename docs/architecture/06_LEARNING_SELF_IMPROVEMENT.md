# 6. Learning — самообучение и развитие KAT9I_OS

## Схема

Работа KAT9I_OS
→ Telemetry (события работы)
→ Metrics (числовые показатели)
→ MetricsSnapshot (компактный снимок метрик)
+ Feedback (обратная связь пользователя и QA)
+ ошибки / повторные попытки / успешные решения
→ Learning Engine (движок самообучения)
→ поиск закономерностей
→ улучшение Rule (правил), Skill (навыков), Workflow (процессов), Context (контекста), Routing (маршрутизации), Provider (провайдера ИИ), Worker (исполнителя), Executable Core (исполняемого кода), Personal Knowledge (личных знаний)
→ оценка риска изменения
→ L0 наблюдение / L1 безопасная автоматическая адаптация / L2 проверяемое изменение / L3 системное изменение
→ эксперимент / тесты / QA при необходимости
→ сравнение с Baseline (базовым уровнем)
→ Promotion (продвижение изменения) или откат
→ новая версия системы
→ новые метрики

## 6.1. Назначение

Самообучение — одна из основных возможностей KAT9I_OS.

Его задача — накапливать опыт реальной работы системы и автоматически улучшать её там, где улучшение можно доказать.

KAT9I_OS должна со временем становиться быстрее, дешевле, точнее, автономнее, лучше адаптированной к владельцу, менее зависимой от внешних ИИ и более предсказуемой.

## 6.2. Что считается обучением

Самообучение включает улучшение:

- Rules (правил);
- Skills (навыков);
- Workflow (процессов);
- Executable Core (исполняемой части);
- Context (контекста);
- Inference (выбора ИИ);
- Coworker (выбора исполнителя);
- Personal Layer (личного слоя).

Ключевой принцип: система должна не только учить ИИ работать лучше, но и постепенно уменьшать объём работы, которую вообще нужно поручать ИИ.

## 6.3. Источники обучения

Learning использует структурированные сигналы:

- завершённые и неудачные задачи;
- повторные попытки;
- результаты QA;
- пользовательские исправления;
- команды «принято»;
- отменённые решения;
- MetricsSnapshot;
- аномалии;
- результаты экспериментов;
- ошибки инструментов;
- выбор Provider и Worker;
- стоимость, время и токены;
- случаи ручного вмешательства.

## 6.4. Самообучение не должно существенно расходовать токены

Learning не анализирует всю историю системы после каждой задачи.

Обычный цикл сохраняет дешёвые структурированные факты. Глубокий анализ запускается по событию, аномалии, накопленному объёму данных или плановому анализу.

## 6.5. Два контура обучения

### Быстрый контур

Во время обычного выполнения:

- счётчики;
- обновление статистики;
- кэш;
- рейтинги;
- простые локальные правила;
- обновление текущих показателей.

Цель — 0 внешних LLM-токенов.

### Аналитический контур

Запускается при:

- достаточном количестве новых примеров;
- аномалии;
- падении качества;
- росте стоимости;
- росте Retry Rate (доли повторных попыток);
- повторяющихся пользовательских исправлениях;
- новом типе задачи;
- плановом анализе.

## 6.6. Local-first для самообучения

Приоритет:

1. обычный локальный код;
2. статистический анализ;
3. локальный ИИ;
4. подписочный внешний ИИ;
5. платный API.

Определение ухудшения показателя не требует ИИ. ИИ нужен для объяснения причин и выработки гипотез.

## 6.7. MetricsSnapshot вместо истории

Learning получает компактный снимок метрик, а не полную историю.

В него входят только релевантные агрегаты и аномалии. История остаётся в локальном хранилище.

## 6.8. Уровни самообучения

### L0 — наблюдение

Система сохраняет факт или закономерность, но не меняет поведение.

### L1 — безопасная адаптация

Автоматически изменяются низкорисковые параметры, если:

- обязательные Rules не меняются;
- Scope не расширяется;
- безопасность не ослабляется;
- есть простой откат;
- изменение измеримо.

### L2 — проверяемое изменение

Изменения Skill, Workflow, Prompt, Context Policy, Provider Routing, Validator или нового исполняемого шага проходят Proposal → тест → сравнение с Baseline → QA → Promotion или откат.

### L3 — системное изменение

Изменения Core, TaskContract, Rule Manager, Security, системных Rules, прав и критических контрактов проходят наиболее строгий процесс: Proposal → отдельная задача разработки → тесты → независимый QA → Approval (утверждение) → изменение → контроль регрессий.

## 6.9. Принцип риска

Чем выше потенциальный ущерб от самоизменения, тем сильнее требования к проверке изменения.

## 6.10. Learning Proposal

Для нетривиального изменения фиксируются:

- что меняется;
- почему;
- какие наблюдения это подтверждают;
- какие Metrics ухудшены;
- ожидаемый эффект;
- риск;
- Scope изменения;
- способ проверки;
- Baseline;
- способ отката.

## 6.11. Experiment

Новая версия может сначала использоваться ограниченно и сравниваться с текущей по QA PASS, времени, токенам, Retry Rate, пользовательским исправлениям и стоимости.

## 6.12. Promotion

Изменение считается успешным только при измеримом улучшении относительно Baseline.

## 6.13. Regression

После Promotion система продолжает наблюдение. Существенное ухудшение приводит к автоматическому откату там, где это допустимо, либо к BLOCKED + QA.

## 6.14. Самообучение Skills

Для каждого Skill желательно хранить историю версий и показатели качества, времени, токенов, повторных исправлений и доли исполняемого кода.

## 6.15. Skill Compiler

Learning связан со Skill Compiler (компилятором навыков), который ищет повторяемую модельную работу и пытается превратить её в локальный исполняемый алгоритм.

Путь развития:

MODEL Skill → HYBRID Skill → CODE Skill, если это возможно без потери качества.

## 6.16. Workflow Learning

Learning анализирует повторяемые последовательности работы и может предлагать новые исполняемые Workflow.

## 6.17. Routing Learning

Маршрутизация обучается на фактических результатах Provider / Worker / Model при сохранении минимальных требований TaskContract.

## 6.18. Обучение выбору контекста

Система учится определять минимальный достаточный контекст и уменьшать его без потери качества.

## 6.19. Пользовательские исправления

Исправление пользователя — сильный сигнал, но не автоматическое новое Rule. Система различает кандидата в Knowledge, Preference, Rule или временное решение.

## 6.20. Scope обучения

Возможные области:

- SYSTEM;
- DOMAIN;
- WORKSPACE;
- USER;
- SKILL;
- WORKER.

Личное обучение не должно автоматически становиться глобальным правилом продукта.

## 6.21. Provenance — происхождение обучения

Для каждого изменения сохраняются причины, версия системы, тесты, QA, метрики до и после, время принятия и факт отката.

## 6.22. Метрики Learning

Основные KPI (ключевые показатели эффективности):

- Learning Gain — улучшение качества;
- Proposal Success Rate — доля полезных предложений;
- Regression Rate — доля откатов;
- Automation Gain — снижение ручного вмешательства;
- Token Reduction — снижение токенов;
- Determinization Gain — перевод модельной работы в код;
- Routing Gain — улучшение маршрутизации;
- Context Reduction — сокращение контекста без потери качества.

## 6.23. Ограничение накладных расходов

Learning имеет собственную стоимость. Измеряются время, CPU, GPU, storage, внешние токены и API-стоимость.

В обычном Task Runtime накладные LLM-расходы Learning должны стремиться к нулю.

## 6.24. Независимый QA изменений KAT9I_OS

Для значимых изменений сохраняется правило:

Implementation Worker (исполнитель изменения) != QA Worker (независимый проверяющий).

## 6.25. Самообучение подчиняется Rule Manager

Learning не может:

- отменять DENY;
- расширять Scope;
- снижать Security;
- менять канонический репозиторий без разрешения;
- отключать обязательный QA;
- скрывать собственные изменения;
- удалять неудобные метрики.

## 6.26. Основной цикл развития

Работа → измерение → обнаружение закономерности → гипотеза → самое дешёвое возможное улучшение → предпочтительно локальный код → проверка → сравнение с Baseline → QA → Promotion → наблюдение → новое обучение.

## 6.27. Главный принцип

KAT9I_OS должна становиться умнее не за счёт постоянного увеличения промптов и числа обращений к моделям, а за счёт накопления проверенного опыта, улучшения маршрутизации, сокращения контекста и постепенного переноса повторяемой работы в локальный исполняемый код.

## 6.28. Обучение операционным параметрам

Learning должно учитывать параметры отказоустойчивости и исполнения как измеримые адаптивные величины, а не только как постоянные константы.

К кандидатам относятся:

- soft/hard timeout — мягкие и жёсткие таймауты;
- Lease duration — срок владения задачей;
- Heartbeat interval — интервал подтверждения активности Worker;
- Retry count — число повторных попыток;
- Backoff — увеличение интервала повторов;
- Circuit Breaker thresholds — пороги временного отключения неисправного маршрута;
- Checkpoint frequency — частота контрольных точек;
- параметры Cache Policy;
- пороги Context Drift;
- параметры прогнозирования ресурсов.

Такие изменения допустимы автоматически только на уровне L1, если они низкорисковые, ограничены Scope, имеют обратимый диапазон и не ослабляют Security.

## 6.29. Пример обучения таймауту

Если Worker возвращается через одну секунду после истечения таймаута, система фиксирует это как `near-timeout recovery` — возврат непосредственно после порога.

Один случай не должен менять глобальную настройку. Learning накапливает статистику по конкретному Worker, Runtime, Workspace, типу задачи и сетевому маршруту.

Если повторяется закономерность, система сравнивает стоимость двух ошибок:

- слишком короткий timeout → ложный отказ, повторное назначение, возможное дублирование;
- слишком длинный timeout → позднее обнаружение настоящего отказа и увеличение времени восстановления.

Оптимальный параметр выбирается по фактическому распределению задержек, например с использованием медианы, P95/P99, стоимости ошибки и Baseline.

## 6.30. Самообучение прогнозированию

Модуль «Планирование и прогнозирование ресурсов» должен обучаться на паре:

`прогноз → факт`.

Для каждой задачи сохраняются прогноз и фактические значения:

- токены;
- время;
- стоимость;
- доля кэша;
- Retry;
- повышение LOW/NORMAL/HIGH;
- выбор Worker;
- вероятность успешного завершения с первой попытки.

Learning вычисляет ошибку прогноза по типу задачи, Domain, Worker, Provider, Context и Cache и корректирует локальную модель оценки.

Полная история задач не передаётся LLM. В первую очередь используются локальная статистика и обычные алгоритмы.

## 6.31. Не оптимизировать один показатель

Learning не должно улучшать одну метрику ценой скрытого ухудшения другой.

Например увеличение timeout может снизить False Timeout Rate, но ухудшить Mean Recovery Time. Увеличение Cache TTL может повысить Cache Hit Rate, но увеличить Stale Hit Rate.

Поэтому адаптация оценивается по совокупному эффекту: качество, безопасность, время, стоимость, повторные действия и восстановление.
