# 7. Context — система управления контекстом

## Схема

**TaskContract (контракт задачи)**  
↓  
**Context Requirements (требования к контексту)**  
↓  
**Context Resolver (определение нужных источников)**  
↓  
**Можно передать ссылку?**

**Да** → `ContextRef (ссылка на контекст)`  
**Нет** → минимальная локальная материализация

↓  
**локальный поиск / фильтрация / индекс / код**  
↓  
при необходимости **локальный ИИ**  
↓  
**Context Budget (лимит контекста)**  
↓  
**Context Manifest (паспорт контекста)**  
↓  
**Provider / Worker получает только необходимое**  
↓  
**исполнение**

После задачи:

**Metrics → что реально использовалось → Learning → улучшение выбора контекста**

## 7.1. Назначение

`Context (контекст)` отвечает за один вопрос:

> **Что конкретному исполнителю действительно необходимо знать для выполнения конкретного этапа задачи?**

Контекст KAT9I_OS не должен означать: «передать модели всё, что мы знаем».

Правильный принцип:

> **Передать минимальный достаточный набор информации, необходимый для качественного результата.**

## 7.2. Context не является хранилищем знаний

`Context` не должен хранить весь GitHub, всю личную базу знаний, всю историю пользователя, все документы, все Skills и все Rules.

Эти данные находятся в соответствующих источниках.

Context отвечает за поиск нужного, ссылки, отбор, область, актуальность, минимизацию и подготовку к исполнению.

`Resources (ресурсы)` отвечают: где находится информация?  
`Context` отвечает: какая часть этой информации нужна сейчас?

## 7.3. Reference-first — сначала ссылка

Основная политика Context:

> **Не переносить содержимое, если исполнитель способен открыть источник самостоятельно.**

Например вместо передачи полного репозитория:

**Task → ContextRef на GitHub → Worker открывает GitHub самостоятельно**

Вместо передачи длинного Google Drive документа:

**Task → ссылка на документ → Provider читает его через свой Connector (подключение)**

Это основной механизм экономии токенов, памяти, сетевого трафика, времени подготовки и дублирования данных.

## 7.4. ContextRef — ссылка на источник контекста

`ContextRef` должен описывать источник без обязательного копирования содержимого.

Минимально требуется знать:

| Поле | Назначение |
|---|---|
| тип | GitHub, Drive, local, Knowledge и т. д. |
| URI / ID | где находится ресурс |
| revision | какая версия |
| scope | какая часть нужна |
| access | какие права требуются |
| trust | уровень доверия |
| freshness | актуальность |
| resolver | каким способом получить |

Один GitHub-репозиторий может быть получен через GitHub Connector, API, MCP, локальный Git или существующий Worktree.

Context не должен зависеть от конкретного способа доступа.

## 7.5. Материализация — только запасной путь

Если Worker или Provider не умеет самостоятельно открыть ContextRef:

**ContextRef → можно подключить Connector?**

Если да — подключить.

Если нет — KAT9I_OS материализует только необходимую часть контекста, а не весь источник.

## 7.6. Executable-first при подготовке контекста

Большая часть подготовки контекста не требует ИИ.

Сначала используются поиск по файлам, Git, индексы, AST (структурное представление кода), поиск символов, граф зависимостей, полнотекстовый поиск, хэши, фильтры, метаданные, SQL и отдельный CacheEngine.

ИИ не должен читать весь репозиторий только для того, чтобы определить, где находится функция.

## 7.7. Local-first при обработке контекста

Если после обычного кода требуется интеллектуальная фильтрация, локальный ИИ имеет первый приоритет, если его качества достаточно.

Локально можно выполнять ранжирование найденных фрагментов, предварительное суммирование, классификацию документов, поиск вероятных дубликатов, выделение ключевых частей логов и очистку больших технических данных.

После этого внешней модели передаётся уже уменьшенный контекст.

## 7.8. Context Funnel — воронка контекста

Контекст должен последовательно уменьшаться:

**Большой источник → детерминированный поиск → релевантные кандидаты → локальное ранжирование → минимальный Context Pack → модель**

## 7.9. Context Manifest — паспорт контекста

Для каждой задачи должен формироваться `Context Manifest (паспорт контекста)`.

Он описывает не содержимое всех данных, а набор используемых источников.

Это позволяет повторить выполнение, понять, на каких данных принято решение, выполнить независимый QA, обнаружить устаревший контекст и сравнить две попытки задачи.

## 7.10. Context Budget — лимит контекста

Каждый этап получает собственный лимит.

Нельзя использовать один максимальный контекст на всю задачу.

Контекст определяется этапом, а не размером всей задачи.

## 7.11. Лимит — не только токены

Context Budget должен учитывать токены, количество файлов, количество источников, размер передаваемых данных, число внешних запросов, время поиска данных и стоимость Provider.

## 7.12. Progressive Disclosure — постепенное раскрытие контекста

Исполнителю сначала даётся минимально необходимый набор.

Если его недостаточно, Worker создаёт `Context Request (запрос дополнительного контекста)`.

Каждое расширение должно быть объяснимым и измеримым.

## 7.13. Контекст Skills и Tools

Worker не должен видеть весь каталог возможностей KAT9I_OS.

Ему передаются только необходимые Skills (навыки), Tools (инструменты) и Rules (правила) для текущей задачи.

## 7.14. Контекст Rules

Исполнитель получает только `Effective Ruleset (итоговый набор применимых правил)`, а не всю базу правил.

## 7.15. История диалогов

KAT9I_OS не должна постоянно передавать исполнителю всю историю чата пользователя.

Вместо этого история используется как источник, из которого локально извлекаются релевантные решения, Knowledge (знания), Rules (правила) и Preferences (предпочтения).

Полный чат используется только когда это действительно необходимо.

## 7.16. Контекст текущего обсуждения

Для длительных процессов должна существовать компактная рабочая память — `Working Context Snapshot (рабочий снимок контекста)` с принятыми решениями, открытыми вопросами, противоречиями, текущим разделом и ссылками на уже принятые документы.

При необходимости оригинальная история остаётся доступной как источник проверки.

## 7.17. Нельзя бесконечно пересказывать пересказы

Summary (сводка) всегда должна сохранять ссылку на первоисточник.

Если решение критичное, проверяется первичный источник, а не очередной пересказ.

## 7.18. Уровни контекста

Предлагаются уровни:

- L0 — ссылки;
- L1 — метаданные;
- L2 — выбранные фрагменты;
- L3 — локальное резюме;
- L4 — расширенный материализованный контекст.

Начинать следует с минимального уровня и повышать только при необходимости.

## 7.19. Freshness — актуальность

Context должен знать, насколько данные актуальны.

Особенно это важно для GitHub, Issues, PR, CI, документации, правил, MetricsSnapshot и активных задач.

Контекст должен быть привязан к точной версии, когда это возможно.

## 7.20. Provenance — происхождение

Каждый важный фрагмент контекста должен позволять определить источник, версию, время получения, Resolver, факт материализации и факт суммирования/преобразования.

## 7.21. Trust — доверие к источнику

Context должен передавать уровень доверия к источнику: канонический репозиторий, официальный документ, пользовательское правило, внешний сайт, старый summary и т. д.

## 7.22. Context Cache и CacheEngine

Повторно используемый контекст должен кэшироваться через отдельный системный `CacheEngine`, определённый в `docs/architecture/34_CACHE_ENGINE.md`.

Context является клиентом CacheEngine и не владеет физическим кэшем.

Если источник не изменился, его не нужно обрабатывать заново. Ключ кэша привязывается к точной revision / hash, версии преобразования, параметрам и security scope.

В штатном режиме CacheEngine работает RAM-first. Context не должен требовать постоянной записи своих производных данных на SSD.

Полная потеря кэша не меняет корректность Context: нужный Context Pack или индекс повторно строится из первоисточника.

Нативное prompt caching внешнего AI Provider является отдельным механизмом и не заменяет локальный CacheEngine KAT9I_OS.

## 7.23. Context Pack — минимальный пакет

Если ContextRef использовать невозможно и данные нужно передать модели, создаётся `Context Pack (минимальный пакет контекста)`.

Он содержит только цель этапа, применимые Rules, необходимые данные, ссылки на первоисточники и ожидаемый результат.

## 7.24. Контекст и безопасность

Context не может самостоятельно расширять доступ.

Если для нового источника нужны дополнительные права, запрос проходит через Security.

## 7.25. Контекст и приватность

Sensitive Data (чувствительные данные) должны по возможности обрабатываться локальным кодом, затем локальным ИИ и только затем разрешённым внешним Provider.

Если правила запрещают внешний доступ, внешний Provider не рассматривается.

## 7.26. Контекст и Coworker

Контекст может зависеть от конкретного Worker.

Один `Context Manifest` может иметь разные способы доставки для разных Worker.

## 7.27. Контекст и Provider Affinity

Если Provider уже имеет прямой доступ к источнику, это должно учитываться при маршрутизации.

`Source Affinity (близость провайдера к источнику данных)` снижает необходимость материализации и передачи данных.

## 7.28. Контекст и Metrics

Нужно измерять, сколько контекста найдено, сколько отфильтровано, сколько реально передано, сколько токенов использовано, сколько ContextRef разрешено напрямую, сколько пришлось материализовать, количество расширений контекста, задержку подготовки, CacheEngine hit rate и объём повторной обработки, которого удалось избежать.

## 7.29. Context Efficiency — эффективность контекста

Цель — минимальный контекст при сохранении требуемого качества.

Уменьшение контекста не считается успехом, если из-за него падает качество.

## 7.30. Context Learning

Learning должен постепенно улучшать Context Policy на основании фактического использования источников, запросов дополнительного контекста, влияния размера контекста на качество и эффективности локальных summaries.

## 7.31. Что Context не должен делать

Context не должен самостоятельно определять правила, выбирать конкретную модель, выбирать Worker, выполнять доменную задачу, хранить всю Knowledge Base, изменять Security Policy, передавать всю историю по умолчанию или материализовывать источник только потому, что это проще реализовать.

## 7.32. Основные принципы Context

1. Минимальный достаточный контекст.
2. Reference-first — сначала ссылка.
3. Материализация только если прямое разрешение ссылки невозможно.
4. Executable-first — поиск и фильтрация сначала кодом.
5. Local-first — интеллектуальная предварительная обработка сначала локально.
6. Контекст формируется отдельно для каждого этапа задачи.
7. Полная история не передаётся по умолчанию.
8. Summary всегда сохраняет связь с первоисточником.
9. Контекст привязывается к версии источника.
10. Skills, Rules и Tools также раскрываются постепенно.
11. Повторно используемые производные данные передаются в CacheEngine и никогда не становятся SSoT.
12. Security имеет приоритет над удобством получения контекста.
13. Метрики измеряют полезность и стоимость контекста.
14. Learning постепенно сокращает лишний контекст без потери качества.

## 7.33. Главный принцип

> **Лучший контекст — не самый большой и не самый маленький. Лучший контекст — минимальный набор проверяемых источников, достаточный конкретному исполнителю для качественного выполнения конкретного этапа задачи.**
