# 8. Knowledge Base — база знаний KAT9I_OS

## Схема

Источники знаний
→ Knowledge Intake (приём знаний)
→ локальное извлечение
→ классификация
→ проверка
→ дедупликация
→ определение Scope (области действия)
→ проверка чувствительности
→ Knowledge Candidate (кандидат в знание)
→ маршрутизация по типу: Knowledge / Rule / Preference / Setting / временный контекст / отклонить
→ Knowledge Record (структурированная запись знания)
→ Knowledge Registry + Index (реестр и индекс)
→ KnowledgeRef (ссылка на знание)
→ Context / Learning / Domain / Worker / пользователь

## 8.1. Назначение

Knowledge Base (база знаний) — отдельная системная подсистема KAT9I_OS. Она хранит и индексирует проверенные факты, решения, наблюдения, выводы и связи между ними, но не должна становиться свалкой всей переписки, всех документов и всех состояний системы.

Главный принцип:

> Не всё, что увидела модель или сказал пользователь, автоматически становится знанием.

## 8.2. Роли

В системе различаются пять ролей:

- Knowledge Source (источник знаний) — где физически или логически находится информация;
- Knowledge Supplier (поставщик знаний) — кто передал или сформировал утверждение;
- Knowledge Store (хранилище знаний) — где физически лежит запись;
- Knowledge Connector (подключение к знаниям) — как KAT9I_OS получает доступ к источнику или хранилищу;
- Knowledge Consumer (потребитель знаний) — кто использует знание.

Слово Provider (провайдер) для этой роли не используется, чтобы не смешивать её с Provider (провайдером ИИ) в Inference.

## 8.3. Источники знаний

Источником может быть:

- GitHub;
- Google Drive;
- Obsidian;
- локальная файловая система;
- отдельное внешнее хранилище знаний;
- документация проекта;
- Issue (задача GitHub);
- PR (запрос на внесение изменений);
- чат;
- сайт;
- PDF;
- база данных;
- MCP-ресурс;
- результат исследования;
- ранее созданный артефакт.

Источник не обязан физически находиться внутри KAT9I_OS.

Сохраняется принцип Reference-first (сначала ссылка): большие материалы по возможности остаются во внешнем источнике, а Knowledge Record хранит структурированное знание и ссылку на первоисточник.

## 8.4. Поставщики знаний

Поставщиком может быть:

- пользователь;
- Worker (исполнитель);
- Learning Engine (система самообучения);
- Research (исследовательский процесс);
- Import (импорт);
- внешняя система, например GitHub.

Поставщик и источник хранятся отдельно для Provenance (происхождения).

## 8.5. Потребители знаний

Потребителями могут быть:

- Context;
- Core;
- Rule Manager;
- Learning;
- Inference;
- Coworker;
- Domain (домен);
- Worker;
- пользователь.

Потребитель не получает всю базу знаний. Он запрашивает релевантные KnowledgeRef.

## 8.6. Knowledge Record — запись знания

Канонической единицей базы знаний является структурированная запись Knowledge Record, а не произвольный документ.

Минимальные поля:

- id — уникальный идентификатор;
- type — тип знания;
- statement — краткая формулировка;
- scope — область действия;
- source_ref — ссылка на первоисточник;
- supplier — поставщик;
- confidence — степень уверенности;
- trust — доверие к источнику;
- created_at — время получения;
- valid_from — начало действия;
- valid_until — срок действия, если есть;
- revision — версия;
- sensitivity — чувствительность;
- status — состояние знания;
- relations — связи с другими знаниями.

Большие исходные материалы хранятся ссылками.

## 8.7. Типы знаний

Минимальные типы:

- Fact (факт);
- Decision (принятое решение);
- Observation (наблюдение);
- Insight (проверенный вывод);
- Reference (важная ссылка);
- Relation (связь);
- Procedure Knowledge (знание о процессе).

Исполняемая процедура должна жить в Skill / Workflow, а не только в Knowledge Base.

## 8.8. Что база знаний не должна дублировать

Канонические места:

- обязательное правило → Rules;
- предпочтение → Preferences;
- настройка среды → Settings;
- исполняемый алгоритм → Executable Skill / Workflow;
- сырые метрики → Metrics;
- состояние задачи → TaskRuntimeState;
- задача → TaskContract;
- большой исходный документ → внешнее хранилище + ResourceRef;
- знание, решение, факт → Knowledge Base.

Knowledge Base может ссылаться на эти сущности, но не становится вторым источником истины.

## 8.9. Когда знание попадает в базу

Основные пути:

1. Явная команда пользователя "запомни" — после классификации как Knowledge / Rule / Preference / Setting.
2. Команда "принято" — проектное решение получает статус Accepted Decision (принятое решение), записывается в документацию и становится доступным через KnowledgeRef.
3. Проверенный результат задачи — после подтверждения источником или QA.
4. Повторяемая закономерность — сначала как Observation или Insight Candidate.
5. Импорт — с сохранением происхождения и уровня доверия.

## 8.10. Что не попадает автоматически

Не сохраняются как подтверждённое знание:

- случайные предположения модели;
- одноразовые ошибки;
- промежуточный brainstorming (обсуждение идей);
- неподтверждённые внешние утверждения;
- весь текст чата;
- каждый ответ Worker;
- полный лог;
- временные значения без политики актуальности.

## 8.11. Knowledge Intake — приём знаний

Конвейер:

событие / источник
→ локальное извлечение кандидата
→ классификация типа
→ проверка Knowledge / Rule / Preference / Setting
→ дедупликация
→ проверка источника
→ определение Scope
→ оценка Confidence
→ проверка чувствительности
→ сохранение
→ индексирование.

Максимум этих шагов выполняется по принципам Executable-first (сначала исполняемый код) и Local-first (сначала локально).

## 8.12. Жизненный цикл знания

Статусы:

CANDIDATE (кандидат)
→ VERIFIED (подтверждено)
→ ACTIVE (активно)
→ STALE (возможно устарело)
→ SUPERSEDED (заменено новым)
или REVOKED (отозвано).

Знание не считается вечным по умолчанию.

## 8.13. Freshness Policy — политика актуальности

Для разных типов знаний действует разная скорость старения.

Например:

- архитектурное решение — проверяется при изменении документа;
- текущий commit SHA — проверяется почти всегда;
- версия программы — периодически;
- решение пользователя — действует до отмены;
- исследовательский вывод — в зависимости от предметной области.

Проверка актуальности по возможности выполняется локальным кодом или Connector без вызова ИИ.

## 8.14. Knowledge Graph — связи знаний

Knowledge Base должна поддерживать связи между записями, но первая версия не требует тяжёлой графовой базы данных.

Достаточно структурированных отношений и локального индекса.

## 8.15. Физическое хранение

Публичный репозиторий KAT9I_OS хранит:

- схемы;
- код;
- формат Knowledge Record;
- адаптеры;
- политики;
- тесты.

Личные и приватные знания должны храниться во внешнем Knowledge Store.

Возможные хранилища:

- локальная БД;
- Markdown / Obsidian;
- отдельное внешнее хранилище знаний;
- Google Drive;
- отдельный GitHub-репозиторий;
- другие подключаемые системы.

## 8.16. Storage-agnostic — независимость от хранилища

KAT9I_OS не должна зависеть от конкретного физического хранилища.

Она работает через KnowledgeRef и Knowledge Store Adapter (адаптер хранилища знаний).

## 8.17. Trust и Provenance

Доверие относится не только к поставщику, а к сочетанию:

- утверждение;
- источник;
- доказательство;
- версия;
- способ получения.

Для каждой записи должна сохраняться Provenance (история происхождения).

## 8.18. Связь с Learning

Learning получает релевантные выборки Knowledge, а не всю базу.

Learning может создавать Knowledge Candidate, но не должен автоматически превращать предположение в подтверждённое знание.

## 8.19. Метрики базы знаний

Минимальные показатели:

- количество активных знаний;
- кандидатов;
- дубликатов;
- устаревших знаний;
- конфликтов;
- среднее количество Knowledge в Context;
- сколько найденных знаний реально использовалось;
- сколько Knowledge было загружено зря;
- токены на Knowledge Context;
- Cache Hit Rate (доля попаданий в кэш);
- процент знаний с первичным источником;
- процент знаний без надёжного Provenance.

Метрики считаются локально и не требуют анализа всей истории моделью на каждом цикле.

## 8.20. Основные принципы

1. Knowledge Base — отдельный системный модуль.
2. Личные знания — один из типов данных, а не вся база знаний.
3. Не всё наблюдаемое становится знанием.
4. Каноническая единица — Knowledge Record + ссылка на первоисточник.
5. Source, Supplier, Store, Connector и Consumer — разные роли.
6. Большие материалы остаются во внешних источниках по принципу Reference-first.
7. Knowledge Intake максимально выполняется локальным кодом.
8. Знание имеет Scope, Trust, Confidence, Freshness и Provenance.
9. Knowledge Base не дублирует Rules, Metrics, TaskContract, Settings и Workflow как второй источник истины.
10. Потребители получают только релевантные KnowledgeRef.
11. Устаревшие знания должны выявляться и заменяться новыми.
12. База знаний должна быть независима от конкретного физического хранилища.
