# 9. Resources — единый слой ресурсов KAT9I_OS

## Схема

**TaskContract (контракт задачи)**
→ **ResourceRef (ссылка на ресурс)**
→ **Resource Registry (реестр ресурсов)**
→ **Resolver (определитель способа доступа)**
→ выбор лучшего маршрута:

**локальный файл / локальный Git / кэш**
→ если подходит — использовать локально

иначе:

**нативный Connector (подключение)**
→ **API (программный интерфейс)**
→ **MCP**
→ **материализация через KAT9I_OS только как запасной вариант**

→ **Security (проверка прав)**
→ **Consumer (потребитель)**

После выполнения:

**ResultSink (место записи результата)**
→ **ResultRef (ссылка на результат)**
→ следующий Worker / QA / пользователь

## 9.1. Назначение Resources

`Resources (ресурсы)` — системный слой KAT9I_OS, который отвечает за единое представление внешних и внутренних источников данных и результатов работы независимо от того, где они физически находятся и каким способом к ним обращаются.

Он отвечает на вопрос: **где находится объект и как получить к нему доступ?**

## 9.2. Главный принцип

Нужно строго разделить две сущности.

### ResourceRef — что это

Например: конкретный GitHub Issue, репозиторий, Google Drive документ, локальный файл, Knowledge Record, PR, результат задачи.

### Connector / Resolver — как получить

Например один GitHub PR можно получить через локальный Git, GitHub Connector, GitHub API, MCP или уже открытый Workspace.

> **ResourceRef описывает ресурс. Connector описывает способ доступа.**

Доменные модули не должны зависеть от конкретного транспорта.

## 9.3. Почему это важно

Без такого слоя каждый Domain начнёт самостоятельно реализовывать GitHub, Drive, файловую систему и MCP. Это создаст дублирование, разные модели прав, разные форматы ссылок, разные механизмы кэша и проблемы безопасности.

Resources создаёт один общий язык ресурсов для всей KAT9I_OS.

## 9.4. Типы ресурсов

Минимально KAT9I_OS должна поддерживать:

- локальный файл;
- каталог;
- Git-репозиторий;
- GitHub repository;
- Issue;
- PR;
- commit;
- branch;
- Google Drive документ;
- Knowledge Record;
- MCP-ресурс;
- Artifact (созданный артефакт);
- Result (результат задачи);
- Metrics Snapshot;
- внешний Web-ресурс.

Типы можно расширять без изменения TaskContract.

## 9.5. ResourceRef — единая ссылка

ResourceRef должен включать минимум:

- тип ресурса;
- URI / ID;
- источник;
- revision / version;
- Scope;
- требуемые права;
- уровень чувствительности;
- Freshness;
- Trust;
- Resolver hints;
- Provenance.

ResourceRef не обязан содержать сам объект.

## 9.6. Стабильная идентичность

Один ресурс должен иметь стабильную логическую идентичность. Например GitHub PR #123 остаётся одним объектом, хотя его head commit может измениться.

Поэтому различаются **Resource identity** и **Resource revision**.

Это критично для QA: QA должен проверять конкретную revision, а не просто «PR #123».

## 9.7. URI ресурсов

KAT9I_OS должна использовать единообразные логические ссылки, например концептуально `github://`, `gdrive://`, `file://`, `knowledge://`, `artifact://`, `mcp://`.

Точный синтаксис определяется при проектировании контрактов. URI не должен жёстко задавать единственный транспорт получения данных.

## 9.8. Resource Registry — реестр ресурсов

Registry хранит метаданные известных ресурсов: идентичность, тип, известные версии, доступные Resolver, кэш, права, Trust, Freshness и связи.

Это не копия всех данных ресурса. Registry хранит описание и состояние доступа.

## 9.9. Resolver — получение ресурса

Resolver определяет, как получить конкретный ResourceRef.

Приоритетная логика:

1. доступен актуальный локальный clone — использовать Git;
2. Worker имеет нативный Connector — передать ссылку;
3. доступен API — использовать API;
4. доступен MCP — использовать MCP;
5. иначе материализовать минимально допустимым способом.

## 9.10. Local-first для ресурсов

При одинаковой корректности предпочтение получает локальный доступ.

Приоритет:

**локальный актуальный ресурс → локальный кэш → нативный Connector → API / MCP → материализация KAT9I_OS**.

Security и Freshness всегда проверяются до выбора.

## 9.11. Reference-first

Resources — главный технический механизм реализации Reference-first.

KAT9I_OS должна стремиться передавать ссылку на ресурс вместо копии всего ресурса, особенно для репозиториев, больших документов, PR, Knowledge Base и результатов других Workers.

## 9.12. Provider-native access — доступ через самого исполнителя

Если ChatGPT, Antigravity или другой Worker уже имеет собственный Connector к GitHub, KAT9I_OS передаёт ResourceRef, а Worker самостоятельно получает содержимое.

KAT9I_OS не должна скачивать GitHub, превращать содержимое в токены и пересылать его модели, если модель способна открыть GitHub напрямую.

## 9.13. Materializer — материализация

Materializer нужен только когда ResourceRef невозможно разрешить непосредственно для выбранного Worker.

Его задача — получить минимально необходимую часть ресурса и подготовить её для потребителя, а не скачать всё.

## 9.14. Source и Sink

Resources должен одинаково работать как с входом, так и с выходом.

- **Resource Source** — откуда читаем.
- **ResultSink** — куда записываем.

Примеры ResultSink: GitHub PR, GitHub Issue, Google Drive, локальный файл, Artifact Store, Knowledge Base.

## 9.15. ResultRef — ссылка на результат

После выполнения Worker должен по возможности возвращать не большой текст, а ResultRef.

Например Worker создаёт PR #251, а KAT9I_OS получает ResultRef на PR #251 и точный head SHA. QA Worker затем читает PR напрямую.

## 9.16. Распределённая работа

Предпочтительная схема:

**Worker A → общий ResultSink → ResultRef → Worker B**.

Например Worker A создаёт GitHub PR, Worker B читает тот же PR через GitHub. KAT9I_OS передаёт управление и ссылки, а не большой промежуточный результат.

## 9.17. Resources и Coworker

При выборе Worker учитывается его доступ к ресурсам. Это `Data Affinity (близость исполнителя к данным)`.

Worker с прямым Connector к источнику может быть эффективнее немного более сильного Worker без такого доступа.

## 9.18. Resources и Inference

Inference должен учитывать не только качество модели, но и доступ к источнику, возможность записи результата, необходимость материализации, стоимость передачи данных, приватность и задержку.

## 9.19. Resource Permissions — права

ResourceRef не означает автоматическое разрешение доступа.

Перед операцией Security проверяет необходимые права: read, write, create, update, delete, merge, admin.

Worker получает только необходимый Capability Grant (разрешение на конкретные действия).

## 9.20. Минимальные права

Если задача требует только чтения, Worker не должен получать запись. Если требуется создать PR, это не означает автоматического разрешения merge.

Ресурс и операция рассматриваются отдельно.

## 9.21. Provenance — происхождение

Resources должен сохранять, откуда объект получен, каким Resolver, какую revision, когда, использовался ли кэш, выполнялась ли материализация и какие преобразования применялись.

## 9.22. Cache — кэш ресурсов

KAT9I_OS должна активно использовать локальный кэш. Если ресурс уже получен и его revision не изменилась, повторно получать и обрабатывать его не нужно.

Кэш может хранить метаданные, индекс, разобранное представление, summaries, временные копии и результаты детерминированного анализа.

## 9.23. Кэш не является источником истины

Кэш — производное состояние. Всегда должна существовать возможность определить первичный ResourceRef, revision и срок актуальности.

Если актуальность нельзя доказать, ресурс считается потенциально устаревшим.

## 9.24. Offline-first — работа без сети

Для ресурсов, уже доступных локально, KAT9I_OS должна по возможности сохранять работоспособность без внешней сети.

Это относится к локальным репозиториям, Knowledge cache, документации, индексам, Metrics и локальным моделям.

## 9.25. Дедупликация ресурсов

Один и тот же объект может быть доступен несколькими путями: локальный clone, GitHub URL, MCP GitHub, GitHub Connector.

Registry должен понимать, что это один логический ресурс с несколькими способами доступа.

## 9.26. Resource Graph — связи ресурсов

Нужно уметь хранить простые связи между Repository, Issue, PR, commit, artifact и другими ресурсами.

Тяжёлая графовая БД на первом этапе не обязательна.

## 9.27. Resources и Knowledge Base

Knowledge Base использует Resources для первоисточников.

Knowledge хранит утверждение, Resources обеспечивает доступ к доказательству.

## 9.28. Resources и Context

Граница ответственности:

- Resources: где ресурс и как до него добраться?
- Context: нужен ли этот ресурс для текущей задачи и какая его часть нужна?

## 9.29. Resources и Integrations

Граница ответственности:

- Resources работает с логическими объектами;
- Integrations реализует техническое действие через конкретный транспорт.

Integrations — транспорт. Resources — абстракция над транспортом.

## 9.30. Метрики Resources

Минимально измеряются:

- количество ResourceRef;
- доля локального доступа;
- доля Connector access;
- доля API;
- доля MCP;
- доля материализации;
- Cache Hit Rate;
- объём скачанных данных;
- объём переданных данных;
- количество ошибок разрешения ссылок;
- время получения;
- количество устаревших ресурсов;
- количество повторных загрузок одного объекта.

## 9.31. KPI

### Direct Resolution Rate — доля прямого доступа

Процент ресурсов, которые исполнитель смог получить напрямую по ссылке.

### Materialization Rate — доля материализации

Желательно снижать без потери качества.

### Local Resolution Rate — доля локального доступа

Показывает эффективность Local-first.

## 9.32. Learning и Resources

Learning может улучшать выбор Resolver, кэширование, Source Affinity, локальные индексы и другие параметры, но не может обходить Security.

## 9.33. Что Resources не должен делать

Resources не должен:

- решать, нужен ли ресурс по смыслу задачи — это Context;
- выбирать модель — это Inference;
- выбирать Worker — это Coworker;
- определять правила — это Rule Manager;
- реализовывать предметную логику — это Domain;
- хранить всё содержимое внешних систем внутри KAT9I_OS;
- давать права без Security.

## 9.34. Основные принципы

1. ResourceRef отвечает «что», Connector отвечает «как».
2. Один логический ресурс может иметь несколько способов доступа.
3. Reference-first используется по умолчанию.
4. Local-first применяется к разрешению ресурсов.
5. Материализация — запасной путь.
6. KAT9I_OS не должна быть транспортом больших данных без необходимости.
7. Входы и результаты используют общий механизм ресурсов.
8. ResultRef предпочтительнее пересылки больших результатов между Workers.
9. Revision должна фиксироваться для воспроизводимых и QA-критичных операций.
10. Права проверяются отдельно от наличия ссылки.
11. Кэш используется активно, но не является источником истины.
12. Resources не зависит от конкретного Connector или внешнего сервиса.
13. Метрики должны показывать, насколько редко KAT9I_OS приходится материализовывать данные.

## 9.35. Главный принцип

> **KAT9I_OS должна перемещать между исполнителями управление и ссылки, а не сами большие данные, если эти данные уже доступны через общий источник.**
