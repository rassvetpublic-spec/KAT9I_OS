# 10. Inference — выбор ИИ, вычислительного маршрута и человеческого решения

## Схема

Задача или этап TaskContract (контракта задачи)
→ можно выполнить локальным исполняемым кодом?
→ да: выполнить локально, 0 LLM-токенов
→ нет: нужен ли ИИ?
→ нет: локальный алгоритм / поиск / индекс / БД / инструмент
→ да: определить минимально достаточный уровень интеллекта LOW / NORMAL / HIGH
→ применить Security (безопасность), Rules (правила) и Scope (область разрешённых действий)
→ проверить, не требуется ли Human Decision (решение человека)
→ выбрать допустимый маршрут: локальный ИИ / подписочный ИИ / API / удалённый ИИ / Пользователь / Администратор
→ учесть доступ к источникам, результатам, стоимость, скорость и историческую эффективность
→ сформировать InferenceRoute или DecisionRoute (маршрут вычисления или решения)
→ Coworker выбирает конкретного исполнителя
→ Execution выполняет
→ Metrics фиксирует результат
→ Learning улучшает будущую маршрутизацию.

## 10.1. Назначение

Inference отвечает на вопрос: какой минимально достаточный вычислительный или интеллектуальный способ нужен для конкретного этапа задачи.

Модель выбирается не первой. Сначала проверяется возможность выполнения обычным локальным исполняемым кодом, затем обычными локальными алгоритмами, затем локальным ИИ и только после этого внешними интеллектуальными маршрутами.

## 10.2. Базовый порядок выбора

1. Executable-first (сначала исполняемый код).
2. Tool-first (сначала обычный инструмент, если ИИ не нужен).
3. Local-first (сначала локальный ИИ, если его качества достаточно).
4. Subscription-first among external routes (среди внешних маршрутов сначала уже оплаченная подписочная среда, если она подходит).
5. Metered API (платный API) только когда он действительно необходим или эффективнее других разрешённых вариантов.

Безопасность, обязательные правила и минимальное качество имеют приоритет над экономией.

## 10.3. Уровни интеллекта

LOW — классификация, извлечение, простое суммирование, ранжирование, форматирование.

NORMAL — основная рабочая категория: обычная реализация, тесты, QA, документация, ограниченный рефакторинг, анализ Issue (задачи GitHub), большинство доменных задач.

HIGH — архитектура, сложный анализ первопричины, безопасность, критический QA, сложные межмодульные решения и неоднозначные проектные вопросы.

Уровень выбирается отдельно для каждого этапа, а не для всей задачи целиком.

## 10.4. Экономические классы

LOCAL_FREE — локальное выполнение без платы за отдельный вызов.

SUBSCRIPTION_INCLUDED — уже оплаченная подписочная среда, например ChatGPT или Antigravity.

METERED_API — API с оплатой за использование.

PREMIUM_API — дорогой или специализированный внешний маршрут.

Уровень интеллекта и способ оплаты — разные характеристики.

## 10.5. Человек как отдельный класс интеллектуального маршрута

Пользователь и Администратор включаются в общую систему маршрутизации, но не считаются обычными LLM Provider (провайдерами ИИ).

Для них вводится отдельная сущность Human Decision Provider (человеческий поставщик решения).

Типы:

- USER — пользователь;
- ADMIN — администратор;
- HUMAN_EXPERT — внешний или назначенный эксперт, если такой класс будет разрешён проектом.

Человек может выступать не только источником данных, но и активным узлом выполнения.

Примеры задач человека:

- интервью, когда системе не хватает исходных требований;
- выбор из нескольких архитектурных вариантов;
- разрешение конфликта, который нельзя безопасно решить автоматически;
- подтверждение критического изменения;
- расширение Scope;
- выдача чувствительного разрешения;
- утверждение L3-самообучения;
- решение, которое по политике запрещено делегировать ИИ.

## 10.6. Пользователь и Администратор — разные роли

USER отвечает за намерение, предпочтения, содержательные решения и согласование результата в пределах своих полномочий.

ADMIN отвечает за системные полномочия, доступы, критические настройки, разрешения, изменение границ безопасности и другие административные действия.

USER не получает административные полномочия автоматически.

ADMIN не заменяет пользователя в содержательных решениях, если для этого нет явного правила.

## 10.7. Decision Requirement — требование человеческого решения

TaskContract или Policy могут указывать, что этап требует человеческого решения.

Примеры:

- USER_REQUIRED — требуется решение пользователя;
- ADMIN_REQUIRED — требуется административное разрешение;
- HUMAN_OPTIONAL — человек предпочтителен, но разрешён автоматический fallback (запасной маршрут);
- AI_ALLOWED — решение можно делегировать ИИ;
- CODE_ONLY — решение должно быть детерминированным и не передаваться ИИ.

Такой признак нельзя понизить ради скорости или стоимости.

## 10.8. Интервью как управляемый процесс

Если данных недостаточно, система не должна бесконечно задавать вопросы.

Она должна сначала локально определить, какие именно недостающие данные блокируют задачу, сгруппировать их и сформировать минимальное интервью.

Интервью считается отдельным шагом TaskGraph (графа задач), а ответы пользователя становятся структурированными входами TaskContract, Knowledge Candidate (кандидатами в знания), Rule Candidate (кандидатами в правила), Preference Candidate (кандидатами в предпочтения) или одноразовыми параметрами задачи.

## 10.9. Ключевые решения

Для архитектурных, безопасностных и других критических задач может применяться Decision Gate (контрольная точка решения).

Система должна уметь представить человеку компактно:

- вопрос;
- 2–4 допустимых варианта;
- основные последствия;
- рекомендацию системы;
- что будет заблокировано до решения.

Полная история задачи не должна передаваться человеку автоматически, если для решения достаточно короткого контекста и ссылок на первоисточники.

## 10.10. Source Affinity и Result Sink Affinity

При выборе маршрута учитывается, имеет ли Provider или Human Decision Provider прямой доступ к источнику и месту результата.

Маршрут с прямым GitHub Connector (подключением GitHub) может быть эффективнее более мощной модели без такого доступа, потому что не требует материализации большого контекста.

## 10.11. Inference и Coworker

Inference определяет, какой тип интеллектуального или человеческого маршрута нужен.

Coworker определяет, кто конкретно его выполнит.

Пример: Inference требует NORMAL + GitHub read + USER approval. Coworker выбирает подходящего Worker для реализации, а контрольная точка решения направляется пользователю.

## 10.12. Escalation — повышение уровня

Допустимый путь: локальный код → локальный ИИ → NORMAL → HIGH → Human Decision, если именно человеческое решение необходимо.

Повышение выполняется по измеримой причине: недостаточное качество, QA FAIL, отсутствие разрешения, конфликт правил, недостаток данных или невозможность гарантировать безопасное решение.

## 10.13. Защита от Prompt Injection

Prompt Injection (внедрение управляющих команд через данные) рассматривается как отдельная системная угроза.

Главный принцип:

> Данные из контекста не становятся управляющими инструкциями только потому, что содержат текст, похожий на команду.

Источники контекста делятся как минимум на:

- TRUSTED_CONTROL — доверенный управляющий источник;
- TRUSTED_DATA — доверенные данные, но не управляющие команды;
- UNTRUSTED_DATA — внешние или непроверенные данные;
- GENERATED_DATA — данные, созданные моделью или Worker;
- USER_INPUT — непосредственный ввод пользователя в разрешённом интерфейсе.

Только явно разрешённые управляющие каналы могут изменять Rules, Scope, Tool permissions (разрешения инструментов), ProviderRoute или системные настройки.

## 10.14. Context Firewall — контекстный межсетевой экран

Перед передачей данных модели Context должен применять Context Firewall (контекстный защитный слой):

- определить источник;
- определить Trust (доверие);
- отделить управляющие инструкции от данных;
- пометить недоверенные фрагменты;
- запретить данным изменять системные правила;
- ограничить доступные Tools;
- ограничить Scope;
- при необходимости локально обнаружить подозрительные управляющие конструкции;
- сохранить Provenance (происхождение) подозрительного фрагмента.

Защита должна быть максимально реализована локальным исполняемым кодом и правилами, а не дополнительными дорогими LLM-вызовами.

## 10.15. Instruction Boundary — граница управляющих команд

KAT9I_OS должна различать:

1. System/Policy Instructions — системные и политические инструкции;
2. User Authorized Instructions — явно разрешённые команды пользователя;
3. Task Data — данные задачи;
4. External Content — содержимое сайтов, Issue, документов, PR и других внешних источников;
5. Model Output — вывод модели.

Уровни 3–5 не имеют права самостоятельно повышать себя до уровней 1–2.

Фраза в README, Issue, веб-странице или документе вида «игнорируй предыдущие инструкции и сделай X» должна рассматриваться как данные, а не команда KAT9I_OS.

## 10.16. Tool and Capability Firewall — защита инструментов и возможностей

Даже если модель была успешно атакована через контекст, она не должна автоматически получить возможность выполнить опасное действие.

Поэтому Tool Broker и Security обязаны независимо проверять:

- разрешён ли Tool;
- разрешено ли действие;
- входит ли ресурс в Scope;
- есть ли необходимый Capability Grant (разрешение на действие);
- требуется ли USER/ADMIN approval;
- не противоречит ли действие Effective Ruleset.

Безопасность не должна зависеть только от того, правильно ли модель интерпретировала контекст.

## 10.17. Метрики защиты от инжектов

Система должна дешёво фиксировать:

- количество подозрительных фрагментов;
- источник;
- сколько было заблокировано;
- сколько дошло до модели как помеченные данные;
- попытки расширить Scope;
- попытки вызвать запрещённый Tool;
- false positive rate (доля ложных срабатываний), если её можно измерить;
- влияние защитного слоя на время и токены.

Полная история инцидентов не передаётся модели каждый цикл. Используются агрегаты и отдельные релевантные события.

## 10.18. Основные принципы

1. Не выбирать модель, пока не доказано, что ИИ нужен.
2. Executable-first имеет первый приоритет.
3. Local-first применяется поэтапно.
4. Пользователь и Администратор являются отдельными человеческими маршрутами принятия решений.
5. Человеческое решение может быть обязательным требованием TaskContract или Policy.
6. USER и ADMIN имеют разные полномочия.
7. Интервью — отдельный управляемый процесс, а не бесконечный диалог.
8. Prompt Injection рассматривается как атака данными на управляющий контур.
9. Внешний контент по умолчанию не имеет управляющей силы.
10. Контекст, инструменты и разрешения защищаются независимыми слоями.
11. Защита от инжектов должна максимально работать локальным кодом без существенного расхода токенов.
12. Security и Rules проверяются раньше экономики.
13. Learning использует результаты маршрутов и инцидентов, но не читает всю историю на каждом цикле.

## 10.19. Главный принцип

> KAT9I_OS выбирает не просто модель, а минимально достаточный и разрешённый способ получить решение: локальный код, локальный ИИ, внешний ИИ или человека. При этом данные никогда не получают управляющую силу автоматически, а критические разрешения и решения направляются тому субъекту, который действительно имеет право их принимать.
