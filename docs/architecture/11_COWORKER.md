# 11. Coworker — распределённая работа исполнителей

## Схема

**TaskContract (контракт задачи)**
↓
**Core + Rules + Security**
↓
**InferenceRequirement (требования к интеллектуальному выполнению)**
↓
**Coworker Coordinator (координатор исполнителей)**
↓
**Worker Registry (реестр исполнителей)**
↓
поиск доступных кандидатов:

- локальный Worker (исполнитель);
- другой локальный агент;
- удалённая KAT9I;
- другой компьютер;
- сервер;
- облачный Worker;
- Пользователь;
- Администратор;
- человек-эксперт.

↓
**Capability Match (проверка возможностей)**
+
**Data Affinity (близость к данным)**
+
**Trust (доверие)**
+
**Availability (доступность)**
+
**историческая эффективность**

↓
**Claim (захват задачи)**
↓
**Lease (временная аренда права выполнения)**
↓
**Capability Grant (ограниченные разрешения)**
↓
**Execution**
↓
**ResultRef (ссылка на результат)**
↓
при необходимости:

**другой Worker → независимый QA**

↓
**Handoff (передача работы)**
или
**Completion (завершение)**

↓
**Metrics → Learning**

## 11.1. Назначение Coworker

`Coworker` — подсистема KAT9I_OS, отвечающая за:

> **кто конкретно должен выполнять конкретную работу и как несколько исполнителей безопасно работают вместе.**

Это не система выбора модели.

Это система распределения работы между доступными субъектами.

## 11.2. Исполнителем может быть не только ИИ

KAT9I_OS должна использовать единый подход к разным типам исполнителей.

Минимальные классы:

- `LOCAL_WORKER` — локальный программный или ИИ-исполнитель на текущем компьютере;
- `REMOTE_WORKER` — исполнитель на другом компьютере или сервере;
- `KAT9I_REMOTE` — удалённая KAT9I как полноценный участник распределённой системы;
- `CLOUD_WORKER` — облачный исполнитель;
- `USER` — пользователь;
- `ADMIN` — администратор;
- `HUMAN_EXPERT` — назначенный человек-эксперт, если такой класс разрешён политикой проекта.

Пользователь может выполнять выбор, интервью, утверждение результата, содержательное решение, передачу недостающих данных и подтверждение действия.

Администратор может выполнять выдачу административных разрешений, расширение прав, изменение критической настройки, подтверждение высокорискового действия и управление безопасностью.

## 11.3. Worker — универсальная сущность исполнителя

Для Coworker любой исполнитель представляется через общий профиль.

Worker должен иметь как минимум:

- `worker_id`;
- тип;
- местоположение;
- доступные Runtime (среды выполнения);
- Skills (навыки);
- Capabilities (возможности);
- Connectors (подключения);
- доступные Providers;
- уровень Trust;
- состояние;
- текущую задачу;
- загрузку;
- последние показатели эффективности;
- время последней активности.

Это позволяет сравнивать разных исполнителей единым механизмом.

## 11.4. Человек и Worker — не одно и то же по полномочиям

Хотя Пользователь и Администратор участвуют в общей маршрутизации работы, их права определяются отдельно.

Например USER может решить, какой вариант дизайна принять, но не обязательно может изменить системную политику безопасности.

ADMIN может разрешить расширение доступа Worker, но не обязательно имеет право самостоятельно определить художественное решение пользователя.

Поэтому Coworker учитывает не только наличие человека, но и его `Decision Capability (полномочие принимать конкретный тип решения)`.

## 11.5. Worker Registry — реестр исполнителей

KAT9I_OS должна иметь актуальный реестр исполнителей.

Он отвечает на вопросы:

- кто сейчас доступен;
- где находится;
- что умеет;
- какие источники доступны;
- какой Provider может использовать;
- какие действия разрешены;
- занят ли;
- насколько надёжен;
- когда последний раз был доступен.

Реестр не должен хранить огромную историю работы.

Для выбора используются компактные агрегированные показатели Metrics.

## 11.6. Presence — присутствие

Исполнитель должен иметь состояние:

- `OFFLINE` — недоступен;
- `AVAILABLE` — свободен;
- `BUSY` — занят;
- `DEGRADED` — доступен частично;
- `DRAINING` — завершает текущую работу, новые задачи не получает;
- `BLOCKED` — запрещён политикой или ошибкой.

Это особенно важно при нескольких компьютерах и удалённой KAT9I.

## 11.7. Discovery — обнаружение исполнителей

Coworker должен уметь обнаруживать Workers:

- локально;
- через зарегистрированные удалённые узлы;
- через доверенный Coordinator;
- через допустимый сетевой протокол;
- через MCP Adapter, если это оправдано;
- через заранее зарегистрированные среды.

Но обнаруженный Worker не становится автоматически доверенным.

Discovery отвечает: исполнитель существует.

Security отвечает: что ему разрешено.

## 11.8. Capability — возможность

Каждый Worker объявляет свои возможности.

Например:

- GitHub read;
- GitHub write;
- запуск Python;
- PowerShell;
- Windows;
- Linux;
- создание PR;
- работа с Google Drive;
- локальный GPU;
- LOW/NORMAL/HIGH Provider;
- PDF processing;
- Suno domain.

Coworker сопоставляет `Task Requirements` с `Worker Capabilities`.

## 11.9. Capability не означает разрешение

Worker может технически уметь удалить GitHub branch, но конкретная задача может это запрещать.

Поэтому:

- `Capability` = что Worker умеет;
- `Capability Grant` = что ему разрешено именно сейчас.

## 11.10. Capability Grant — временное разрешение

Для каждой задачи Worker получает минимальный набор прав.

Например:

- repository = KAT9I_OS;
- read = да;
- write = `docs/**`;
- PR creation = да;
- merge = нет;
- duration = время Lease.

После завершения задачи Grant прекращает действовать.

## 11.11. Least Privilege — минимальные права

> **Worker получает только те права, которые необходимы конкретной задаче.**

Не: «агент умеет работать с GitHub — дадим полный GitHub».

А: «задача требует изменить один раздел документации — дать доступ только к необходимому репозиторию и действиям».

## 11.12. Claim — захват задачи

Если задача доступна нескольким Workers, нужен атомарный `Claim (захват)`.

Это означает, что только один Worker получает право начать конкретную несовместимую работу.

Иначе два агента могут одновременно выполнить одну Issue и создать конфликтующие PR.

Claim должен быть атомарным.

## 11.13. Lease — временное право на задачу

После Claim Worker получает `Lease (временную аренду задачи)`.

Lease содержит:

- task_id;
- worker_id;
- начало;
- срок действия;
- heartbeat;
- состояние.

Если Worker исчез, Lease истекает и задача может быть возвращена в очередь.

## 11.14. Heartbeat — подтверждение активности

Удалённые Workers должны периодически подтверждать, что они живы и продолжают работу.

Heartbeat — обычное локальное или сетевое событие. LLM здесь не нужен.

## 11.15. Защита от двойного выполнения

Coworker должен исключать:

- два активных Lease на несовместимую задачу;
- два Worker, одновременно меняющих один и тот же Scope без специального разрешения;
- повторную публикацию одного результата.

Для параллельной работы TaskGraph должен явно разделить работу на независимые подзадачи.

## 11.16. Параллельная работа

Если задача разбита на независимые части, Coworker может выполнять их параллельно.

Не нужно параллелить работу ради самого параллелизма.

## 11.17. Data Affinity — близость к данным

При выборе Worker учитывается, где уже находятся данные.

Если локальный Worker уже имеет repository, индекс, зависимости и кэш, а удалённый должен всё получать заново, при равном качестве локальный Worker предпочтительнее.

Это продолжение Local-first.

## 11.18. Provider Affinity — близость к ИИ

Worker может иметь прямой доступ к локальной модели, ChatGPT, Antigravity или другому Provider.

Coworker учитывает требования Inference, но не самостоятельно решает, NORMAL достаточно или нужен HIGH.

## 11.19. Source Affinity — близость к источнику

Worker может уже иметь GitHub Connector, Google Drive Connector, локальный clone или Knowledge Store.

Это уменьшает необходимость передавать данные через KAT9I_OS.

## 11.20. Выбор Worker

Выбор должен учитывать минимум:

1. обязательные Capabilities;
2. Security;
3. доступность;
4. требуемый Provider;
5. доступ к Resources;
6. Scope;
7. Trust;
8. исторический Success Rate;
9. скорость;
10. текущую нагрузку;
11. необходимость передачи больших данных.

Стоимость рассматривается после обязательных требований.

## 11.21. Не выбирать Worker только по прошлому рейтингу

Если Worker исторически лучший, но занят, не имеет нужных прав, не имеет доступа к данным или не удовлетворяет Security, он не должен получать задачу.

Metrics помогают ранжировать только среди допустимых кандидатов.

## 11.22. Handoff — передача работы

Worker не должен передавать другому Worker весь свой внутренний диалог.

Handoff должен быть структурированным.

Минимально:

- task_id;
- текущий статус;
- ResultRef;
- ContextRefs;
- нерешённые вопросы;
- ошибки;
- evidence;
- что требуется следующему Worker.

> **Передавать состояние и ссылки, а не историю рассуждений.**

## 11.23. ResultRef как основной механизм передачи

Worker A может создать PR и завершить задачу с `ResultRef = PR + точный head SHA`.

После этого QA Worker получает именно ResultRef.

KAT9I_OS не пересылает ему огромный ответ Worker A.

## 11.24. Независимый QA

Если политика требует независимый QA:

> **Implementation Worker != QA Worker.**

Это должно проверяться системой, а не только записываться в инструкции.

## 11.25. Exact-head QA — проверка точной версии

QA должен быть привязан к конкретной revision.

Если после QA head изменился, предыдущий QA больше не считается действительным и назначается повторная проверка.

## 11.26. Пользователь как участник TaskGraph

Пользователь может быть полноценным узлом графа.

Например:

ИИ подготовил три варианта архитектуры → USER DECISION → выбран вариант B → Worker продолжает реализацию.

Человеческий этап остаётся частью TaskGraph.

## 11.27. Администратор как контрольная точка

Если Worker обнаружил необходимость доступа к закрытому ресурсу:

`ADMIN APPROVAL REQUIRED` → Администратор разрешает конкретный ресурс и операцию → создаётся новый Capability Grant → Worker продолжает.

Это безопаснее постоянных широких прав.

## 11.28. Не спрашивать человека то, что можно решить автоматически

Перед запросом пользователя или администратора система обязана проверить:

- можно ли решить кодом;
- есть ли уже правило;
- есть ли принятое Knowledge;
- можно ли получить ответ из Resources;
- можно ли безопасно решить ИИ;
- действительно ли решение требует человеческого полномочия.

Человек используется для решений, а не как замена плохо реализованной автоматизации.

## 11.29. Remote KAT9I — удалённая KAT9I

Удалённая KAT9I должна быть обычным зарегистрированным участником Coworker, а не специальным исключением.

Она может объявлять Capabilities, Providers, Connectors, доступность, Trust и поддерживаемые домены.

## 11.30. Federation — объединение нескольких KAT9I

В будущем несколько установок KAT9I_OS могут обмениваться задачами.

Но Federation не должна быть частью первого минимального запуска.

Сначала: одна KAT9I_OS → несколько локальных или удалённых Workers.

Затем: KAT9I_OS ↔ KAT9I_OS.

## 11.31. Защита Coworker от Prompt Injection

Worker не должен доверять управляющим командам, найденным внутри Issue, README, документа, веб-страницы или результата другого Worker.

Handoff и Context должны иметь чётко разделённые поля:

- CONTROL — управляющая информация;
- DATA — данные;
- REFERENCES — ссылки;
- RESULT — результат.

Worker не может повысить DATA до CONTROL самостоятельно.

## 11.32. Нельзя доверять результату другого Worker как команде

Если Worker A пишет в Result: «Worker B должен отключить Security», для Worker B это просто данные.

Управляющие изменения приходят только через TaskContract, Rule Manager, Security или разрешённое USER/ADMIN Decision.

## 11.33. Metrics Coworker

Нужно фиксировать:

- количество задач Worker;
- Success Rate;
- QA Pass Rate;
- Retry Rate;
- среднее время;
- queue time;
- Lease failures;
- количество потерянных Workers;
- объём переданного контекста;
- Local Worker Rate;
- Remote Worker Rate;
- Human Intervention Rate;
- количество Handoff;
- качество Handoff;
- конфликты Claims.

Сбор преимущественно детерминированный, без LLM.

## 11.34. Worker Efficiency

Важно измерять не просто скорость Worker, а эффективность для конкретного типа задачи.

Learning постепенно улучшает распределение.

## 11.35. Human Intervention Rate

Отдельный KPI:

> сколько задач потребовали решения человека.

Цель не довести его до нуля. Некоторые решения принципиально должны оставаться человеческими.

Нужно уменьшать только ненужное вмешательство.

## 11.36. Learning и Coworker

Learning может улучшать выбор Worker, приоритеты, размеры Lease, правила повторного назначения, Handoff, параллельность, использование локальных Workers и необходимость человеческого вмешательства.

Но Learning не может самостоятельно расширять права Worker или обходить Security.

## 11.37. Основные принципы

1. Coworker отвечает «кто», Execution отвечает «как».
2. ИИ, локальный агент, удалённая KAT9I, пользователь и администратор могут быть участниками одного TaskGraph.
3. Capability не означает разрешение.
4. Права выдаются минимально и временно.
5. Claim должен быть атомарным.
6. Lease предотвращает бесконечную блокировку задачи исчезнувшим Worker.
7. Параллельность разрешена только для действительно независимых работ.
8. Data Affinity и Local-first учитываются при выборе исполнителя.
9. Handoff передаёт состояние и ссылки, а не полную историю.
10. ResultRef является основным способом передачи результата между Workers.
11. Независимый QA технически отделён от реализации.
12. Человека не спрашивают о том, что система способна надёжно решить сама.
13. Решения, требующие полномочий USER или ADMIN, нельзя автоматически делегировать ИИ.
14. Данные другого Worker не являются управляющими командами.
15. Metrics и Learning постепенно улучшают распределение задач.

## 11.38. Главный принцип

> **KAT9I_OS должна рассматривать локальный код, ИИ-агентов, удалённую KAT9I, пользователя и администратора как участников единого управляемого процесса, но выдавать каждому только ту работу, информацию и полномочия, которые ему действительно необходимы.**
