# 17. Визуализация процессов KAT9I_OS

## 17.1. Назначение

KAT9I_OS должна иметь отдельный домен и программный модуль:

> **Визуализация процессов — наглядное представление работы системы в реальном времени и в истории.**

Основной пользовательский принцип:

> **Состояние KAT9I_OS должно быть видно глазами, а не только через логи и таблицы.**

Ответственный за разработку модуля:

**Артём — `Art3m1da`.**

Назначение ответственного не означает автоматической выдачи дополнительных прав GitHub. Права репозитория регулируются отдельно.

## 17.2. Основная схема

Запрос пользователя → Core (ядро управления) → Rule Manager (менеджер правил) → Context (контекст) → Resources (ресурсы) → Inference (выбор ИИ) → Coworker (выбор исполнителя) → Execution (исполнение) → QA (независимая проверка) → ResultRef (ссылка на результат).

Параллельно каждый этап создаёт Telemetry (телеметрию) и Metrics (метрики), которые поступают в модуль визуализации и отображаются в браузерном интерфейсе.

Пользователь должен видеть движение задачи по системе в реальном времени.

## 17.3. Главный принцип архитектуры

Визуализация не должна сама управлять системой. Она наблюдает и отображает.

По умолчанию действует принцип **только чтение (read-only by default)**.

Управляющие действия, если они будут добавлены позднее, обязаны проходить обычные механизмы прав, Rule Manager, Security и подтверждение Пользователя или Администратора.

## 17.4. Браузер как основной интерфейс

Основным интерфейсом предлагается локальное веб-приложение, открываемое браузером.

Причины:
- подходит для анимации;
- позволяет строить графы;
- поддерживает интерактивность;
- удобно масштабируется;
- не требует отдельного тяжёлого настольного интерфейса;
- может работать локально;
- подходит для нескольких экранов;
- допускает разрешённый удалённый доступ.

По умолчанию интерфейс должен работать полностью локально.

## 17.5. Карта архитектуры в реальном времени

Основной экран показывает модули KAT9I_OS как узлы. При прохождении задачи между модулями объект задачи анимированно перемещается по соответствующим связям.

## 17.6. Состояния модулей

Каждый модуль должен визуально показывать состояние:
- ожидание;
- обработка;
- успешно;
- предупреждение;
- ошибка;
- заблокировано;
- ожидается пользователь;
- ожидается администратор;
- повторная попытка.

Пользователь должен сразу видеть, где находится задача и почему она остановилась.

## 17.7. Визуализация нескольких задач

Если одновременно выполняется несколько задач, каждая имеет собственный визуальный идентификатор. Это особенно важно для распределённой системы Coworker.

## 17.8. Граф задач

Для сложной задачи отображается TaskGraph (граф связанных задач): завершённые, выполняемые, ожидающие, параллельные и блокирующие подзадачи.

## 17.9. Исполнители

Отдельный экран показывает Workers (исполнителей): локальных, удалённых, KAT9I_REMOTE, облачных, Пользователя и Администратора — с их текущим состоянием и занятостью.

## 17.10. Визуализация выбора ИИ

Inference должен отображаться наглядно: локальный код, локальный ИИ, подписочный NORMAL, HIGH после повышения уровня и другие маршруты. Пользователь должен видеть, почему и когда система начала использовать более дорогой интеллект.

## 17.11. Расход токенов в реальном времени

Для каждой активной задачи показываются:
- входные токены;
- выходные токены;
- кэшированные токены;
- внешние токены;
- локальные вызовы;
- NORMAL-вызовы;
- HIGH-вызовы.

Значения должны обновляться по мере выполнения.

## 17.12. Расход денег

Если используется платный API, показываются текущая стоимость, стоимость этапа, накопленная стоимость задачи, проекта и периода.

Локальный код, локальная модель и уже оплаченная подписка отображаются отдельно.

## 17.13. Экономия

Нужно показывать не только расходы, но и экономию:
- благодаря локальному коду;
- благодаря кэшу;
- благодаря Reference-first (сначала ссылка);
- благодаря локальной обработке.

## 17.14. Визуализация кэша

Показываются:
- полное попадание в кэш;
- частичное попадание;
- промах;
- устаревший кэш;
- запрещённое кэширование;
- очистка кэша.

## 17.15. Изменение контекста

Должна отображаться оценка изменения контекста и её влияние на пригодность кэша.

## 17.16. Потоки данных

Визуально различаются:
- управляющие команды;
- ссылки;
- данные;
- результаты;
- метрики;
- события.

Должно быть видно, когда система передала несколько ContextRef вместо материализации большого объёма данных.

## 17.17. Управляющие данные и обычные данные

Граница CONTROL (управляющая информация) и DATA (обычные данные) должна быть видимой. Попытка внедрения команды из внешнего документа остаётся DATA и может отображаться как событие безопасности.

## 17.18. Ошибки

Ошибки визуально привязываются к месту возникновения: Resources, Execution, Security, Context и т.д. Пользователь не должен искать причину только в общем журнале.

## 17.19. Цепочка ошибки

Для сложной ошибки показывается последовательность: задача → модуль → ошибка → повтор → повышение уровня → успешное или неуспешное завершение.

## 17.20. Безопасность

Отдельный режим отображает:
- заблокированные действия;
- попытки расширения Scope;
- Prompt Injection (внедрение управляющих инструкций через контекст);
- Command Injection (внедрение команд ОС);
- отказ в правах;
- запрос ADMIN Approval;
- доступ к секретам;
- отозванные разрешения.

Чувствительные значения не отображаются.

## 17.21. Не показывать секреты

В интерфейс не должны попадать пароли, API-ключи, токены доступа, значения секретов и полный чувствительный Context. Показывается только факт разрешённого использования SecretRef.

## 17.22. История выполнения

Визуализация должна работать и для завершённых задач. Пользователь может открыть задачу и воспроизвести её прохождение через KAT9I_OS.

## 17.23. Повторное воспроизведение

Replay (повторное воспроизведение событий) строится по сохранённой телеметрии и показывает временную последовательность этапов, ошибок, повторов, затрат и человеческих решений.

## 17.24. Источник истории

Для Replay не нужно хранить видео. Хранятся структурированные события Telemetry, из которых браузер восстанавливает визуальное представление.

## 17.25. Временная шкала

Для каждой задачи отображается временная шкала с длительностью этапов, ожиданиями, ошибками, повторами и человеческими решениями.

## 17.26. Узкие места

На основе Metrics визуализация должна показывать Bottleneck (узкие места): где система теряет больше всего времени, токенов или внешних ресурсов.

## 17.27. Панель эффективности

Отдельный экран показывает количество задач, успешность, QA PASS, долю локальной работы, внешние токены, экономию кэшем, HIGH-вызовы, среднее время и число вмешательств человека.

## 17.28. Сравнение периодов

Можно сравнивать периоды: изменение токенов, времени, QA, Local-first и доли исполняемого кода.

## 17.29. Визуализация самообучения

Показывается цепочка: Learning обнаружил повторяемую модельную операцию → создано предложение → реализован локальный модуль → измерена экономия и изменение качества.

## 17.30. Развитие навыков

Можно отображать эволюцию Skill (навыка): какая доля выполняется кодом и какая ИИ в разных версиях.

## 17.31. Источники данных модуля

Визуализация читает:
- Telemetry;
- Metrics;
- TaskRuntimeState;
- TaskGraph;
- Coworker;
- Inference;
- Context;
- Resources;
- Cache Policy;
- Execution;
- Security Events;
- Learning.

## 17.32. Не делать отдельную телеметрию для интерфейса

Модули создают стандартную общесистемную Telemetry. Визуализация преобразует её в отображение. Telemetry является источником истины для визуального состояния.

## 17.33. Поток обновлений

Для режима реального времени браузер получает компактные изменения состояния. Технически это может быть реализовано через WebSocket (постоянный двусторонний канал) или Server-Sent Events / SSE (поток событий от сервера браузеру). Конкретная технология выбирается при реализации.

Архитектурное требование: не перезагружать всю историю задачи при каждом новом событии.

## 17.34. Локальная агрегация

Перед браузером данные агрегируются локальным кодом. Повторяющиеся мелкие события суммируются, чтобы не создавать лишнюю нагрузку.

## 17.35. Визуализация не должна увеличивать расход ИИ

Обычная работа интерфейса должна требовать примерно 0 дополнительных LLM-токенов. Графики, счётчики, анимации, статусы и временные шкалы строятся обычным программным кодом.

## 17.36. Нагрузка интерфейса

Модуль измеряет собственные CPU, память, сеть, размер телеметрии, задержку и использование диска. Визуализация не должна замедлять основное выполнение задач.

## 17.37. Режимы детализации

Минимальные режимы:
- обзор;
- задача;
- исполнитель;
- ресурсы;
- стоимость;
- производительность;
- безопасность;
- самообучение.

## 17.38. Режим «Рентген KAT9I_OS»

Диагностический режим показывает максимально подробно:
- какой модуль вызвал какой;
- какой ResourceRef передан;
- какой Worker выбран;
- какой Provider выбран;
- сколько Context материализовано;
- какой кэш использован;
- сколько токенов потрачено;
- какие Rules действовали;
- почему действие заблокировано.

Секреты не раскрываются.

## 17.39. Управление масштабом

Интерфейс должен группировать события, сворачивать модули, агрегировать повторяющиеся операции, фильтровать и увеличивать выбранный участок.

## 17.40. Фильтры

Нужны фильтры по задаче, HIGH-вызовам, ошибкам, Security, Worker, GitHub, платным операциям, cache miss и запросам пользователя.

## 17.41. Сигналы и предупреждения

Визуализация подсвечивает аномалии, уже выявленные системой Metrics. Сам интерфейс не должен постоянно вызывать HIGH-модель для поиска таких событий.

## 17.42. Доступ из браузера

По умолчанию интерфейс локальный. Удалённый доступ включается только через отдельную Security Policy.

## 17.43. Права просмотра

Можно предусмотреть роли Пользователь, Администратор и разработчик домена. Разработчик визуализации не получает автоматического доступа ко всем пользовательским данным.

## 17.44. Ответственность Артёма

`Art3m1da` является ответственным за разработку домена визуализации.

Зона ответственности:
- архитектура пользовательского интерфейса;
- браузерная визуализация;
- анимация потока задач;
- отображение телеметрии;
- отображение метрик;
- временные шкалы;
- историческое воспроизведение;
- диагностические экраны;
- производительность интерфейса.

Форматы канонической Telemetry и Metrics остаются общесистемными контрактами KAT9I_OS, а не частным форматом визуализатора.

## 17.45. Независимость от реализации интерфейса

KAT9I_OS не должна зависеть от конкретного браузерного движка или библиотеки визуализации. Главный контракт: структурированные события и метрики → интерфейс визуализации.

## 17.46. Самообучение интерфейса

Learning может анализировать, какие экраны пользователь открывает чаще, какие показатели полезны, какую детализацию предпочитает и какие предупреждения игнорирует. Такие изменения относятся преимущественно к Preferences (предпочтениям). Интерфейс не может самостоятельно менять Security или скрывать критические события.

## 17.47. Главные показатели модуля

Нужно измерять:
- задержку визуализации;
- потерю событий;
- нагрузку визуализации;
- объём телеметрии;
- пользу диагностирования.

## 17.48. Что модуль не должен делать

Визуализация не должна:
- становиться вторым Core;
- изменять TaskRuntimeState напрямую;
- самостоятельно выдавать права;
- менять Rules;
- управлять Worker в обход Coworker;
- запускать команды в обход Execution;
- хранить отдельную копию всей базы знаний;
- создавать конкурирующую Telemetry;
- показывать секреты;
- отправлять телеметрию внешним ИИ без необходимости.

## 17.49. Основные принципы

1. Визуализация — отдельный домен KAT9I_OS.
2. Ответственный разработчик — Артём (`Art3m1da`).
3. Основной интерфейс — локальное браузерное приложение.
4. Работа системы анимируется в реальном времени.
5. Источник истины — общая Telemetry и Metrics.
6. Визуализация по умолчанию только читает состояние.
7. Токены, стоимость, время, кэш, ошибки и Worker отображаются в реальном времени.
8. Поддерживается историческое воспроизведение задач.
9. Отображается экономия Local-first, Executable-first, Reference-first и Cache.
10. Интерфейс не должен существенно увеличивать расход токенов или ресурсов.
11. CONTROL и DATA различаются визуально и архитектурно.
12. Security Events отображаются без раскрытия секретов.
13. Пользователь может менять уровень детализации.
14. Формат телеметрии не зависит от конкретного интерфейса.
15. Удалённый доступ к визуализации закрыт по умолчанию.

## 17.50. Главный принцип

> **Человек должен иметь возможность открыть KAT9I_OS в браузере и буквально увидеть, как его запрос проходит через систему: какие модули его обрабатывают, кто выполняет работу, какие данные перемещаются, где используется кэш, сколько расходуется времени и токенов, где возникла ошибка и чему система научилась после выполнения.**
