# 19. Планирование и прогнозирование ресурсов KAT9I_OS

## 19.1. Назначение

Модуль отвечает на вопрос:

> **Сколько времени, токенов, денег и вычислительных ресурсов вероятно потребуется для выполнения задачи и какой маршрут даст лучший ожидаемый результат?**

Он работает до выполнения, уточняет прогноз после получения контекста и кэша, а затем пересчитывает его во время работы.

Это отдельный общесистемный модуль. Он не является частью только Inference (выбора ИИ), потому что должен оценивать также локальный код, ожидание Worker (исполнителя), интеграции, тесты, QA, кэш, человека и другие этапы.

## 19.2. Основная схема

TaskContract (контракт задачи)
→ предварительный TaskGraph (граф задачи)
→ Анализатор задачи
→ Анализатор истории
→ Предсказатель ресурсов
→ Калькулятор стоимости и времени
→ TaskEstimate (прогноз задачи)
→ сравнение допустимых маршрутов
→ Context / Resources / Cache
→ уточнённый прогноз
→ Inference / Coworker / Execution
→ текущий пересчитываемый прогноз
→ фактические Metrics
→ сравнение «прогноз / факт»
→ Learning
→ калибровка будущих прогнозов.

## 19.3. Три обязательных режима прогноза

### Предварительный прогноз

Формируется сразу после TaskContract и предварительной декомпозиции.

Он нужен, чтобы ещё до дорогих операций понимать примерный масштаб задачи и выбирать общую стратегию.

### Уточнённый прогноз

Формируется после того, как известны:
- реальный Context;
- доступные Resources;
- состояние Cache;
- Context Drift (степень изменения контекста);
- кандидаты Worker;
- кандидаты Provider;
- обязательный QA;
- реальные ограничения Security.

Этот прогноз используется для сравнения конкретных маршрутов.

### Текущий пересчитываемый прогноз

Во время Execution прогноз обновляется по мере появления новых фактов.

Например:
- тест упал;
- появился Retry;
- Worker стал недоступен;
- потребовался HIGH;
- кэш оказался хуже ожидаемого;
- задача ждёт пользователя.

После такого события KAT9I_OS должна обновить ожидаемые оставшиеся секунды, токены и стоимость.

## 19.4. Анализатор задачи

Анализатор задачи определяет признаки новой работы без дорогого интеллектуального анализа там, где это возможно.

Минимальные признаки:
- Domain (предметная область);
- Task Type (тип задачи);
- Scope (область изменений);
- предполагаемое число подзадач;
- число файлов или ресурсов;
- размер входных данных;
- ожидаемый размер Context;
- Skill и Workflow;
- наличие QA;
- требуемый уровень качества;
- количество внешних систем;
- необходимость человеческого решения.

Формализуемые признаки извлекаются локальным кодом.

## 19.5. Анализатор истории

Анализатор истории использует агрегированные Metrics предыдущих похожих задач.

Он не должен передавать модели полные чаты или историю сотен задач.

Используются компактные статистики по сочетаниям:
- Domain;
- Task Type;
- Worker;
- Provider;
- Model;
- Skill;
- Workflow;
- размер Context;
- Cache;
- тип QA;
- Workspace.

Минимальные статистики:
- количество наблюдений;
- медианное время;
- P50 / P95 времени;
- медианные токены;
- P50 / P95 токенов;
- стоимость;
- Retry Rate (доля повторов);
- Escalation Rate (доля повышения уровня);
- First Pass Success Rate (успех с первой попытки);
- Cache Hit Rate;
- QA Pass Rate;
- Human Intervention Rate.

## 19.6. Холодный старт

Если истории ещё недостаточно, используется статическая базовая модель оценки.

Она опирается на:
- размер задачи;
- предполагаемый Context;
- тип Domain;
- число этапов;
- класс Provider;
- наличие QA;
- доступность кэша;
- известные нормативы Runtime.

Отсутствие истории не должно блокировать систему.

## 19.7. Предсказатель ресурсов

Предсказатель корректирует историческую базовую линию с учётом конкретной новой задачи.

Он должен учитывать как минимум:
- размер и сложность Scope;
- Context;
- Context Drift;
- ожидаемый Cache Hit;
- Direct Resolution Rate (доля прямого доступа к ресурсам);
- предполагаемую материализацию;
- Worker;
- Provider;
- LOW / NORMAL / HIGH;
- вероятность Retry;
- вероятность Escalation;
- QA;
- очередь Worker;
- задержки интеграций;
- необходимость USER / ADMIN решения.

## 19.8. Калькулятор стоимости и времени

Калькулятор работает обычным локальным кодом.

Он объединяет:
- ожидаемые входные токены;
- ожидаемые выходные токены;
- ожидаемые кэшированные токены;
- тариф Provider;
- вероятность дополнительных вызовов;
- вероятность HIGH;
- время Tool;
- время Runtime;
- время ожидания Worker;
- время интеграций;
- время QA;
- ожидаемое человеческое ожидание, если оно известно статистически.

Для арифметики вызов ИИ не требуется.

## 19.9. TaskEstimate — прогноз задачи

Канонический прогноз должен содержать минимум:
- task_id;
- версия прогноза;
- тип прогноза: предварительный / уточнённый / текущий;
- ожидаемые входные токены;
- ожидаемые выходные токены;
- ожидаемые кэшированные токены;
- ожидаемые внешние токены;
- ожидаемое время выполнения;
- ожидаемое время ожидания;
- ожидаемую стоимость;
- ожидаемое число модельных вызовов;
- ожидаемое число Tool-вызовов;
- вероятность Retry;
- вероятность Escalation NORMAL → HIGH;
- ожидаемый Cache Hit;
- ожидаемую долю локальной работы;
- вероятность завершения с первой попытки;
- диапазон неопределённости;
- факторы, сильнее всего влияющие на прогноз.

## 19.10. Прогноз должен быть диапазоном

KAT9I_OS не должна создавать ложную точность.

Вместо:

> задача займёт 103 секунды

предпочтительно:

> ожидаемое время 90–130 секунд, центральная оценка 108 секунд.

Аналогично для токенов и денег.

## 19.11. Уровень уверенности

Прогноз должен иметь Confidence (уровень уверенности), основанный на:
- числе похожих наблюдений;
- разбросе исторических результатов;
- новизне типа задачи;
- Context Drift;
- неизвестных зависимостях;
- доступности Worker и Provider.

Низкая уверенность должна быть видимой пользователю и Inference.

## 19.12. Сравнение альтернатив до запуска

Одна из основных функций модуля — сравнивать допустимые маршруты до выполнения.

Например:

| Маршрут | Время | Внешние токены | Стоимость | Успех с первой попытки |
|---|---:|---:|---:|---:|
| Локальный NORMAL | 190 сек | 0 | 0 | 72% |
| Подписочный NORMAL | 85 сек | 22 000 | включено в подписку | 91% |
| Платный HIGH API | 68 сек | 31 000 | 0,24 условной единицы | 97% |

Это не означает, что самый дешёвый маршрут всегда выбирается.

Security, Rules и минимальное качество остаются жёсткими ограничениями.

## 19.13. Inference использует прогноз, но не подменяется им

Inference получает несколько допустимых RouteEstimate (оценок маршрутов).

Он выбирает маршрут с учётом:
1. Security;
2. Rules;
3. Scope;
4. обязательного качества;
5. необходимых возможностей;
6. доступности источников;
7. прогнозируемой успешности;
8. времени;
9. стоимости;
10. Local-first.

Прогноз — вход в решение, а не самостоятельное разрешение на действие.

## 19.14. Coworker и прогноз очереди

Coworker должен предоставлять прогнозу сведения о:
- доступности Worker;
- текущей загрузке;
- очереди;
- историческом времени выполнения похожих задач;
- Data Affinity (близости к данным).

Более быстрый Provider не обязательно даст более быстрый результат, если подходящий Worker занят.

## 19.15. Кэш как обязательный фактор прогноза

Прогноз должен моделировать экономию Cache Policy.

Учитываются:
- FULL_HIT — полное попадание;
- PARTIAL_HIT — частичное повторное использование;
- MISS — промах;
- STALE — устаревший кэш;
- FORBIDDEN — кэш запрещён.

Прогноз должен учитывать не только наличие кэша, но и ожидаемую полезность.

## 19.16. Изменение контекста и полезность кэша

Если Context Similarity снизился, ожидаемая выгода кэша также уменьшается.

Например старый исторический Cache Hit = 70%, но текущий Context Drift значительно выше обычного. Прогноз обязан уменьшить ожидаемую экономию и увеличить оценку пересчёта.

Фиксированный порог 50% не является глобальным правилом. Порог зависит от типа данных и обучается по фактическим результатам в разрешённых пределах.

## 19.17. Частичный пересчёт

Если часть контекста или ресурса не изменилась, предсказатель должен учитывать Incremental Recompute (частичный пересчёт).

Например изменено 2 модуля из 10 — прогноз не должен автоматически считать стоимость полного повторного анализа всех 10 модулей.

## 19.18. Reference-first в прогнозе

Прямой доступ Worker к GitHub, Drive или другому источнику должен уменьшать прогноз:
- материализации;
- сетевой передачи;
- внешних токенов;
- времени подготовки Context.

Таким образом выгода Reference-first становится измеримой ещё до выполнения.

## 19.19. Executable-first в прогнозе

Если часть Workflow имеет исполняемую локальную реализацию, прогноз должен считать её как локальную операцию, а не как модельный вызов.

Это позволяет количественно показывать выгоду детерминизации Skills.

## 19.20. Человеческие этапы

USER, ADMIN и HUMAN_EXPERT учитываются в прогнозе отдельно.

Система может оценивать:
- вероятность необходимости человеческого решения;
- тип решения;
- техническое время подготовки вопроса;
- историческое время ожидания ответа, если такая статистика разрешена.

Но KAT9I_OS не должна обещать точное время ответа человека.

## 19.21. Текущий пересчитываемый прогноз

После каждого значимого события прогноз может обновляться:
- этап завершён быстрее или медленнее ожидаемого;
- изменился Cache Hit;
- выполнена часть токенного бюджета;
- появился Retry;
- произошла Escalation;
- Worker сменился;
- появилась блокировка;
- изменился TaskGraph.

Пересчёт должен быть дешёвым и преимущественно локальным.

## 19.22. Оценка остатка

Во время выполнения система должна уметь показывать:
- сколько уже потрачено;
- сколько примерно осталось;
- какой диапазон остатка;
- что изменило прогноз.

Например:

> прошло 64 секунды; ожидаемый остаток 45–75 секунд; после FAIL теста прогноз вырос на 28 секунд и примерно на 7 000 внешних токенов.

## 19.23. Сравнение «прогноз / факт»

После завершения задачи прогноз автоматически сравнивается с фактическими Metrics.

Минимально сравниваются:
- время;
- внешние токены;
- общие токены;
- стоимость;
- Cache Hit;
- число Retry;
- Escalation;
- First Pass Success;
- количество Tool-вызовов.

## 19.24. Метрики точности прогнозирования

Вводятся отдельные показатели:
- Token Forecast Error — ошибка прогноза токенов;
- Time Forecast Error — ошибка прогноза времени;
- Cost Forecast Error — ошибка прогноза стоимости;
- Cache Forecast Error — ошибка прогноза кэша;
- Retry Calibration Error — ошибка прогноза повторов;
- Escalation Calibration Error — ошибка прогноза повышения уровня;
- First Pass Calibration Error — ошибка прогноза успеха с первой попытки.

Для системного контроля полезны медиана ошибки и P95 ошибки по каждому разрезу.

## 19.25. История прогнозов

История прогнозов должна хранить структурированные пары:

> прогноз → фактический результат.

Полный Context и полный чат для обучения предсказателя не требуются.

Запись связывается с:
- Task Type;
- Domain;
- Worker;
- Provider;
- Skill;
- Workflow;
- размером Context;
- состоянием Cache;
- результатом QA.

## 19.26. Самообучение предсказателя

Learning использует ошибки прогноза для калибровки модели оценки.

Сначала применяются простые методы:
1. исторические медианы;
2. коэффициенты сложности;
3. скользящие статистики;
4. простая регрессия.

При достаточном объёме данных могут применяться локальные модели машинного обучения, если они доказанно улучшают точность.

Платный ИИ для обычного прогнозирования не нужен.

## 19.27. Самообучаемые параметры

Learning может корректировать в разрешённых границах:
- коэффициенты сложности;
- влияние размера Context;
- вероятность Retry;
- вероятность HIGH;
- ожидаемый Cache Hit;
- влияние Context Drift;
- оценку Tool latency;
- оценку Worker queue;
- диапазон неопределённости.

Security и жёсткие лимиты не могут быть ослаблены предсказателем.

## 19.28. Бюджеты

TaskContract или политика могут задавать Budget (бюджет):
- максимальные внешние токены;
- максимальную стоимость;
- максимальное число HIGH-вызовов;
- максимальное время;
- максимальное число Retry.

Прогноз должен заранее показать, если ожидаемый маршрут не помещается в бюджет.

Система не должна молча ухудшать обязательное качество ради бюджета.

## 19.29. Выбор по стоимости успешного результата

Оптимизируется не цена первого вызова, а Expected Cost per Successful Task (ожидаемая стоимость успешного результата).

Бесплатный локальный маршрут может оказаться хуже, если он часто приводит к FAIL, Retry и последующему дорогому HIGH.

## 19.30. Визуализация прогнозов

Домен «Визуализация процессов» должен показывать до запуска:
- прогноз времени;
- прогноз токенов;
- прогноз стоимости;
- ожидаемый Cache Hit;
- вероятность HIGH;
- вероятность успеха с первой попытки;
- уровень уверенности.

Во время работы:
- факт на текущий момент;
- ожидаемый остаток;
- изменение прогноза;
- причина изменения.

После завершения:
- прогноз против факта;
- ошибку прогноза;
- динамику точности предсказателя.

## 19.31. Прогноз в режиме «Рентген KAT9I_OS»

Диагностический режим должен показывать, какие факторы сформировали прогноз:
- историческая база;
- размер Context;
- Worker;
- Provider;
- Cache;
- QA;
- Retry probability;
- Context Drift;
- стоимость маршрута.

Это объяснение факторов, а не внутренний Chain of Thought модели.

## 19.32. Безопасность и приватность

История прогнозов не должна становиться обходным способом сохранения чувствительного Context.

Хранятся агрегированные признаки и ссылки, если это разрешено.

Для SENSITIVE / LOCAL_ONLY данных применяются те же правила Security и Cache Policy.

## 19.33. Что модуль не должен делать

Модуль прогнозирования не должен:
- выдавать права;
- менять Rules;
- выбирать Worker напрямую;
- выполнять задачу;
- считать прогноз гарантией;
- снижать обязательный уровень качества;
- передавать всю историю задач LLM;
- самостоятельно увеличивать бюджет;
- сохранять запрещённые данные ради обучения.

## 19.34. Основные принципы

1. **До дорогого выполнения должен существовать прогноз ресурсов.**
2. **Прогноз выполняется минимум в трёх режимах: предварительный, уточнённый и текущий пересчитываемый.**
3. **История анализируется агрегированно, а не через полные старые чаты.**
4. **Калькуляция токенов, времени и денег выполняется локальным кодом.**
5. **Кэш и изменение контекста являются обязательными факторами прогноза.**
6. **Inference сравнивает допустимые маршруты на основе прогноза, качества и Security.**
7. **После каждой задачи прогноз сравнивается с фактом.**
8. **Learning калибрует предсказатель по ошибкам прогноза.**
9. **Начальная версия должна быть простой и детерминированной; сложное машинное обучение добавляется только при доказанной пользе.**
10. **Визуализация показывает прогноз, факт и остаток в реальном времени.**
11. **Прогноз выражается диапазоном и уровнем уверенности, а не ложной точностью.**
12. **Security и обязательное качество имеют приоритет над экономическим прогнозом.**

## 19.35. Главный принцип

> **KAT9I_OS должна не только измерять, сколько ресурсов уже потрачено, но и до выполнения прогнозировать стоимость успешного результата, сравнивать разрешённые маршруты, пересчитывать прогноз по ходу работы и учиться на разнице между прогнозом и фактом.**

## QA budget для Promotion (§36)

External FULL QA учитывается Planning как ограниченный ресурс времени, токенов и стоимости. После ранее принятого PASS Planning сравнивает стоимость нового FULL QA с Impact Assessment + DELTA QA и не запускает FULL повторно без machine-readable reason из §23.

Целевой KPI — QA Amplification Factor около 1 для STRICT accepted change и 0 для SAFE.
