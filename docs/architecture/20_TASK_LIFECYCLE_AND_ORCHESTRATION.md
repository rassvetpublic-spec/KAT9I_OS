# 20. Жизненный цикл задачи и оркестрация KAT9I_OS

## 20.1. Назначение

Этот раздел определяет, как один запрос проходит через всю KAT9I_OS от входа до проверенного результата и последующего самообучения.

Оркестрация не должна выполнять предметную работу сама. Она управляет состояниями, переходами, контрактами и вызовами системных модулей.

## 20.2. Сквозная схема

Пользователь / Администратор / внешнее событие
→ приём запроса
→ классификация CONTROL / DATA
→ определение Identity (источника и роли)
→ определение Workspace (рабочего пространства)
→ Effective Ruleset (набор применимых правил)
→ Domain (предметная область)
→ TaskContract (контракт задачи)
→ при необходимости TaskGraph (граф подзадач)
→ предварительный прогноз ресурсов
→ Context / Knowledge / Resources / Cache
→ уточнённый прогноз ресурсов
→ Executable-first (можно ли выполнить локальным кодом)
→ Inference (какой интеллект или человеческое решение требуется)
→ сравнение допустимых маршрутов по прогнозу
→ Coworker (кто выполняет)
→ Security (что разрешено)
→ Claim / Lease / Capability Grant
→ Execution (физическое выполнение)
→ текущий пересчитываемый прогноз
→ Validators (проверки)
→ Evidence (доказательства)
→ при необходимости независимый QA
→ ResultSink
→ ResultRef
→ Cleanup
→ Telemetry
→ Metrics
→ Visualization
→ сравнение «прогноз / факт»
→ Learning
→ улучшение системы.

## 20.3. Приём запроса

Запрос может поступить от:
- Пользователя;
- Администратора;
- Worker;
- автоматизации;
- GitHub;
- внешней интеграции;
- удалённой KAT9I;
- другого разрешённого источника.

Сам факт получения запроса не создаёт разрешение на выполнение.

## 20.4. Граница управляющей информации и данных

На входе применяется CONTROL / DATA boundary (граница управляющей информации и данных).

Внешние Issue, README, сайт, документ, Tool response и результат другого Worker по умолчанию являются DATA.

Они не могут самостоятельно изменять Rules, Scope, права или системное поведение.

## 20.5. Проверка источника и роли

Определяются:
- Identity;
- роль USER / ADMIN / WORKER / SERVICE;
- Trust (уровень доверия);
- применимые полномочия.

Если для критичного действия Identity определить нельзя — состояние BLOCKED.

## 20.6. Определение рабочего пространства

Workspace задаёт проектный контекст:
- связанные Resources;
- Rules;
- Knowledge;
- настройки;
- Domains;
- ответственных;
- разрешённые интеграции.

Смена Workspace должна автоматически менять применимый контекст.

## 20.7. Формирование применимых правил

Менеджер правил формирует Effective Ruleset из:
- системных правил;
- правил Workspace;
- правил Domain;
- персональных правил;
- Security Policy.

Действуют Scope и принцип «запрет выше разрешения».

Критичная неоднозначность обязательного правила приводит к BLOCKED.

## 20.8. Определение предметной области

Одна исполняемая задача имеет один основной Domain.

Междоменная работа разбивается на связанные TaskContract через TaskGraph.

## 20.9. Формирование TaskContract

TaskContract фиксирует минимум:
- цель;
- основной Domain;
- Scope;
- ContextRefs;
- RulesRef;
- требования к возможностям;
- требования к интеллекту;
- Output Contract;
- ResultSink;
- требования QA;
- бюджеты и ограничения, если заданы.

После отправки исполнителю контракт нельзя незаметно расширять.

## 20.10. Декомпозиция

Если задача сложная, создаётся TaskGraph.

Подзадачи могут выполняться последовательно или параллельно, но параллельность допускается только там, где зависимости это разрешают.

Каждая подзадача получает собственный контракт и состояние.

## 20.11. Предварительный прогноз

После TaskContract и предварительного TaskGraph модуль «Планирование и прогнозирование ресурсов» создаёт предварительный TaskEstimate (прогноз задачи).

Он оценивает:
- время;
- токены;
- стоимость;
- число модельных и инструментальных вызовов;
- вероятность Retry;
- вероятность Escalation;
- вероятность человеческого решения;
- ожидаемую долю локальной работы;
- ожидаемый Cache Hit;
- вероятность успеха с первой попытки;
- диапазон неопределённости.

Цель — понять масштаб задачи до дорогого выполнения.

## 20.12. Формирование минимального контекста

Context определяет минимально достаточную информацию для конкретного этапа.

Не передаются автоматически:
- весь чат;
- весь репозиторий;
- вся База знаний;
- вся история Metrics;
- все Skills.

Используются ContextRef и Progressive Disclosure (постепенное раскрытие).

## 20.13. Получение знаний

Knowledge Base возвращает только релевантные KnowledgeRef с учётом:
- Scope;
- Trust;
- Freshness;
- Security;
- типа задачи.

Не каждый старый результат считается знанием.

## 20.14. Разрешение ресурсов

Resources определяет, где находятся входы и результаты и какими Resolver они доступны.

Reference-first требует передавать ссылку вместо большого содержимого, когда Worker способен разрешить источник напрямую.

## 20.15. Проверка кэша

До повторного вычисления проверяются:
- Cache Classification;
- source revision;
- RulesRef;
- Skill / Workflow version;
- TTL;
- Context Similarity;
- Context Drift;
- Security;
- стоимость пересчёта.

Результат: FULL_HIT, PARTIAL_HIT, MISS, STALE или FORBIDDEN.

## 20.16. Частичное повторное использование

При PARTIAL_HIT пересчитывается только изменившаяся часть, если это безопасно и поддерживается конкретным процессом.

Полезный кэш не выбрасывается только потому, что изменился один фрагмент большого контекста.

## 20.17. Уточнённый прогноз

После Context, Resources и Cache формируется второй TaskEstimate.

Он уже учитывает:
- фактический размер Context;
- прямой доступ Worker к данным;
- реальную материализацию;
- фактическую пригодность кэша;
- Context Drift;
- доступных Worker;
- доступных Provider;
- очередь;
- обязательный QA;
- ограничения Security.

Этот прогноз используется Inference при сравнении допустимых маршрутов.

## 20.18. Проверка Executable-first

Для каждого этапа сначала проверяется:

> можно ли надёжно выполнить его локальным исполняемым кодом?

Если да — LLM не вызывается.

Это относится к поиску, индексам, Git, валидации, расчётам, Scope Guard, тестам, метрикам, кэшу и другим формализуемым операциям.

## 20.19. Проверка Local-first

Если нужен интеллект, при одинаково достаточном качестве предпочтение получает:
1. локальная вычислительная реализация;
2. локальный ИИ;
3. уже оплаченная внешняя возможность;
4. платный API.

Security и обязательное качество проверяются раньше экономики.

## 20.20. Определение уровня интеллекта

Inference определяет минимально достаточный уровень конкретного этапа:
- LOW;
- NORMAL;
- HIGH.

Уровень не назначается всей большой задаче автоматически.

## 20.21. Человек как маршрут решения

Если этап требует содержательного выбора или полномочия, Inference может сформировать требование:
- USER_REQUIRED;
- ADMIN_REQUIRED;
- HUMAN_EXPERT.

Человек не используется как ленивый запасной путь вместо доступной автоматизации.

## 20.22. Сравнение маршрутов

Допустимые маршруты сравниваются по прогнозируемым:
- качеству;
- First Pass Success;
- времени;
- токенам;
- стоимости;
- Cache benefit;
- Data Affinity;
- вероятности Retry;
- вероятности HIGH.

Оптимизируется ожидаемая стоимость успешного результата, а не стоимость первого вызова.

## 20.23. Выбор Worker

Coworker выбирает конкретного исполнителя по:
- Capabilities;
- Security;
- Trust;
- доступности;
- Data Affinity;
- Provider Affinity;
- историческому качеству;
- очереди;
- прогнозу выполнения.

Inference отвечает «какой маршрут нужен», Coworker — «кто его выполнит».

## 20.24. Claim, Lease и разрешения

Перед исполнением Worker получает:
- Claim — захват задачи;
- Lease — временное право выполнения;
- Capability Grant — минимальные разрешения.

Capability не означает автоматического разрешения использовать всё, что технически умеет Worker.

## 20.25. Проверка безопасности

До физического действия Security проверяет:
- Identity;
- Rules;
- Scope;
- Capability Grant;
- чувствительность данных;
- допустимые Provider и Tool;
- права на Resource;
- необходимость USER / ADMIN Approval.

Неопределённость опасного действия приводит к BLOCKED.

## 20.26. Предварительная проверка Execution

Execution выполняет Preflight:
- Runtime доступен;
- целевая revision актуальна;
- Workspace чист или изолирован;
- зависимости доступны;
- Scope известен;
- ResultSink известен;
- разрешения действительны.

Только после этого начинается реальное выполнение.

## 20.27. Изоляция

Изменяющие задачи по возможности выполняются в отдельном:
- Git Worktree;
- branch;
- временном Workspace;
- контейнере;
- другом изолированном Runtime.

Работа одной задачи не должна загрязнять другую.

## 20.28. Физическое выполнение

Execution запускает разрешённые:
- локальные процессы;
- Tools;
- Runtime;
- модельные этапы;
- интеграции.

Действие считается выполненным только по факту реального Runtime и Evidence.

## 20.29. Текущий пересчитываемый прогноз

Во время Execution прогноз пересчитывается после значимых событий.

Например:
- этап завершился быстрее или медленнее;
- изменился Cache Hit;
- появился Retry;
- NORMAL повышен до HIGH;
- Worker сменился;
- внешний сервис замедлился;
- появился HUMAN WAIT;
- изменился TaskGraph.

Пользователь и маршрутизатор получают новый ожидаемый остаток по времени, токенам и стоимости.

## 20.30. Контроль области изменений

Scope Guard детерминированно сравнивает разрешённую и фактическую область изменений.

Выход за Scope не должен приниматься на основании самооценки модели.

SCOPE_VIOLATION блокирует автоматическую публикацию.

## 20.31. Проверки результата

Сначала выполняются дешёвые детерминированные Validators:
- схема;
- формат;
- тесты;
- статический анализ;
- лимиты;
- наличие обязательных частей.

Затем при необходимости выполняется содержательная модельная или человеческая проверка.

## 20.32. Evidence

Execution сохраняет структурированные доказательства:
- точную revision;
- exit codes;
- результаты тестов;
- changed files;
- Scope Guard status;
- ResultRef;
- временные отметки.

Заявление модели не заменяет Evidence.

## 20.33. Независимый QA

Если политика требует QA:

> Implementation Worker != QA Worker.

QA получает точную revision, ResultRef, Evidence и RulesRef.

Самооценка исполнителя не считается независимой проверкой.

## 20.34. Применимость QA после изменения revision

Точная source revision прежнего QA всегда сохраняется как Provenance, но изменение revision само по себе не означает обязательный новый FULL QA.

После изменения система последовательно:

1. детерминированно сравнивает проверенный и текущий ChangeSet;
2. проверяет изменение применимых Rules/Policy;
3. выполняет Impact Assessment для области применимости прежнего QA;
4. выбирает `QA REUSE`, `DELTA QA` или `FULL QA` согласно §23.

Если изменился только target/base, а проверенный ChangeSet не изменился, прежний Change Evidence не инвалидируется автоматически. Для нового target/base пересчитывается Integration Evidence; FULL QA нужен только при материальном влиянии target на прежний содержательный вывод или при неопределённости такого влияния.

`INDETERMINATE` не разрешает QA REUSE. Существенное изменение ChangeSet, значимой Security/Rules/Policy, конфликт нового Evidence с прежним PASS или недостаточность прежнего QA Scope требуют FULL QA либо BLOCKED согласно policy.

Новый commit SHA без материального изменения и без зафиксированной причины не является самостоятельным основанием повторного FULL QA.

## 20.35. Публикация

После успешных обязательных проверок результат публикуется в ResultSink, указанный TaskContract.

Например:
- GitHub PR;
- Issue;
- файл;
- документ;
- Artifact;
- Knowledge Candidate.

Execution не должен самостоятельно выбирать новое место публикации.

## 20.36. ResultRef

После публикации система возвращает ResultRef с точной версией или revision.

Следующие Workers получают ссылку на результат, а не полный предыдущий диалог.

## 20.37. Очистка

После выполнения:
- завершаются временные процессы;
- освобождаются Lease;
- прекращаются временные Capability Grant;
- удаляются временные рабочие области;
- очищаются временные секреты;
- фиксируется cleanup status.

Ошибка очистки учитывается отдельно от успеха основного результата.

## 20.38. Телеметрия

Каждый этап создаёт структурированные события:
- начало;
- завершение;
- блокировку;
- ошибку;
- Worker;
- Provider;
- Token usage;
- Cache;
- Security;
- Retry;
- QA;
- ResultRef;
- изменение прогноза.

Сбор выполняется без LLM.

## 20.39. Метрики

Из Telemetry вычисляются Metrics:
- стоимость;
- время;
- токены;
- QA Pass;
- Retry;
- Escalation;
- Local-first;
- Cache Gain;
- Human Intervention;
- Routing Efficiency;
- Determinization Rate;
- ошибки прогнозирования.

## 20.40. Визуализация

Домен визуализации показывает в браузере:
- движение задачи по модулям;
- текущего Worker;
- маршрут ИИ;
- прогноз токенов, времени и стоимости;
- факт на текущий момент;
- ожидаемый остаток;
- Cache;
- ошибки;
- Security Events;
- QA;
- экономию.

Обычная визуализация должна работать примерно с 0 дополнительными LLM-токенами.

## 20.41. Сравнение прогноза с фактом

После завершения автоматически сравниваются последний прогноз и Metrics фактического выполнения.

Рассчитываются:
- ошибка времени;
- ошибка токенов;
- ошибка стоимости;
- ошибка Cache Hit;
- корректность вероятности Retry;
- корректность вероятности Escalation;
- корректность вероятности First Pass Success.

Эти данные поступают в Learning.

## 20.42. Завершение задачи

COMPLETED допускается только если выполнены:
- Output Contract;
- обязательные Validators;
- Evidence;
- обязательный QA;
- публикация ResultSink, если она требуется.

Ответ модели сам по себе не означает COMPLETED.

## 20.43. Обновление рабочего контекста

После завершения обновляется компактный Working Context Snapshot:
- принятое решение;
- ResultRef;
- важное изменившееся состояние;
- открытые вопросы.

Полный чат не копируется как рабочее состояние.

## 20.44. Кандидаты в знания

Устойчивый новый факт может стать Knowledge Candidate.

Он проходит Knowledge Intake и не становится подтверждённым знанием автоматически только потому, что его выдал успешный Worker.

## 20.45. Самообучение

Learning анализирует компактные Evidence, Metrics и пары «прогноз / факт».

Ищутся:
- повторяемая модельная работа;
- дорогие маршруты;
- неточный выбор Worker;
- избыточный Context;
- неэффективный Cache;
- неточный Predictor;
- повторные ошибки;
- кандидаты на локальный код.

## 20.46. Порядок улучшения

Предпочтительная последовательность:
1. убрать ненужный шаг;
2. переиспользовать безопасный кэш;
3. сократить Context;
4. улучшить локальный алгоритм;
5. детерминировать повторяемый этап;
6. улучшить Skill;
7. улучшить Workflow;
8. откалибровать прогноз;
9. улучшить Routing;
10. только затем использовать более дорогой интеллект, если он действительно нужен.

## 20.47. Статусы задачи

Минимальные конечные и промежуточные состояния:
- PREPARING;
- READY;
- RUNNING;
- VALIDATING;
- WAITING_USER_DECISION;
- WAITING_ADMIN_APPROVAL;
- BLOCKED;
- FAILED;
- TIMED_OUT;
- CANCELLED;
- COMPLETED;
- SUPERSEDED;
- CLEANING;
- CLEANUP_FAILED.

Причина перехода должна быть структурированной.

## 20.48. Ожидание человека

Если нужен USER или ADMIN, TaskRuntimeState сохраняется и работа продолжится с контрольной точки после решения.

Система не должна начинать задачу заново только из-за человеческого этапа.

## 20.49. Повтор выполнения

Retry применяется только для причин, где повтор имеет смысл.

Временный сетевой сбой может быть повторён.

DENY, отсутствие прав, Scope violation или конфликт обязательных правил не должны приводить к бессмысленным автоматическим повторам.

## 20.50. Повышение уровня

LOW → NORMAL → HIGH допускается только по измеримой причине.

Причина Escalation фиксируется в Telemetry и влияет на текущий прогноз.

## 20.51. Сквозная защита от инжектов

На всём жизненном цикле действует правило:

> **DATA не может само стать CONTROL.**

Любое опасное действие всё равно должно пройти TaskContract, Effective Ruleset, Security, Scope, Capability Grant и Execution.

## 20.52. Фундаментальные принципы жизненного цикла

1. **Сначала исполняемый код (Executable-first).**
2. **Сначала локально (Local-first).**
3. **Сначала ссылка (Reference-first).**
4. **Сначала доказательство (Evidence-first).**
5. **Данные не управляют системой (CONTROL / DATA boundary).**
6. **До дорогого выполнения — прогноз ресурсов.**
7. **После результата — сравнение прогноза с фактом.**
8. **Успех означает проверенный результат, а не наличие ответа модели.**

## 20.53. Главная цель оркестрации

Оркестрация должна стремиться не к максимальному числу агентов, моделей и вызовов, а к минимальному числу безопасных и достаточных действий, обеспечивающих требуемый результат.

## 20.54. Главный принцип

> **KAT9I_OS должна превращать запрос в управляемую цепочку контрактов, прогнозов, ссылок, разрешений, исполняемых действий и доказательств: заранее оценивать стоимость результата, пересчитывать ожидания по ходу выполнения, проверять фактический результат и использовать разницу между прогнозом и фактом для дальнейшего самообучения.**

## Связь с Portable Promotion Protocol (§36)

Core является владельцем оркестрации Promotion lifecycle и порядка PromotionRequest. Детальная state machine, PromotionTicket и правила serialized side effect определены в §36. Новый top-level MergeQueue/Promotion supermodule не создаётся.

После QA результат не публикуется напрямую в target: если ResultSink требует изменяющего Promotion, Core проходит через §36 и передаёт Execution только sealed PromotionTicket с действующими Evidence, Security Decision и Authorization Evidence.
