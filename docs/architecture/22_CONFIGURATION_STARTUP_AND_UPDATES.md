# 22. Конфигурация, запуск и обновление KAT9I_OS

## 22.1. Назначение

Этот раздел определяет, как KAT9I_OS устанавливается, впервые настраивается, обнаруживает доступные ресурсы, запускается, проверяет своё состояние и безопасно обновляется.

Первая целевая пользовательская среда: **Windows 11**.

Архитектура при этом не должна искусственно привязывать внутренние контракты KAT9I_OS только к Windows.

## 22.2. Основные требования

Запуск KAT9I_OS должен быть:

- воспроизводимым;
- максимально автоматическим;
- локальным по умолчанию;
- безопасным;
- диагностируемым;
- восстанавливаемым;
- независимым от наличия внешнего ИИ;
- способным продолжать работу после обновления;
- понятным через браузерную визуализацию.

## 22.3. Минимум ручной настройки

Пользователь не должен вручную создавать десятки конфигурационных файлов, прописывать внутренние идентификаторы, искать пути ко всем установленным программам, вручную регистрировать каждый локальный Tool (инструмент) или вводить одну и ту же настройку в нескольких местах.

> **Система сначала сама обнаруживает доступное окружение, затем спрашивает только то, что невозможно определить надёжно автоматически.**

## 22.4. Первый запуск

Запуск KAT9I_OS → проверка среды → обнаружение локальных возможностей → создание системного профиля → проверка безопасности → минимальное интервью Пользователя / Администратора → подключение разрешённых интеграций → создание начального рабочего пространства → проверка работоспособности → открытие браузерной панели.

## 22.5. Диагностика среды

До настройки система автоматически определяет:

- операционную систему;
- архитектуру CPU;
- объём памяти;
- доступный диск;
- GPU;
- локальную сеть;
- Python;
- PowerShell;
- Git;
- контейнерные среды;
- локальные модели;
- локальные серверы моделей;
- IDE;
- доступные CLI (командные интерфейсы);
- существующие репозитории;
- доступные Runtime (среды выполнения);
- существующих Workers (исполнителей).

Результат — `Environment Snapshot (снимок среды)`.

## 22.6. Обнаружение не означает разрешение

Если KAT9I_OS обнаружила GitHub CLI, это означает только наличие технической возможности. Любой Worker не получает автоматически право записи в GitHub.

Обнаружение → Capability Registry (реестр возможностей).
Разрешение → Security (безопасность) + Capability Grant (выданное разрешение).

## 22.7. Автоматическое обнаружение локального ИИ

KAT9I_OS должна уметь обнаруживать разрешённые локальные среды ИИ, например Ollama, llama.cpp, LM Studio, vLLM и другие локальные серверы.

Конкретные реализации не являются частью Core (ядра).

После обнаружения проверяются:

- доступность;
- модели;
- контекстное окно;
- возможности;
- скорость;
- GPU;
- пригодность для LOW / NORMAL / HIGH;
- ограничения.

## 22.8. Автоматическое обнаружение инструментов

Аналогично обнаруживаются Git, Python, PowerShell, Node.js, компиляторы, тестовые среды, PDF-инструменты, аудиоинструменты и специализированные доменные инструменты.

Инструмент регистрируется только после проверки его фактической работоспособности.

## 22.9. Не доверять только PATH

Наличие исполняемого файла в `PATH` не является достаточным доказательством.

Желательно проверять реальный запуск, версию, exit code (код завершения) и минимальную безопасную диагностическую команду.

Это создаёт Evidence (доказательство) доступности инструмента.

## 22.10. Системный реестр возможностей

После обнаружения формируется `Capability Registry (реестр возможностей)`.

Он отвечает на вопрос: **что эта конкретная установка KAT9I_OS технически умеет прямо сейчас?**

Например:

- локальный Git;
- Python;
- GitHub;
- локальный NORMAL ИИ;
- GPU;
- браузерная визуализация;
- PDF;
- Telegram;
- удалённые Workers.

## 22.11. Реестр возможностей динамический

Он обновляется при установке нового Tool, удалении программы, подключении Provider (провайдера ИИ), появлении Worker, обновлении локальной модели, изменении прав или потере внешнего сервиса.

Перезапуск всей KAT9I_OS для каждого такого изменения не требуется, если адаптер поддерживает безопасное обновление состояния.

## 22.12. Иерархия конфигурации

От общего к частному:

1. системные значения по умолчанию;
2. системная конфигурация KAT9I_OS;
3. конфигурация пользователя;
4. конфигурация рабочего пространства;
5. конфигурация домена;
6. конфигурация конкретной задачи.

Эта иерархия не применяется для обхода Rules (правил) и Security.

## 22.13. Настройка не равна правилу

Например `preferred_provider = local` может быть настройкой.

А требование `LOCAL_ONLY данные запрещено передавать наружу` является Rule / Security Policy (правилом / политикой безопасности).

Настройка не может отменить правило.

## 22.14. Канонический формат конфигурации

Системные настройки должны иметь схему, типы, версию, значения по умолчанию, проверки и описание.

Не допускается хаотичная работа с произвольными ключами, разбросанными по коду.

## 22.15. Не хранить секреты в обычной конфигурации

Обычные конфигурационные файлы не содержат API-ключи, токены, пароли или приватные ключи.

Используются `SecretRef (ссылка на секрет)` или защищённое локальное хранилище секретов.

## 22.16. Переменные окружения

Переменные окружения могут использоваться для передачи настроек среды выполнения и ссылок на секреты, но не должны быть единственным механизмом конфигурации KAT9I_OS.

Их значения требуют проверки, Scope (области действия) и защиты от попадания в Logs (журналы).

## 22.17. Минимальное интервью первого запуска

После автоматического обнаружения система спрашивает только действительно необходимые вещи, например:

- кто является владельцем;
- имеет ли владелец роль ADMIN;
- какие внешние интеграции разрешено подключить;
- какие каталоги считать рабочими;
- разрешён ли удалённый доступ;
- какие данные должны оставаться только локально;
- использовать ли Telegram;
- включать ли автоматические обновления.

## 22.18. Интервью должно быть адаптивным

Если система уже знает ответ, повторный вопрос не задаётся.

Если GitHub не установлен и не подключён, нет смысла заранее задавать множество вопросов о GitHub permissions (правах доступа).

Интервью строится по фактически обнаруженной среде.

## 22.19. Пользовательский и административный этапы

Пользовательские решения:

- язык;
- интерфейс;
- предпочтения;
- рабочие пространства;
- уведомления.

Административные решения:

- внешние права;
- секреты;
- удалённый доступ;
- доверенные Workers;
- критические интеграции;
- Security Policy.

## 22.20. Создание первого рабочего пространства

Пользователь может указать проект или локальный каталог.

KAT9I_OS выполняет:

- обнаружение репозитория;
- определение источников;
- регистрацию ResourceRef (ссылок на ресурсы);
- поиск проектных Rules;
- поиск Knowledge (знаний);
- определение возможных Domains (доменов);
- создание профиля рабочего пространства.

## 22.21. Импорт существующего контекста

При подключении существующего проекта система может предложить импортировать документацию, Rules, архитектурные решения, Knowledge, настройки, Research state (состояние исследований) и существующие Skills (навыки).

Импорт проходит классификацию. Старый файл не становится автоматически системным Rule.

## 22.22. Доноры существующей системы

При миграции KAT9I_OS может анализировать AG25, существующий `kat9i_skills`, KAT9I_IIIJIIOXA и другие старые проекты.

Элементы импортируются по новой архитектурной ответственности, а не путём копирования старой структуры.

## 22.23. Режимы запуска

### NORMAL — обычный режим

Полноценная работа.

### SAFE MODE — безопасный режим

Диагностика, чтение и восстановление.

### OFFLINE — автономный режим

Работа только с доступными локальными возможностями.

### MAINTENANCE — обслуживание

Обновление, миграции, резервное копирование и диагностика.

## 22.24. Порядок запуска модулей

Желательный порядок:

1. конфигурация;
2. хранилище секретов;
3. Security;
4. Rule Manager (менеджер правил);
5. хранилище состояния задач;
6. Resources;
7. Knowledge;
8. Cache (кэш);
9. Telemetry / Metrics (телеметрия / метрики);
10. Recovery Manager (менеджер восстановления);
11. Integrations (интеграции);
12. Inference (выбор вычислительного маршрута);
13. Coworker (координация исполнителей);
14. Execution (исполнение);
15. Domains (домены);
16. Planning & Forecasting (планирование и прогнозирование);
17. Visualization (визуализация);
18. внешние каналы, включая Telegram.

## 22.25. Восстановление раньше новых задач

Перед приёмом новых изменяющих задач Recovery Manager обязан проверить незавершённую работу от предыдущего запуска.

Сначала восстановление, затем новая работа.

## 22.26. Самодиагностика после запуска

После старта выполняется `Health Check (проверка состояния)`.

Минимально проверяется:

- Rules загружены;
- Security активна;
- Task Store доступен;
- Recovery завершён;
- локальные Runtime доступны;
- критические хранилища доступны;
- браузерная визуализация доступна;
- обязательные адаптеры работоспособны.

## 22.27. Состояния системы

Общий статус KAT9I_OS может быть:

- `HEALTHY` — работает штатно;
- `DEGRADED` — часть возможностей недоступна;
- `OFFLINE` — внешняя сеть недоступна;
- `RECOVERING` — выполняется восстановление;
- `MAINTENANCE` — обслуживание;
- `SAFE_MODE` — безопасный режим;
- `FAILED` — критическое состояние.

## 22.28. Частичный отказ не равен полному отказу

Например Telegram недоступен, но локальный код, Git, Context и Execution работают. Состояние системы в таком случае — `DEGRADED`, а не `FAILED`.

## 22.29. Браузерная панель запуска

После старта визуализация должна показывать:

- версию KAT9I_OS;
- общий статус;
- активный режим;
- Workers;
- Providers;
- Integrations;
- локальные модели;
- активные рабочие пространства;
- проблемы;
- Recovery state;
- прогноз доступных ресурсов.

## 22.30. Уведомление Telegram

Если Telegram подключён и разрешён, после значимого запуска можно уведомить о состоянии KAT9I_OS, количестве Workers, доступности локального ИИ, GitHub и активных задачах без передачи секретов.

## 22.31. Версия KAT9I_OS

Каждый запуск должен знать:

- версию приложения;
- revision (точную редакцию) кода;
- версию схем данных;
- версию системных контрактов;
- версию конфигурации.

## 22.32. Обновление — отдельный процесс

Обновление KAT9I_OS не должно быть простым копированием нового кода поверх старого. Используется управляемый Workflow (исполняемый процесс).

## 22.33. Процесс обновления

Новая версия обнаружена → проверка источника → сведения о выпуске → проверка совместимости → прогноз обновления → Backup (резервная копия) → DRAINING / MAINTENANCE → остановка безопасных процессов → обновление кода → миграция данных → Health Check → Regression tests (проверка регрессий) → успех или Rollback (откат).

## 22.34. Источник обновления

Обновление принимается только из канонического репозитория, доверенного Release (выпуска) или другого явно разрешённого источника.

Внешний Worker не может сам указать произвольный URL обновления и повысить его до доверенного источника.

## 22.35. Проверка обновления до применения

До установки определяется:

- что изменилось;
- затронутые модули;
- изменение схем;
- изменение Rules;
- изменение Security;
- изменение зависимостей;
- необходимость ADMIN Approval;
- ожидаемое время;
- риск.

## 22.36. Прогноз обновления

Модуль планирования должен оценивать:

- время обновления;
- время недоступности;
- размер загрузки;
- время миграций;
- вероятность проблем по истории;
- необходимость перезапуска;
- ожидаемое время Rollback.

Эти данные отображаются до начала обновления.

## 22.37. Критические обновления

Изменения Security, Rule Manager, TaskContract, схем состояния, системы прав и Recovery относятся к повышенному уровню риска и требуют усиленной проверки и при необходимости ADMIN Approval.

## 22.38. Обновление без потери задач

Перед обновлением активные задачи завершаются до безопасного Checkpoint (контрольной точки), либо приостанавливаются, либо сохраняют состояние для Resume (продолжения).

Обновление не должно уничтожать TaskRuntimeState.

## 22.39. Резервная копия перед обновлением

Перед значимым обновлением сохраняются:

- критическое состояние;
- конфигурация;
- Rules;
- Security state;
- Knowledge metadata;
- Task state;
- версия схем;
- текущая версия приложения.

Cache можно не резервировать полностью, если он восстанавливаем.

## 22.40. Миграция данных

Изменение схем выполняется через версионированные миграции.

Каждая миграция должна знать исходную и целевую версии, проверять предварительные условия, сохранять Evidence и завершаться безопасно.

## 22.41. Нельзя мигрировать критические данные через LLM

Перенос Task State, Rules, Security configuration и системных идентификаторов должен выполняться детерминированным кодом.

ИИ может помочь разработать миграцию, но не заменяет исполняемый механизм миграции.

## 22.42. Проверка после обновления

После установки запускаются:

- проверка конфигурации;
- проверка схем;
- Security tests;
- Rule tests;
- Recovery tests;
- минимальные Runtime smoke tests (короткие проверки запуска);
- проверка Integrations;
- проверка визуализации.

До успешного завершения система не объявляется `HEALTHY`.

## 22.43. Откат

Если новая версия не проходит обязательные проверки, выполняется Rollback.

Откат должен восстанавливать код, совместимую конфигурацию, критическое состояние и версию схем.

## 22.44. Не каждый сбой требует полного отката

Если новая версия работает, но необязательная интеграция недоступна, состояние может быть `DEGRADED`.

Полный Rollback нужен только согласно политике критичности.

## 22.45. Автоматические обновления

Режимы:

### MANUAL

Только по команде ADMIN.

### NOTIFY

Система обнаруживает новую версию и сообщает.

### SAFE_AUTO

Низкорисковые обновления устанавливаются автоматически после проверок.

### CONTROLLED_AUTO

Автоматическое обновление с Checkpoint, Backup и Rollback.

Критические системные изменения могут требовать ADMIN независимо от режима.

## 22.46. Канареечное обновление

При нескольких Workers или узлах новую версию полезно сначала установить на один узел.

`Canary Update (пробное обновление)` наблюдается по ошибкам, Metrics, совместимости, Routing и восстановлению. Только после подтверждения обновляются остальные.

## 22.47. Совместимость распределённых узлов

Удалённые KAT9I и Workers могут временно иметь разные версии.

Протокол обмена обязан иметь версию. Если версии несовместимы, взаимодействие блокируется или используется совместимый режим.

Нельзя надеяться, что модели «как-нибудь договорятся».

## 22.48. Обновление Workers

Worker имеет собственные Runtime, version (версию) и capabilities (возможности).

Coworker должен знать совместимость Worker с текущей системой.

Устаревший Worker может получить статус `DEGRADED` или `INCOMPATIBLE`.

## 22.49. Самообучение конфигурации

Learning (самообучение) может оптимизировать безопасные параметры:

- Timeout;
- Lease;
- Heartbeat;
- Cache TTL;
- Retry;
- Backoff;
- размер Context;
- выбор локального Runtime;
- прогнозирование;
- частоту Health Check;
- Cache warming.

Только внутри разрешённых границ.

## 22.50. Самообучаемые параметры должны иметь границы

Для каждого автоматически адаптируемого параметра желательно определить:

- минимальное значение;
- максимальное значение;
- начальное значение;
- область применения;
- число наблюдений;
- доверительный уровень;
- скорость изменения;
- способ отката.

Например Timeout Worker A для GitHub-задач может обучаться отдельно от Timeout локального PDF Worker.

## 22.51. Не делать глобальный вывод по локальному случаю

Если конкретный удалённый Worker регулярно опаздывает на одну секунду, Learning сначала адаптирует сочетание Worker + Runtime + Task Type, а не увеличивает все таймауты KAT9I_OS.

Это соответствует минимальному Scope обучения.

## 22.52. Конфигурация и прогнозирование

Перед изменением важного параметра Learning может моделировать последствия, например увеличение Timeout с 30 до 40 секунд.

Используется история:

- числа ложных таймаутов;
- реального времени обнаружения отказа;
- стоимости ожидания;
- числа повторных назначений.

Изменение выбирается по ожидаемой общей выгоде.

## 22.53. История конфигурации

Значимые изменения настроек должны иметь:

- прежнее значение;
- новое значение;
- источник изменения;
- USER / ADMIN / Learning;
- Scope;
- время;
- причину;
- возможность отката.

## 22.54. Визуализация изменений конфигурации

Интерфейс может показывать пример:

> Timeout Worker A: было 30 сек, стало 34 сек; причина — 17% ложных таймаутов; наблюдений — 86; ожидаемый эффект — снижение лишних переназначений.

Это делает самообучение прозрачным.

## 22.55. Сброс адаптивного параметра

USER или ADMIN с соответствующими полномочиями должен иметь возможность вернуть значение по умолчанию, отключить самообучение конкретного параметра, зафиксировать значение или ограничить диапазон.

## 22.56. Экспорт диагностики

При проблеме система должна уметь сформировать диагностический пакет.

Он может содержать версии, статусы модулей, ошибки, обезличенные Metrics, Evidence, конфигурационные схемы, состояние Workers и список интеграций.

Секреты и приватный Context автоматически не включаются.

## 22.57. Команда проверки системы

Нужен единый механизм **«проверить KAT9I_OS»**.

Он запускает локальную диагностику:

- конфигурация;
- Rules;
- Security;
- Storage;
- Runtime;
- Workers;
- Integrations;
- Cache;
- Recovery;
- Forecasting;
- Visualization.

Результат должен быть понятен человеку.

## 22.58. Конфигурация как код — только частично

Версионируемые схемы и публичные настройки можно хранить рядом с кодом.

Приватное пользовательское состояние и секреты не должны попадать в публичный Git.

## 22.59. Что модуль запуска и конфигурации не должен делать

Он не должен:

- обходить Rules;
- выдавать себе административные права;
- хранить секреты открытым текстом;
- считать обнаруженный Tool автоматически разрешённым;
- изменять настройки без Provenance;
- выполнять обновление без Backup критического состояния;
- считать обновление успешным без Health Check;
- стирать незавершённые задачи;
- глобально менять адаптивный параметр по одному наблюдению.

## 22.60. Основные принципы

1. **Первый запуск максимально автоматический.**
2. **Сначала обнаружение среды, затем минимальное интервью.**
3. **Обнаруженная возможность не означает выданное разрешение.**
4. **Конфигурация, Rules и Security — разные сущности.**
5. **Секреты не хранятся в обычной конфигурации.**
6. **Recovery выполняется до приёма новой изменяющей работы.**
7. **Частичный отказ переводит систему в DEGRADED, а не обязательно в FAILED.**
8. **Обновление является отдельным управляемым Workflow.**
9. **До обновления создаётся Backup и оценивается риск.**
10. **Миграции критического состояния выполняются детерминированным кодом.**
11. **После обновления обязательны проверки работоспособности.**
12. **Неудачное обновление должно поддерживать Rollback.**
13. **Несколько узлов могут обновляться постепенно.**
14. **Самообучение может адаптировать операционные параметры только в безопасных границах и минимальном Scope.**
15. **Любое значимое изменение конфигурации имеет происхождение и возможность отката.**

## 22.61. Главный принцип

> **KAT9I_OS должна устанавливаться и запускаться как управляемая локальная система: сама обнаруживать доступные возможности, спрашивать человека только о действительно необходимых решениях, сохранять критическое состояние перед изменениями и обновляться так, чтобы любой неудачный шаг можно было диагностировать, восстановить или откатить.**
