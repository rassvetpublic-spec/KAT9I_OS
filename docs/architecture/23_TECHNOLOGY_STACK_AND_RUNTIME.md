# 23. Технологический стек и границы среды выполнения KAT9I_OS

> **Статус:** принято.
>
> Этот раздел фиксирует базовый технологический стек KAT9I_OS. Он определяет ответственность языков и сред выполнения, но не утверждает конкретные библиотеки, версии и детали упаковки приложения.

## 23.1. Назначение

KAT9I_OS строится как гибридная система из трёх основных технологических слоёв:

1. **Electron + TypeScript** — настольная оболочка и пользовательский интерфейс.
2. **Rust** — системное ядро KAT9I_OS и основной локальный Runtime (среда выполнения).
3. **Python** — специализированный AI/ML Worker-слой для задач, где важна экосистема искусственного интеллекта, машинного обучения и быстрой экспериментальной разработки.

Главный принцип:

> **Интерфейс показывает и инициирует действия; Rust управляет системой и её безопасным состоянием; Python выполняет специализированную интеллектуальную и вычислительную работу через ограниченные контракты.**

## 23.2. Общая схема

Пользователь взаимодействует с настольным приложением Electron / TypeScript.

Настольная оболочка обращается к Rust Core (ядру на Rust) через явный IPC/API-контракт (контракт межпроцессного или программного взаимодействия).

Rust Core управляет жизненным циклом задач, состоянием системы, правами, исполнителями и системными ресурсами.

Когда задаче требуется Python-экосистема, Rust Core запускает или вызывает Python Worker (исполнителя на Python), передавая ему только необходимый TaskContract (контракт задачи), ContextRefs (ссылки на контекст), Capability Grant (ограниченные разрешения) и Output Contract (контракт результата).

Python Worker возвращает результат и Evidence (доказательства выполнения) через определённый контракт. Он не получает право самостоятельно расширять Scope (область разрешённых действий) или менять системные правила.

## 23.3. Electron + TypeScript — настольная оболочка

Electron используется как базовая среда настольного приложения KAT9I_OS.

TypeScript является основным языком пользовательского интерфейса и логики оболочки.

Этот слой отвечает за:

- главное окно KAT9I_OS;
- представление задач и их состояний;
- визуализацию TaskGraph (графа задач);
- отображение Worker (исполнителей), ресурсов, Evidence и QA;
- пользовательские настройки;
- управление подключениями через разрешённые системные API;
- передачу команд в Rust Core;
- получение событий и состояния от Rust Core.

Electron / TypeScript не является владельцем канонического состояния выполнения задачи.

Закрытие окна, перезагрузка интерфейса или сбой UI не должны сами по себе уничтожать состояние активной задачи.

Критические проверки безопасности и полномочий не должны существовать только в UI.

## 23.4. Rust — системное ядро

Rust является основным языком системного ядра KAT9I_OS.

Rust Core отвечает за критичную управляющую логику и локальную среду выполнения, включая:

- жизненный цикл TaskContract;
- TaskGraph и переходы состояний;
- очередь и планирование выполнения;
- запуск и контроль процессов;
- Worker Supervisor (надзор за исполнителями);
- Claim и Lease (захват задачи и временное право на неё);
- IPC и локальные системные протоколы;
- работу с файловой системой в пределах разрешений;
- контроль Scope;
- Capability Grant;
- sandbox / изоляцию там, где она требуется;
- управление тайм-аутами;
- контроль ресурсов;
- восстановление после сбоев;
- локальный daemon/service (фоновую системную службу), если такой режим потребуется;
- сбор системного Evidence;
- безопасную передачу заданий специализированным Worker.

Rust Core является границей, через которую должны проходить критические операции с состоянием и системными ресурсами.

Отдельный `CacheEngine` также реализуется на Rust, но имеет собственный процесс и жизненный цикл. Он является runtime-ускорителем, а не частью Electron и не владельцем канонического состояния Core. Взаимодействие с ним идёт через версионированный локальный контракт и допускает fail-open работу без кэша.

Высокоуровневый Worker не должен обходить эту границу только потому, что ему технически доступна файловая система, shell или внешний API.

## 23.5. Python — AI/ML Worker-слой

Python используется не как системное ядро KAT9I_OS, а как специализированная среда выполнения для задач, где его экосистема даёт практическое преимущество.

Типовые области:

- локальные и удалённые AI-интеграции;
- машинное обучение;
- embeddings (векторные представления);
- retrieval / RAG (поиск и дополнение контекста);
- обработка текста, аудио и других данных;
- исследовательские модули;
- прототипирование новых алгоритмов;
- специализированные Domain Worker;
- интеграция с существующими Python-проектами и библиотеками.

Python Worker должен работать по тому же контрактному принципу, что и любой другой исполнитель KAT9I_OS.

Python не получает особых системных полномочий только потому, что является частью официального стека.

## 23.6. Граница между Rust и Python

Rust и Python не должны образовывать неявно связанную систему, где один слой зависит от внутреннего устройства другого.

Взаимодействие строится через версионируемые контракты.

Минимально контракт должен позволять передать:

- идентификатор задачи;
- тип операции;
- Scope;
- ContextRefs;
- RulesRef;
- Capability Grant;
- входные параметры;
- бюджет и ограничения;
- Output Contract;
- требования к Evidence;
- тайм-аут и условия отмены.

Ответ Worker должен позволять получить:

- статус;
- ResultRef;
- Evidence;
- метрики выполнения;
- диагностическую информацию;
- явно классифицированную ошибку при неуспехе.

Замена Python Worker на Worker, написанный на другом языке, не должна требовать переписывания архитектуры Core, если новый исполнитель соблюдает тот же контракт.

## 23.7. Граница между Electron и Rust

Desktop UI не должен напрямую управлять системными Worker, shell-процессами, Lease, Capability Grant или каноническими переходами состояния.

Пользовательское действие сначала превращается в запрос к Core.

Core:

- проверяет допустимость операции;
- применяет правила;
- изменяет каноническое состояние;
- выполняет или планирует действие;
- возвращает состояние или событие интерфейсу.

Это позволяет отделить пользовательский интерфейс от системной логики и в дальнейшем иметь дополнительные интерфейсы без дублирования Core.

## 23.8. Что является основным стеком

Для первой полноценной реализации KAT9I_OS принимается следующий базовый набор:

| Слой | Основная технология | Роль |
|---|---|---|
| Desktop / UI | Electron + TypeScript | пользовательский интерфейс и настольная оболочка |
| Core / Runtime | Rust | системное ядро, оркестрация, безопасность и управление исполнением |
| AI/ML Workers | Python | специализированные интеллектуальные и вычислительные задачи |
| External Intelligence | локальные или удалённые модели через разрешённые интеграции | инференс и внешние интеллектуальные сервисы |

## 23.9. Что этим решением НЕ утверждается

На данный момент этим разделом не фиксируются:

- конкретный UI-фреймворк внутри Electron;
- конкретная IPC-библиотека или формат транспорта;
- конкретная база данных;
- конкретный Python web/API framework;
- конкретный async-runtime и набор Rust-библиотек;
- package manager для каждого слоя;
- точные версии Electron, TypeScript, Rust и Python;
- формат установщика;
- механизм автообновления;
- конкретный поставщик AI-моделей;
- конкретный формат плагинов;
- окончательная схема процессов одного компьютера.

Эти решения принимаются отдельно, когда для них появятся достаточные требования и критерии выбора.

## 23.10. Правило развития

Новый язык программирования не добавляется в основной стек только ради удобства отдельной реализации.

Для добавления ещё одного основного языка должно быть показано, что существующие Rust, Python и TypeScript не решают задачу разумно либо новый язык даёт существенное преимущество по безопасности, переносимости, производительности или интеграции.

Domain-модуль может использовать внешний инструмент на другом языке как зависимость или Worker, если он изолирован контрактом и не размывает границы Core.

## 23.11. Связь с существующей архитектурой

Этот раздел уточняет технологическое воплощение уже принятой модульной архитектуры:

- `Core`, `Execution`, системные части `Coworker`, `Security` и Recovery ориентируются на Rust;
- `Domains` могут использовать Python Worker там, где это оправдано предметной задачей;
- `Visualization` и настольный пользовательский интерфейс ориентируются на Electron + TypeScript;
- `Integrations` могут иметь адаптеры в соответствующем слое, но полномочия и каноническое состояние остаются под контролем Core;
- контракты должны оставаться независимыми от конкретного языка реализации настолько, насколько это практически возможно.

## 23.12. Итог

Принята базовая технологическая архитектура KAT9I_OS:

> **Electron + TypeScript — интерфейс. Rust — системное ядро. Python — AI/ML Worker-слой.**

Это является исходной точкой для реализации, а не требованием переписать на Rust или Python каждый внешний инструмент, библиотеку или интеграцию системы.
