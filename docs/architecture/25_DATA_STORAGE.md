# 25. Хранилища данных и физическое размещение состояния KAT9I_OS

## 25.1. Назначение

Этот раздел определяет:

> **что именно KAT9I_OS хранит, где это физически размещается, что является источником истины, что можно пересоздать, что обязательно резервируется и какие данные нельзя смешивать между собой.**

Главный принцип:

> **не существует одного огромного хранилища «памяти KAT9I_OS». Разные классы данных должны храниться в подходящих для них местах и иметь чётко определённого владельца.**

## 25.2. Основные классы данных

KAT9I_OS должна различать как минимум:

1. системное состояние;
2. состояние задач;
3. правила;
4. настройки;
5. знания;
6. ресурсы;
7. кэш;
8. телеметрию;
9. метрики;
10. состояние самообучения;
11. секреты;
12. рабочие файлы;
13. доказательства выполнения;
14. диагностические журналы;
15. пользовательские данные.

Эти сущности не должны превращаться в один неструктурированный каталог.

## 25.3. Единый источник истины

Для каждого типа данных должен быть определён `SSoT — Single Source of Truth — единый источник истины`.

Это место, которому система доверяет как каноническому состоянию данного объекта.

Например:

- GitHub Issue → состояние работы в GitHub;
- Git commit → версия кода;
- Rule Manager → действующее правило;
- Knowledge Base → подтверждённое знание;
- Task State Store → внутреннее состояние задачи KAT9I_OS;
- Secret Store → секрет.

Другие копии считаются представлением, индексом, кэшем, локальным зеркалом или материализованной копией.

## 25.4. Один объект — один канонический владелец

Нельзя одновременно объявлять GitHub Issue и локальный JSON каноническим состоянием одной и той же GitHub-задачи.

Допустимо:

**GitHub Issue — источник истины** → **локальный индекс — ускоритель доступа**.

Локальный индекс не получает равного статуса.

## 25.5. Внутреннее и внешнее каноническое состояние

KAT9I_OS должна поддерживать два вида источников истины.

### Внутренние

Созданные самой KAT9I_OS, например TaskRuntimeState, Worker Registry, Learning State, локальные настройки, KnowledgeRecord.

### Внешние

Принадлежащие другим системам: GitHub, Google Drive, Obsidian, Telegram, файловая система, внешняя база данных.

KAT9I_OS не должна без необходимости копировать внешнее каноническое состояние внутрь себя.

## 25.6. Предпочтительная физическая база первой версии

Для первой версии предлагается:

> **SQLite как основное локальное структурированное хранилище состояния KAT9I_OS.**

Причины: работает без отдельного сервера, локальна, транзакционна, надёжна, проста для резервного копирования, поддерживает индексы, подходит для Windows 11 и легко переносится.

SQLite не становится архитектурным контрактом навсегда. Модули должны работать через внутренние интерфейсы хранения.

## 25.7. Что хранить в SQLite

В SQLite разумно хранить:

- TaskRuntimeState;
- TaskGraph metadata;
- Claim;
- Lease;
- Worker Registry;
- Capability Registry;
- Resource Registry metadata;
- Knowledge metadata;
- Preferences;
- Settings;
- Metrics;
- Learning State;
- Forecast history;
- Cache Registry;
- Checkpoints;
- Event Journal metadata;
- Security Events metadata;
- Integration Registry;
- Workspace Registry.

## 25.8. Что не надо хранить прямо в SQLite

Не следует помещать туда без необходимости большие бинарные файлы, Git-репозитории, видео, аудио, большие PDF, модели, огромные логи, полные копии внешних документов и секреты открытым текстом.

Для них используются ссылки и специализированные хранилища.

## 25.9. ResourceRef вместо копирования файла

Если документ уже находится на GitHub, в Google Drive, Obsidian, локально или у другого Worker, KAT9I_OS хранит `ResourceRef — ссылку на ресурс` и его метаданные: URI, revision, hash, Trust, Scope, Sensitivity, Resolver.

## 25.10. Большие локальные файлы

Большие локальные артефакты размещаются в управляемом файловом хранилище. Логически могут использоваться каталоги `data/resources/`, `data/artifacts/`, `data/evidence/`, `data/cache/`, `data/logs/`, но конкретные пути задаются конфигурацией.

## 25.11. Рабочая директория KAT9I_OS

Нужна единая корневая директория локального состояния, условно `KAT9I_HOME`.

Она может содержать database, config, cache, logs, artifacts, evidence, workspaces, backups, temp.

Пользователь не должен вручную управлять внутренней структурой.

## 25.12. Код и состояние должны быть разделены

Исходный код KAT9I_OS не должен храниться вперемешку с пользовательским состоянием.

**Репозиторий KAT9I_OS ≠ локальное пользовательское состояние KAT9I_OS.**

Это позволяет обновлять код, откатывать версию и переустанавливать систему без уничтожения пользовательских данных.

## 25.13. Рабочие пространства проектов

Каждый Workspace может иметь свои ResourceRef, локальные checkout, рабочие ветки, временные файлы, индексы, настройки, привязки Knowledge и Cache. Системные данные KAT9I_OS не должны физически смешиваться с файлами проекта без необходимости.

## 25.14. Git-репозитории

Git-репозитории остаются обычными Git-репозиториями. KAT9I_OS не строит поверх них собственную систему версий, а использует commit SHA, branches, tags, worktrees, diff и Git metadata. Git остаётся источником истины для версии кода.

## 25.15. Git Worktree для изолированной работы

Для параллельных задач предпочтительно использовать `Git Worktree — отдельную рабочую копию ветки без полного повторного клонирования репозитория`. Это снижает расход диска, время подготовки и вероятность конфликтов. Каждый изменяющий Worker получает собственную рабочую область.

## 25.16. База знаний

Knowledge Base остаётся логически отдельной от Task State. Она хранит проверенные факты, решения, связи, наблюдения, процедуры и Provenance. Задача может исчезнуть из активной очереди, но подтверждённое знание может остаться.

## 25.17. Знания и документы — не одно и то же

Большой документ не должен полностью копироваться в Knowledge Base.

Правильная схема:

**документ → ResourceRef → извлечённые утверждения → KnowledgeRecord.**

KB хранит знания, а не дублирует библиотеку файлов.

## 25.18. Obsidian

Obsidian можно использовать как пользовательское хранилище заметок, внешний Knowledge Source, внешний Knowledge Store и удобный человеческий интерфейс к Markdown-знаниям. Он не является обязательным компонентом Core. Если Obsidian недоступен, KAT9I_OS продолжает работать.

## 25.19. Локальная База знаний и Obsidian

Возможна схема: структурированный Knowledge Store KAT9I_OS ↔ Obsidian-представление. Нельзя допустить двух независимых версий одной записи без правила синхронизации.

## 25.20. Секреты

Секреты хранятся отдельно: API-ключи, токены, пароли, приватные ключи. Используется `Secret Store — защищённое хранилище секретов`. Остальные модули получают `SecretRef`, а не сам секрет, пока он реально не нужен Runtime.

## 25.21. Windows Credential Manager

Для Windows 11 одним из допустимых первых механизмов может быть Диспетчер учётных данных Windows или другое защищённое локальное хранилище. Архитектура не должна быть жёстко привязана к одному варианту.

## 25.22. Секрет не должен попадать в обычные данные

Запрещено автоматически сохранять секрет в TaskContract, Logs, Metrics, Knowledge, Cache, ResultRef, Git, HTML или Telegram. Если секрет случайно обнаружен, Security создаёт событие и ограничивает дальнейшее распространение.

## 25.23. Кэш (CacheEngine)

`CacheEngine` физически и логически отделён от канонического состояния (SSoT) и хранилища `Storage`:
- **Не является источником истины (SSoT)**: в кэше строго запрещено хранить канонические данные (TaskRuntimeState, RulesRef, Secrets, Evidence, Git commits). Полное удаление директории кэша или сброс RAM безопасны для целостности системы (система может работать медленнее, но корректность сохраняется);
- **RAM-first размещение**: в штатном режиме объекты кеша размещаются исключительно в оперативной памяти процесса Rust CacheEngine;
- **Immutable spill segments на SSD**: сброс на диск происходит только при достижении порогов memory pressure пакетами в неизменяемые сегменты с контрольными суммами;
- **Содержимое кэша**: результаты поисков, materialized context, синтаксические AST-индексы, эмбеддинги, промежуточные артефакты и детерминированные результаты шагов. При повреждении или протухании (stale) данные лениво пересоздаются из первоисточника.

Подробная архитектура зафиксирована в разделе [docs/architecture/34_CACHE_ENGINE.md](34_CACHE_ENGINE.md).

## 25.24. Индексы

Поисковые индексы являются производными данными: полнотекстовый индекс, векторный индекс, индекс символов кода, dependency index. При повреждении они пересоздаются из источника.

## 25.25. Векторные представления

`Embeddings — числовые векторные представления содержания` могут храниться локально для поиска. Они не являются Knowledge, не являются каноническим содержанием, связаны с точной версией источника и пересчитываются при значимом изменении данных.

## 25.26. Телеметрия

Сырые события Telemetry желательно хранить отдельно от основной оперативной базы либо в логически отдельной таблице/хранилище, потому что событий может быть много, их жизненный цикл отличается и старые события можно агрегировать или архивировать.

## 25.27. Метрики

Metrics хранят компактные вычисленные значения: токены, стоимость, время, Retry, Cache Hit, QA Pass, Forecast Error. Метрики должны быть удобны для анализа без чтения миллионов сырых событий.

## 25.28. Политика хранения

Для каждого класса данных определяется `Retention Policy — политика хранения`, то есть как долго данные сохраняются. Нет единого срока для всего.

## 25.29. Архивация

Старые данные могут переходить из `HOT — активно используемые` в `WARM — редко используемые`, затем в `ARCHIVE — архив`. Особенно это полезно для Telemetry, Evidence, старых задач и Metrics history.

## 25.30. Очистка данных

Очистка должна быть управляемой. Команда «очистить кэш» не должна удалить Knowledge, Rules, Task history, Evidence или настройки. Каждый вид очистки имеет собственный Scope.

## 25.31. Удаление пользовательских данных

Нужно отличать очистку Cache, удаление Workspace, удаление Knowledge, удаление пользователя и полное уничтожение локального состояния. Каждая операция имеет отдельную политику подтверждения.

## 25.32. Provenance — происхождение

Для важных данных фиксируется происхождение: откуда пришли, кто создал, какой Worker, какая задача, какая revision, какой источник и когда. Это особенно обязательно для Knowledge, Rules, Evidence, Learning Proposal и Metrics.

## 25.33. Версионирование записей

Критические записи не следует безвозвратно перезаписывать. Для Rules, Settings, Knowledge, Learning state и Security configuration может храниться история старой и новой версии, причины, источника и времени.

## 25.34. Транзакции

Операции, меняющие несколько связанных записей, должны быть атомарными там, где возможно. Например при назначении нового Worker согласованно обновляются Claim, Lease и TaskRuntimeState.

## 25.35. Блокировки

Для критичных записей нужны механизмы защиты от одновременного изменения. Следует избегать длинных глобальных блокировок всей базы и использовать минимальную область блокировки.

## 25.36. Идентификаторы

Внутренние объекты имеют стабильные ID: task_id, worker_id, resource_id, knowledge_id, operation_id, lease_id, event_id. Отображаемое имя может меняться, ID — нет.

## 25.37. Ссылочная целостность

Если TaskResult ссылается на ResourceRef, система должна понимать, существует ли ссылка, актуальна ли она, не удалён ли ресурс и какая revision использовалась. Мёртвые ссылки в критическом состоянии не допускаются без явного статуса.

## 25.38. Удаление ресурса

Если внешний ресурс удалён, его ResourceRef может перейти в `UNAVAILABLE — недоступен` или `DELETED — удалён`, чтобы сохранить историю Provenance.

## 25.39. Снимок состояния

Перед обновлением, миграцией или крупной операцией восстановления создаётся `Snapshot — снимок состояния` критических данных. Он не обязан включать Cache, временные файлы и пересоздаваемые индексы.

## 25.40. Резервное копирование

Backup должен включать основную структурированную базу, Rules, Security configuration, Personal settings, Knowledge metadata, Task State, Learning state, важный Evidence и конфигурацию хранилищ.

## 25.41. Резервное копирование секретов

Секреты требуют отдельной политики. Нельзя просто складывать Secret Store в обычный ZIP рядом с backup. Нужен защищённый механизм либо повторная авторизация после восстановления.

## 25.42. Проверяемое восстановление

Backup считается рабочим только если система умеет реально восстановиться из него. Периодические Recovery Tests должны это подтверждать.

## 25.43. Миграции схемы

Структура SQLite и других хранилищ меняется через `Schema Version — версию схемы` и последовательные `Migrations — миграции`. Нельзя полагаться на то, что модель сама догадается о несовместимом поле.

## 25.44. Обратная совместимость

Во время обновления несколько Workers могут временно работать с разными версиями. Для общих контрактов нужна совместимость либо явная блокировка несовместимых клиентов.

## 25.45. Локальный режим по умолчанию

Основное пользовательское состояние первой версии хранится локально. Внешние облачные хранилища подключаются как Integrations и не являются обязательной частью Core.

## 25.46. Несколько пользователей

Даже если первая версия ориентирована на одного владельца, записи должны поддерживать user_id, owner, Scope и allowed consumers. Это позволяет позже добавить нескольких пользователей без полного изменения модели хранения.

## 25.47. Изоляция пользователей

Личные Preferences, Personal Knowledge, Settings, History и приватные Resources одного пользователя не должны автоматически попадать в Context другого.

## 25.48. Удалённые Workers

Удалённый Worker не получает прямой доступ ко всей локальной базе. Ему выдаются TaskContract, минимальный Context, ResourceRef и временные Capability Grant. Worker работает через контракты, а не через прямой доступ ко всему состоянию KAT9I_OS.

## 25.49. Синхронизация между KAT9I_OS

Если появляется несколько узлов KAT9I_OS, не надо сразу синхронизировать всю базу. Передаются только необходимые сущности: TaskContract, Worker status, ResultRef, ResourceRef, Lease и разрешённые KnowledgeRef.

## 25.50. Конфликты синхронизации

При конфликте система не должна автоматически выбирать «последняя запись по времени побеждает», особенно для Rules, Security, Knowledge и Task State. Нужна семантика конкретного типа данных.

## 25.51. Хранилище событий

Для важных переходов состояния желательно использовать append-only принцип: старое событие не переписывается, новое добавляется. Это подходит для Task transitions, Security Events, Lease changes, Recovery и Learning changes.

## 25.52. Вычисленное текущее состояние

`Materialized State — вычисленное текущее состояние` может храниться отдельно для производительности. Event Journal плюс текущий TaskRuntimeState позволяют восстанавливать состояние при повреждении.

## 25.53. Логи

Logs нужны для диагностики, но не являются системой состояния. KAT9I_OS не должна восстанавливать критическое состояние чтением текстовых логов и угадыванием того, что произошло.

## 25.54. Структурированные логи

Диагностические журналы желательно хранить структурированно: timestamp, module, task_id, worker_id, level, event, correlation_id. Текстовое сообщение может прилагаться.

## 25.55. Correlation ID — идентификатор связи

Каждый сквозной запрос должен иметь идентификатор, связывающий Telemetry, Logs, Metrics, Tasks, Workers и Integration calls. Это позволяет проследить прохождение запроса и место сбоя.

## 25.56. Evidence — доказательства

Evidence хранится отдельно от обычных Logs. Оно должно быть компактным, структурированным, связанным с revision и неизменяемым либо версионированным. Примеры: SHA, test result, Scope Pass, operation_id, ResultRef.

## 25.57. Artifact — артефакт

Artifact — созданный файл или пакет результатов: PDF, архив, отчёт, изображение, сборка. Он может находиться локально, в GitHub, Drive или другом внешнем хранилище. KAT9I_OS хранит ResultRef.

## 25.58. Большие результаты между Workers

Большие результаты не передаются через модельные сообщения. Worker A сохраняет Artifact и возвращает ResultRef. Worker B получает ResultRef и разрешает ресурс напрямую.

## 25.59. Экономика хранения

Система учитывает стоимость диска, сети, облачного хранения, резервных копий, индексов и дублирования. Learning может оптимизировать Retention и Cache, но не удаляет обязательные Evidence или Security Events ради экономии.

## 25.60. Самообучение хранения

Learning может обнаруживать редко используемый Cache, слишком большой индекс, ненужное дублирование, чрезмерный срок Telemetry, неэффективную Materialization и часто повторно загружаемые ресурсы, а затем предлагать безопасную оптимизацию.

## 25.61. Прогнозирование хранилищ

Модуль планирования может оценивать объём новых данных, рост Cache, размер Artifact, объём Telemetry, размер Backup, время миграции и восстановления.

## 25.62. Визуализация хранения

В браузерном интерфейсе можно показывать размер основной базы, Cache, Logs, Evidence, Artifacts, Backups, состояние хранилищ, последние Backup, ошибки целостности и рост по времени.

## 25.63. Режим «Рентген KAT9I_OS»

В режиме диагностики должно быть видно, какой объект где физически хранится. Например: Task State — SQLite, исходник — GitHub, Context Cache — локальный диск, Artifact — Drive, Evidence — локальный Evidence Store, ResultRef — GitHub PR.

## 25.64. Проверка целостности

Нужно периодически проверять SQLite, ResourceRef, Cache metadata, Evidence, Backup, индексы и версию схемы. Проверки по возможности выполняются локально обычным кодом.

## 25.65. Повреждение основного хранилища

Если основная база не проходит проверку, система останавливает опасные изменения, переходит в SAFE MODE, сохраняет диагностику, пытается восстановиться из Backup/Event Journal, проверяет восстановление и только затем возвращается в NORMAL.

## 25.66. Полная переносимость

Пользователь должен иметь возможность перенести KAT9I_OS на другой компьютер. Экспорт разделяет переносимые данные, пересоздаваемые данные и особые данные вроде секретов и внешних credentials.

## 25.67. Экспорт не равен публикации

Создание переносимого Backup не означает, что его безопасно загружать в GitHub. По умолчанию такой пакет приватный.

## 25.68. Публичный репозиторий KAT9I_OS

В публичном GitHub находятся код, схемы, документация, тесты, публичные примеры, шаблоны, миграции и политики. Не находятся пользовательская база, реальные Task history, приватный Knowledge, токены, секреты, приватные документы и чувствительные Metrics.

## 25.69. Один источник истины для документации

Markdown-документы в репозитории являются каноническим текстом. HTML генерируется из Markdown и не хранит вручную независимую копию того же ТЗ.

## 25.70. Один источник истины для терминов

Определения терминов ссылаются на единый словарь KAT9I_OS. HTML может показывать простое и техническое объяснение, но не создавать противоречащие определения.

## 25.71. Что нельзя смешивать

Особенно важно разделять Cache и Knowledge, Logs и Evidence, Settings и Rules, Task State и GitHub Issue, Resource и Knowledge, Secret и обычный Context.

## 25.72. Что считается потерей данных

Не вся потеря является аварией: Cache и индексы пересоздаются; Task State, Rules, Knowledge и важный Evidence критичны; потеря Secret требует повторной авторизации или восстановления защищённым способом.

## 25.73. Классы критичности хранилищ

### Класс A — критическое состояние
Rules, Security, Task State, Knowledge, настройки, Learning State. Нужен Backup.

### Класс B — важная история
Metrics, Evidence, Security Events, Task history. Нужна политика хранения и архив.

### Класс C — пересоздаваемое
Cache, индексы, materialized Context. Backup обычно не нужен.

### Класс D — временное
temp, runtime scratch, промежуточные файлы. Удаляется автоматически.

## 25.74. Контроль свободного места

KAT9I_OS должна следить за свободным диском и ростом Logs, Cache, Artifacts и Backups. Недостаток диска обнаруживается до критического отказа.

## 25.75. Автоматическая очистка

При нехватке места безопасный порядок очистки начинается с temp, просроченного Cache, пересоздаваемых индексов и архивируемых старых Logs. Критические данные автоматически не удаляются.

## 25.76. Дедупликация

Если один ресурс доступен локально, через GitHub и Drive, Resource Registry должен уметь понимать, что это один логический ресурс либо связанные версии. Это снижает дублирование Context и Cache.

## 25.77. Хэширование

Hash используется для проверки целостности, обнаружения изменений, Cache validity, дедупликации и Evidence. Hash не заменяет semantic revision там, где важна версия внешнего объекта.

## 25.78. Безопасное удаление

Для секретных и чувствительных данных политика удаления учитывает тип носителя, шифрование, резервные копии и внешние копии.

## 25.79. Физическое шифрование

Для чувствительного локального состояния желательно использовать защиту диска ОС. На Windows 11 это может быть BitLocker или эквивалентная защита. Это дополнительный слой, а не замена Security KAT9I_OS.

## 25.80. Главные принципы

1. Каждый класс данных имеет своего владельца и источник истины.
2. SQLite подходит как основное локальное структурированное хранилище первой версии.
3. Код KAT9I_OS и пользовательское состояние физически разделены.
4. Большие внешние ресурсы передаются ссылками, а не копируются внутрь системы.
5. Git остаётся источником истины версий кода.
6. Knowledge хранит утверждения, а не копии всех документов.
7. Cache и индексы являются пересоздаваемыми.
8. Секреты хранятся отдельно и передаются по SecretRef.
9. Logs не являются каноническим состоянием и не заменяют Evidence.
10. Event Journal помогает восстановлению, но не заменяет текущее оперативное состояние.
11. Backup приоритетно защищает критическое состояние.
12. Каждая миграция хранилища версионирована и детерминирована.
13. Удалённые Workers не получают прямой доступ ко всей локальной базе.
14. Синхронизация между узлами передаёт только необходимые сущности.
15. Публичный GitHub не содержит приватное пользовательское состояние.
16. HTML и другие представления не создают второй источник истины.
17. Самообучение может оптимизировать хранение, но не удалять обязательные критические данные.
18. Потеря Cache должна влиять на скорость и стоимость, но не на корректность.

## 25.81. Главный принцип

> **KAT9I_OS должна хранить не «всё в одном месте», а каждую сущность там, где ей место: каноническое состояние — в надёжном структурированном хранилище, большие ресурсы — у их владельцев с доступом по ссылке, знания — в Базе знаний, секреты — в защищённом хранилище, а кэш и индексы — как безопасно пересоздаваемые ускорители.**
