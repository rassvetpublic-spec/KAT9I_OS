# 26. Внутренние контракты и протоколы между модулями KAT9I_OS

## 26.1. Назначение

Этот раздел определяет:

> **как модули KAT9I_OS обмениваются задачами, командами, ссылками, состоянием, результатами и событиями, не превращаясь в связанную сеть произвольных вызовов.**

Главный принцип:

> **модули взаимодействуют через типизированные системные контракты, а не через свободный текст и не через скрытые договорённости между моделями.**

## 26.2. Зачем нужны контракты

Без единого набора контрактов быстро возникает ситуация:

- Context сам выбирает Worker;
- Worker сам расширяет Scope;
- Integration сама решает, что ей разрешено;
- Learning напрямую меняет Rule;
- модель передаёт другой модели свободный текст вместо состояния;
- два модуля по-разному понимают слово `DONE`.

Это запрещается архитектурой.

## 26.3. Внутренний протокол не равен MCP

Для взаимодействия модулей внутри модульного монолита KAT9I_OS используются:

> **внутренние типизированные интерфейсы и контракты.**

`MCP — Model Context Protocol — протокол подключения моделей и инструментов`

используется преимущественно на внешних границах.

Внутри Core не нужно превращать каждый вызов модуля в MCP.

## 26.4. Основные классы сообщений

Все внутренние сообщения логически делятся на:

### 1. Команды

> «Выполни действие».

Например:

- создать Task;
- назначить Worker;
- начать Execution;
- остановить процесс.

### 2. Запросы

> «Верни информацию».

Например:

- найти Resources;
- получить Knowledge;
- вычислить прогноз.

### 3. Ответы

Результат запроса.

### 4. События

> «Что-то уже произошло».

Например:

- Worker пропал;
- задача завершилась;
- Cache стал STALE;
- Security заблокировала действие.

### 5. Ссылки

ResourceRef, ResultRef, KnowledgeRef, EvidenceRef и другие ссылки на объекты.

## 26.5. Команда и событие — не одно и то же

Команда:

> `остановить задачу`.

Событие:

> `задача остановлена`.

Событие не должно использоваться как скрытая команда.

Это важно для:

- восстановления;
- аудита;
- повторного воспроизведения;
- Security.

## 26.6. CONTROL и DATA сохраняются на уровне протокола

Каждый объект должен сохранять своё назначение.

### CONTROL

Доверенные управляющие данные:

- TaskContract;
- Effective Ruleset;
- Security Decision;
- Capability Grant;
- подтверждённое USER/ADMIN Decision.

### DATA

Содержимое:

- файл;
- Issue;
- сайт;
- сообщение Telegram;
- Tool response;
- Result Worker;
- документ.

DATA не становится CONTROL только потому, что было передано через внутренний интерфейс.

## 26.7. Общая оболочка системного сообщения

Каждое значимое сообщение должно иметь служебную оболочку.

Минимально:

- message_id;
- message_type;
- schema_version;
- timestamp;
- correlation_id;
- task_id, если применимо;
- sender;
- receiver или topic;
- Scope;
- classification CONTROL/DATA;
- sensitivity;
- payload reference или payload;
- provenance.

## 26.8. Версия схемы обязательна

Каждый устойчивый контракт имеет:

> `schema_version — версию схемы`.

Например:

`TaskContract v1`.

Это позволяет менять KAT9I_OS без скрытой несовместимости между Workers.

## 26.9. Незнакомая версия

Если получатель не поддерживает версию обязательного контракта:

> сообщение не должно интерпретироваться «примерно».

Возможные действия:

- использовать совместимый адаптер;
- запросить старую поддерживаемую версию;
- BLOCKED;
- отметить Worker как INCOMPATIBLE.

## 26.10. TaskContract — центральный контракт выполнения

`TaskContract — контракт задачи`

передаёт:

> **что должно быть сделано.**

Он содержит:

- цель;
- основной Domain;
- Scope;
- RulesRef;
- ContextRefs;
- требования;
- OutputContract;
- ResultSink;
- QA Policy;
- ограничения.

TaskContract не должен содержать mutable runtime state.

## 26.11. TaskRuntimeState — текущее состояние

`TaskRuntimeState — текущее состояние выполнения`

отвечает:

> **что происходит с задачей сейчас.**

Например:

- CREATED;
- READY;
- CLAIMED;
- RUNNING;
- WAITING_USER_DECISION;
- WAITING_ADMIN_APPROVAL;
- WAITING_EXTERNAL_PUBLISH;
- QA;
- COMPLETED;
- BLOCKED;
- FAILED.

## 26.12. TaskGraph — зависимости

`TaskGraph — граф задач`

определяет:

- parent;
- children;
- зависимости;
- параллельность;
- обязательные предыдущие результаты.

Он не должен содержать скрытый текстовый план модели вместо структурированных зависимостей.

## 26.13. Effective Ruleset — применимые правила

Rule Manager передаёт:

> `Effective Ruleset — набор правил, реально применимых к данной операции`.

Другие модули не должны самостоятельно собирать правила из разных файлов и решать конфликт заново.

## 26.14. RulesRef

Если полный Effective Ruleset уже доступен получателю:

может передаваться:

> `RulesRef — ссылка на точную версию набора правил`.

Критическое действие должно иметь возможность доказать:

> по каким правилам оно было разрешено.

## 26.15. Security Decision — решение безопасности

Security возвращает структурированный результат:

- ALLOW;
- DENY;
- REQUIRE_USER_APPROVAL;
- REQUIRE_ADMIN_APPROVAL;
- REQUIRE_REDUCED_SCOPE;
- BLOCKED.

Также фиксируются:

- action;
- subject;
- Scope;
- reason_code;
- policy_ref;
- expiry, если применимо.

## 26.16. Причина решения безопасности

Для системной обработки предпочтительно использовать:

> `reason_code — код причины`.

Например:

`SCOPE_EXCEEDED`.

Человеку визуализация может показать:

> «Исполнитель пытается изменить файл вне разрешённой области».

Это лучше свободного текста, который трудно анализировать автоматически.

## 26.17. Capability Grant — временное разрешение

`Capability Grant — временно выданное разрешение`

определяет:

- кто;
- для какой задачи;
- какое действие;
- над каким ресурсом;
- в каком Scope;
- до какого времени;
- при каком Lease generation.

Worker не должен получать постоянное широкое право только потому, что оно однажды понадобилось.

## 26.18. Claim и Lease

`Claim — захват задачи`

фиксирует временного владельца исполнения.

`Lease — временное право продолжать исполнение`

содержит:

- task_id;
- worker_id;
- generation;
- started_at;
- expires_at;
- heartbeat policy.

Это системные контракты Coworker.

## 26.19. Generation — поколение разрешения

Каждый новый Lease получает:

> `generation — номер поколения`.

Новое поколение делает старое недействительным.

Это используется для защиты от «воскресшего» Worker.

## 26.20. Worker Profile — профиль исполнителя

Coworker хранит структурированный профиль Worker:

- worker_id;
- class;
- capabilities;
- supported_contract_versions;
- Runtime;
- доступные Providers;
- Source Affinity;
- Trust;
- current state;
- performance metrics.

Описание Worker в свободном тексте может существовать для человека, но маршрутизация опирается на структурированные поля.

## 26.21. Inference Requirement — требование к интеллекту

Core/Domain формируют:

`Inference Requirement — требование к вычислительному интеллекту`.

Оно описывает:

- нужен ли вообще ИИ;
- необходимый уровень LOW/NORMAL/HIGH;
- требуемые способности;
- допустимую чувствительность данных;
- требования к инструментам;
- требования к качеству.

Оно не обязано заранее указывать конкретную модель.

## 26.22. Provider Route — маршрут вычисления

Inference возвращает:

`Provider Route — выбранный маршрут вычисления`.

Например:

- локальный код;
- локальный ИИ;
- подписочный Provider;
- API Provider.

Маршрут содержит:

- выбранный механизм;
- экономический класс;
- Context transport;
- Source Affinity;
- ограничения;
- fallback;
- причину выбора.

## 26.23. TaskEstimate — прогноз задачи

Planning & Forecasting передаёт:

`TaskEstimate — прогноз ресурсов задачи`.

Он включает:

- ожидаемые токены;
- время;
- стоимость;
- Cache Hit;
- Retry probability;
- вероятность HIGH escalation;
- Local Share;
- вероятность First Pass Success;
- диапазон неопределённости.

## 26.24. Версия прогноза

Одна задача может иметь несколько прогнозов:

- PRELIMINARY — предварительный;
- REFINED — уточнённый;
- ROLLING — пересчитываемый во время выполнения;
- FINAL_COMPARISON — прогноз против факта.

Каждый прогноз имеет `estimate_id`.

## 26.25. ContextRef

`ContextRef — ссылка на элемент контекста`

содержит:

- источник;
- revision;
- Scope;
- trust;
- freshness;
- sensitivity;
- resolver.

Он не означает автоматического разрешения на чтение.

## 26.26. Context Manifest — манифест использованного контекста

Для значимых этапов фиксируется:

> **какие именно источники реально использовались.**

Это позволяет потом ответить:

- почему модель получила этот документ;
- почему не получила другой;
- на какой revision опиралось решение.

## 26.27. Context Pack — минимальный пакет контекста

Перед вызовом Worker/Provider создаётся:

`Context Pack — минимальный пакет сведений для текущего этапа`.

Он содержит только:

- цель этапа;
- правила;
- необходимые данные;
- ссылки;
- ожидаемый результат.

## 26.28. ResourceRef

`ResourceRef — ссылка на ресурс`

отвечает:

> **что это за ресурс и где его искать.**

Он не отвечает:

> **разрешено ли Worker его читать.**

Разрешение проверяется отдельно.

## 26.29. KnowledgeRef

`KnowledgeRef — ссылка на знание`

указывает на конкретный KnowledgeRecord или набор записей.

Вместо передачи всей Базы знаний Worker получает только нужные ссылки.

## 26.30. ResultRef

`ResultRef — ссылка на результат`

является основным способом передачи результатов между этапами.

Например:

- GitHub PR;
- commit;
- PDF;
- отчёт;
- файл;
- Artifact.

ResultRef является DATA до прохождения требуемой проверки.

## 26.31. EvidenceRef

`EvidenceRef — ссылка на доказательство`

указывает на структурированное подтверждение выполнения:

- тесты;
- точную revision;
- exit code;
- Scope check;
- опубликованный объект;
- QA result.

ResultRef отвечает:

> **что получилось.**

EvidenceRef:

> **чем доказано, что это действительно произошло и проверено.**

## 26.32. OutputContract — контракт результата

Domain/TaskContract определяет:

> **какой результат считается корректным.**

Например:

- формат;
- обязательные поля;
- тип Artifact;
- ResultSink;
- Validators;
- критерии качества.

Worker не должен сам менять OutputContract ради удобства.

## 26.33. QA Result — результат независимой проверки

QA возвращает структурированный объект:

- PASS;
- FAIL;
- BLOCKED;
- NOT_APPLICABLE.

Также:

- qa_worker_id;
- checked_revision;
- checks;
- EvidenceRef;
- findings;
- timestamp.

## 26.34. QA относится к exact revision

В QA Result обязательно присутствует:

> `checked_revision — точная проверенная версия`.

Если ResultRef изменился после проверки:

предыдущий QA становится устаревшим.

## 26.35. Human Decision — решение человека

Решение USER или ADMIN должно быть структурированным.

Минимально:

- decision_id;
- actor;
- role;
- choice;
- Scope;
- task_id;
- timestamp;
- expiry, если нужно;
- supersedes.

Фраза из старого чата не должна автоматически использоваться как новое ADMIN Approval.

## 26.36. Preference и Rule не должны иметь одинаковый контракт

`Preference — предпочтение`

можно применять мягко.

`Rule — обязательное правило`

может блокировать действие.

Они должны быть разными типами, чтобы модуль не мог случайно трактовать предпочтение как запрет.

## 26.37. Integration Request — запрос интеграции

Domain или Execution не должны обращаться напрямую к конкретной реализации GitHub/MCP/CLI, если логически запрашивается capability.

Они передают:

`Integration Request — запрос внешней возможности`.

Например:

> «Получить содержимое ResourceRef».

Tool Broker выбирает конкретный adapter.

## 26.38. Adapter Result — результат адаптера

Интеграционный адаптер возвращает:

- success/failure;
- structured data;
- ResultRef/ResourceRef;
- external revision;
- error class;
- Evidence, если было внешнее изменение.

Результат адаптера остаётся DATA.

## 26.39. Ошибки должны быть типизированы

Не следует передавать только:

> «Что-то пошло не так».

Используются классы ошибок:

- VALIDATION_ERROR;
- SECURITY_DENY;
- SCOPE_ERROR;
- AUTH_REQUIRED;
- RATE_LIMIT;
- NETWORK_ERROR;
- PROVIDER_ERROR;
- WORKER_LOST;
- TIMEOUT;
- RESOURCE_STALE;
- CONFLICT;
- INTERNAL_ERROR.

Человеческое описание прилагается отдельно.

## 26.40. Retry зависит от класса ошибки

Например:

`NETWORK_ERROR`

может разрешать Retry.

`SECURITY_DENY`

автоматически повторять бессмысленно.

Таким образом Retry Policy работает на структуре ошибки, а не на догадке модели.

## 26.41. События

События системы должны иметь стабильный тип.

Например:

- TASK_CREATED;
- TASK_CLAIMED;
- WORKER_LOST;
- EXECUTION_STARTED;
- EXECUTION_COMPLETED;
- SECURITY_BLOCKED;
- QA_PASSED;
- CACHE_HIT;
- FORECAST_UPDATED;
- RESULT_PUBLISHED.

## 26.42. Событие не содержит весь объект без необходимости

Событие:

> `RESULT_PUBLISHED`

может содержать ResultRef.

Оно не должно копировать внутрь Event Journal весь PDF или весь PR.

Снова действует:

> **Reference-first — сначала ссылка.**

## 26.43. Доставка события может повториться

Система должна считать, что одно событие иногда может быть доставлено повторно.

Поэтому используется:

> `event_id`.

Получатель умеет обнаруживать уже обработанное событие.

## 26.44. Доставка события не всегда означает немедленную обработку

Некоторые события могут обрабатываться:

- сразу;
- очередью;
- пакетно;
- Learning позже.

Это позволяет Telemetry и Learning не блокировать основной Execution.

## 26.45. Приоритеты сообщений

Полезно различать:

### CRITICAL

Security, аварийная остановка, отзыв Grant.

### HIGH

отказ Worker, потеря Lease, критическая ошибка задачи.

### NORMAL

обычное выполнение.

### LOW

фоновые Metrics, Learning, обслуживание.

Но приоритет не может обходить Security.

## 26.46. Внутренняя очередь

Для асинхронных операций может использоваться:

`Internal Queue — внутренняя очередь сообщений`.

В первой версии она может быть локальной.

Не нужно сразу вводить Kafka/RabbitMQ только ради модной архитектуры.

## 26.47. Executable-first для протоколов

Валидация контрактов должна выполняться локальным кодом.

Например:

- обязательное поле отсутствует;
- schema_version неизвестна;
- Scope пуст;
- revision неправильного формата.

Для этого не нужен LLM.

## 26.48. Fail-closed для критичных контрактов

Если повреждён:

- Capability Grant;
- Security Decision;
- TaskContract;
- RulesRef;

опасное действие не выполняется.

Система не должна «догадываться», что имелось в виду.

## 26.49. Совместимость модулей

Каждый модуль должен уметь объявлять:

- поддерживаемые версии входных контрактов;
- поддерживаемые версии выходных контрактов;
- обязательные capabilities.

Health Check проверяет совместимость до выполнения задачи.

## 26.50. Совместимость удалённых Workers

Перед назначением Coworker проверяет:

> понимает ли Worker необходимые версии контрактов.

Capability `GitHub write` недостаточна, если Worker не понимает актуальный TaskContract.

## 26.51. Протокол между двумя KAT9I_OS

Между узлами передаются только необходимые контрактные объекты.

Например:

**Node A**
→ TaskContract
→ ContextRefs
→ Capability Grant
→ Lease

**Node B**
→ TaskRuntime update
→ ResultRef
→ EvidenceRef.

Не передаётся вся SQLite-база.

## 26.52. Федерация в будущем

Будущая Federation должна строиться поверх тех же контрактов.

То есть переход:

> локальный Worker → удалённая KAT9I_OS

не должен требовать переписывания Domain.

## 26.53. Telegram и человеческие каналы

Telegram message сначала становится:

> внешним входным DATA-событием.

Только после:

**Identity → Role → command parsing → Rules → Security**

структурированная команда может стать доверенным CONTROL.

Telegram не меняет внутренние контракты KAT9I_OS.

## 26.54. GitHub Issue как внешний объект

GitHub Issue не является TaskContract напрямую.

Правильная схема:

**GitHub Issue**
→ Resource/Event
→ Intake
→ Task Candidate
→ Rules/Security
→ TaskContract.

Это предотвращает выполнение вредоносной инструкции из текста Issue как системной команды.

## 26.55. Learning Proposal

Learning не меняет систему произвольным сообщением:

> «Я решил увеличить Timeout».

Он создаёт:

`Learning Proposal — предложение самообучения`.

Минимально:

- proposed change;
- Scope;
- evidence;
- affected metrics;
- expected effect;
- risk;
- verification;
- rollback.

## 26.56. Safe Adaptation — безопасная адаптация

Для разрешённого низкорискового изменения Learning может использовать отдельный контракт:

`Safe Adaptation — безопасная адаптация`.

Даже он имеет:

- границы;
- Scope;
- old value;
- new value;
- evidence;
- rollback.

## 26.57. MetricsSnapshot

Learning не получает всю историю Metrics по умолчанию.

Передаётся:

`MetricsSnapshot — компактный снимок метрик`.

Это снижает:

- контекст;
- токены;
- стоимость;
- риск информационного шума.

## 26.58. Telemetry Event

Telemetry Event является максимально дешёвым структурированным событием.

Его создание по умолчанию:

> **не вызывает LLM.**

## 26.59. Visualization Snapshot

Visualization должна получать:

`Visualization Snapshot — текущий снимок состояния`

плюс поток новых событий.

После переподключения браузеру не нужно перечитывать всю историю с начала.

## 26.60. Визуализация не отправляет команды напрямую в модули

Если в будущем пользователь нажимает в интерфейсе:

> «Остановить задачу»,

это создаёт обычную системную Command:

**UI → Identity → Rules → Security → Orchestration → Execution.**

UI не получает обходной административный канал.

## 26.61. Correlation ID

Один пользовательский запрос получает:

`correlation_id`.

Он проходит через:

- Task;
- Context;
- Inference;
- Worker;
- Execution;
- Integration;
- Telemetry;
- Metrics;
- QA.

Это позволяет режиму «Рентген KAT9I_OS» собрать единый маршрут.

## 26.62. Causation ID — причина события

Помимо correlation_id полезно хранить:

`causation_id — идентификатор непосредственной причины`.

Например:

> Retry #2 появился из-за NETWORK_ERROR #918.

Это позволяет строить реальную цепочку причин.

## 26.63. Idempotency Key — ключ безопасного повтора

Для внешних изменяющих операций используется:

`idempotency_key — идентификатор, не позволяющий случайно повторить одно действие`.

Особенно:

- создание Issue;
- PR;
- комментария;
- файла;
- публикации результата.

## 26.64. Operation ID — идентификатор операции

Каждое значимое побочное действие получает:

`operation_id`.

Если связь оборвалась:

> сначала проверяем, завершилась ли эта операция.

Только потом решаем, повторять ли её.

## 26.65. Нельзя передавать Chain of Thought

Между Workers передаются:

- задача;
- факты;
- ссылки;
- результат;
- Evidence;
- краткое структурированное состояние.

Не передаётся внутренний скрытый ход рассуждений модели.

## 26.66. Handoff — передача работы

`Handoff — передача работы другому исполнителю`

содержит:

- task_id;
- current stage;
- completed stages;
- remaining objective;
- ResultRefs;
- EvidenceRefs;
- ContextRefs;
- known blockers.

Это позволяет другому Worker продолжить работу без полного предыдущего разговора.

## 26.67. Минимальный Handoff

Handoff должен стремиться быть:

> **минимально достаточным.**

Нельзя автоматически передавать новому Worker весь журнал предыдущего исполнителя.

## 26.68. Принцип запрета скрытой зависимости

Если модулю требуется информация другого модуля:

это должно быть видно через контракт.

Нельзя строить архитектуру, где:

> Execution случайно знает внутренний путь SQLite Coworker и читает его таблицу напрямую.

## 26.69. Внутренние API вместо прямого доступа к таблицам

Даже внутри модульного монолита один модуль не должен без необходимости читать внутренние таблицы другого.

Например:

> Execution спрашивает Coworker о действующем Lease через интерфейс,

а не выполняет собственный SQL к его внутренним данным.

## 26.70. Владение контрактом

У каждого системного контракта должен быть один владелец.

Например:

| Контракт | Владелец |
|---|---|
| TaskContract | Core |
| Effective Ruleset | Rule Manager |
| Security Decision | Security |
| Context Pack | Context |
| ResourceRef | Resources |
| Provider Route | Inference |
| TaskEstimate | Planning & Forecasting |
| Claim / Lease | Coworker |
| Evidence | Execution |
| QA Result | QA |
| MetricsSnapshot | Metrics |
| Learning Proposal | Learning |

Потребители могут использовать контракт, но не создавать собственную несовместимую версию его смысла.

## 26.71. Один источник истины для схем

Схема каждого контракта хранится:

> **в одном каноническом месте.**

Документация, HTML и примеры ссылаются на эту схему.

Нельзя иметь отдельные независимые описания `TaskContract v1` в пяти модулях.

## 26.72. Генерация документации из схем

В будущем из канонических схем можно автоматически генерировать:

- справочник;
- HTML;
- таблицы полей;
- примеры;
- проверки совместимости.

Это поддерживает правило одного источника истины.

## 26.73. Примеры не являются контрактом

Пример нужен для понимания.

Но если пример противоречит канонической схеме:

> **побеждает схема.**

Quality Gate должен со временем проверять примеры автоматически.

## 26.74. Изменение контракта

Изменение системного контракта является архитектурным изменением.

Процесс:

**предложение**
→ анализ потребителей
→ новая версия
→ compatibility check
→ тесты
→ независимый QA
→ migration/adapters
→ promotion.

## 26.75. Ломающие изменения

`Breaking Change — несовместимое изменение`

нельзя незаметно вносить в существующую версию контракта.

Создаётся новая версия либо официальная миграция.

## 26.76. Устаревание версии

Старая версия может пройти состояния:

`SUPPORTED → DEPRECATED → BLOCKED`.

Переход должен быть виден Workers и администраторам.

## 26.77. Проверка контрактов в GitHub

Quality Gate должен со временем проверять:

- существование канонических схем;
- уникальность владельцев;
- номера версий;
- ссылки документации;
- обратную совместимость;
- отсутствие дублирования SSoT.

## 26.78. Метрики протокола

Следует измерять:

- число сообщений;
- размер сообщений;
- долю передачи по ссылкам;
- число schema errors;
- число incompatible Workers;
- число duplicate events;
- contract validation time;
- Handoff size;
- Context transfer size.

## 26.79. Самообучение протокола

Learning может обнаруживать:

- слишком большие Handoff;
- часто неиспользуемые поля;
- повторную материализацию Resources;
- частые ошибки конкретного контракта;
- избыточное количество сообщений.

Но изменение публичного системного контракта проходит обычный контролируемый процесс.

## 26.80. Что внутренний протокол не должен делать

Он не должен:

- передавать полный чат без необходимости;
- передавать скрытый ход рассуждения;
- выдавать Permission вместе с ResourceRef;
- превращать DATA в CONTROL;
- позволять Worker самостоятельно расширять Scope;
- использовать свободный текст как единственный статус;
- позволять одному модулю напрямую менять внутреннее состояние другого;
- использовать LLM для проверки формальной схемы;
- скрывать версию контракта;
- допускать несовместимые изменения под тем же номером версии.

## 26.81. Главные принципы

1. **Модули общаются через типизированные контракты.**
2. **Команды, запросы, ответы и события различаются.**
3. **CONTROL и DATA остаются разделёнными при передаче.**
4. **Каждый устойчивый контракт имеет версию.**
5. **Неизвестная критичная версия не интерпретируется приблизительно.**
6. **TaskContract хранит требования, TaskRuntimeState — текущее состояние.**
7. **ResourceRef не является разрешением.**
8. **ResultRef не является Evidence.**
9. **QA всегда связан с точной revision.**
10. **Errors и Security decisions типизированы.**
11. **Повторная доставка событий должна быть безопасна.**
12. **Внутри монолита используются внутренние API, а не обязательный MCP.**
13. **Удалённые Workers используют те же логические контракты.**
14. **Handoff передаёт структурированное состояние, а не историю рассуждений.**
15. **Каждый контракт имеет одного владельца.**
16. **Каждая схема имеет один источник истины.**
17. **Примеры не дублируют контракт как отдельный источник истины.**
18. **Формальная валидация выполняется локальным кодом.**
19. **Несовместимое изменение получает новую версию.**
20. **Протокол сам измеряется и оптимизируется через Metrics и Learning.**

## 26.82. Главный принцип

> **KAT9I_OS должна быть системой, в которой каждый модуль точно знает, что он получает, что имеет право с этим сделать и какой структурированный результат обязан вернуть; свободный текст используется как содержимое работы, но не заменяет системные контракты, права, состояния и доказательства.**
