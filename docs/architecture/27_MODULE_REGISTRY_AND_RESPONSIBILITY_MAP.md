# 27. Реестр модулей и карта ответственности KAT9I_OS

## 27.1. Назначение

Этот раздел определяет, какой модуль KAT9I_OS за что отвечает, чего он делать не имеет права и через какие контракты взаимодействует с остальной системой.

Цель — не допустить ситуации, когда одна функция постепенно появляется одновременно в нескольких модулях.

> **Для каждой архитектурной ответственности должен существовать один канонический владелец.**

## 27.2. Не второй источник истины

Подробное устройство каждого модуля остаётся в его каноническом архитектурном разделе.

Раздел 27 является канонической картой владения ответственностью: он показывает владельца функции, но не дублирует полную спецификацию каждого модуля.

Если обнаружено противоречие между этой картой и профильным разделом, оно должно быть устранено в исходной спецификации при кросс-анализе, а не скрыто ещё одной формулировкой.

## 27.4. Core — ядро управления

Core создаёт и поддерживает общесистемные контракты задачи, координирует жизненный цикл, связывает модули через формальные интерфейсы и управляет TaskContract и TaskGraph.

Core не выполняет Shell-команды, не выбирает конкретную модель вместо Inference, не выбирает конкретного Worker вместо Coworker, не хранит всю Базу знаний, не реализует GitHub и не забирает предметную логику Domain.

Каноническое владение: TaskContract, общая модель TaskGraph и жизненный цикл задачи.

## 27.5. Rule Manager — менеджер правил

Rule Manager хранит и применяет обязательные правила, определяет применимость по Scope, разрешает конфликты по принципу `deny wins — запрет выше разрешения` и формирует Effective Ruleset.

Rule Manager не хранит Preferences, не выбирает Worker, не исполняет действие и не создаёт новые обязательные правила из наблюдений Learning без контролируемой процедуры.

Каноническое владение: система обязательных правил, Effective Ruleset и RulesRef.

## 27.6. Security — безопасность

Security отвечает на вопрос: разрешено ли конкретному субъекту совершить конкретное действие над конкретным объектом в данном Scope.

Проверяются Identity, Trust, CONTROL/DATA, Scope, Capability Grant, чувствительность данных, SecretRef, внешний Provider и USER/ADMIN Approval.

Security не оценивает предметное качество результата, не выбирает лучший Worker и не оптимизирует стоимость.

Каноническое владение: Security Decision и системная граница разрешений.

## 27.7. Domains — предметные области

Domain отвечает за смысл правильного выполнения задачи конкретного класса: предметные Workflow, Skills, Validators, формат результата, Domain Rules и связи с Knowledge.

Domain не реализует общий Security, не выбирает Provider или Worker напрямую и не управляет общесистемным TaskRuntimeState.

Каноническое владение: предметная логика.

## 27.8. Context — контекст

Context определяет минимально достаточную информацию для конкретного этапа и формирует ContextRef, Context Manifest, Context Pack и Context Budget.

Context не является Базой знаний, не выдаёт разрешения на ресурсы, не выбирает Worker и не хранит все исходные данные.

Каноническое владение: политика формирования рабочего контекста.

## 27.9. Knowledge — База знаний

Knowledge хранит подтверждённые факты, решения, наблюдения, связи и Provenance.

Knowledge не заменяет Rules, Cache, Task State или Secret Store и не должна превращаться в склад полных копий всех документов.

Каноническое владение: KnowledgeRecord, KnowledgeRef и жизненный цикл знаний.

## 27.10. Resources — ресурсы

Resources отвечает, что это за объект и где он логически находится. Управляет ResourceRef, Resource Registry, revision, Resolver hints и дедупликацией логических ресурсов.

ResourceRef не выдаёт Permission. Технический доступ к внешнему ресурсу реализуют Integrations после проверки Security.

Каноническое владение: логическая модель ресурсов.

## 27.11. CacheEngine — движок кэша

CacheEngine является единственным каноническим владельцем кэширования KAT9I_OS и реализуется отдельным Rust-модулем согласно `docs/architecture/34_CACHE_ENGINE.md`.

Он одновременно отвечает за логическую Cache Policy — можно ли безопасно повторно использовать ранее вычисленный результат — и за высокопроизводительное RAM-first размещение производных данных. При проверке валидности учитываются revision/hash, RulesRef / Effective Ruleset, значимый Context Drift, версия Skill/Workflow/transformation, параметры, Security scope и TTL там, где нет более сильной revision-модели.

Состояния `FULL_HIT`, `PARTIAL_HIT`, `MISS`, `STALE`, `FORBIDDEN` являются единым словарём результата Cache Policy. Они не означают конкретный backend хранения.

Runtime Cache Registry является внутренним пересоздаваемым индексом CacheEngine. Он не является канонической SQLite-сущностью Storage и может быть полностью удалён вместе с кэшем.

CacheEngine не является SSoT, Knowledge, Evidence или Storage. Потеря CacheEngine влияет только на производительность и стоимость, но не на корректность системы.

Каноническое владение: Cache Policy, runtime Cache Registry, CacheKey/CacheEntry/PayloadRef и состояния FULL_HIT/PARTIAL_HIT/MISS/STALE/FORBIDDEN.

## 27.12. Planning & Forecasting — планирование и прогнозирование

Модуль прогнозирует токены, время, стоимость, вероятность Cache Hit, Retry, HIGH escalation, Local Share и First Pass Success.

Поддерживаются предварительный, уточнённый и текущий пересчитываемый прогнозы.

Planning не выбирает окончательно Provider или Worker и не разрешает действие.

Каноническое владение: TaskEstimate, модели прогнозирования и оценка ошибки прогноза.

## 27.13. Inference — выбор вычислительного интеллекта

Inference выбирает минимально достаточный вычислительный маршрут с учётом Executable-first, Local-first, Security, качества и TaskEstimate.

Варианты включают локальный код, локальный ИИ, LOW/NORMAL/HIGH, подписочные и API-маршруты.

Inference не выбирает конкретного Worker и не исполняет Tool.

Каноническое владение: Provider Route и маршрутизация вычислительного интеллекта.

## 27.14. Coworker — исполнители

Coworker отвечает, кто конкретно должен выполнить работу. Управляет Worker Registry, Capability Profile, availability, Claim, Lease, generation, scheduling и Handoff.

Coworker не выдаёт себе Security-разрешения, не определяет предметную правильность и не выполняет работу вместо Execution.

Каноническое владение: Worker Registry, Claim, Lease и выбор Worker.

## 27.15. Execution — исполнение

Execution отвечает, как физически выполнить уже назначенное и разрешённое действие. Управляет Runtime, процессами, Worktree, Timeout, Scope Guard, Cleanup, побочными эффектами, Evidence и публикацией ResultRef.

Execution не выбирает Worker, не расширяет Scope и не отменяет Security.

Каноническое владение: фактический процесс выполнения и Evidence выполнения.

## 27.16. Integrations — интеграции

Integrations отвечают за технический способ обращения к внешним системам и включают Connector, Adapter, Tool Broker, API, CLI, MCP, Telegram, GitHub, Drive и другие подключения.

Они не решают, разрешён ли вызов, не определяют предметную задачу и не становятся владельцами ResourceRef.

Каноническое владение: транспорт и техническая адаптация внешних возможностей.

## 27.17. QA — независимая проверка

QA доказывает, что конкретная revision соответствует требованиям, используя Validators, tests, Evidence, OutputContract и точную revision.

Исполнитель не может исправить результат и одновременно считать своё же исправление независимым QA.

Каноническое владение: QA Result.

## 27.18. Recovery — восстановление

Recovery определяет, что фактически произошло до сбоя и как безопасно продолжить. Использует Checkpoints, Event Journal, TaskRuntimeState, Lease, Evidence и реальное состояние внешних ресурсов.

Recovery не восстанавливает состояние по догадке LLM, не расширяет права и не повторяет опасную операцию без проверки operation_id.

Каноническое владение: процедура восстановления и Recovery State.

## 27.19. Telemetry — телеметрия

Telemetry фиксирует структурированные события о том, что реально произошло.

Она не оценивает качество, не принимает решений и по умолчанию не требует LLM.

Каноническое владение: Telemetry Event и сырой событийный поток.

## 27.20. Metrics — метрики

Metrics превращает фактические события в числовые показатели качества, времени, стоимости, Cache Gain, Routing Efficiency, Recovery, Forecast Error и Learning Gain.

Metrics не заменяет Telemetry и не изменяет настройки напрямую.

Каноническое владение: числовые показатели и MetricsSnapshot.

## 27.21. Learning — самообучение

Learning определяет, что можно улучшить на основании доказанной истории работы: Routing, Skills, Context, Cache, Forecasting, Timeout, Lease, Retry, Workflow и долю локального исполняемого кода.

Learning не обходит Rules/Security, не снимает DENY и не превращает единичное наблюдение в глобальное правило.

Каноническое владение: Learning Proposal, Safe Adaptation и Learning State.

## 27.22. Personal Layer — персональный слой

Personal Layer связывает с конкретным пользователем Preferences, Settings, USER-scope Knowledge, Workspace, персональные RulesRef и Working Context Snapshot.

Он не создаёт вторую Knowledge Base или второй Rule Manager, не хранит весь чат и не публикует персональные данные в публичный репозиторий.

Каноническое владение: структурированная персонализация пользователя.

## 27.23. Visualization — визуализация процессов

Visualization отображает движение задач, Workers, Providers, токены, стоимость, Cache, Forecast, Errors, QA, Security Events, Learning и Recovery.

Источник состояния — общесистемные Telemetry, Metrics и системные контракты. Визуализация не создаёт собственную конкурирующую телеметрию, не меняет TaskRuntimeState напрямую и не обходит Security.

Ответственный за направление разработки домена визуализации — Артём (`Art3m1da`). Это не означает автоматического назначения на каждый GitHub Issue и не выдаёт дополнительных системных прав.

Каноническое владение: логика визуального представления состояния.

## 27.24. Electron — штатная настольная оболочка KAT9I_OS

Принято архитектурное решение:

> **Основной пользовательский интерфейс KAT9I_OS реализуется как настольное приложение на Electron.**

Electron является оболочкой пользовательского интерфейса, а не заменой Core.

В Electron размещаются как минимум:

- визуализация процессов;
- панель управления задачами и Workers;
- экран Forecast / Fact;
- настройки;
- onboarding — режим «Я здесь впервые»;
- встроенная документация;
- диагностика и режим «Рентген KAT9I_OS»;
- управление обновлениями;
- отображение QA, Security, Recovery и Learning;
- уведомления, системный трей и другие настольные функции, если они нужны.

HTML/CSS/JavaScript используются как технология renderer-интерфейса внутри Electron. Публичная HTML-документация и GitHub Pages остаются производными представлениями канонических Markdown-документов и не являются отдельным источником истины.

## 27.25. Граница Electron и Core

Electron main process не должен превращаться во второй оркестратор или второй Core.

Renderer не получает прямого широкого доступа к Node.js, файловой системе, Shell, секретам, базе состояния или административным API.

Управляющее действие из интерфейса проходит обычный системный путь:

**Electron UI → Identity → Rules → Security → Core / соответствующий владелец функции → Execution / Integration.**

Таким образом кнопка «остановить задачу» или «опубликовать результат» является только пользовательским запросом на системную команду, а не прямым привилегированным вызовом из интерфейса.

## 27.26. Безопасная модель Electron

Базовые требования:

- `contextIsolation` включена;
- прямой `nodeIntegration` в renderer не используется;
- renderer по возможности работает в sandbox;
- preload предоставляет только узкий явно разрешённый API;
- IPC имеет типизированные каналы и проверяемые аргументы;
- запрещено экспортировать в renderer универсальный произвольный IPC/Shell/FS API;
- удалённый контент рассматривается как DATA и не получает нативные права;
- системные команды Electron должны сопоставляться с внутренними контрактами KAT9I_OS.

Эти требования являются продолжением CONTROL/DATA и принципа минимальных полномочий.

## 27.27. Локальный Electron и удалённый интерфейс

Electron — основной интерфейс владельца KAT9I_OS.

При необходимости в будущем может существовать ограниченный удалённый web-клиент, использующий те же канонические UI/API-контракты. Он является дополнительным представлением, а не второй системой управления.

Наличие удалённого клиента не должно заставлять Core зависеть от Electron или браузера.

## 27.28. Configuration — конфигурация

Configuration хранит и применяет системные, пользовательские, Workspace и Runtime settings, режим запуска и адаптивные параметры.

Configuration не заменяет Rules, не хранит секреты открытым текстом и не выдаёт Permission.

Каноническое владение: схема конфигурации и история её изменений.

## 27.29. Storage — физическое хранение

Storage отвечает, где физически и каким механизмом хранится системное состояние. Предоставляет SQLite, файловые хранилища, Event Journal, backup, migrations и integrity checks.

Storage не определяет предметную семантику Knowledge или Rules и не даёт модулям бесконтрольно читать внутренние таблицы друг друга.

Каноническое владение: физические механизмы хранения канонического и долговечного состояния. Runtime RAM-кэш, spill-сегменты и пересоздаваемый Cache Registry принадлежат CacheEngine и не входят в ответственность Storage.

## 27.30. Secret Store — хранилище секретов

Secret Store является специализированной инфраструктурной возможностью Security/Storage и хранит токены, API-ключи, пароли и приватные ключи.

Остальные модули преимущественно работают через SecretRef.

## 27.31. Оркестрация

Оркестрация является функцией Core и жизненного цикла задач. Не создаётся отдельный супермодуль, которому начинают принадлежать Security, Context, Coworker, Inference и Execution.

Оркестратор вызывает владельцев функций и управляет переходами, но не забирает их ответственность.

## 27.32. Кто принимает ключевые решения

- **Что делать:** USER/событие → Core → Domain → TaskContract.
- **Какие правила действуют:** Rule Manager.
- **Можно ли:** Security.
- **Что нужно знать:** Context.
- **Где данные:** Resources.
- **Как технически получить внешний ресурс:** Integrations.
- **Сколько примерно будет стоить:** Planning & Forecasting.
- **Чем думать:** Inference.
- **Кто делает:** Coworker.
- **Как физически выполнить:** Execution.
- **Что реально произошло:** Evidence + Telemetry.
- **Соответствует ли результат:** QA.
- **Насколько хорошо сработала система:** Metrics.
- **Что улучшить:** Learning.
- **Как это показать человеку:** Visualization внутри Electron.

## 27.33. Правило одного владельца

Допустимы несколько потребителей, адаптеров и представлений, но не несколько конкурирующих владельцев одной семантики.

Например плохая архитектура — отдельные Worker selectors внутри Context, Domain и Core. Правильно: все эти модули формируют требования и передают их Coworker.

## 27.34. Совместная ответственность не равна дублированию

Пример внешнего GitHub write:

Domain знает, что нужен PR; Resources знает репозиторий; Security разрешает запись; Coworker назначает исполнителя; Execution инициирует действие; Integration вызывает GitHub; Evidence подтверждает созданный PR.

Каждый модуль выполняет только свою часть.

| Фактическое выполнение | Evidence |
| QA | QA Result точной revision |
| Сырые события | Telemetry |
| Числовые показатели | Metrics |
| Прогноз | TaskEstimate |

## 27.37. Порядок ключевых решений

Независимые операции могут выполняться параллельно, но операции с побочными эффектами остаются управляемыми зависимостями TaskGraph.

## 27.38. Реализация может заменяться

Логический модуль не должен быть связан навсегда с одной библиотекой или продуктом.

Например Storage первой версии может использовать SQLite, а внутренние адаптеры Integrations могут меняться без изменения Domain.

Исключение принятого уровня продукта: Electron выбран штатной настольной оболочкой KAT9I_OS. При этом Core и внутренние контракты всё равно не должны зависеть от Electron API, чтобы системные процессы могли работать без UI.

## 27.39. Критерий нового верхнеуровневого модуля

Новый верхнеуровневый модуль оправдан, если у него есть собственная устойчивая ответственность, собственные контракты, отдельный жизненный цикл, несколько потребителей, возможность независимого развития и смысловая граница с соседями.

Новый модуль не создаётся только ради красивого названия.

## 27.40. Executable-first внутри модулей

В каждом модуле отдельно ищется возможность перехода `MODEL → HYBRID → CODE`.

Особенно это касается валидации контрактов, Security checks, CacheEngine, Planning calculations, Worker state, Lease, Git operations, Metrics, Recovery, Storage и UI-агрегации.

ИИ остаётся там, где действительно нужна содержательная интерпретация.

## 27.41. Module Registry — машинно-читаемый реестр модулей

В реализации эта карта должна иметь машинно-читаемое представление с полями:

- module_id;
- version;
- responsibility;
- owned contracts;
- consumed contracts;
- optional contracts;
- required dependencies;
- optional dependencies;
- health;
- capabilities;
- owner/team;
- documentation reference.

Electron UI и будущая HTML-документация должны строить архитектурные представления из Module Registry, канонических схем и Markdown, а не поддерживать вторую ручную копию карты.

## 27.42. Автоматическая проверка архитектурной ответственности

Quality Gate должен со временем обнаруживать:

- двух владельцев одного контракта;
- контракт без владельца;
- неизвестную зависимость;
- запрещённую прямую зависимость;
- циклическую управляющую связь;
- модуль без документации;
- контракт без версии;
- нарушение SSoT.

## 27.43. Кросс-анализ всей архитектуры

После принятия всех разделов эта карта становится основой обязательного кросс-аудита.

Проверяются:

- все разделы друг против друга;
- дублирование ответственности;
- несовместимые определения;
- разная терминология;
- циклы;
- лишние и отсутствующие модули;
- лишние переходы через ИИ;
- нарушение Local-first;
- нарушение Executable-first;
- нарушение Reference-first;
- нарушение SSoT;
- конфликт Security и удобства;
- конфликт Learning и владения параметрами;
- соответствие Electron UI границам Core/Security.

## 27.44. Сравнение с внешними проектами

После внутреннего аудита карта используется для сравнительного исследования актуальных аналогов в интернете и внутренних доноров AG25 и `kat9i_skills`.

Сравниваются архитектурные способности: Task model, Context, Memory/Knowledge, Workflow, Workers, Security, Tool routing, Observability, Recovery, Learning, Forecasting, Desktop/UI и Federation.

Чужая структура не копируется механически.

## 27.45. Что реестр модулей не должен делать

Реестр не должен:

- дублировать полную документацию каждого раздела;
- становиться вторым Rule Manager;
- определять Runtime-логику;
- содержать секреты;
- позволять одному контракту иметь двух владельцев;
- автоматически назначать GitHub Issues ответственному за архитектурное направление;
- превращать Electron в обходной путь к Core, Execution или Security.

## 27.46. Основные принципы

1. Каждая ответственность имеет одного канонического владельца.
2. Оркестратор вызывает модули, но не забирает их ответственность.
3. Domain определяет предметную работу.
4. Rule Manager определяет обязательные правила.
5. Security определяет разрешённость действия.
6. Context определяет минимально достаточные сведения.
7. Resources определяет логический ресурс, Integrations — способ доступа.
8. Planning прогнозирует, Inference выбирает интеллект, Coworker выбирает исполнителя, Execution выполняет.
9. Evidence и QA являются разными уровнями подтверждения.
10. Telemetry фиксирует события, Metrics их измеряет, Learning улучшает систему.
11. Visualization является представлением, а не источником состояния.
12. Electron является штатной настольной оболочкой KAT9I_OS, но не Core.
13. Renderer не получает прямых системных полномочий.
14. Storage физически хранит данные, но не владеет их предметным смыслом.
15. Module Registry должен стать машинно-читаемым.
16. UI, HTML и визуализация строятся из канонических источников и не создают второй SSoT.
17. Quality Gate должен автоматически проверять архитектурные границы.

## 27.47. Главный принцип

> **KAT9I_OS должна иметь настолько чёткие границы ответственности, чтобы для любой функции можно было однозначно ответить: какой модуль ею владеет, кто её использует, через какой контракт она доступна и какой другой модуль не имеет права незаметно присвоить её себе; человек взаимодействует с системой через штатное Electron-приложение, но Electron не получает права обходить эти границы.**
