# 28. Развёртывание и распределённая работа KAT9I_OS

## 28.1. Назначение

Этот раздел определяет, как KAT9I_OS работает на одном компьютере, с несколькими локальными Workers (исполнителями), между несколькими компьютерами и через удалённую сеть.

Система должна начинаться просто:

> **один компьютер должен быть полноценной рабочей KAT9I_OS.**

Распределённость добавляется только тогда, когда она действительно нужна.

## 28.2. Local-first относится и к развёртыванию

Приоритет:

1. один локальный компьютер;
2. локальные Workers;
3. компьютеры в локальной сети;
4. доверенные удалённые компьютеры;
5. внешняя инфраструктура.

Не нужно превращать KAT9I_OS в облачную распределённую систему, если задача нормально решается на одном компьютере.

## 28.3. Основной узел

В первой версии существует `Primary Node (основной узел KAT9I_OS)`.

На нём находятся:

- Core;
- Task State;
- Rules;
- Security;
- Knowledge;
- Resources Registry;
- Planning;
- Inference;
- Coworker;
- Metrics;
- Learning;
- основной Storage;
- Electron-приложение.

Для простого пользователя:

> **Primary Node — главный компьютер, на котором живёт Катя.**

## 28.4. Electron как основной пользовательский интерфейс

На основном пользовательском компьютере запускается **KAT9I_OS Desktop на Electron**.

Через него пользователь видит:

- задачи;
- Workers;
- процессы;
- расходы;
- прогнозы;
- ошибки;
- Security;
- Learning;
- Knowledge;
- настройки;
- документацию.

Electron является интерфейсом. Core остаётся самостоятельной системной частью.

## 28.5. Electron и Core — разные процессы ответственности

Рекомендуемая логическая схема:

Electron UI ↔ защищённый локальный API / IPC ↔ KAT9I_OS Core.

Если окно Electron зависнет, это не должно повреждать состояние выполняемой задачи.

Если Core работает, пользовательский интерфейс можно восстановить из текущего состояния и Telemetry.

## 28.6. Закрытие окна

Закрытие окна не обязательно означает остановку KAT9I_OS.

Можно поддержать режим сворачивания в системный трей с продолжением работы.

Пользователь должен явно понимать, приложение только скрыто или Core действительно остановлен.

## 28.7. Фоновая работа

Для автоматизации может существовать `Headless Mode (режим без графического интерфейса)`.

Например:

- серверный Worker;
- ночная задача;
- удалённый компьютер.

Это не отменяет Electron как штатный пользовательский интерфейс.

## 28.8. Типы узлов

Предлагаются основные роли:

- `PRIMARY` — главный узел пользователя;
- `WORKER NODE` — компьютер, предоставляющий вычислительные возможности;
- `FULL NODE` — будущая полноценная установка KAT9I_OS, способная иметь собственные задачи и Workers;
- `UI CLIENT` — дополнительный интерфейс управления разрешённой KAT9I_OS.

Для первой версии достаточно `PRIMARY + WORKER NODE`.

## 28.9. Worker Node

Worker Node может предоставлять:

- CPU;
- GPU;
- локальную модель;
- Git;
- Python;
- специализированный Tool;
- доступ к локальному Resource;
- специализированный Domain Worker.

Он не получает автоматически:

- всю Knowledge Base;
- всю SQLite;
- все Secrets;
- права ADMIN.

## 28.10. Пример

Основной компьютер: Windows 11 + Electron + KAT9I_OS Core.

Второй компьютер: мощная GPU + локальные модели.

Coworker видит Worker `GPU-PC-2`.

Inference определяет, что локальный ИИ достаточен.

Planning видит, что на `GPU-PC-2` ожидается 22 секунды.

Coworker отправляет туда задачу.

## 28.11. Узел имеет стабильную личность

Каждый узел получает `node_id`.

Он не должен определяться только по IP, имени компьютера или hostname. IP может измениться. Идентичность узла должна оставаться стабильной.

## 28.12. Криптографическая идентичность

Для доверенных удалённых узлов желательно иметь собственную пару ключей.

Это позволяет проверять, что это действительно тот же самый узел, которому система доверяла раньше.

## 28.13. Подключение нового компьютера

Новый Worker Node не становится доверенным автоматически.

Процесс:

обнаружение → предложение подключения → проверка личности → USER/ADMIN Approval при необходимости → регистрация → Capability discovery → Trust → готовность к задачам.

## 28.14. Простое подключение

Для пользователя подключение должно выглядеть примерно так:

> «Найден компьютер OFFICE-PC. Подключить его как Worker?»

Далее:

> «На нём доступны GPU, Python и Ollama.»

Пользователю не нужно вручную писать сетевые конфигурации, если это можно безопасно определить автоматически.

## 28.15. Код или QR для сопряжения

Для простого первоначального соединения можно использовать:

- короткий одноразовый код;
- QR;
- приглашение;
- локальное подтверждение на двух устройствах.

После первого соединения используются постоянные машинные ключи.

## 28.16. Обнаружение не означает доверие

KAT9I_OS может автоматически обнаружить устройство в локальной сети.

Но видеть устройство не означает доверять устройству.

Discovery только сообщает о возможности подключения.

## 28.17. Локальное обнаружение

В локальной сети можно использовать автоматический Discovery. Конкретная технология выбирается позднее.

Discovery должен передавать только минимальные сведения:

- node_id;
- адрес подключения;
- версию протокола;
- тип узла.

## 28.18. Не открывать KAT9I_OS всему интернету

По умолчанию KAT9I_OS не должна открывать публичный управляющий порт в интернет.

Удалённое подключение включается явно.

## 28.19. Удалённое соединение

Для удалённых узлов допустимы:

- защищённая частная сеть;
- VPN;
- разрешённый relay;
- прямое защищённое соединение.

Конкретный транспорт является заменяемой реализацией.

## 28.20. Шифрование

Сетевой обмен между доверенными узлами должен быть защищён.

Минимально:

- шифрование транспорта;
- проверка узла;
- защита от подмены;
- защита от повторного использования старых команд.

## 28.21. Взаимная проверка

Для критичных узлов желательно, чтобы обе стороны проверяли друг друга.

Не только Worker проверяет сервер, но и Primary проверяет Worker.

## 28.22. Worker не подключается напрямую к базе Primary

Удалённому Worker запрещается давать обычный сетевой доступ к:

- SQLite;
- Secret Store;
- Knowledge Store;
- внутренним таблицам Coworker.

Он работает через контракты KAT9I_OS.

## 28.23. Что получает удалённый Worker

Минимальный набор:

- TaskContract;
- необходимые RulesRef;
- Context Pack;
- ResourceRef;
- Capability Grant;
- Lease;
- необходимые ResultRef предыдущих этапов.

Не передаётся полный снимок компьютера пользователя.

## 28.24. Reference-first особенно важен в сети

Если Worker уже может получить ресурс напрямую, Primary передаёт ResourceRef.

Например вместо передачи гигабайтного репозитория передаётся Git URL + commit SHA.

## 28.25. Source Affinity — близость к источнику

Если файл уже находится на Worker B, выгоднее выполнять работу там.

Planning и Coworker должны учитывать:

- где находятся данные;
- сколько стоит передача;
- насколько быстро их можно получить;
- разрешена ли передача.

## 28.26. Data Locality — локальность данных

Для чувствительных данных может существовать правило: данные не покидают конкретный компьютер.

Тогда задача либо выполняется на этом узле, либо BLOCKED.

## 28.27. Секреты между узлами

Секрет не копируется на Worker только потому, что он существует на Primary.

Если секрет нужен:

- проверяется Security;
- выдаётся минимально необходимое временное разрешение;
- либо операция выполняется на узле, где секрет уже находится.

Предпочтительно перемещать вычисление к секрету, а не секрет к вычислению.

## 28.28. Capability Registry распределённой системы

Primary знает возможности узлов.

Например:

| Узел | Возможности |
|---|---|
| MAIN-PC | Git, Python, Electron |
| GPU-PC | RTX GPU, Ollama |
| STUDIO-PC | Ableton, аудиоинструменты |
| SERVER-1 | круглосуточные автоматизации |

Coworker использует эти данные при маршрутизации.

## 28.29. Presence — присутствие

Узел имеет состояния:

- ONLINE;
- BUSY;
- DEGRADED;
- UNREACHABLE;
- OFFLINE;
- DRAINING;
- INCOMPATIBLE.

## 28.30. Heartbeat — сигнал жизни

Worker периодически подтверждает, что он доступен.

Heartbeat используется для определения потери Worker. Параметры Heartbeat и Timeout адаптируются по статистике.

## 28.31. Самообучение сетевых таймаутов

Learning учитывает:

- обычную задержку узла;
- сеть;
- тип задачи;
- время суток;
- нагрузку;
- историю ложных Timeout.

Если Worker стабильно возвращается через 31 секунду при Timeout 30 секунд, Learning может предложить изменить Timeout для сочетания этого Worker + этой сети + этого типа операций, а не глобально для всей системы.

## 28.32. Один владелец изменяющей задачи

Для операции с побочными эффектами существует только один действующий Lease generation.

Даже если сеть разделилась, два Worker не должны одновременно иметь законное право опубликовать один результат.

## 28.33. Split Brain — разделение системы

Сценарий: Primary потерял связь с Worker A, Worker A считает, что всё ещё работает, а Primary выдал задачу Worker B.

Для защиты применяются:

- Lease;
- generation;
- Fencing Token;
- operation_id.

Старый Worker не может законно завершить внешнее изменяющее действие после появления нового поколения.

## 28.34. Сетевая задержка не равна отказу

Система должна различать:

- медленный Worker;
- временный разрыв;
- настоящий отказ.

Для этого используются история, Heartbeat, Timeout, состояние процесса и повторные проверки.

## 28.35. Работа без связи

Worker может выполнять часть задачи автономно, если у него уже есть:

- TaskContract;
- Context;
- нужные Resources;
- действующее разрешение;
- локальные Tools.

Операции, требующие нового Security Decision или внешнего подтверждения, могут остановиться.

## 28.36. Возврат после offline

После восстановления связи Worker передаёт:

- своё состояние;
- выполненные этапы;
- ResultRef;
- EvidenceRef;
- текущий Lease generation.

Primary проверяет, результат ещё имеет право быть принят.

## 28.37. Не доверять отчёту Worker без проверки

После восстановления связи фраза «я всё сделал» не является достаточным доказательством.

Используется Evidence-first.

## 28.38. Очередь задач

Если Worker временно занят, задача может ждать в очереди.

Coworker учитывает:

- приоритет;
- прогноз времени ожидания;
- альтернативных Workers;
- стоимость переноса.

## 28.39. Backpressure — защита от перегрузки

Primary не должен бесконечно отправлять задачи перегруженному Worker.

Worker сообщает загрузку, очередь и ресурсные ограничения. Coworker снижает маршрутизацию на перегруженный узел.

## 28.40. Планирование распределённой задачи

Planning учитывает не только вычисление, но и:

- очередь Worker;
- сеть;
- загрузку данных;
- передачу Artifact;
- удалённый QA;
- вероятность разрыва.

## 28.41. Пример выбора

Worker A: 10 секунд вычисления + 40 секунд загрузки данных.

Worker B: 25 секунд вычисления, но данные уже локальны.

Итого Worker B быстрее. Planning должен видеть это.

## 28.42. Частичный TaskGraph

Сложная задача может распределяться:

- Task A → MAIN-PC;
- Task B → GPU-PC;
- Task C → SERVER;
- Task D собирает результаты.

Передаются ResultRef, а не полные истории Workers.

## 28.43. Параллельность

Независимые ветки TaskGraph могут выполняться одновременно.

Зависимые этапы ждут подтверждённый результат предыдущего этапа.

## 28.44. Удалённый QA

QA может выполняться на другом Worker. Это желательно для независимости.

QA получает:

- точную revision;
- OutputContract;
- Evidence;
- ResultRef.

## 28.45. Версии протокола

Каждый Node объявляет:

- версию KAT9I_OS;
- поддерживаемые версии контрактов;
- Worker protocol;
- capabilities.

Несовместимый Worker получает статус `INCOMPATIBLE`.

## 28.46. Обновление узлов

Не обязательно обновлять всё одновременно.

Можно:

1. обновить один Worker;
2. проверить;
3. сравнить Metrics;
4. обновить остальных.

Это соответствует Canary Update.

## 28.47. Primary обновляется осторожнее

Основной узел содержит критическое состояние.

До обновления:

- Checkpoint;
- Backup;
- DRAINING;
- сохранение Task State;
- проверка совместимости Workers.

## 28.48. Worker можно заменить

Worker считается вычислительным ресурсом.

Потеря одного Worker не должна означать потерю KAT9I_OS.

Если задача переносима, она назначается другому.

## 28.49. Primary первой версии один

На первом этапе не нужен сложный кластер с автоматическими выборами нового лидера.

Первая версия: один канонический Primary Node.

Это резко уменьшает сложность Consistency, Split Brain, Security, Storage и Recovery.

## 28.50. Не строить Kubernetes внутри KAT9I_OS

Не нужно заранее вводить сложные кластеры, распределённый Consensus, Kafka, Kubernetes или Service Mesh, если реальные задачи этого ещё не требуют.

Используется принцип минимально достаточной архитектуры.

## 28.51. Будущая Federation — федерация

В будущем несколько полноценных KAT9I_OS могут сотрудничать.

Каждая сохраняет собственные:

- Rules;
- Security;
- Knowledge;
- пользователей;
- Secrets.

## 28.52. Федерация не равна общей базе

Две KAT9I_OS не должны автоматически объединять Knowledge, Task State, Secrets или Personal Layer.

Они обмениваются только разрешёнными контрактами.

## 28.53. Делегирование между KAT9I_OS

Одна KAT9I_OS может передать другой TaskContract ограниченного Scope.

Получатель возвращает:

- ResultRef;
- Evidence;
- Metrics summary.

## 28.54. Доверие между системами

Для федерации нужен отдельный Trust relationship.

Например:

- TRUSTED_NODE;
- LIMITED;
- EXTERNAL;
- BLOCKED.

Trust не заменяет Security Decision конкретной операции.

## 28.55. Electron в распределённой системе

Основной Electron-клиент показывает всю доступную распределённую картину:

- узлы;
- Workers;
- сеть;
- задачи;
- очереди;
- задержки;
- версии;
- Trust;
- ошибки;
- текущие Lease;
- прогноз.

## 28.56. Карта сети

В режиме «Рентген KAT9I_OS» можно видеть MAIN-PC, GPU-PC, SERVER и текущие перемещения TaskContract, ContextRef, ResultRef, Artifact и Telemetry.

Секреты и чувствительное содержимое не отображаются.

## 28.57. Electron не является сетевым сервером доверия

Electron UI не должен самостоятельно:

- регистрировать Worker;
- выдавать Capability Grant;
- принимать сетевую Identity.

Он только инициирует пользовательское решение.

Фактическое действие выполняют Core + Security + Coworker.

## 28.58. Несколько Electron-клиентов

В будущем можно разрешить несколько UI-клиентов.

Но два открытых интерфейса не создают два Core. Они являются двумя представлениями одного канонического состояния.

## 28.59. Одновременные человеческие команды

Если два разрешённых интерфейса одновременно дают противоречащие команды, используются:

- actor;
- role;
- timestamp;
- decision_id;
- current task state;
- Security;
- optimistic concurrency / revision.

Не применяется принцип «кто последний нажал — тот и прав».

## 28.60. Публичный web-интерфейс

Если когда-нибудь понадобится web-доступ, он должен использовать те же системные контракты.

Основным штатным интерфейсом остаётся Electron.

Web может использоваться как:

- read-only монитор;
- удалённая облегчённая панель;
- публичная документация.

## 28.61. GitHub Pages

GitHub Pages используется для:

- публичной документации;
- обучения;
- архитектурного описания.

Он не является управляющим интерфейсом работающей локальной KAT9I_OS.

## 28.62. Логи распределённой системы

Не нужно собирать все полные Logs каждого Worker на Primary постоянно.

Primary получает:

- нужную Telemetry;
- Metrics;
- Evidence;
- ошибки;
- диагностические данные по запросу.

## 28.63. Локальная Telemetry Worker

Worker может временно буферизовать Telemetry.

После восстановления сети недостающие события передаются Primary.

## 28.64. Порядок событий

Распределённая система не доверяет только времени часов разных компьютеров.

Используются:

- event_id;
- sequence;
- generation;
- causation_id;
- revision.

## 28.65. Часы компьютеров

Синхронизация времени полезна.

Но критическое решение вроде «какой Lease новее» не должно зависеть исключительно от системных часов Windows.

## 28.66. Артефакты

Большой Artifact может оставаться на Worker, если:

- он доступен;
- защищён;
- ResultRef способен его разрешить;
- политика хранения это допускает.

Не обязательно автоматически копировать всё на Primary.

## 28.67. Важные результаты

Для важных результатов может действовать политика: после завершения перенести Artifact в канонический ResultSink.

Например:

- GitHub;
- Drive;
- локальное хранилище Primary.

## 28.68. Выключение Worker

Перед плановым выключением Worker переходит в `DRAINING`.

Новые задачи ему не выдаются.

Текущие завершаются, достигают Checkpoint либо передаются.

## 28.69. Сон Windows

Для настольных Workers нужно учитывать:

- Sleep;
- Hibernate;
- потерю сети;
- закрытие ноутбука.

Worker не должен считаться надёжно круглосуточным только потому, что сейчас ONLINE.

## 28.70. История доступности

Learning собирает статистику доступности узлов.

Например если ноутбук почти всегда выключается после 23:00, Planning может учитывать это при длинной задаче.

## 28.71. Энергия и стоимость

В будущем Scheduling может учитывать:

- энергопотребление;
- GPU;
- облачную стоимость;
- электричество;
- доступное время устройства.

Это не является P0 первой версии.

## 28.72. Минимальная первая реализация

Для первого рабочего варианта достаточно:

### Primary Node

Windows 11:

- Core;
- SQLite;
- Electron;
- локальные Workers.

### Remote Worker Runtime

На втором компьютере:

- Node Identity;
- Capability discovery;
- Heartbeat;
- TaskContract;
- Lease;
- Execution;
- ResultRef;
- Evidence.

### Без

- сложного Consensus;
- автоматического leader election;
- глобальной базы;
- Kubernetes;
- обязательного облака.

## 28.73. Первый реальный тест

Минимальный распределённый тест:

1. MAIN-PC создаёт задачу.
2. Planning оценивает локальный и удалённый вариант.
3. Coworker выбирает PC-2.
4. PC-2 получает TaskContract.
5. PC-2 выполняет локальный код.
6. На половине задачи сеть временно отключается.
7. Worker продолжает допустимый локальный этап.
8. Сеть возвращается.
9. Worker передаёт Evidence и ResultRef.
10. QA проверяет результат.
11. Electron показывает всю историю.

## 28.74. Тест потери Worker

Отдельный сценарий:

1. Worker получил Lease.
2. Worker исчез.
3. Heartbeat пропал.
4. Timeout истёк.
5. Primary проверил фактическое состояние.
6. Lease generation изменён.
7. Задача передана Worker B.
8. Worker A вернулся.
9. Его старое право публикации отклонено.

Это обязательный системный тест.

## 28.76. Самообучение распределённой системы

Learning может улучшать:

- выбор Worker;
- сетевые Timeout;
- Heartbeat;
- Lease;
- Queue policy;
- Source Affinity;
- Cache placement;
- предварительное размещение Resources;
- прогноз передачи данных.

Но не может:

- автоматически доверять новому узлу;
- ослаблять Security;
- отключать fencing ради скорости.

## 28.77. Что распределённая система не должна делать

Она не должна:

- автоматически доверять найденному компьютеру;
- раздавать полную SQLite Workers;
- копировать все Secrets;
- открывать публичные порты без разрешения;
- использовать IP как единственную Identity;
- запускать два владельца одной изменяющей операции;
- синхронизировать всё состояние между всеми узлами;
- считать потерю сети доказательством падения Worker;
- повторять внешнюю операцию без operation_id;
- строить сложный кластер до появления реальной необходимости.

## 28.78. Основные принципы

1. **Один компьютер является полноценной KAT9I_OS.**
2. **Распределённость добавляется постепенно.**
3. **Первая версия имеет один канонический Primary Node.**
4. **Electron является основным пользовательским интерфейсом Primary.**
5. **Удалённый Worker получает только минимально необходимые контракты и данные.**
6. **Worker не получает прямой доступ к внутренней базе Primary.**
7. **Обнаружение узла не означает доверие.**
8. **Сетевой обмен аутентифицирован и зашифрован.**
9. **Reference-first применяется и между компьютерами.**
10. **Данные по возможности обрабатываются рядом с источником.**
11. **Secrets не копируются без необходимости.**
12. **Lease + generation + fencing защищают изменяющие операции.**
13. **Система умеет работать при временном разрыве сети.**
14. **История Worker используется для адаптивных Timeout и Scheduling.**
15. **Planning учитывает сеть и очередь, а не только скорость CPU/GPU.**
16. **Несовместимые версии узлов не пытаются «договариваться» через ИИ.**
17. **Утрата отдельного Worker не должна означать утрату KAT9I_OS.**
18. **Сложный распределённый Consensus не нужен первой версии.**

## 28.79. Главный принцип

> **KAT9I_OS должна начинаться как простая локальная система на одном компьютере, но иметь такие контракты, Identity, Lease и механизмы безопасности, чтобы дополнительные компьютеры можно было подключать как вычислительные ресурсы без передачи им всей системы, всех данных и всех полномочий.**
