# 29. Пользовательский интерфейс KAT9I_OS на Electron

## 29.1. Назначение

Основной пользовательский интерфейс KAT9I_OS — настольное приложение на Electron.

Electron объединяет в одном приложении управление задачами, визуализацию процессов, Workers, Knowledge, настройки, диагностику, безопасность, самообучение, прогнозирование, документацию и обучение новых пользователей и коворкеров.

Пользователю не должно требоваться открывать несколько отдельных программ, чтобы понять состояние KAT9I_OS.

## 29.2. Главный принцип

Electron показывает систему и позволяет человеку взаимодействовать с ней, но не становится самой системой управления.

Core, Security, Rule Manager, Coworker, Execution и другие системные модули сохраняют собственную ответственность.

## 29.3. Архитектурная граница Electron

Логическая схема:

Renderer — интерфейс → Preload — ограниченный мост → IPC / локальный API → KAT9I_OS Core.

Renderer не должен напрямую получать полный доступ к файловой системе, Shell, секретам, SQLite, Git, Worker Runtime и системным процессам.

## 29.4. Renderer

Renderer — процесс отображения интерфейса — отвечает только за страницы, кнопки, графики, схемы, формы, анимации, документацию и пользовательское взаимодействие.

Он работает как изолированное веб-приложение внутри Electron.

## 29.5. Main Process

Main Process — главный процесс Electron — отвечает за оболочку приложения: окна, системный трей, жизненный цикл Electron, безопасное создание Renderer, обновление интерфейса, системные уведомления и разрешённое взаимодействие с Core.

Main Process не должен становиться заменой Core.

## 29.6. Preload

Preload — ограниченный мост между интерфейсом и системными возможностями — предоставляет Renderer только заранее определённые методы.

Например логически: получить список задач, открыть Task, запросить остановку, получить Metrics, открыть документацию.

Не допускается универсальный маршрут вида «выполни любой Shell-код, который передал Renderer».

## 29.7. Все управляющие действия проходят обычный путь

Если пользователь нажимает «Остановить задачу», Electron не останавливает процесс напрямую.

Правильный путь:

Electron → Identity → Rules → Security → Core → Execution.

То же относится к удалению, публикации, выдаче прав, подключению Worker и изменению критической настройки.

## 29.8. Основное меню

Первая версия должна иметь понятные разделы:

1. Главная
2. Задачи
3. Исполнители
4. Процессы
5. Знания
6. Ресурсы
7. Расходы
8. Самообучение
9. Безопасность
10. Диагностика
11. Документация
12. Настройки

Названия интерфейса по умолчанию — на русском языке.

## 29.9. Главная страница

Главная должна отвечать максимум за несколько секунд: всё нормально или есть проблема?

Показываются состояние KAT9I_OS, активные задачи, Workers, ошибки, запросы решения человека, прогноз нагрузки, текущие расходы и последние результаты.

## 29.10. Не превращать главную в приборную панель самолёта

По умолчанию показывается только важное.

Например: 3 задачи выполняются; 2 Worker свободны; ошибок нет; ожидаемое завершение ближайшей задачи — 4 минуты.

Подробности доступны по раскрытию.

## 29.11. «Я здесь впервые»

В интерфейсе должна быть отдельная кнопка «Я здесь впервые».

Она запускает очень простой вводный режим.

## 29.12. Уровень объяснения для ребёнка

Первое объяснение:

KAT9I_OS помогает раздавать работу людям и программам, следить, чтобы они сделали её правильно, и запоминать полезный опыт.

Без терминов orchestration, dependency injection, event sourcing и federation.

## 29.13. Пошаговый первый вход

Режим новичка объясняет:

1. Что такое KAT9I_OS?
2. Что такое задача?
3. Кто такой Worker?
4. Как система проверяет результат?
5. Как посмотреть, что происходит?
6. Как задать вопрос или предложить улучшение?

После этого человек уже может пользоваться системой.

## 29.14. Обучение не должно быть отдельной копией документации

Обучающий интерфейс использует канонические Markdown, словарь, Module Registry и схемы контрактов.

Он не содержит независимые версии архитектурных фактов.

## 29.15. Уровни подробности

В документации и объяснениях используются пять уровней:

1. Очень просто — для человека без технических знаний.
2. Просто — что это, зачем нужно и как использовать.
3. Рабочий — достаточно коворкеру для выполнения задач.
4. Технический — контракты, модули, состояния, безопасность.
5. Максимум — крайние случаи, Recovery, Evidence, протоколы, детали реализации.

## 29.16. Один глобальный переключатель подробности

В верхней части документации: «Подробность: Очень просто / Просто / Рабочий / Технический / Максимум».

Настройка применяется ко всей документации.

Пользователю не нужно выбирать уровень заново на каждой странице.

## 29.17. Глобальные переключатели отображения

Дополнительно:

- Показывать примеры;
- Показывать схемы;
- Показывать технические детали;
- Показывать крайние случаи;
- Показывать Evidence.

Это позволяет быстро читать только необходимое.

## 29.18. Примеры сворачиваемые

Каждый пример можно раскрыть отдельно, свернуть отдельно и подчинить глобальной настройке «Показывать примеры».

Если примеры отключены, основной текст остаётся цельным и понятным.

## 29.19. Не повторять основной текст внутри примеров

Пример должен показывать применение правила.

Он не должен ещё раз пересказывать весь раздел другими словами.

## 29.20. Единый словарь

Технические термины берутся из канонического словаря.

Например пользователь видит Lease. При наведении: «Временное право Worker выполнять конкретную задачу».

По переходу можно открыть подробное техническое определение.

## 29.21. Быстрые подсказки

Если пользователь впервые видит Worker, TaskContract, ResultRef, Cache или Scope, Electron может показать небольшую подсказку.

После изучения подсказки не должны постоянно мешать работе.

## 29.22. Задачи

Экран «Задачи» показывает активные, ожидающие, требующие решения, заблокированные, завершённые и ошибочные задачи.

По умолчанию пользователь видит понятные статусы на русском.

## 29.23. Карточка задачи

Минимально показываются:

- что делаем;
- кто делает;
- состояние;
- сколько уже заняло;
- сколько примерно осталось;
- стоимость;
- результат;
- нужна ли помощь пользователя.

## 29.24. Технический режим карточки

По раскрытию доступны task_id, TaskContract, TaskGraph, RulesRef, Context Manifest, Worker, Provider Route, Lease, Evidence, Metrics и QA.

## 29.25. TaskGraph

Сложная задача визуализируется графом.

Пользователь видит, что уже готово, что выполняется, что ждёт, что заблокировано и какие ветки идут параллельно.

## 29.26. Анимация процессов

При необходимости можно буквально видеть, как задача перемещается от одного модуля к другому, например Context → Planning → Inference → Coworker → Execution → QA.

Это особенно полезно при обучении и диагностике.

## 29.27. Возможность отключить анимацию

Анимация не должна быть обязательной.

Пользователь может выбрать полную, минимальную или выключенную.

Отключение анимации не влияет на работу KAT9I_OS.

## 29.28. Экран Workers

Для каждого Worker показываются имя, тип, компьютер, состояние, возможности, текущая задача, очередь, загрузка, Trust, версия и история успешности.

## 29.29. Простое отображение Worker

Для новичка: «GPU-PC — свободен» или «Codex Worker — выполняет задачу #184».

Не нужно сразу показывать Lease generation или P95 latency.

## 29.30. Карта компьютеров

Для распределённой системы показываются Primary, локальные Workers, удалённые Nodes, состояние связи и текущая работа.

В режиме диагностики видны маршруты передачи задач и данных.

## 29.31. Экран прогнозирования

До выполнения человек может увидеть ожидаемое время, внешние токены, ожидаемую стоимость, вероятность Cache Hit и вероятность успеха с первого прохода.

## 29.32. Прогноз и факт различаются визуально

Нельзя смешивать прогноз и уже потрачено.

Например: прогноз — 8 минут; факт — 4:21; осталось — примерно 3 минуты.

## 29.33. После завершения

Показывается прогноз, факт и ошибка прогноза.

Это делает Forecasting наблюдаемым.

## 29.34. Экран расходов

Отображаются токены, API, подписочные вызовы, HIGH, Local, Cache saving, время, стоимость задач и проектов.

## 29.35. Не изображать локальную работу как «бесплатную»

Можно отдельно показывать внешнюю стоимость €0, но локальная работа всё равно имеет время, CPU, GPU, электроэнергию и ресурсы устройства.

## 29.36. Экран знаний

Пользователь может искать Knowledge, видеть источники, доверие, связь с проектом и понимать, откуда знание появилось.

## 29.37. Knowledge не редактируется как бесконтрольный текст

Если пользователь меняет подтверждённую запись, создаётся структурированное изменение с Provenance.

## 29.38. Экран самообучения

Learning должен быть визуально прозрачным.

Например: «Обнаружено: Worker X регулярно получает ложный Timeout. Предложение: изменить 30 → 34 сек только для GitHub-задач Worker X. Наблюдений: 86. Ожидаемый эффект: −12% лишних повторов.»

## 29.39. История самообучения

Можно посмотреть, что система заметила, что предложила, что было принято, что изменилось, помогло ли изменение и выполнялся ли Rollback.

## 29.40. Пользователь может ограничить Learning

Через интерфейс можно отключить адаптацию параметра, зафиксировать значение, вернуть default или задать диапазон, но только в рамках полномочий пользователя.

## 29.41. Экран безопасности

Показывает заблокированные операции, Scope violations, Prompt Injection, попытки доступа, ADMIN Approval, отозванные Grants и подозрительные Integrations.

## 29.42. Безопасность простыми словами

Вместо SECURITY_DENY_SCOPE_EXCEEDED обычному пользователю: «Исполнитель хотел изменить файл, который не входит в эту задачу. Действие заблокировано.»

Технический код остаётся доступен по раскрытию.

## 29.43. Секреты не показываются

UI не отображает значения токенов, паролей, API-ключей и приватных ключей.

Можно показывать «GitHub: подключён», но не сам credential.

## 29.44. Диагностика

Экран диагностики отвечает на вопрос «почему сейчас что-то не работает?».

Проверяются Core, Storage, Rules, Security, Workers, Models, Git, Integrations, Cache, Recovery и Electron.

## 29.45. Диагностика несколькими уровнями

Просто: GitHub недоступен.

Рабочий: авторизация GitHub не прошла.

Технический: adapter, error class, operation_id, timestamp, Evidence.

## 29.46. Режим «Рентген KAT9I_OS»

Отдельный режим максимальной детализации показывает модули, вызовы, контракты, TaskGraph, Worker, Provider, Context, ResourceRef, Cache, Rules, Security, Telemetry, Metrics и Evidence.

## 29.47. Рентген нужен разработчикам, а не всем

По умолчанию обычный пользователь не видит весь внутренний поток.

Режим включается отдельно.

## 29.48. Replay

Для завершённой задачи можно нажать «Показать, как выполнялась задача».

Electron воспроизводит сохранённые структурированные события. Это не видео.

## 29.49. Временная шкала

Replay показывает начало, этапы, Worker, ожидание, Retry, ошибки, USER Decision, QA и завершение.

## 29.50. Документация внутри Electron

Полная документация доступна прямо в приложении.

Она строится из тех же канонических Markdown, что используются для GitHub.

Таким образом нет отдельной документации Electron.

## 29.51. GitHub Pages и Electron используют один источник

Схема:

канонические Markdown + схемы + словарь → генератор → Electron Docs и GitHub Pages.

Ни одна HTML-версия не редактируется вручную как источник истины.

## 29.52. Поиск по документации

Поиск должен работать локально.

Приоритет: обычный текстовый индекс → локальный семантический индекс → ИИ только если действительно нужен.

## 29.53. Связь документации с реальной системой

Из описания модуля можно перейти «Открыть этот модуль в Рентгене», а из ошибки — «Что означает эта ошибка?».

Это связывает обучение и реальную эксплуатацию.

## 29.54. GitHub-обучение

В Electron должен быть раздел «Как мы разрабатываем KAT9I_OS через GitHub» с реальными примерами проекта: Issue, ветка, Commit, PR, QA, Merge, Release.

## 29.55. Объяснение GitHub для ребёнка

Issue — записка «что нужно сделать».

Branch — отдельный стол, где можно работать, не ломая основной проект.

Commit — сохранённый шаг.

PR — «Я закончил. Проверьте мою работу».

QA — другой человек проверяет.

Merge — проверенная работа становится частью проекта.

## 29.56. Обратная связь

В Electron должна быть кнопка «Задать вопрос / предложить улучшение».

Она помогает оформить структурированное обращение.

При наличии GitHub создаётся разрешённый Issue через существующую русскую форму или API.

## 29.57. Человеку не нужно знать внутренние labels

Пользователь пишет «Я не понимаю эту кнопку».

KAT9I_OS может помочь классифицировать обращение.

Пользователю не нужно выбирать P1, component/ui, severity или milestone.

## 29.58. Настройки

Настройки группируются по смыслу: Общие, Интерфейс, AI, Workers, Integrations, Privacy, Security, Learning, Notifications, Storage, Updates.

## 29.59. Настройка не равна Rule

UI должен явно различать предпочтение и обязательное правило безопасности.

Недоступное из-за Policy поле показывается как заблокированное с объяснением причины.

## 29.60. Не показывать невозможные настройки

Если система не имеет GPU, не нужно занимать главный интерфейс десятком GPU-настроек.

Используется Progressive Disclosure.

## 29.61. Notifications — уведомления

Electron может показывать системные уведомления о завершении задачи, ошибке, USER Decision, ADMIN Approval и Critical Security Event.

Не каждое событие Telemetry становится уведомлением.

## 29.62. Центр уведомлений

В приложении хранится понятная очередь: требует действия, предупреждение, информация.

Критичность определяется системой, а не декоративным цветом UI.

## 29.63. Системный трей

Tray может показывать состояние, число активных задач, ошибки, быстрый переход в приложение и безопасную команду остановки.

## 29.64. Emergency Stop

Аварийная остановка должна быть доступна быстро.

Но UI только инициирует Emergency Stop Command.

Фактическое действие проходит через системный контур безопасности.

## 29.65. Состояние OFFLINE

Если интернет пропал, Electron продолжает показывать локальные задачи, Workers, Knowledge, Cache, Metrics и документацию.

Внешние Integrations получают понятный статус OFFLINE.

## 29.66. Состояние DEGRADED

Если сломана одна Integration, интерфейс показывает конкретно «GitHub недоступен», а не «KAT9I_OS сломана».

## 29.67. Восстановление интерфейса

После перезапуска Electron UI получает свежий Snapshot, затем подписывается на новые события.

Не требуется воспроизводить всю историю системы с начала.

## 29.68. Производительность

Визуализация не должна мешать выполнению задач.

Нужно измерять CPU, RAM, GPU UI, задержку Renderer, размер событий, частоту обновления, потерянные frames и время запуска.

## 29.69. Агрегация событий

Если Worker создаёт тысячу однотипных событий, UI не обязан рисовать тысячу отдельных анимаций.

Локальный агрегатор может показать «1 247 операций чтения».

## 29.70. Виртуализация больших списков

Большие Task history, Logs, Workers и Events не должны полностью одновременно рендериться в DOM.

UI должен масштабироваться на большие истории.

## 29.71. Примерно нулевой расход LLM

Обычная работа Electron должна потреблять примерно 0 дополнительных LLM-токенов.

ИИ не нужен для рисования графика, фильтра, сортировки, подсчёта, отображения TaskGraph и обычной документации.

## 29.72. ИИ в интерфейсе

ИИ можно использовать для объяснения сложной ошибки, поиска по смыслу, помощи в формулировке Issue и анализа аномальной ситуации, но как отдельную разрешённую функцию.

## 29.73. Безопасность Renderer

Renderer считается менее доверенной зоной, чем Core.

Он не должен получать широкие системные полномочия.

## 29.74. Изоляция контекста Electron

Для Renderer должна использоваться изоляция контекста.

Интерфейс получает только ограниченный API через безопасный мост.

## 29.75. Node.js не выдаётся Renderer без необходимости

Прямой широкий доступ Renderer к Node.js должен быть запрещён по умолчанию.

## 29.76. Удалённый контент

Произвольная внешняя web-страница не должна загружаться в привилегированный Renderer KAT9I_OS.

Внешние ссылки предпочтительно открывать отдельно безопасным способом.

## 29.77. Content Security Policy

Electron-приложение должно иметь строгую политику разрешённого содержимого.

Это снижает риск выполнения внедрённого кода в интерфейсе.

## 29.78. IPC должен быть узким

Запрещён универсальный IPC вида «вызови любую функцию с любыми параметрами».

Каждое опасное действие получает отдельный проверяемый системный маршрут.

## 29.79. Валидация IPC

Даже сообщение из собственного Renderer не считается автоматически безопасным.

Проверяются schema, type, Scope, Identity и актуальное состояние.

## 29.80. DevTools

В режиме разработки DevTools доступны.

В обычной сборке доступ регулируется политикой.

DevTools не должны превращаться в способ обхода Security Core.

## 29.81. Ошибка Renderer не равна ошибке Core

Если интерфейс упал, задача продолжает безопасную работу, состояние сохраняется, Electron можно перезапустить.

Это важная архитектурная граница.

## 29.82. Обновление Electron

Оболочка обновляется через общий Workflow обновления KAT9I_OS: проверка версии, Backup критического состояния, совместимость, обновление, Health Check и Rollback.

## 29.83. UI Version

Интерфейс имеет собственную версию сборки, но должен знать совместимость с Core, schema и contracts.

Несовместимый UI не пытается «угадать» структуру данных.

## 29.84. Accessibility — доступность

Интерфейс должен учитывать масштабирование текста, управление клавиатурой, контраст, системные настройки масштабирования Windows и понятные текстовые статусы помимо цвета.

## 29.85. Цвет не является единственным сигналом

Нельзя показывать красный = ошибка без текста или символа.

Пользователь должен видеть «Ошибка: GitHub недоступен».

## 29.86. Состояния загрузки

UI должен отличать: данные загружаются, данных нет, ошибка получения, модуль недоступен, доступ запрещён.

Пустой экран недопустим как универсальное состояние.

## 29.87. Самообучение интерфейса

Learning может анализировать часто используемые экраны, уровень подробности, скрываемые блоки и полезность предупреждений.

Это используется преимущественно как Preferences.

## 29.88. Learning не может скрыть критическое

Если пользователь обычно закрывает Security warning, Learning не получает права автоматически перестать его показывать.

## 29.89. Персональные макеты

В дальнейшем пользователь может настроить порядок панелей, избранные Metrics, стартовый экран и уровень подробности.

Это Personal Preference, а не изменение архитектуры.

## 29.90. Роли интерфейса

Разные пользователи могут видеть разные возможности:

- USER — обычная работа;
- ADMIN — права, Security, критические настройки;
- разработчик — диагностические возможности согласно разрешениям.

Роль интерфейса не создаёт права сама по себе.

## 29.91. Electron и Telegram

Electron — полный центр управления.

Telegram — карманный канал взаимодействия.

Telegram может сообщить «Задача требует решения», а кнопка «Открыть подробнее» может вести в Electron.

## 29.92. Electron и GitHub

Electron может показывать Issue, PR, QA, Actions и Releases.

Но GitHub остаётся внешним источником истины соответствующих объектов.

Electron не создаёт собственную независимую копию GitHub Project.

## 29.93. Один источник истины

Electron никогда не становится самостоятельным владельцем тех данных, которые он только отображает.

Он показывает Task State из Core, Metrics из Metrics, Knowledge из KB, GitHub state из GitHub, Rules из Rule Manager.

## 29.94. Кэш интерфейса

UI может иметь локальный presentation cache.

Но он используется только для скорости отображения.

При конфликте побеждает актуальное системное состояние.

## 29.95. История действий пользователя

Значимые управляющие действия пользователя создают структурированные события: кто, что, над чем, результат.

Не требуется записывать каждое перемещение мыши.

## 29.96. Интерфейс для разработки самой KAT9I_OS

Со временем Electron может стать рабочей средой управления разработкой самой системы: GitHub backlog, PR, Workers, QA, CI, Releases, архитектурные Issues.

Получается: KAT9I_OS помогает строить KAT9I_OS.

## 29.97. Минимальная первая версия Electron

P0:

1. запуск приложения;
2. связь с Core;
3. Главная;
4. Задачи;
5. Workers;
6. Task details;
7. TaskGraph;
8. Metrics;
9. Diagnostics;
10. Docs;
11. Settings;
12. System Tray.

Не нужно пытаться сразу реализовать все будущие красивые визуализации.

## 29.98. Второй этап

После рабочей P0:

- Replay;
- Рентген;
- Learning UI;
- Security dashboard;
- Network map;
- Forecast visualization;
- интерактивный onboarding;
- GitHub cockpit.

## 29.99. Тестирование Electron

Минимально проверяются запуск, закрытие, Tray, восстановление окна, потеря Core, потеря сети, большой TaskGraph, большой поток Telemetry, Renderer crash, запрещённый IPC, попытка доступа к секрету, обновление и восстановление после обновления.

## 29.100. Метрики интерфейса

Нужно измерять Startup Time, Renderer Crash Rate, UI Latency, Memory Usage, CPU Usage, Event Rendering Delay, Dropped Event Count, время поиска документации, время до нахождения ошибки и использование уровней подробности.

## 29.101. Что Electron не должен делать

Electron не должен:

- становиться вторым Core;
- иметь собственный Rule Manager;
- напрямую изменять TaskRuntimeState;
- выполнять Shell из Renderer;
- читать Secret Store напрямую;
- хранить вторую Базу знаний;
- создавать отдельную Telemetry;
- редактировать независимую HTML-копию документации;
- обходить Security через IPC;
- прекращать работу Core только потому, что закрыто окно;
- требовать LLM для обычной визуализации.

## 29.102. Основные принципы

1. Electron — основной пользовательский интерфейс KAT9I_OS.
2. Core и Electron имеют разные ответственности.
3. Renderer изолирован от системных полномочий.
4. Все управляющие действия проходят Core, Rules и Security.
5. Интерфейс русский по умолчанию.
6. Новичок должен понять систему без технической подготовки.
7. Документация имеет пять глобальных уровней подробности.
8. Примеры и дополнительные детали можно глобально скрывать.
9. Один источник истины используется и для Electron Docs, и для GitHub Pages.
10. Прогноз и факт всегда визуально разделяются.
11. Learning отображается прозрачно.
12. Секреты никогда не выводятся в UI.
13. Рентген и Replay строятся по структурированным данным.
14. UI должен потреблять примерно ноль дополнительных LLM-токенов в обычной работе.
15. Закрытие или сбой Renderer не должны ломать Core.
16. Electron может стать рабочим центром разработки самой KAT9I_OS.

## 29.103. Главный принцип

KAT9I_OS должна выглядеть просто для новичка и одновременно позволять специалисту раскрыть систему до уровня конкретного контракта, Worker, Evidence и события — при этом оба человека смотрят на одно и то же каноническое состояние, а не на разные версии системы.
