# 30. Версии, выпуски и жизненный цикл KAT9I_OS

## 30.1. Назначение

Этот раздел определяет, как понять, какая версия KAT9I_OS установлена, насколько она стабильна, с чем совместима, как выпускается новая версия и как безопасно вернуться назад.

Версия должна быть не красивой надписью, а точным идентификатором проверенного состояния системы.

## 30.2. Основная версия приложения

Для KAT9I_OS используется Semantic Versioning — семантическое версионирование.

Формат: `MAJOR.MINOR.PATCH`.

## 30.3. Значение версий

MAJOR — большое несовместимое изменение.
MINOR — новая совместимая функциональность.
PATCH — исправление без изменения основного поведения.

## 30.4. До версии 1.0

Версии `0.x.y` означают, что система развивается до первого стабильного публичного контракта. Даже до `1.0.0` значимые несовместимые изменения должны объявляться явно.

## 30.5. Что означает 1.0.0

`KAT9I_OS 1.0.0` означает первую стабильную эксплуатационную архитектуру с проверенными контрактами, Core, Electron, Security, Task execution, независимым QA, Recovery, Storage, Metrics, обновлением, Rollback и хотя бы одной полноценной end-to-end вертикалью.

## 30.6. Версия продукта и Git revision

Версия удобна человеку, commit SHA является точным техническим идентификатором исходного состояния. Они сохраняются вместе.

## 30.7. Раздельные версии

KAT9I_OS отдельно знает версию приложения, commit SHA, версии TaskContract и внутренних контрактов, Worker Protocol, Storage schema, config schema, Electron UI и критичных модулей.

## 30.8. Release Manifest

Каждый официальный выпуск имеет машинно-читаемый Release Manifest — паспорт версии.

Минимально: product_version, commit_sha, build_id, release_channel, contract_versions, worker_protocol_version, storage_schema_version, config_schema_version, Electron version, минимально совместимые Workers, дата сборки, EvidenceRef и QA Result.

## 30.9. Назначение Release Manifest

Electron, Core, Workers и Update Manager автоматически используют Manifest для проверки совместимости.

## 30.10. Каналы стабильности

DEV — текущая разработка.
ALPHA — основная идея работает, возможны крупные изменения.
BETA — архитектура в основном сформирована и проходит реальную эксплуатационную проверку.
RC — кандидат в выпуск, основной режим — поиск дефектов.
STABLE — проверенная версия для обычного использования.

## 30.11. Предварительные версии

Допускаются версии вида `0.8.0-beta.2` и `1.0.0-rc.1`, после подтверждения — `1.0.0`.

## 30.12. DEV не является Release

Каждый commit в `main` не объявляется официальным выпуском. Официальный выпуск требует Git tag, GitHub Release, Release Manifest и Evidence.

## 30.13. Git tag

Каждый официальный выпуск получает тег вида `v0.5.0`, указывающий на точный commit.

## 30.14. Опубликованный тег не переписывается

После публикации `v1.0.0` всегда означает ту же revision. Исправление создаёт `v1.0.1`.

## 30.15. GitHub Release

GitHub Release является официальной карточкой выпуска и содержит версию, Release Notes, tag, установочные файлы, контрольные суммы, известные проблемы, требования и сведения о миграции.

## 30.16. Release Notes

Основные разделы: что нового, что исправлено, что изменилось, есть ли несовместимость, требуется ли действие пользователя, известные проблемы.

## 30.17. Технические подробности

Техническая детализация доступна отдельно через PR, Issues, schemas, migrations и Evidence. Обычному пользователю не нужно читать все commit messages.

## 30.18. Язык выпусков

Основные Release Notes публикуются на русском языке. Технические идентификаторы сохраняются без перевода.

## 30.19. Воспроизводимая сборка

Release строится из точного commit через воспроизводимый Workflow: зависимости → тесты → build → package → validation → checksum/signature → Release Artifact.

## 30.20. Release Artifact

Для Windows основным Artifact может быть установщик, portable-пакет или update package. Конкретный формат выбирается при реализации.

## 30.21. Связь бинарной сборки с исходниками

Для любого бинарного Release должно быть возможно определить исходный commit.

## 30.22. Build ID

Сборка может иметь отдельный build_id. Официальный стабильный Release должен оставаться однозначным.

## 30.23. Quality Gate перед Release

Официальный выпуск невозможен до успешного прохождения обязательных проверок: структура, contracts, unit и integration tests, Security, migrations, Recovery, Electron smoke tests, независимый QA и Release build validation.

## 30.24. PASS относится к точному Release commit

Если commit изменился после QA, прежний QA не подтверждает новую revision.

## 30.25. Release Candidate

После появления RC новые крупные функции обычно не добавляются. Допустимы исправления, документация, тесты и безопасные корректировки. Существенная новая функция запускает новый RC-цикл.

## 30.26. Пример RC

`1.0.0-rc.1` → исправление Recovery → `1.0.0-rc.2` → после прохождения обязательных проверок `1.0.0`.

## 30.27. Версии контрактов

Системные контракты имеют собственные версии и не обязаны увеличиваться при каждом PATCH продукта.

## 30.28. Версия контракта меняется только при изменении контракта

UI-исправление не меняет TaskContract. Несовместимое изменение обязательного поля требует новой версии контракта.

## 30.29. Совместимые изменения контрактов

Совместимое расширение допускается только при подтверждении тестами конкретной схемы.

## 30.30. Breaking Contract Change

Несовместимое изменение получает новую версию, migration/adaptation plan, проверку потребителей и запись в Release Notes.

## 30.31. Worker Protocol

Worker при соединении объявляет runtime version, protocol version, supported contracts и capabilities. Coworker проверяет совместимость до назначения задачи.

## 30.32. Матрица совместимости

Совместимость Core и Worker определяется детерминированно, включая adapter-режимы и статус INCOMPATIBLE. Модель не угадывает совместимость.

## 30.33. Версия схемы данных

Storage имеет отдельную `schema_version`, не обязанную совпадать с версией продукта.

## 30.34. Миграция схемы

Обновление схемы выполняется последовательностью детерминированных миграций с проверкой каждого шага.

## 30.35. Неизвестная новая схема

Core, не понимающий schema version, не работает приблизительно: BLOCKED, upgrade required либо Recovery/Rollback.

## 30.36. Совместимость Electron

Electron UI проверяет совместимость Core API, contracts и Visualization Snapshot. Несовместимый UI не угадывает структуру данных.

## 30.37. Feature Flags

Новые функции могут вводиться постепенно через управляемые Feature Flags.

## 30.38. Feature Flag не обходит Security

Переключатель функции не может отключать обязательные Security-проверки.

## 30.39. Experimental Features

Экспериментальная функция явно обозначается и не считается стабильной частью контракта.

## 30.40. Deprecation

Важная функция проходит состояния `SUPPORTED → DEPRECATED → REMOVED`.

## 30.41. Предупреждение об устаревании

Electron должен показывать понятное предупреждение о будущей потере поддержки старого Worker или протокола.

## 30.42. Не поддерживать всё бесконечно

Удаление поддержки допустимо, но должно быть явным, документированным и прогнозируемым.

## 30.43. Update Manager

Специализированный системный компонент отвечает за обнаружение версии, проверку источника, совместимость, Backup, установку, migrations, Health Check и Rollback.

## 30.44. Update Manager не заменяет Security

Разрешение на обновление определяется Rules, Security, Update Policy и ADMIN Approval, если требуется.

## 30.45. Проверка новой версии до установки

До обновления оцениваются текущая и целевая версии, Breaking Changes, migrations, совместимость Workers, требуемый диск, время и риск.

## 30.46. Прогноз обновления

Planning формирует Update Estimate: время, размер, перезапуски, миграции, риск и Rollback.

## 30.47. DRAINING

Перед значимым обновлением новые изменяющие задачи временно не принимаются, активные доходят до безопасного Checkpoint.

## 30.48. Backup

Перед рискованным обновлением создаётся Backup критического состояния, связанный с конкретным обновлением.

## 30.49. Rollback Point

Точка возврата связывает старый код, schema, config, Task State и Backup.

## 30.50. Rollback

При провале обязательного Health Check выполняется возврат к совместимой предыдущей версии.

## 30.51. Rollback целостный

Нельзя откатить только EXE и оставить несовместимую базу. Учитываются приложение, schema, configuration, contracts и Task State.

## 30.52. Автоматический Rollback

Для заранее определённых критичных ошибок — Core startup failure, Storage integrity FAIL, Security subsystem FAIL, mandatory migration FAIL — автоматический откат предпочтительнее ремонта на месте.

## 30.53. Частичный сбой

Необязательная сломанная Integration может привести к DEGRADED без полного Rollback.

## 30.54. Canary Update

При нескольких Workers новая версия сначала может ставиться на один узел с проверкой Metrics, compatibility и Recovery.

## 30.55. Stable Channel

Обычный пользователь по умолчанию получает STABLE.

## 30.56. Beta Channel

BETA включается добровольно и означает повышенный риск в обмен на ранний доступ.

## 30.57. Dev Channel

DEV предназначен преимущественно для разработки и не включается обычному пользователю случайно.

## 30.58. Переход между каналами

Переходы между каналами должны учитывать совместимость схем и возможность downgrade migration либо Backup restore.

## 30.59. Автоматическая проверка обновлений

Проверка наличия новой версии может быть автоматической, но обнаружение не означает автоматическую установку.

## 30.60. Update Policy

Используются ранее принятые режимы MANUAL, NOTIFY, SAFE_AUTO и CONTROLLED_AUTO без дублирования их отдельного смысла.

## 30.61. Security Update

Критическое Security-исправление маркируется отдельно и ясно объясняется в Electron.

## 30.62. Emergency Release

Срочный PATCH не отменяет минимальные build, Security, regression, QA и Evidence.

## 30.63. Release Evidence

Для каждого официального выпуска сохраняются commit, Quality Gate, тесты, QA, build checks, checksums, migration tests и Release Manifest.

## 30.64. Release как результат

Официальный Release является отдельным ResultRef с EvidenceRef, подтверждающим публикацию именно проверенной revision.

## 30.65. Повторная сборка

Повреждённый Artifact не заменяется незаметно под тем же стабильным Release; используется новая исправляющая версия либо управляемая процедура до финальной публикации.

## 30.66. Draft Release

До публикации можно подготовить tag, Release Notes, Artifacts, Manifest и проверки, но такой выпуск ещё не считается STABLE.

## 30.67. Milestone и Release

Milestone описывает план версии, но фактически выпущенное состояние определяется Git tag + Release + Manifest.

## 30.68. Issue и версия

Issue может иметь целевую версию, но Release Gate определяется обязательностью требования, а не только количеством закрытых Issues.

## 30.69. Release Gate

Перед публикацией проверяется выполнение всех обязательных требований конкретной версии.

## 30.70. Критерии v0.1

v0.1 должна доказать минимальный живой каркас: Core запускается, Electron подключается, TaskContract существует, одна локальная задача проходит полный жизненный цикл, Telemetry работает, результат сохраняется.

## 30.71. Следующие рабочие версии

Дальнейшие версии добавляют реальные вертикали: GitHub workflow, независимый QA, Recovery, Planning, remote Worker. Версии отмечают эксплуатационные этапы, а не произвольное число commit.

## 30.72. Критерии 1.0

Перед 1.0 обязательны целостный Core, стабильные базовые контракты, Rule Manager, Security, Context, Resources, Inference, Coworker, Execution, QA, Recovery, Storage, Metrics, базовый Learning, Electron, безопасное обновление, Rollback, документация и реальный end-to-end dogfood.

## 30.73. Dogfood

Перед 1.0 KAT9I_OS должна реально использоваться в собственной разработке по цепочке `Issue → Task → Worker → PR → QA → Merge → Metrics`.

## 30.74. Release Dashboard

Electron показывает текущую версию, канал, commit, доступное обновление, Breaking Changes, состояние Workers, Backup status и прогноз обновления.

## 30.75. История версий

Пользователь может получить компактную разницу между установленной и новой версией.

## 30.76. Learning и Releases

Learning анализирует ошибки обновлений, Rollback, нестабильные модули, длительность migrations и проблемы Worker versions, но не имеет права объявлять версию STABLE.

## 30.77. Метрики выпусков

Минимально: Release Failure Rate, Rollback Rate, Upgrade Success Rate, Migration Failure Rate, Post-release Regression Rate, Mean Upgrade Time, Recovery after Upgrade и Canary Failure Rate.

## 30.78. Один источник версии

Номер версии имеет один канонический источник, который используют build, Electron, Release, About screen и Manifest.

## 30.79. Что система версий не должна делать

Не переписывать опубликованные теги; не объявлять любой commit Release; не смешивать product и schema version; не скрывать Breaking Changes; не угадывать совместимость; не объявлять STABLE без Evidence; не выполнять рискованное обновление без Rollback strategy; не использовать LLM вместо детерминированной migration.

## 30.80. Основные принципы

1. Версия KAT9I_OS использует MAJOR.MINOR.PATCH.
2. Версия продукта и commit SHA сохраняются вместе.
3. Контракты, Storage schema и Worker Protocol имеют собственные версии.
4. Официальный Release привязан к точному Git tag.
5. Опубликованная версия не переписывается задним числом.
6. Release Manifest описывает техническую совместимость выпуска.
7. DEV, ALPHA, BETA, RC и STABLE имеют разный уровень доверия.
8. QA и Evidence относятся к точному Release commit.
9. Breaking Change всегда объявляется явно.
10. Workers проверяют совместимость до получения задачи.
11. Storage migrations детерминированы и версионированы.
12. Обновление имеет Backup и Rollback Point.
13. Один необязательный сбой может дать DEGRADED вместо полного отката.
14. GitHub Release является официальной карточкой выпуска.
15. Перед 1.0 система должна пройти реальный dogfood на собственной разработке.
16. Версия имеет один канонический источник истины.

## 30.81. Главный принцип

> Каждый выпуск KAT9I_OS должен быть воспроизводимым, проверенным и однозначно связанным с конкретным кодом, контрактами и схемой данных, чтобы система всегда могла ответить: что именно сейчас установлено, с чем это совместимо, почему этой версии можно доверять и как безопасно вернуться к предыдущему состоянию.
