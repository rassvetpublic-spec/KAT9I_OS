# 31. Roadmap и критерии первой рабочей версии KAT9I_OS

## 31.1. Назначение

Этот раздел определяет:

> **в каком порядке строить KAT9I_OS, чтобы как можно раньше получить реально работающую систему, а не десятки недоделанных модулей.**

Главный принцип:

> **сначала один полный рабочий путь от запроса до проверенного результата, затем расширение возможностей.**

## 31.2. Главная ошибка, которой нужно избежать

Нельзя сначала отдельно построить весь Learning, всю Knowledge Base, распределённую сеть, красивую визуализацию, десятки Domains и сложный Scheduler, а потом пытаться связать их между собой.

Это создаст большое количество интеграционных проблем.

## 31.3. Вертикальная разработка

KAT9I_OS развивается вертикальными срезами.

`Vertical Slice — вертикальный срез` означает маленький, но полностью работающий путь через несколько модулей.

Например:

GitHub Issue → TaskContract → Worker → локальное изменение → тесты → PR → независимый QA → ResultRef → Metrics.

Это ценнее, чем десять изолированных модулей по 80% готовности.

## 31.4. Первая задача KAT9I_OS

Первая полноценная рабочая область:

> **разработка программного обеспечения через GitHub.**

Причины:
- проект KAT9I_OS уже ведётся в GitHub;
- есть реальные Issues;
- есть PR;
- есть QA;
- Git предоставляет revision и Evidence;
- можно dogfood-разрабатывать KAT9I_OS самой KAT9I_OS.

## 31.5. GitHub Domain как первая вертикаль

Первая end-to-end цепочка:

GitHub Issue → Intake → Rules → TaskContract → Context → Planning → Inference → Coworker → Git Worktree → Execution → Tests → Evidence → PR → независимый QA → Merge → Metrics → Learning.

## 31.6. Приоритет запуска

До первой рабочей вертикали не требуется полный функционал всех 31 разделов.

Нужно реализовать минимально достаточную версию каждого критического компонента.

## 31.7. Этап 0 — архитектурная заморозка

До активного написания Core необходимо завершить:
- все основные разделы ТЗ;
- кросс-анализ разделов;
- устранение противоречий;
- единый словарь;
- Module Registry;
- список контрактов;
- SSoT-карту;
- сравнительный анализ внешних проектов.

После этого базовая архитектура получает статус Architecture Baseline.

## 31.8. Что означает Architecture Baseline

Это не означает, что архитектура больше никогда не меняется.

Это означает, что изменения после этой точки являются явными архитектурными решениями, а не случайным переписыванием ТЗ.

## 31.9. Этап 1 — фундамент

Первыми реализуются:
1. Configuration;
2. Storage;
3. Event Journal;
4. Rule Manager;
5. Security;
6. TaskContract;
7. TaskRuntimeState;
8. TaskGraph;
9. базовая Telemetry.

Без этого нельзя безопасно строить верхние слои.

## 31.10. Почему Storage рано

Task State, Rules, Events и Recovery должны иметь место хранения с самого начала.

Нельзя сначала хранить всё во временных JSON, а затем пытаться мигрировать хаотичное состояние.

## 31.11. Почему Security рано

Security нельзя добавлять после реализации всех Tools.

Иначе архитектура уже будет построена вокруг широких полномочий.

## 31.12. Минимальный Rule Manager

P0-версия должна уметь:
- загрузить правила;
- определить Scope;
- применить deny wins;
- сформировать Effective Ruleset;
- вернуть BLOCKED при неоднозначности обязательного правила.

Не нужен сложный AI-анализ правил.

## 31.13. Минимальный Security

P0:
- Identity;
- Scope;
- Capability Grant;
- CONTROL/DATA;
- LOCAL_ONLY;
- deny;
- USER/ADMIN approval boundaries;
- защита Secrets.

## 31.14. Минимальный TaskContract

До первого реального запуска контракт должен быть машинно-валидируемым.

Минимально:
- task_id;
- objective;
- Domain;
- Scope;
- RulesRef;
- ContextRefs;
- OutputContract;
- QA Policy;
- ResultSink.

## 31.15. Этап 2 — локальное исполнение без ИИ

Следующий важный тест:

> **KAT9I_OS умеет выполнить детерминированную локальную задачу вообще без LLM.**

Например:
- прочитать файл;
- создать Worktree;
- запустить тест;
- вычислить hash;
- проверить контракт.

## 31.16. Зачем сначала без ИИ

Так проверяются Core, Task State, Security, Execution, Evidence и Telemetry без дополнительной нестабильности модели.

Это соответствует Executable-first.

## 31.17. Первый полный локальный сценарий

Пример: «Проверь, что файл существует и соответствует заданной схеме».

Система должна:
1. создать TaskContract;
2. проверить Scope;
3. выбрать локальный код;
4. выполнить;
5. получить exit result;
6. сохранить Evidence;
7. завершить Task;
8. показать результат в Electron.

## 31.18. Этап 3 — Electron P0

Electron подключается рано, но сначала без сложной графики.

P0:
- запуск;
- связь с Core;
- статус системы;
- список задач;
- карточка задачи;
- Worker status;
- Errors;
- Metrics;
- Diagnostics;
- Docs;
- Settings;
- Tray.

## 31.19. Electron сначала наблюдает

На первом этапе большинство экранов read-only.

Управляющие команды добавляются после проверки полного пути UI → Security → Core → Execution.

## 31.20. Этап 4 — Resources и Context

После рабочего Core:
- Resource Registry;
- ResourceRef;
- локальные Resolver;
- Context Funnel;
- Context Pack;
- Context Manifest.

## 31.21. Первый Context должен быть простым

Сначала:
- конкретные файлы;
- конкретный commit;
- конкретная документация.

Не нужно сразу строить универсальный RAG для всего диска пользователя.

## 31.22. Этап 5 — Inference

После детерминированного пути подключается AI Routing.

Сначала достаточно:
- CODE;
- LOCAL_AI;
- NORMAL;
- HIGH.

Маршрутизация должна объяснять, почему выбран этот уровень.

## 31.23. Первый AI-сценарий

Простая задача: проанализировать небольшой файл и дать структурированный результат.

Проверяется:
- Context;
- Provider Route;
- token Metrics;
- Result validation;
- fallback.

## 31.24. Этап 6 — Coworker

Затем вводятся:
- Worker Registry;
- capabilities;
- presence;
- scheduling;
- Claim;
- Lease;
- generation.

Сначала один локальный Worker.

## 31.25. Один Worker до нескольких

Нельзя отлаживать distributed scheduling, пока обычный Task не умеет стабильно выполняться одним Worker.

## 31.26. Этап 7 — GitHub Integration

После устойчивого локального выполнения подключается первый внешний рабочий Domain.

Минимально:
- чтение Issue;
- чтение repo;
- branch/worktree;
- commit;
- PR;
- чтение Actions;
- Evidence.

## 31.27. Изменения GitHub только через контролируемый путь

Для кодовых задач принята модель:

> **Issue → отдельная ветка → PR → проверки → независимый QA → Merge.**

Прямое изменение `main` рабочим Worker не является нормальным путём разработки.

## 31.28. Исключение для согласования документации

Пока архитектурное ТЗ согласовывается владельцем проекта разделами, принятое решение может фиксироваться напрямую согласно текущему проектному процессу.

После Architecture Baseline правила `main` ужесточаются.

## 31.29. Этап 8 — независимый QA

QA добавляется до масштабирования автономности.

Минимально:
- отдельный Worker;
- точная revision;
- обязательные tests;
- Evidence;
- PASS/FAIL/BLOCKED;
- запрет self-QA.

## 31.30. Первый dogfood-сценарий

После этого KAT9I_OS должна выполнить реальную задачу из собственного GitHub:
1. взять Issue KAT9I_OS;
2. сформировать TaskContract;
3. создать Worktree;
4. выполнить изменение;
5. запустить проверки;
6. открыть PR;
7. другой Worker выполняет QA;
8. после PASS выполнить Merge согласно разрешениям;
9. закрыть Issue;
10. записать Metrics.

Это первая значимая победа проекта.

## 31.31. v0.1 — живой каркас

Цель `v0.1`:

> **система действительно запускается и умеет провести простую локальную задачу через полный минимальный жизненный цикл.**

Обязательно:
- Storage;
- Core;
- TaskContract;
- Rules;
- Security;
- Execution;
- Telemetry;
- простой Electron;
- Evidence.

## 31.32. Что не требуется в v0.1

Не обязательны:
- remote Workers;
- полноценный Learning;
- сложная Knowledge Base;
- красивый Replay;
- Telegram;
- все Domains;
- federation;
- сложный semantic search.

## 31.33. Критерий готовности v0.1

Не «все папки созданы», а одна реальная задача успешно проходит систему и оставляет доказуемое состояние.

## 31.43. Цель v0.6

## 31.50. v1.0 — первая стабильная система

Критерии раздела 30 должны быть подтверждены Evidence.

Особенно:
- безопасность;
- восстановление;
- обновление;
- Rollback;
- независимый QA;
- dogfood;
- понятный Electron;
- документация;

- поддержку всех возможных AI Providers;
- десятки Domains;
- сложный enterprise cluster;

- абсолютную автономность.

## 31.54. Некоторые работы выполняются параллельно

Порядок не означает один длинный последовательный проект.

Например одновременно можно разрабатывать Electron shell, contract schemas, test harness и documentation generator.

Но интеграционный приоритет остаётся у вертикального сценария.

## 31.55. Не начинать следующий слой без Evidence предыдущего

Например до remote Workers должны быть подтверждены локальный Lease, Worker loss, idempotency и Recovery.

Иначе сеть только увеличит число ошибок.

## 31.56. Definition of Done — что значит «готово»

Модуль не считается готовым только потому, что код написан.

Минимально:
- контракт;
- реализация;
- tests;
- ошибки;
- Telemetry;
- Security implications;
- документация;
- Evidence;
- независимый QA для критичных изменений.

## 31.57. Definition of Ready — что значит «можно брать в работу»

Issue готов к реализации, если понятны:
- цель;
- Scope;
- требования;
- зависимости;
- критерии результата;
- QA requirement.

Если это нельзя определить, сначала создаётся архитектурная/аналитическая задача.

## 31.58. GitHub Issues — рабочий backlog

Вся реализация Roadmap должна раскладываться на Issues.

Issue является SSoT состояния работы.

Roadmap не должен превращаться во второй параллельный список задач.

## 31.59. GitHub Project — представление Roadmap

Project показывает Issues по этапам: входящие, готово, в работе, QA, blocked, completed.

Но Project остаётся представлением Issues.

## 31.60. Milestones

Рекомендуются Milestones:
- v0.1;
- v0.2;
- v0.3;
- v0.4;
- v0.5;
- v0.6;
- v0.7;
- v0.8;

Issue может быть привязан к целевому Milestone.

## 31.61. Не планировать всё до 1.0 в деталях

Чем дальше версия, тем крупнее должны быть задачи Roadmap.

Например для v0.1 — конкретные Issues. Для v0.8 — capability-level задачи.

Это снижает фиктивную точность.

## 31.62. Приоритизация

Основные классы:

### P0
Без этого текущий этап не работает.

### P1
Очень важно, но не блокирует базовую вертикаль.

### P2
Полезное улучшение.

### P3
Будущее / эксперимент.

## 31.63. Security повышает приоритет

Критический Security defect автоматически может стать P0 независимо от Roadmap.

## 31.64. Regression повышает приоритет

Если рабочая ранее вертикаль перестала работать, её восстановление важнее большинства новых функций.

## 31.65. Технический долг

Technical Debt — технический долг не должен быть невидимым.

Он оформляется Issue с объяснением:
- какой риск;
- почему пока не исправлено;
- когда станет блокирующим.

## 31.66. Не создавать фиктивные Issues

Issue должна представлять реально управляемую работу.

Не нужно создавать сотни карточек «реализовать каждый метод будущего класса».

Подзадачи можно создавать, когда родительская задача реально готова к реализации.

## 31.67. Доноры

AG25 и `kat9i_skills` используются как источники:
- проверенных идей;
- уже работающих механизмов;
- тестов;
- ошибок;
- архитектурного опыта.

Но перенос осуществляется по ответственности нового модуля, а не копированием старой структуры.

## 31.68. Donor Adoption Record

При переносе существенного механизма желательно фиксировать:
- источник;
- что взято;
- что изменено;
- почему;
- лицензия;
- какие тесты подтверждают перенос.

## 31.69. Внешние аналоги

После завершения архитектурного ТЗ выполняется отдельный comparative research.

Цель — не найти проект и скопировать его, а найти проверенные решения конкретных проблем KAT9I_OS.

## 31.70. Обязательный кросс-анализ перед стартом реализации

Перед заморозкой Architecture Baseline проверяются все разделы одновременно.

Минимально:
- терминология;
- SSoT;
- владельцы контрактов;
- зависимости;
- дублирование;
- циклы;
- Security;
- Learning boundaries;
- Electron;
- Storage;
- distributed model;
- GitHub workflow.

## 31.71. После кросс-анализа создаётся Architecture Debt Backlog

Все обнаруженные проблемы делятся на:
- MUST FIX BEFORE IMPLEMENTATION;
- MUST FIX BEFORE v0.1;
- MUST FIX BEFORE 1.0;
- OPTIONAL.

Это предотвращает бесконечный аудит без запуска разработки.

## 31.72. Quality Gate развивается постепенно

На раннем этапе он проверяет:
- структуру;
- схемы;
- ссылки;
- UTF-8;
- SSoT-базовые правила.

Позже:
- unit tests;
- architecture boundaries;
- contracts compatibility;
- Electron;
- security;
- regressions;
- release readiness.

## 31.73. CI не должен быть декоративным

Красный обязательный Quality Gate означает реальную проблему текущей revision.

Не должно быть привычки «там Actions всегда красные, не обращай внимания».

## 31.74. Исторические FAIL

Старые FAIL сохраняются как история.

Текущее здоровье определяется последней проверенной revision текущей ветки/Release.

Исправленный дефект подтверждается новым PASS.

## 31.75. Работа коворкеров

Порог входа должен быть минимальным.

Новый коворкер должен быстро понять:
1. что за проект;
2. что сейчас строится;
3. какую Issue можно взять;
4. какие правила действуют;
5. как открыть PR;
6. кто выполняет QA.

## 31.76. Good First Issue

Для простых задач используется класс `good first issue — хорошая первая задача`.

Она должна иметь особенно простое описание и ограниченный Scope.

## 31.77. Учебные задачи

Можно иметь безопасные учебные Issues, не затрагивающие критический Core.

Например:
- улучшить пояснение термина;
- добавить тест;
- исправить ссылку;
- улучшить onboarding.

## 31.78. Electron показывает Roadmap

В будущем Electron может отображать GitHub Roadmap:
- текущий Milestone;
- сколько P0 осталось;
- какие задачи blocked;
- какие PR ждут QA;
- готовность текущей версии.

Но GitHub Issues остаются SSoT.

## 31.79. Процент готовности версии

Не стоит считать готовность только как «закрыто 85% Issues».

Нужно учитывать:
- обязательность;
- P0;
- QA;
- regressions;
- Security;
- end-to-end scenarios.

## 31.80. Release Readiness Score

Можно использовать вычисляемый показатель готовности версии.

Например учитываются:
- mandatory gates;
- open P0;
- QA;
- regressions;
- security;
- recovery;
- documentation.

Но он является индикатором и не заменяет Release Gate.

## 31.81. Основной MVP проекта

`MVP — минимально полезная версия` KAT9I_OS:

> **система, которая может безопасно взять GitHub Issue, передать его подходящему Worker, выполнить изменение в отдельной ветке, доказать результат тестами, отправить на независимый QA и вернуть проверенный результат пользователю через Electron.**

Это целевой первый действительно полезный продукт.

## 31.82. Почему именно этот MVP

Он одновременно проверяет Core, Rules, Security, Context, Resources, Inference, Coworker, Execution, Git, QA, Evidence, Telemetry и Electron.

То есть почти всю ключевую архитектуру на одном реальном процессе.

## 31.83. Learning не блокирует MVP

MVP должен работать без Learning.

Learning улучшает уже работающую систему.

Он не должен быть необходим, чтобы базовая задача вообще завершалась.

## 31.84. Cache не блокирует корректность

MVP должен оставаться корректным даже при полностью пустом Cache.

Cache ускоряет, но не является фундаментом истинности.

## 31.85. Remote Worker не блокирует MVP

Первый полезный продукт должен работать на одном Windows 11 компьютере.

Удалённые Workers добавляются позднее.

## 31.86. Критический путь до MVP

Architecture Baseline → Contracts → Storage → Rules/Security → Core → Local Execution → Electron → Resources/Context → Inference → Coworker → GitHub → QA → MVP.

## 31.87. Следующий путь после MVP

MVP → Recovery → Planning → Learning → Knowledge → Remote Worker → Beta hardening → 1.0.

## 31.88. Что Roadmap не должен делать

Roadmap не должен:
- быть вторым Issue tracker;
- требовать реализации всех модулей сразу;
- ставить красивый UI выше рабочего Core;
- строить distributed architecture раньше локального Worker;
- делать Learning зависимостью корректности;
- считать количество commit показателем прогресса;
- выпускать версию только ради номера;
- позволять новым функциям постоянно вытеснять исправление регрессий.

## 31.89. Основные принципы

1. **Разработка идёт вертикальными срезами.**
2. **Первая полноценная вертикаль — GitHub-разработка.**
3. **Один компьютер должен дать первый полезный результат.**
4. **Security и Storage строятся рано.**
5. **Сначала проверяется детерминированное выполнение без ИИ.**
6. **Electron подключается рано как интерфейс наблюдения.**
7. **AI добавляется после рабочего Core.**
8. **Один Worker отлаживается до распределённой работы.**
9. **Независимый QA появляется до высокой автономности.**
10. **Recovery появляется до удалённых Workers.**
11. **Learning улучшает уже работающую систему, а не обеспечивает её базовую корректность.**
12. **GitHub Issues являются SSoT работы.**
13. **Milestones группируют Issues по версиям.**
14. **Каждая версия имеет проверяемую эксплуатационную цель.**
15. **Перед реализацией проводится общий кросс-анализ архитектуры и внешних аналогов.**
16. **MVP должен dogfood-разрабатывать саму KAT9I_OS.**

## 31.90. Главный принцип

> **KAT9I_OS должна расти не количеством модулей, а количеством полностью работающих и доказанных путей от задачи до результата: сначала один локальный путь, затем GitHub-разработка, затем восстановление, прогнозирование, обучение и только после этого распределённая работа и расширение системы.**

## Portable Promotion в первой GitHub-вертикали (§36)

GitHub dogfood использует единый Portable Promotion Protocol: PR → Change Evidence → Promotion Queue → synthetic candidate → Integration Evidence → sealed PromotionTicket → AUTO или `mtd` → verified side effect.

Первая реализация допускает GitHub Actions Promotion Bridge без собственной GitHub App. Native Merge Queue остаётся optional acceleration и не является условием работы на personal account.
