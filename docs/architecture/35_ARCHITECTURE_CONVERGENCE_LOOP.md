# 35. Architecture Convergence Loop — цикл архитектурной сходимости

## 35.1. Назначение

Architecture Convergence Loop — обязательный способ системно пересматривать архитектурные разделы KAT9I_OS без преждевременного усложнения.

Цикл воспроизводит подход, который был применён при проектировании CacheEngine:

1. сначала фиксируются простые базовые законы;
2. затем пространство решений намеренно расширяется максимально широко;
3. каждая идея получает оценку пользы, цены и риска;
4. после этого лишняя сложность жёстко отсекается;
5. финальное решение снова сверяется с исходными законами простоты, корректности и восстановимости;
6. будущее развитие сохраняется контрактами, а не заранее реализованной неиспользуемой функциональностью.

Главный принцип:

> **Полная архитектура — минимальная реализация.**

Дополнительный принцип:

> **Будущая функция должна обеспечиваться совместимым контрактом, а не заранее написанным неиспользуемым кодом.**

Цель цикла — не сделать архитектуру максимально функциональной. Цель — сделать её минимальной среди решений, которые сохраняют корректность, безопасность, восстановимость и ожидаемое развитие системы.

## 35.2. Почему обычного review недостаточно

Обычный review чаще всего отвечает на вопрос: «Есть ли здесь ошибка?»

Architecture Convergence Loop дополнительно спрашивает:

- что является минимально правильным решением;
- какие сильные возможности вообще существуют в пространстве решений;
- какая из них нужна уже сейчас;
- какая нужна только как будущая совместимость;
- что можно добавить позже без breaking change;
- что создаёт новый SSoT, обязательный процесс или сложный recovery path;
- что произойдёт, если удалить каждую возможность;
- осталась ли система простой после полного брейншторма.

Максималистская стадия обязательна. Без неё система может преждевременно зафиксировать слабую исходную идею.

Гильотина сложности также обязательна. Без неё брейншторм превращается в накопление функций.

## 35.3. Calibration Case — эталон CacheEngine

Обязательный calibration case (эталон калибровки):

`docs/architecture/34_CACHE_ENGINE.md`

Именно CacheEngine показывает правильную траекторию:

`простое ядро → максимальный брейншторм → классификация → атака на сложность → удаление лишнего → простое ядро с будущей совместимостью`.

Сценарий считается плохо откалиброванным, если без нового Evidence он снова делает обязательной реализацию возможностей, которые в CacheEngine были намеренно оставлены как будущая совместимость или отложены, например distributed cache, AI eviction, zero-copy, mmap, learning-tuned policy и сходные оптимизации.

Calibration Case не означает, что решения CacheEngine копируются в другие подсистемы. Копируется метод мышления.

## 35.4. Фаза 0 — исходные законы

Перед генерацией идей из раздела извлекаются:

- назначение;
- владелец ответственности;
- SSoT;
- входы и выходы;
- основные инварианты;
- требования безопасности;
- требования отказоустойчивости;
- зависимости;
- запрещённые действия;
- требования degraded mode;
- свойства, которые должны оставаться простыми.

Результат — короткий набор исходных законов раздела.

Эти законы нельзя незаметно менять внутри дальнейшего брейншторма. Если закон оказался ошибочным, это отдельное обнаруженное архитектурное решение, которое требует явного Evidence.

## 35.5. Фаза 1 — Minimal Baseline

Строится самое маленькое решение, которое выполняет исходные законы.

Для каждого элемента задаётся вопрос:

> Без этого текущая система перестанет быть корректной?

Если нет, элемент не считается обязательным для минимальной реализации.

Результат называется `MINIMAL_BASELINE`.

## 35.6. Фаза 2 — Maximal Brainstorm

На этой фазе ограничение на простоту временно снимается.

Нужно намеренно исследовать как можно более широкое пространство разумных вариантов:

- производительность;
- параллелизм;
- распределённость;
- масштабирование;
- восстановление;
- безопасность;
- наблюдаемость;
- автоматизация;
- AI / Learning;
- кэширование;
- дедупликация;
- shared memory;
- zero-copy;
- оптимизация памяти и диска;
- версионирование;
- расширяемость;
- portability;
- multi-worker;
- multi-machine;
- диагностика;
- benchmarking;
- future hardware.

На этой фазе запрещено отбрасывать идею только потому, что она сложная.

Можно использовать идеи из других разделов KAT9I_OS, AG25, kat9i_skills и внешних архитектурных решений, но внешние идеи не становятся требованиями автоматически.

Результат называется `MAXIMAL_CANDIDATE_ARCHITECTURE`.

## 35.7. Фаза 3 — карточка каждой идеи

Для каждой идеи фиксируются:

- проблема, которую она решает;
- существует ли проблема сейчас;
- Evidence существования проблемы;
- стоимость реализации;
- стоимость поддержки;
- влияние на связанность модулей;
- новые состояния отказа;
- новые зависимости;
- влияние на Security;
- влияние на Recovery;
- обратимость решения;
- возможность добавить позже без breaking change;
- возможность обеспечить будущее только контрактом.

Каждая идея получает ровно один класс решения.

### REQUIRED_NOW

Без идеи текущая архитектура некорректна или не выполняет обязательное требование.

### USEFUL_NOW

Идея не обязательна для корректности, но уже имеет измеримую пользу и оправданную стоимость.

### CONTRACT_ONLY

Реализация сейчас не нужна, но контракт должен позволять добавить возможность позже без breaking change.

### DEFERRED

Идею можно безопасно добавить позже без предварительной реализации или специальной точки расширения сейчас.

### REJECTED

Цена сложности выше пользы либо идея нарушает исходные законы.

## 35.8. Фаза 4 — атака на максимальную архитектуру

Нужно предположить, что максималистский проект уже реализован, и посчитать его реальную цену.

Проверяются:

- процессы;
- persistent state;
- API и контракты;
- фоновые задачи;
- обязательные зависимости;
- recovery paths;
- security boundaries;
- конфигурационные параметры;
- новые причины получить неконсистентное состояние.

Для каждого элемента задаётся Deletion Test:

> Что реально сломается, если полностью удалить эту возможность?

Если ответ сводится к «станет немного медленнее», «станет менее удобно» или «потеряем оптимизацию, которая пока не измерена», возможность не считается фундаментальной.

## 35.9. Фаза 5 — Complexity Guillotine

На этой фазе нужно намеренно удалить максимум сложности.

Приоритет удаления:

1. неиспользуемая функциональность;
2. оптимизации без benchmark Evidence;
3. сложность, которую можно добавить позже;
4. derived state, который можно восстановить из SSoT;
5. собственная реализация при наличии зрелого компонента;
6. AI в critical/hot path без доказанной необходимости;
7. persistent state, который не обязан быть persistent;
8. уровни абстракции без текущего пользователя;
9. фоновые процессы «на всякий случай»;
10. распределённость без текущей задачи распределения.

Главный критерий:

> Если элемент удалить, останется ли система корректной?

Если да, требуется отдельное доказательство, почему элемент всё же должен быть `REQUIRED_NOW` или `USEFUL_NOW`.

## 35.10. Фаза 6 — возврат к исходным законам

После отсечения максималистская архитектура сравнивается с Фазой 0.

Проверяется:

- появился ли второй SSoT;
- появился ли новый обязательный сервис;
- усложнилось ли восстановление;
- пропал ли degraded mode;
- вошёл ли AI в critical path;
- появился ли необязательный persistent state;
- увеличилось ли число security boundaries;
- стало ли решение трудно объяснить простыми словами.

Финальное решение должно снова быть близким к `MINIMAL_BASELINE`, но уже учитывать знания, полученные в Maximal Brainstorm.

## 35.11. Фаза 7 — Full Architecture / Minimal Implementation

Для важных будущих возможностей создаются только необходимые точки расширения.

Используются три независимых состояния:

- `SUPPORTED` — архитектура и контракт совместимы с возможностью;
- `IMPLEMENTED` — код возможности реально существует;
- `ENABLED` — возможность активирована конфигурацией.

`SUPPORTED` не означает `IMPLEMENTED`.

`IMPLEMENTED` не означает `ENABLED`.

Для каждой будущей функции выполняется Future Without Implementation Test:

> Можно ли обеспечить совместимость контрактом, enum, capability, versioned payload или backend interface, не реализуя сам механизм сейчас?

Если да, реализация функции не должна появляться только ради будущего.

## 35.12. Фаза 8 — проверка соседних разделов

После получения финальной модели определяется blast radius (область влияния).

Минимально проверяются связанные разделы:

- TaskContract;
- Rules;
- Context;
- Knowledge;
- Resources;
- Workers / Coworker;
- Security;
- Reliability and Recovery;
- Data Storage;
- Module Registry / Responsibility Map;
- Metrics;
- Roadmap;
- UI / Visualization;
- Evidence.

Изменение одного архитектурного закона не должно оставлять старое противоречащее описание в соседнем SSoT.

## 35.13. Фаза 9 — независимый Critic

Critic Worker не должен быть единственным Implementation Worker этого изменения.

Он выполняет две противоположные атаки.

### Атака A — удалили слишком много

Critic пытается доказать, что Complexity Guillotine удалила возможность, без которой:

- нарушается корректность;
- ухудшается безопасность;
- ломается recovery;
- появляется breaking change в ожидаемом развитии;
- невозможно выполнить уже принятое требование.

### Атака B — оставили слишком много

Critic пытается доказать, что в финальной модели осталась:

- преждевременная оптимизация;
- лишняя зависимость;
- второй SSoT;
- unnecessary persistent state;
- необязательный процесс;
- AI в critical path;
- сложный recovery производного состояния;
- расширение без текущего пользователя.

PASS возможен только после обеих атак.

## 35.14. Фаза 10 — финальный результат

Для каждого раздела результат должен содержать:

- исходные законы;
- Minimal Baseline;
- Maximal Candidate Architecture;
- список рассмотренных идей;
- классификацию каждой идеи;
- Complexity Budget до и после;
- что осталось;
- что удалено;
- что оставлено только как Contract Only;
- что Deferred;
- что Rejected;
- результаты Deletion Test;
- результаты Future Without Implementation Test;
- затронутые соседние разделы;
- вопросы, требующие Evidence;
- результаты двух Critic-атак;
- итог `PASS`, `FAIL` или `BLOCKED`.

## 35.15. Complexity Budget

Минимальный Complexity Budget содержит восемь счётчиков:

1. Processes — отдельные процессы/сервисы.
2. Persistent State — каноническое или производное постоянное состояние.
3. Public Contracts — публичные API и машинные контракты.
4. Mandatory Dependencies — обязательные зависимости.
5. Background Jobs — фоновые задачи.
6. Recovery Paths — отдельные маршруты восстановления.
7. Security Boundaries — границы доверия и безопасности.
8. Configuration Surface — конфигурационные параметры, влияющие на поведение.

Рост любого счётчика не является автоматическим FAIL, но требует явного обоснования.

## 35.16. Два прохода

### Pass A — разведка

Pass A не изменяет канонические документы.

Он:

- обнаруживает разделы;
- выполняет архитектурный анализ;
- формирует отчёты;
- классифицирует идеи;
- отмечает противоречия;
- предлагает кандидатов на отдельные Issues.

Результат Pass A является Evidence/Analysis, но не новым SSoT.

### Pass B — изменение

Pass B никогда не является автоматическим массовым переписыванием ТЗ.

Каждое независимое изменение проходит канонический процесс:

`Project → Issue → ветка от свежего main → Draft PR → CI → независимый QA → явная mtd → Merge`.

Один общий прогон может создать несколько кандидатов на Issues, но не должен автоматически объединять несвязанные архитектурные изменения в один PR.

## 35.17. Автоматизация первой версии

Первая реализация намеренно минимальна.

Она должна уметь:

- прочитать machine-readable policy;
- обнаружить канонические Markdown-разделы по разрешённым путям;
- вычислить их content hash;
- построить детерминированный manifest прогона;
- включить для каждого раздела задания Explorer и Critic;
- включить Calibration Case CacheEngine;
- проверить наличие всех фаз и классов решений;
- завершиться ошибкой при нарушении policy.

Первая реализация **не должна**:

- создавать собственный AI orchestration runtime;
- автоматически переписывать Markdown;
- автоматически принимать архитектурные решения;
- автоматически создавать merge;
- автоматически ставить QA PASS;
- автоматически ставить Gate PASS;
- автоматически закрывать Issues.

Это соответствует принципу «полная архитектура — минимальная реализация».

## 35.18. Machine-readable policy

Машинный контракт процесса хранится отдельно от объясняющего текста.

Канонический смысл процесса задаётся этим документом.

Machine-readable policy является исполняемым отражением канонического смысла и не должна вводить дополнительные архитектурные требования.

При расхождении правильным считается этот документ, а policy должна быть исправлена.

## 35.19. Reproducible Manifest

Manifest должен быть воспроизводимым.

При одинаковой policy и одинаковом содержимом исходных документов два запуска должны формировать одинаковый смысловой manifest независимо от времени запуска.

Для каждого раздела минимум фиксируются:

- путь;
- content hash;
- порядковый номер;
- список фаз;
- роли Explorer и Critic;
- обязательные тесты идей;
- Complexity Budget dimensions;
- calibration relation, если применимо.

Время запуска, случайный UUID и машинно-зависимые абсолютные пути не должны входить в идентичность manifest.

## 35.20. Безопасность и Gate

Architecture Convergence Loop является системой анализа, а не системой принятия власти над проектом.

Ему запрещено самостоятельно:

- изменять SSoT;
- обходить Rules;
- повышать разрешения;
- считать brainstorm решением пользователя;
- считать CI эквивалентом QA;
- считать QA эквивалентом `mtd`;
- выполнять merge;
- закрывать архитектурную Issue только по факту генерации отчёта.

Любой автоматический результат рассматривается как DATA до явного прохождения принятого процесса управления.

## 35.21. Критерий PASS раздела

Раздел проходит Architecture Convergence Loop, если:

1. исходные законы явно зафиксированы;
2. Minimal Baseline построен;
3. Maximal Brainstorm действительно исследовал широкое пространство решений;
4. каждая существенная идея классифицирована;
5. Complexity Guillotine выполнена;
6. фундаментальные возможности не потеряны;
7. необязательная реализация удалена;
8. будущее развитие не требует ломать текущие контракты без доказанной причины;
9. нет второго SSoT;
10. восстановление остаётся объяснимым и проверяемым;
11. critical path не содержит необязательной сложности;
12. две противоположные Critic-атаки завершены;
13. рост сложности имеет Evidence;
14. итоговая модель снова объясняется простыми словами.

Если любой обязательный пункт нельзя доказать, результат — `BLOCKED` или `FAIL`, но не искусственный PASS.
