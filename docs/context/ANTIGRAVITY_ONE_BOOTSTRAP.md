# Antigravity ONE: контракт Windows-загрузчика (`bootstrap`)

Статус: контракт реализации для GitHub Issue #187 (Issue — рабочая задача). Документ не является разрешением на `merge` (слияние PR в `main`) и не закрывает весь Scope #187 сам по себе.

## Цель

Одна пользовательская точка входа:

```text
C:\Antigravity\ANTIGRAVITY.cmd
```

Windows-загрузчик (`bootstrap`) управляет установкой, проверкой, восстановлением и совместимым патчем (`patch` — точечным изменением исполняемого файла) Antigravity. Профиль и рабочее состояние нельзя менять без проверенной резервной копии (`backup`).

## Порядок патча

1. Найти все копии автономной версии (`standalone`) `resources\bin\language_server.exe` в каноническом каталоге, пользовательских и системных путях.
2. Заблокировать работу при запущенном Antigravity.
3. Для каждой копии отдельно определить версию, архитектуру, SHA-256 и состояние.
4. Встроенный `Patch-Antigravity.ps1` — основной (`primary`) механизм.
5. Разрешён только точный контракт, привязанный к версии и SHA-256, и ровно одна известная сигнатура.
6. Перед записью создать и проверить отдельную резервную копию.
7. После записи перечитать файл, проверить патч и сохранить машинно-читаемый отчёт (`receipt`) без учётных данных и токенов.
8. Если проверка после записи не прошла, немедленно восстановить затронутую копию из её проверенного backup, затем проверить восстановление. При нескольких копиях каждая изменённая копия откатывается и проверяется независимо до возврата ошибки.
9. `Open_AG_Patcher` — резервный сценарий (`fallback`) только по явной команде оператора; он не заменяет основной встроенный механизм.

Неизвестная версия, новая защита, неоднозначный путь или неизвестная сигнатура не исправляются эвристически.

## Эскалация неизвестной версии

При обнаружении новой или неизвестной версии загрузчик:

- завершает патч со статусом `PATCH_INCOMPATIBLE / BLOCKED`;
- всегда сохраняет локальную диагностическую запись без секретов и персональных сегментов пути;
- нормализует пользовательские пути перед любым внешним выводом, например `C:\Users\<name>\AppData\Local\...` -> `%LOCALAPPDATA%\...`;
- создаёт или переиспользует открытую GitHub Issue в `rassvetpublic-spec/KAT9I_OS` только при наличии явного разрешения на внешнюю запись и capability `issues:write`;
- при отсутствии сети, разрешения или `issues:write` не пытается обходить ограничение: патч остаётся `BLOCKED`, а локальный отчёт содержит причину и данные для ручной эскалации;
- при разрешённой внешней записи публикует только нормализованный путь, версию, SHA-256 и причину без секретов;
- формулирует задачу для следующего доступного worker (исполнителя): сверить механизм защиты с внешним upstream-источником `AvenCores/open-antigravity-patcher`, добавить точный manifest (машинный манифест совместимости) и тесты.

Дубликаты открытых Issues не создаются. Команда `status` остаётся диагностической: сама по себе она не получает право на внешнюю запись.

## Команды

```text
ANTIGRAVITY.cmd status
ANTIGRAVITY.cmd install
ANTIGRAVITY.cmd repair
ANTIGRAVITY.cmd fallback
```

`fallback` требует явного выбора. Автоматический переход на внешний patcher запрещён.

## Граница состояния

Локальная реализация находится в `C:\Antigravity\_System` и не переносит credentials (учётные данные) в репозиторий. Профиль Antigravity и данные Antigravity Manager — отдельного менеджера аккаунтов и состояния — не являются частью этого документа и не должны коммититься.

## Критерии приёмки

- одна точка входа сохраняется;
- обнаруживаются все известные копии установки;
- каждая копия получает независимый backup, патч и verify (проверку результата);
- неуспешный post-write verify (проверка после записи) обязательно вызывает rollback (откат) каждой затронутой копии и проверку восстановления;
- неизвестное состояние блокируется и сохраняет локальный diagnostic receipt; внешняя Issue создаётся только при явном разрешении и наличии `issues:write`;
- публикуемые пути обезличиваются до `%LOCALAPPDATA%`, `%APPDATA%`, `%USERPROFILE%` или другого безопасного представления;
- fallback запускается только явно;
- процесс обновления не работает поверх запущенного Antigravity;
- receipt/log не содержат токены, credentials или ненормализованные пользовательские пути;
- независимый QA (проверка качества) и ручной owner gate `mtd` (разрешение владельца на merge) обязательны перед слиянием.
