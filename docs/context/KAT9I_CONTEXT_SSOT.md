# KAT9I_OS Context SSOT

## Назначение

Этот документ хранит устойчивые операционные знания KAT9I_OS, которые появились в рабочих чатах и должны переживать удаление чата.

Он не заменяет канонические документы. При конфликте действует более строгий и более специализированный источник в таком порядке:

1. безусловное правило `mtd` из `AGENTS.md`;
2. `QA_PROTOCOL.md` для Controller ↔ QA Executor;
3. `docs/spec/23_TESTING_QA_AND_READINESS.md` для Evidence и QA freshness;
4. `docs/spec/24_GITHUB_PROJECT_MANAGEMENT.md` для GitHub-процесса;
5. управляющий Gate Issue #62;
6. связанная Issue конкретной работы;
7. этот `docs/context/*` как переносимый операционный контекст.

## Главный принцип

GitHub является SSoT (единым источником истины) проекта. Чат — интерфейс обсуждения и управления, но уникальные решения из чата должны быть материализованы в `docs/`, Issue, PR или Evidence до удаления чата.

## Режим автономной работы

Для KAT9I_OS Worker работает автоматически в пределах уже разрешённого Scope.

Не нужно запрашивать у владельца подтверждение каждого безопасного и обратимого шага. Владелец привлекается, когда требуется хотя бы одно из следующего:

- новый доступ или секрет, которого нет у Worker;
- конфликт канонических правил;
- решение, которое меняет Scope или архитектурный Gate;
- необратимое/разрушительное действие или заметный риск потери данных;
- финальный Owner Gate `mtd` для merge.

Команда `WORKER` означает: взять разрешённую задачу через QUEUE-GUARD, оставить claim Evidence и продолжать автоматически до следующего реального Gate.

## Эксклюзивное владение ChangeSet

- Для одной Issue/PR/ChangeSet одновременно существует один активный Implementation Worker.
- `FAST-CLAIM` означает право этого Worker изменять соответствующую рабочую ветку в рамках Scope.
- Другие Worker могут анализировать, делать рекомендации и готовить независимые выводы, но не должны менять claimed branch, создавать дублирующий PR/Issue или параллельно реализовывать тот же ChangeSet.
- Параллельная подготовка допустима только для непересекающихся ChangeSet. Promotion и merge всё равно сериализуются QUEUE-GUARD.

## Одноразовый Owner Gate mtd

`mtd` / `MTD` / `мтд` — одноразовая авторизация конкретного promotion/merge в актуальном контексте.

- mtd не переносится на другой PR;
- mtd не переиспользуется для следующего merge;
- после материального изменения ChangeSet/HEAD требуется новый Gate после актуализации Evidence;
- если целевой PR уже оказался merged другим разрешённым действием, повторный merge не выполняется; Controller фиксирует фактическое состояние и переходит к post-merge read-back.

## Финальный pre-merge контроль

Непосредственно перед разрешённым merge Controller повторно проверяет:

- live PR и current target/main;
- exact PR HEAD и base;
- требуемый CI/checks на актуальной revision;
- применимый независимый QA Evidence / Evidence Epoch;
- отсутствие unresolved blocking review threads;
- отсутствие нового drift;
- привязку merge к ожидаемому HEAD (`expected_head_sha` или эквивалентный compare-and-swap guard).

Только после этого используется свежий Owner Gate `mtd`.

## QA coordination

Подробности задаёт `QA_PROTOCOL.md`. Дополнительное рабочее правило: после handoff frozen revision в AGY не менять ветку и не создавать шум повторным polling. Любая substantive mutation HEAD делает прежнее основание stale согласно Evidence policy.

## GitHub Project

Project — производное control-plane представление, а не второй источник состояния. Любая automation mutation должна подтверждаться read-back Evidence. Неоднозначное состояние чинится fail-closed, без угадывания Worker/QA/Stage.

Целевой UX Project и восемь представлений отслеживаются #150 / PR #153; до merge соответствующего ChangeSet действует состояние default branch.

## Контекст перед удалением чата

Перед удалением длинного рабочего чата необходимо:

1. найти уникальные Decision / Requirement / Follow-up;
2. выполнить dedupe против `docs/`, Issues, PR и roadmap;
3. материализовать только отсутствующее;
4. оставить ссылку/Evidence на созданный или обновлённый GitHub-артефакт.

Автоматизация этого процесса развивается в #147.
