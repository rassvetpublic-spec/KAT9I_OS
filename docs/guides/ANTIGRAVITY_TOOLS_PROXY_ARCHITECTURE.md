# Архитектура интеграции Antigravity Tools и IDE

Этот документ описывает внутреннюю логику работы менеджера `antigravity-tools`, механизма маршрутизации трафика IDE и правильный способ изоляции рабочих профилей. Знания получены в ходе отладки инцидента с ошибкой `404 Not Found` на туннелях `CONNECT`.

## 1. Фундаментальный принцип работы Antigravity Tools

**`antigravity-tools` — это API-прокси (Layer 7), а не системный HTTP CONNECT прокси (Layer 4).**
- Менеджер построен на веб-фреймворке (Axum) и ожидает стандартные HTTP/HTTPS запросы к конкретным API эндпоинтам (например, `/v1beta/models/...`).
- Менеджер **не поддерживает** сетевое туннелирование через метод `CONNECT`. 
- Если прописать менеджер как системный прокси (`HTTP_PROXY`, `HTTPS_PROXY` или в настройках Windows), IDE попытается завернуть в него весь свой трафик (авторизацию Google, проверку обновлений `play.googleapis.com` и телеметрию). Поскольку метод `CONNECT` не поддерживается, менеджер ответит `404 Not Found`, что приведет к полной неработоспособности IDE (зависание на `Awaiting Authentication...` и ошибки `Unauthorized`).

## 2. Как оригинальный патч маршрутизирует ИИ-трафик

Оригинальная интеграция Antigravity Tools работает **без** системных прокси.
Утилита `Antigravity ONE` (Open AG Patcher) напрямую модифицирует бинарный файл `language_server.exe`. 
- Патч изменяет жестко зашитые внутри бинарника адреса Google API (`https://generativelanguage.googleapis.com`) на локальный адрес менеджера (`http://127.0.0.1:8045`).
- Благодаря этому, IDE отправляет обычные (не `CONNECT`) API-запросы прямо в менеджер.
- Системный трафик (авторизация, обновления) остается нетронутым и идет напрямую через системный шлюз (или VPN пользователя).

## 3. Настройка менеджера

Для корректной работы пропатченной IDE менеджер должен быть настроен так, чтобы не требовать ключ авторизации для локальных соединений:
В файле `gui_config.json`:
```json
"proxy": {
  "enabled": true,
  "allow_lan_access": true,
  "auth_mode": "off",
  "port": 8045
}
```
*Внимание: использование `auth_mode: "none"` недопустимо и приведет к мгновенному крашу (unknown variant) менеджера при запуске.*

## 4. Правильная изоляция мульти-воркеров

При создании параллельных изолированных профилей (Worker 1, 2, 3...) необходимо соблюдать два правила:

1. **Никаких `HTTP_PROXY`:** Скрипт запуска воркера **не должен** устанавливать переменные среды `HTTP_PROXY` или `HTTPS_PROXY`. ИИ-трафик и так пойдет в менеджер благодаря патчу бинарника.
2. **Клонирование состояния сессии:** При создании нового профиля (флаг `--user-data-dir="...\DataDir"`), Electron-часть IDE считает, что это первый запуск, и показывает экран настройки (Welcome/Sign In). Поскольку бинарник уже пропатчен и перенаправлен на менеджер, попытка авторизации "с нуля" через менеджер может не пройти (или менеджер не поддерживает `/token` эндпоинт). 
   - **Решение:** Копирование уже авторизованной папки профиля из `AppData\Roaming\Antigravity` в целевую папку воркера. Это позволяет воркеру мгновенно открывать рабочий интерфейс без повторной авторизации.

## Резюме для разработчика

Если IDE не может авторизоваться или падает с ошибкой сети:
1. Убедитесь, что глобальные прокси (`HTTP_PROXY`, `HTTPS_PROXY`) **выключены**.
2. Проверьте `Логи трафика` в Antigravity Tools. Если вы видите там методы `CONNECT` — значит, вы ошибочно завернули системный трафик в менеджер. Менеджер должен видеть только методы `POST` и `GET` к эндпоинтам моделей.
3. Проверьте статус порта менеджера (8045) — если он закрыт, возможно, `gui_config.json` содержит невалидные значения и ядро Rust завершилось с паникой.
