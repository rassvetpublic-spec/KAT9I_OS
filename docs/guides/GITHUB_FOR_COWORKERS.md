# GitHub для коворкеров KAT9I_OS — с нуля на примере проекта

## 🚀 Режим «Я здесь впервые»

Если вы впервые в проекте, откройте краткий экспресс-маршрут: [Режим «Я здесь впервые»](FIRST_TIME_GUIDE.md).

Не нужно заранее быть экспертом по Git и GitHub. Достаточно понять базовую цепочку совместной работы:

> появилась задача → создали карточку Issue → сделали изменение в отдельной ветке → сохранили шаги (commit) → создали Pull Request → роботы и другой человек проверили результат → приняли в основную версию (merge).

В GitHub это выглядит так:

`Issue → Ветка → Commit → Pull Request (PR) → Actions (роботы) → Независимый QA (человек) → Merge`

## 🎚️ Уровни объяснения

В соответствии с архитектурным стандартом `docs/spec/24_GITHUB_PROJECT_MANAGEMENT.md` каждое понятие ниже снабжено многоуровневым описанием:
1. **Очень просто** — понятно даже школьнику;
2. **Рабочий уровень** — необходимый минимум для повседневной работы;
3. **Технический уровень** — контракты, гарантии и связи с KAT9I_OS;
4. **Сворачиваемый пример** — демонстрация на практике.

---

## 1. Repository — репозиторий

- **Очень просто:** общая папка проекта в интернете, где хранятся файлы и вся история их изменений.
- **Рабочий уровень:** репозиторий `KAT9I_OS` содержит архитектуру, правила, документацию и исходный код системы.
- **Технический уровень:** каноническое хранилище Git-объектов. Документация в каталоге `docs/` является единственным источником истины для архитектуры.
<details>
<summary><b>Пример на практике (нажмите, чтобы развернуть)</b></summary>

Адрес нашего репозитория: `https://github.com/rassvetpublic-spec/KAT9I_OS`. Когда коворкер делает `git clone`, он получает локальную копию всего репозитория на свой компьютер внутри защищённого контура `C:\GIT\`.
</details>

---

## 2. Issue — задача

- **Очень просто:** электронная карточка с описанием «что нужно сделать».
- **Рабочий уровень:** задача фиксирует цель, границы работ (Scope), исполнителя, приоритет (`[P0]`, `[P1]`, `[P2]`) и текущий статус выполнения. Вопросы без конкретной работы обсуждаются в Discussions или форме обратной связи.
- **Технический уровень:** канонический источник истины для состояния работы в проекте. Является внешним аналогом системного `TaskContract` (`docs/architecture/03_TASK_CONTRACT.md`).
<details>
<summary><b>Пример на практике (нажмите, чтобы развернуть)</b></summary>

Задача `#12: [P1] Добавить режим «Я здесь впервые» в документацию`. В ней описано, зачем нужен этот режим, какие шаги должен пройти новичок и каков критерий приёмки.
</details>

---

## 3. Branch — ветка

- **Очень просто:** отдельный рабочий стол, на котором можно безопасно работать, не мешая остальным и не ломая работающую систему.
- **Рабочий уровень:** любые изменения делаются в отдельной ветке, ответвлённой от актуальной `main`. Название ветки отражает суть (например, `docs/issue-12-guide` или `fix/issue-5-checks`).
- **Технический уровень:** изолированное рабочее пространство (Workspace) исполнителя. Защищает стабильный ствол `main` от случайных или непроверенных правок.
<details>
<summary><b>Пример на практике (нажмите, чтобы развернуть)</b></summary>

Команда создания изолированной ветки:
```bash
git checkout -b docs/issue-12-first-time-guide
```
Теперь любые изменения и файлы создаются только в этой изолированной ветке.
</details>

---

## 4. Commit — сохранённый шаг

- **Очень просто:** кнопка «сохранить этот шаг работы» с описанием того, что было сделано.
- **Рабочий уровень:** атомарная фиксация файлов с понятным сообщением на русском языке. Всегда можно посмотреть, кто, когда и почему изменил каждую строчку.
- **Технический уровень:** неизменяемый снимок дерева файлов с SHA-1/SHA-256 идентификатором (revision), образующий криптографически связанную историю изменений.
<details>
<summary><b>Пример на практике (нажмите, чтобы развернуть)</b></summary>

```bash
git add docs/guides/FIRST_TIME_GUIDE.md
git commit -m "docs: добавить руководство первого входа (#12)"
```
</details>

---

## 5. Pull Request / PR — запрос на принятие изменений

- **Очень просто:** вежливое обращение к команде: «Я закончил свою часть работы в отдельной ветке. Пожалуйста, проверьте её и добавьте в общий проект».
- **Рабочий уровень:** запрос на слияние ветки в `main`. Оформляется по русскому шаблону: цель, номер Issue, что изменено, что сознательно не менялось, проверки, evidence и риски.
- **Технический уровень:** объект ревью и точка фиксации ResultRef. Запускает автоматические проверки CI и требует проверки независимого QA.
<details>
<summary><b>Пример на практике (нажмите, чтобы развернуть)</b></summary>

PR `#25: docs: добавить режим «Я здесь впервые» и точку входа в README (#12)`. В нём наглядно виден diff (разница строк) и статус проверок роботами.
</details>

---

## 6. GitHub Actions — автоматические проверки (роботы)

- **Очень просто:** строгие роботы-помощники, которые сразу после сохранения проверяют проект на ошибки.
- **Рабочий уровень:** автоматический запуск тестов, линтеров, проверки UTF-8, русских описаний и целостности структуры. Зелёная галочка обязательна для принятия изменений.
- **Технический уровень:** машиночитаемые доказательства (Automated Evidence). Источник истины факта прохождения проверок конкретной revision.
<details>
<summary><b>Пример на практике (нажмите, чтобы развернуть)</b></summary>

Workflow `Контроль качества репозитория` (`.github/workflows/quality.yml`) запускается на каждый push и PR. Если кто-то забыл перевести заголовок или сломал структуру папок — робот сразу покажет ошибку красным крестиком.
</details>

---

## 7. QA — независимая проверка качества

- **Очень просто:** главный закон честности: «Один сделал — другой проверил».
- **Рабочий уровень:** квалифицирующая проверка значимого изменения выполняется другим коворкером или аудитором. Автор изменения не может сам подписать QA своему коду.
- **Технический уровень:** фундаментальный инвариант `Implementation Worker != QA Worker`. Проверка привязана к точному хэшу версии (commit SHA). Изменение head аннулирует предыдущий QA.
<details>
<summary><b>Пример на практике (нажмите, чтобы развернуть)</b></summary>

В описании PR заполняется блок:
```markdown
## Независимый QA
- [x] Независимый QA выполнен другим коворкером.
QA Worker: @auditor_login
Проверенная revision: c036af00b3ab73dc138b41267638269813d042ce
```
</details>

---

## 8. Merge — принятие изменений

- **Очень просто:** проверенное изменение торжественно становится частью основной версии.
- **Рабочий уровень:** после зелёных тестов CI и одобрения QA ветка сливается в `main`, а решённый Issue автоматически закрывается.
- **Технический уровень:** интеграция проверенного результата (Task Completion). Ветку изменения рекомендуется сразу удалять для чистоты репозитория.
<details>
<summary><b>Пример на практике (нажмите, чтобы развернуть)</b></summary>

Команда слияния через GitHub CLI:
```bash
gh pr merge 25 --merge --delete-branch
```
</details>

## 9. Дополнительные механизмы управления

| Механизм | Очень просто | Рабочее объяснение | Технический статус |
|---|---|---|---|
| **Project (доска)** | Доска с карточками | Столбцы: Входящие → Готово к работе → В работе → QA → Готово. | Только визуализация, не источник истины. |
| **Milestone (этап)** | Коробка с задачами | Группировка Issues под релиз: `v0.1`, `v0.2`, `v1.0`. | Организационная группировка. |
| **Release (выпуск)** | Официальный выпуск | Зафиксированная готовая версия с тегом и описанием. | Канонический факт официального релиза. |
| **Discussions** | Общий форум | Обсуждения, вопросы и свободные идеи до создания задач. | Неканоническое общение. |
| **CODEOWNERS** | Маршрутизатор проверок | Автоматически назначает ревьюера при изменении модуля. | Не даёт прав, только направляет review. |

## 🛡️ Золотое правило коворкера KAT9I_OS

> **Соблюдайте Scope (границы разрешённых изменений). Не трогайте файлы, не относящиеся к вашей задаче.**
> Если по пути вы заметили другую опечатку или баг — не исправляйте её тайком в текущей ветке. Создайте отдельный Issue в GitHub!
