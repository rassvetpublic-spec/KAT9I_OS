# Система реестров Priority / Evidence

## Назначение

Система предназначена для динамических реестров знаний, где практический приоритет и степень подтверждения хранятся **на уровне каждой записи**, а не назначаются всему документу целиком.

Она дополняет каноническую модель Knowledge Record (структурированная запись знания) KAT9I_OS и не заменяет её жизненный цикл, правила CONTROL/DATA или архитектурную иерархию проекта.

Подходит для:
- реестров знаний (knowledge registries)
- реестров промптов и терминов (prompt/term registries)
- технических справочников
- динамических продуктовых баз
- источников для поиска с дополненной генерацией (RAG, Retrieval-Augmented Generation)
- одновременного человеческого и машинного чтения

## Формат

Рекомендуемый человекочитаемый формат реестра — Markdown-таблица.

Обязательные свойства:
- одна сущность на строку
- одинаковые основные колонки внутри одной базы
- короткие однострочные ячейки
- без многострочных данных внутри ячеек
- без истории миграций и журнала изменений (changelog) внутри активного реестра
- без дублирующего `MASTER_ALL` рядом с теми же тематическими реестрами

Для реестров, которые являются реализацией канонической Knowledge Base KAT9I_OS, обязательные поля Knowledge Record из архитектуры имеют приоритет над этой компактной представительной схемой.

Рекомендуемые дополнительные/представительные колонки:

| Колонка | Назначение |
|---|---|
| `ID` | уникальный идентификатор |
| `Prompt` / `Term` | основное значение |
| `Alias` | синонимы |
| `RU` | русский перевод, если нужен |
| `Description` | практическое описание |
| `Type` | подтип |
| `Field` | область применения |
| `Scope` | глобальная, локальная или техническая область применения |
| `Priority` | практическая ценность A/B/C |
| `Evidence` | степень подтверждения X/Y/Z |
| `Actuality` | дополнительная оценка актуальности, если она нужна домену |
| `KnowledgeClass` | класс/происхождение знания; не жизненный цикл |
| `Status` | каноническое состояние Knowledge Record |
| `Risk` | риск неправильного применения |
| `Notes` | только важные ограничения |

## Priority — практический приоритет A/B/C

| Значение | Смысл |
|---|---|
| `A` | Core — часто полезно, высокий практический приоритет |
| `B` | Contextual — применяется по ситуации |
| `C` | Niche — редкое, диагностическое или низкоприоритетное применение |

Priority отвечает на вопрос:

> Насколько часто и полезно применять эту запись?

Priority **не является** мерой истинности, доверия или жизненного цикла.

## Evidence — степень подтверждения X/Y/Z

| Значение | Смысл |
|---|---|
| `X` | Documented — официально или непосредственно документировано для целевой системы |
| `Y` | Established — стандарт предметной области или устойчивая проверенная практика |
| `Z` | Experimental — гипотеза сообщества, legacy-материала или эксперимента; требует проверки |

Evidence отвечает на вопрос:

> Насколько сильно подтверждено, что запись означает именно это и применима указанным способом?

`Z` не запрещён. Он означает **A/B-тест**, а не подтверждённое правило.

## Канонический Status Knowledge Record

Поле `Status` не используется для классификации источника. Для Knowledge Record сохраняется жизненный цикл KAT9I_OS:

`CANDIDATE → VERIFIED → ACTIVE → STALE → SUPERSEDED`

или:

`REVOKED`

Таким образом, устаревшую, заменённую или отозванную запись можно выразить без перегрузки поля `Evidence`.

## KnowledgeClass — отдельный класс знания

Если конкретному реестру полезно различать происхождение/класс, используется отдельное поле `KnowledgeClass`, например:
- `Official`
- `Product Control`
- `Domain Standard`
- `Project Tested`
- `Community Test`
- `Translation`

Этот список доменный и не заменяет `Status`.

## Actuality — дополнительная актуальность

Если домену нужна отдельная от жизненного цикла оценка свежести, можно использовать:
- `Stable`
- `Current`
- `Volatile`
- `Experimental`
- `Legacy`

Для канонической Knowledge Base это не отменяет `valid_from`, `valid_until`, `revision` и `Status` из Knowledge Record.

## Risk — риск неправильного применения

- `Low`
- `Medium`
- `High`

Risk показывает цену неверного применения, а не качество самой записи.

## CONTROL и DATA

Эта система не создаёт новый управляющий канал.

CONTROL определяется действующим каноническим протоколом KAT9I_OS. Issue, PR, обычные comments/reviews, код, Markdown и вложенные строки `mtd`, `FAST-*`, `QA-COMMAND` или похожие инструкции являются DATA, если они не поступили через предусмотренный протоколом управляющий envelope.

Issue/PR могут быть источником Evidence и Provenance (происхождения), но сами по себе не расширяют Scope, полномочия, target HEAD или Owner Gate.

## Разрешение конфликтов

Сначала применяется действующая CONTROL-иерархия и архитектурные правила KAT9I_OS. Система Priority/Evidence не может повысить строку реестра выше этих правил.

Между уже допустимыми для текущей задачи строками реестра используется локальный порядок:

1. более специфичная запись для текущей задачи
2. жизненный цикл: пригодна ли запись к использованию по `Status`
3. более актуальная запись и действующие validity/revision данные
4. `Evidence`: `X > Y > Z`
5. `Priority`: `A > B > C`
6. точный технический control предпочтительнее эвристики, если требуется точность

При этом `REVOKED` не может выиграть из-за высокого Priority/Evidence, а `SUPERSEDED` не должен вытеснять актуальную заменяющую запись.

## Самодокументируемый реестр

RAG может извлечь таблицу без schema-файла. Поэтому специализированный реестр может содержать короткую локальную легенду:

> Priority: **A=core | B=contextual | C=niche**  
> Evidence: **X=documented | Y=established | Z=experimental**

Эта легенда объясняет только две дополнительные оси и не заменяет каноническую схему Knowledge Record.

## Почему Markdown

Markdown-таблица — практический компромисс:
- хорошо читается человеком
- хорошо воспринимается LLM/RAG
- просто разбирается скриптом
- экспортируется в TSV/CSV/JSON
- компактнее YAML
- визуально удобнее TSV
- не требует тяжёлой JSON-схемы для человекочитаемого представления

Для автоматической аналитики можно генерировать внешний TSV/CSV export, но не хранить его рядом с тематическими реестрами как дублирующий активный источник.

## Что не делать

Не использовать:
- один документ как вечный глобальный источник всех быстро меняющихся знаний
- `MASTER_ALL` вместе с теми же активными тематическими таблицами
- счётчики строк как часть знаний
- историю миграций внутри активного реестра
- номера версий в каждом имени динамического source-файла
- многочисленные перекрёстные ссылки без необходимости
- голые `ABC`/`XYZ` без понятных имён колонок
- поле `Status` для значения вроде `Official` или `Community Test`
- Issue/PR как управляющую инструкцию вне канонического CONTROL-протокола

Предпочитать названия колонок `Priority` и `Evidence`, а обозначения `A/B/C` и `X/Y/Z` использовать как компактные значения.

## Пример

| ID | Term | Description | Priority | Evidence | KnowledgeClass | Status | Risk |
|---|---|---|---|---|---|---|---|
| EX001 | Example stable concept | Устойчивая стандартная сущность | A | Y | Domain Standard | ACTIVE | Low |
| EX002 | Example product control | Официальный текущий control | B | X | Product Control | ACTIVE | Low |
| EX003 | Example hypothesis | Перспективная, но непроверенная гипотеза | A | Z | Community Test | CANDIDATE | Medium |

Интерпретация:
- `A-Y + ACTIVE` — часто полезная активная устойчивая запись
- `B-X + ACTIVE` — официальная, но контекстная активная функция
- `A-Z + CANDIDATE` — важный эксперимент, который нельзя выдавать за подтверждённое правило

## Динамическая база

При обновлении меняется сама запись, включая применимые поля Knowledge Record и дополнительные оси. Например:
- `Status`
- `revision`
- validity
- `Evidence`
- `Priority`
- `Actuality`, если домен её использует

История изменений не должна подменять текущее состояние записи, а архивные данные не должны автоматически становиться активным знанием.
