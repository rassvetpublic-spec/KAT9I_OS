# Система реестров Priority / Evidence

## Назначение

Система предназначена для динамических баз знаний, где нельзя назначить один файл вечным единым источником истины (SSOT, Single Source of Truth).
Достоверность и практический приоритет хранятся **на уровне каждой записи**, а не всего документа.

Подходит для:
- реестров знаний (knowledge registries)
- реестров промптов и терминов (prompt/term registries)
- технических справочников
- динамических продуктовых баз
- источников для поиска с дополненной генерацией (RAG, Retrieval-Augmented Generation)
- одновременного человеческого и машинного чтения

## Формат

Рекомендуемый формат активных реестров — Markdown-таблица.

Обязательные свойства:
- одна сущность на строку
- одинаковые основные колонки внутри одной базы
- короткие однострочные ячейки
- без многострочных данных внутри ячеек
- без истории миграций и журнала изменений (changelog) внутри активного реестра
- без дублирующего `MASTER_ALL` рядом с тематическими реестрами

Рекомендуемая схема:

| Колонка | Назначение |
|---|---|
| `ID` | уникальный идентификатор |
| `Prompt` / `Term` | основное значение |
| `Alias` | синонимы |
| `RU` | русский перевод, если нужен |
| `Description` | практическое описание |
| `Type` | подтип |
| `Field` | область применения |
| `Scope` | глобальная, локальная или техническая область применения |
| `Priority` | практическая ценность A/B/C |
| `Evidence` | степень подтверждения X/Y/Z |
| `Actuality` | актуальность |
| `Status` | класс знания |
| `Risk` | риск неправильного применения |
| `Notes` | только важные ограничения |

## Priority — практический приоритет A/B/C

| Значение | Смысл |
|---|---|
| `A` | Core — часто полезно, высокий практический приоритет |
| `B` | Contextual — применяется по ситуации |
| `C` | Niche — редкое, диагностическое или низкоприоритетное применение |

Priority отвечает на вопрос:

> Насколько часто и полезно применять эту запись?

Priority **не является** мерой истинности.

## Evidence — степень подтверждения X/Y/Z

| Значение | Смысл |
|---|---|
| `X` | Documented — официально или непосредственно документировано для целевой системы |
| `Y` | Established — стандарт предметной области или устойчивая проверенная практика |
| `Z` | Experimental — гипотеза сообщества, legacy-материала или эксперимента; требует проверки |

Evidence отвечает на вопрос:

> Насколько сильно подтверждено, что запись означает именно это и применима указанным способом?

`Z` не запрещён. Он означает **A/B-тест**, а не правило.

## Дополнительные оси

### Actuality — актуальность

Рекомендуемые значения:
- `Stable`
- `Current`
- `Volatile`
- `Experimental`
- `Legacy`

### Status — класс знания

Проект задаёт небольшой закрытый словарь статусов, например:
- `Official`
- `Product Control`
- `Domain Standard`
- `Project Tested`
- `Community Test`
- `Translation`

### Risk — риск неправильного применения

- `Low`
- `Medium`
- `High`

Risk показывает цену неверного применения, а не качество самой записи.

## Разрешение конфликтов

Сначала применяется действующая иерархия инструкций и источников KAT9I_OS: system/developer instructions, `AGENTS.md`, актуальные канонические `docs/`, связанная Issue/PR и их Evidence. Система Priority/Evidence не может повысить строку реестра выше этих источников.

Между уже разрешёнными для текущей задачи строками реестра используется локальный порядок:

1. более специфичная запись для текущей задачи
2. более актуальная запись
3. `Evidence`: `X > Y > Z`
4. `Priority`: `A > B > C`
5. точный технический control предпочтительнее эвристики, если требуется точность

## Самодокументируемый реестр

RAG может извлечь таблицу без schema-файла. Поэтому каждый реестр должен содержать короткую локальную легенду:

> Priority: **A=core | B=contextual | C=niche**  
> Evidence: **X=documented | Y=established | Z=experimental**

Полное описание системы хранится отдельно, но для понимания строки оно не обязательно.

## Почему Markdown

Markdown-таблица — практический компромисс:
- хорошо читается человеком
- хорошо воспринимается LLM/RAG
- просто разбирается скриптом
- экспортируется в TSV/CSV/JSON
- компактнее YAML
- визуально удобнее TSV
- не требует тяжёлой JSON-схемы

Для автоматической аналитики можно генерировать внешний TSV/CSV export, но не хранить его рядом с тематическими реестрами как дублирующий активный источник.

## Что не делать

Не использовать:
- один файл как вечный глобальный SSOT для быстро меняющейся базы
- `MASTER_ALL` вместе с теми же активными тематическими таблицами
- счётчики строк как часть знаний
- историю миграций внутри активного реестра
- номера версий в каждом имени динамического source-файла
- многочисленные перекрёстные ссылки
- голые `ABC`/`XYZ` без понятных имён колонок

Предпочитать названия колонок `Priority` и `Evidence`, а обозначения `A/B/C` и `X/Y/Z` использовать как компактные значения.

## Пример

| ID | Term | Description | Priority | Evidence | Actuality | Status | Risk |
|---|---|---|---|---|---|---|---|
| EX001 | Example stable concept | Устойчивая стандартная сущность | A | Y | Stable | Domain Standard | Low |
| EX002 | Example product control | Официальный текущий control | B | X | Current | Product Control | Low |
| EX003 | Example hypothesis | Перспективная, но непроверенная гипотеза | A | Z | Experimental | Community Test | Medium |

Интерпретация:
- `A-Y` — часто полезный устойчивый термин
- `B-X` — официальная, но контекстная функция
- `A-Z` — важный эксперимент, который нельзя выдавать за подтверждённое правило

## Динамическая база

При обновлении меняется сама строка:
- `Actuality`
- `Status`
- `Evidence`
- при необходимости `Priority`

Не требуется выпускать новый глобальный SSOT или переписывать историю базы. Старая сущность может быть помечена `Legacy`, заменена или удалена по правилам конкретного проекта.
