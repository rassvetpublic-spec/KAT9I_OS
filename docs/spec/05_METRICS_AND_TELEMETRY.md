# 5. Metrics & Telemetry — метрики и наблюдение

## Схема работы

```text
Выполнение задачи / этапа
        ↓
Telemetry Collector (сбор событий)
        ↓
Metrics Collector (сбор числовых показателей)
        ↓
Local Aggregator (локальная агрегация без ИИ)
        ↓
MetricsSnapshot (компактная сводка)
        ↓
┌───────────────────────┬────────────────────────┐
│                       │                        │
Обычный цикл       Anomaly Trigger         Periodic Analysis
(без ИИ)           (аномалия)              (периодический анализ)
│                       │                        │
только счётчики          ↓                        ↓
и таймеры           Learning / Analysis      LOW / NORMAL ИИ
│                       │                        │
└───────────────────────┴────────────────────────┘
        ↓
KPI / Baseline / Trends
```

## 5.1. Назначение

Система метрик должна измерять стоимость, скорость, качество, надёжность и эффективность работы KAT9I_OS.

Главный принцип:

> **Система метрик не должна заметно увеличивать расход токенов и стоимость основной работы.**

История метрик не передаётся ИИ целиком на каждом цикле выполнения. В обычном рабочем цикле метрики собираются и агрегируются обычным кодом без вызова LLM (языковой модели).

ИИ получает только компактный `MetricsSnapshot (сводку метрик)` или описание обнаруженной аномалии, когда анализ действительно нужен.

## 5.2. Разделение Telemetry, Metrics и Learning

### Telemetry (телеметрия)

Сырые события системы:

- Worker (исполнитель) запущен;
- провайдер недоступен;
- создан PR (запрос на внесение изменений);
- задача завершена;
- QA (независимая проверка) завершён;
- произошёл timeout (превышение времени выполнения).

### Metrics (метрики)

Числовые показатели, вычисленные из событий:

- длительность;
- количество попыток;
- расход токенов;
- стоимость;
- процент успешных QA;
- доля HIGH / NORMAL / LOW;
- доля локального ИИ;
- объём переданного контекста.

### Learning (самообучение)

Интерпретация накопленных показателей и доказательств:

> какой Worker эффективнее;
> какой Skill (навык) улучшился;
> где используется слишком дорогая модель;
> какой Context (контекст) можно сократить;
> какое изменение действительно улучшило систему.

Связь:

```text
Telemetry
   ↓
Metrics
   ↓
MetricsSnapshot
   ↓
Learning
```

## 5.3. Метрики стоимости

Минимально измеряются:

- входные токены;
- выходные токены;
- cached tokens (токены из кэша), если провайдер их сообщает;
- стоимость API (программного интерфейса), если применимо;
- число вызовов HIGH / NORMAL / LOW;
- использование подписочных провайдеров;
- использование локального ИИ;
- объём переданного контекста;
- объём данных, переданных ссылками вместо содержимого;
- стоимость одной успешно завершённой задачи.

Отдельная метрика:

### Context Transfer Saved (сэкономленная передача контекста)

Показывает, сколько данных KAT9I_OS не пришлось передавать модели благодаря `Reference-first (сначала ссылка)`.

Пример:

```text
Размер исходного контекста: 80 000 условных токенов
Реально передано через KAT9I_OS: 1 200
Экономия передачи: 98,5%
```

## 5.4. Метрики времени

Измеряются отдельно:

- время маршрутизации;
- время подготовки контекста;
- ожидание Worker;
- время работы модели;
- время инструментов;
- время CI (автоматической проверки изменений);
- время QA;
- время ожидания внешней системы;
- полное `Task Lead Time (полное время выполнения задачи)`.

Это позволяет находить реальный источник задержки, а не предполагать, что проблема всегда в ИИ.

## 5.5. Метрики эффективности

### First Pass Success Rate (успех с первой попытки)

Доля задач, которые были выполнены правильно без повторного запуска.

### Retry Rate (доля повторных попыток)

Показывает, сколько задач потребовали повторного выполнения.

### Escalation Rate (доля повышения уровня модели)

Например, сколько этапов пришлось перевести:

```text
LOW → NORMAL
NORMAL → HIGH
```

Высокий показатель означает, что начальная маршрутизация может быть неоптимальной.

### Context Efficiency (эффективность контекста)

Показывает, насколько объём переданного контекста соответствует реально необходимому объёму.

### Tool Efficiency (эффективность инструментов)

Показывает, какую часть работы удалось выполнить обычными инструментами без LLM.

## 5.6. Основные KPI

KAT9I_OS не должна иметь один универсальный KPI (ключевой показатель эффективности). Используется набор независимых показателей.

### Доля успешных проверок качества (QA Pass Rate)

Процент задач, успешно прошедших независимую проверку.

### Стоимость успешной задачи (Cost per Successful Task)

Стоимость одной успешно завершённой задачи.

### Медианное время выполнения задачи (Median Task Lead Time)

Медианное полное время выполнения задачи.

### Доля успешного завершения задач (Successful Completion Rate)

Процент задач, завершившихся реальным подтверждённым результатом.

### Доля вмешательства человека (Human Intervention Rate)

Доля задач, для которых потребовалось ручное вмешательство пользователя.

Связанный показатель:

### Доля автономного завершения задач (Autonomous Completion Rate)

Процент задач, полностью завершённых без вмешательства пользователя.

### Эффективность маршрутизации (Routing Efficiency)

Качество выбора Worker, модели и провайдера.

Пример успешной маршрутизации:

```text
NORMAL
→ выполнение с первой попытки
→ QA PASS
```

Пример неоптимальной маршрутизации:

```text
LOW → FAIL
NORMAL → FAIL
HIGH → PASS
```

## 5.7. Метрики самообучения

Самообучение должно подтверждаться измеримым результатом.

### Learning Gain (эффект обучения)

Сравнение показателей до и после изменения.

Например:

```text
QA Pass до изменения Skill: 71%
QA Pass после изменения Skill: 86%
Learning Gain: +15 п.п.
```

### Доля принятых предложений (Proposal Acceptance Rate)

Доля предложений системы самообучения, которые были приняты и признаны полезными.

### Доля регрессий (Regression Rate)

Доля изменений, после которых качество системы ухудшилось или появились новые ошибки.

Самообучение не считается успешным только потому, что изменение было внесено. Оно считается полезным только при доказанном улучшении метрик без недопустимых регрессий.

## 5.8. Метрики Skills (навыков)

Для каждого Skill при наличии достаточного числа запусков могут отслеживаться:

- число запусков;
- QA Pass Rate;
- доля переделок;
- пользовательское принятие результата;
- средний расход токенов;
- среднее время;
- число повторных попыток;
- Learning Gain после изменения Skill.

История используется для агрегации, но не передаётся модели целиком.

## 5.9. Метрики Worker и провайдеров

Метрики должны поддерживать разрезы:

- SYSTEM (вся система);
- DOMAIN (домен);
- WORKFLOW (рабочий процесс);
- WORKER (исполнитель);
- PROVIDER (провайдер ИИ);
- MODEL (модель);
- SKILL (навык);
- TASK TYPE (тип задачи);
- PROJECT (проект).

Это позволяет отвечать на практические вопросы:

- какой Worker лучше выполняет QA;
- какой провайдер эффективнее для конкретного домена;
- где HIGH используется без необходимости;
- какие Skills чаще требуют переделки;
- какой проект создаёт больше всего повторных запусков.

## 5.10. MetricsSnapshot — компактная сводка

Learning и другие интеллектуальные компоненты не должны читать полную историю метрик при каждом запуске.

Для этого формируется компактный `MetricsSnapshot (снимок метрик)`.

Он может содержать:

- период;
- тип задачи;
- количество наблюдений;
- success rate (процент успеха);
- QA pass rate;
- retry rate;
- средний и P95 расход токенов;
- среднее и P95 время;
- использование HIGH;
- использование локального ИИ;
- стоимость;
- обнаруженные аномалии;
- отклонение от baseline (базовой линии).

ИИ получает именно эту сводку, а не тысячи сырых записей.

## 5.11. Baseline — базовая линия

Для важных показателей хранится `Baseline (базовая линия)` — нормальный уровень работы системы.

Пример:

```text
Baseline QA Pass Rate = 92%
Текущее значение = 84%
Отклонение = -8 п.п.
```

Анализ запускается только при значимом отклонении или по установленному расписанию.

## 5.12. Три режима работы метрик

### Runtime Metrics — текущие метрики

Собираются на каждой задаче:

- счётчики;
- таймеры;
- статусы;
- числовые значения.

Нормальная цель:

> **0 дополнительных LLM-токенов.**

### Periodic Analysis — периодический анализ

Запускается не на каждой задаче, а, например:

- после заданного количества задач;
- раз в определённый период;
- для отдельного домена;
- перед циклом самообучения.

Анализируется агрегированная сводка.

### Anomaly Trigger — запуск по аномалии

Обычный код обнаруживает отклонение, например:

```text
retry_rate > baseline × допустимый коэффициент
cost вырос более установленного порога
QA Pass Rate упал ниже минимального уровня
```

Только после этого может быть вызван ИИ для поиска причины.

## 5.13. Observability Overhead — накладные расходы наблюдения

Система должна измерять стоимость самой системы метрик.

Отслеживаются:

- CPU;
- объём хранения;
- сетевой трафик;
- число дополнительных вызовов ИИ;
- дополнительные LLM-токены;
- дополнительное время выполнения.

Ключевой KPI:

### Накладные расходы LLM на метрики (Metrics LLM Overhead)

Доля токенов, потраченных только на анализ метрик, относительно общего расхода.

В обычном Runtime (рабочем цикле) целевое значение:

```text
≈ 0%
```

Периодический анализ допускает небольшой расход, но система наблюдения не должна становиться заметным потребителем ресурсов.

## 5.14. Архитектурные принципы

1. **Метрики являются первоклассным модулем KAT9I_OS.**
2. **Числа и события обрабатываются обычным кодом прежде, чем привлекать ИИ.**
3. **Полная история метрик не передаётся LLM в обычном цикле.**
4. **ИИ получает компактный MetricsSnapshot или конкретную аномалию.**
5. **Обычный сбор метрик должен требовать примерно 0 дополнительных LLM-токенов.**
6. **Метрики измеряют не только качество, но и стоимость, время, автономность и эффективность маршрутизации.**
7. **Самообучение должно подтверждаться измеримым Learning Gain.**
8. **Regression Rate обязательно учитывается при оценке самообучения.**
9. **Reference-first должен измеряться через экономию передачи контекста.**
10. **Накладные расходы Metrics/Telemetry измеряются самой системой.**
11. **Baseline используется для определения значимых отклонений.**
12. **Анализ истории запускается периодически или по аномалии, но не в каждом цикле задачи.**

## 5.15. Критерий готовности

Минимальная версия Metrics & Telemetry считается работоспособной, если для реального сквозного задания система может без отдельного LLM-вызова записать и агрегировать:

- итоговый статус;
- длительность этапов;
- количество попыток;
- используемый Worker;
- используемый провайдер и уровень модели;
- входные/выходные токены, если доступны;
- стоимость, если доступна;
- факт QA PASS/FAIL;
- объём переданного контекста;
- ResultRef (ссылку на результат);
- накладные расходы наблюдения.

После нескольких задач система должна уметь построить компактный MetricsSnapshot без чтения всей истории языковой моделью.

## 5.16. Стандарт сквозной трассировки (TraceContext и OpenTelemetry)

Для сквозной корреляции распределённых и многоязычных процессов (Rust Core, Electron UI, Python Workers) введён единый стандарт трассировки:

1. **Модель W3C TraceContext**:
   - `trace_id` (32 hex / 16 байт) — общий идентификатор жизненного цикла задачи;
   - `span_id` (16 hex / 8 байт) — уникальный идентификатор отдельного этапа;
   - `parent_span_id` — идентификатор родительского спана для построения полного графа выполнения.
2. **Типология этапов (SpanKind)**:
   - `CORE`, `SECURITY_DECISION`, `CONTEXT_PREPARATION`, `MODEL_CALL`, `TOOL_CALL`, `WORKER_EXECUTION`, `EXTERNAL_INTEGRATION`, `QA`, `STORAGE`, `RECOVERY`.
3. **Совместимость с OpenTelemetry**:
   - Экспорт в формат OTLP JSON (`ResourceSpans`), пригодный для визуализации в Jaeger, Grafana Tempo и SigNoz.
4. **Политика Zero Leak**:
   - Категорический запрет на запись секретов, паролей, токенов аутентификации и скрытых рассуждений модели в атрибуты и события спанов.
5. **Разделение Trace и Evidence**:
   - Trace фиксирует последовательность, тайминги и иерархию шагов;
   - Evidence доказывает факт корректности полученного результата или прохождения приёмочных тестов.

## Метрики Portable Promotion (§36)

Минимально измеряются `full_qa_runs`, `delta_qa_runs`, `qa_reuse_count`, `qa_reuse_rate`, `qa_invalidation_reason`, `saved_full_qa_runs`, `external_qa_tokens`, `external_qa_cost`, `queue_wait_time`, `candidate_rebuild_count`, `integration_retry_count`, `promotion_block_reason`, `promotion_lead_time` и `qa_amplification_factor`.

Обычный сбор и визуализация этих метрик не требуют LLM.
