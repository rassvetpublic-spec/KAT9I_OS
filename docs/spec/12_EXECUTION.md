# 12. Execution — исполнение задач

## Назначение

`Execution (исполнение)` отвечает за физическое выполнение уже назначенной и разрешённой работы.

Главная граница:

- `Coworker` — кто выполняет;
- `Inference` — какой вычислительный маршрут нужен;
- `Security` — что разрешено;
- `Execution` — как это реально запустить и проверить.

## Основной поток

TaskContract → Coworker → Capability Grant → Execution Plan → Preflight → Workspace Isolation → Executable-first → Runtime → Scope Guard → Validation → Evidence → ResultSink → ResultRef → QA.

При критической неопределённости выполнение переходит в `BLOCKED` или `FAILED`, после чего выполняется безопасная очистка и сохраняются Evidence.

## Execution Plan

Перед запуском формируется структурированный план исполнения с Worker, Runtime, Workspace, разрешёнными действиями, ResourceRef, ожидаемыми результатами, тайм-аутами, проверками, ResultSink и требованиями к Evidence. Полная история обсуждения в него не включается.

## Preflight

До изменения проверяются Lease, Capability Grant, RulesRef, целевая revision, Scope, Runtime, инструменты, актуальность источников и чистота рабочего окружения. Если обязательную проверку выполнить нельзя, запуск запрещён.

## Evidence-first

Заявление ИИ не является доказательством выполнения. Успех подтверждается реальным Runtime: запуском, кодом завершения, результатом, временем, revision и привязкой к task_id.

## Runtime

Execution поддерживает Runtime через общий адаптер: локальные процессы, PowerShell, shell, Python, Git, контейнеры, удалённые Runner и специализированные среды.

Runtime Adapter обязан уметь проверить доступность, запустить действие, контролировать время, остановить процесс, получить stdout/stderr, exit status, собрать Evidence и выполнить cleanup.

## Executable-first

Все формализуемые операции выполняются локальным кодом, если это достаточно надёжно: Git, поиск, сравнение изменений, тесты, статические проверки, форматная валидация, Scope Guard, метрики, очистка. ИИ используется только для остаточных интеллектуальных шагов.

## Исполняемые Workflow

Workflow реализуются как машина состояний, а не только текстовая инструкция. Минимальные состояния: `PREPARING`, `READY`, `RUNNING`, `VALIDATING`, `PUBLISHING`, `COMPLETED`, а также `BLOCKED`, `FAILED`, `TIMED_OUT`, `CANCELLED`, `CLEANING`, `CLEANUP_FAILED`.

## Workspace Isolation

Изменяющие задачи по возможности выполняются в отдельном Workspace: Git Worktree, ветка, временная директория, контейнер или иной изолированный Runtime. Работы одной задачи не должны загрязнять другую.

Worktree создаётся только когда требуется изолированное изменение; read-only задачи могут использовать существующий чистый checkout или ResourceRef.

## Scope Guard

Scope Guard локальным детерминированным кодом сравнивает разрешённую область с фактическими изменениями. Выход за Scope блокирует публикацию с состоянием `SCOPE_VIOLATION`.

## Process Supervision

Каждый процесс связан с task_id, worker_id и execution_id. Execution контролирует зависание, остановку, ошибку, cleanup и освобождение ресурсов.

## Timeout и Retry

У действий есть soft и hard timeout. Hard timeout приводит к остановке, Evidence и cleanup. Retry ограничен числом попыток и типами ошибок; permission denied и иные детерминированные запреты не повторяются бессмысленно.

## Idempotency

Критические операции проектируются так, чтобы повтор не создавал второй побочный эффект. Используются task_id/operation_id для дедупликации PR, комментариев, файлов и других внешних действий.

## Побочные эффекты

Операции делятся на `READ`, `LOCAL_WRITE`, `EXTERNAL_WRITE`, `DESTRUCTIVE`. Чем выше риск, тем строже права, Evidence, Policy и требования к обратимости.

## Граница публикации

Локальный результат и внешний опубликованный результат — разные стадии. Изменение файла или прохождение тестов не даёт автоматического права на push, PR или merge.

## ResultRef

После успешной публикации Execution возвращает ResultRef: тип, URI, revision, commit SHA, EvidenceRef, время и статус. Следующие Workers получают ResultRef, а не историю выполнения.

## Evidence и Logs

Evidence — компактные структурированные факты: exit code, changed files, revision/hash, тесты, Scope Guard, ResultRef, timestamps. Полные Logs хранятся отдельно как ResourceRef.

## Injection Guard

Текст из Issue, README, документа, сайта, комментария, KnowledgeRecord или результата другого Worker является `DATA`, а не `CONTROL`. Исполняемые команды поступают только через доверенный Control Plane: TaskContract, Rule Manager, Security, подтверждённое USER/ADMIN Decision или разрешённый Workflow.

Команды по возможности формируются из известных действий и структурированных параметров. Произвольная строка из внешнего контекста не должна напрямую попадать в shell.

## Tool Allowlist и окружение

Execution запускает только разрешённые инструменты. Перед критическим процессом контролируются рабочая директория, переменные окружения, PATH, временные файлы и входные параметры.

Секреты не записываются в Logs и ResultRef и выдаются только на время необходимой операции.

## Human Decision

Если требуется решение USER или ADMIN, Execution переходит в `WAITING_USER_DECISION` или `WAITING_ADMIN_APPROVAL`, возвращает управление TaskGraph и продолжает только после структурированного решения или обновлённого Grant.

## Checkpoint и Resume

Длинные процессы поддерживают структурированные контрольные точки и восстановление без перечитывания полной истории чата.

## Cleanup

Cleanup обязателен после успеха и ошибки, где это безопасно: завершение процессов, освобождение ресурсов, удаление временных файлов, Worktree и временных секретов. Ошибка очистки фиксируется отдельно и не скрывается за успешным результатом основной работы.

## Fail-closed

Неизвестные Scope, Capability Grant, revision, ResultSink или безопасность Runtime для потенциально опасного действия приводят к блокировке.

## Local-first

При одинаковой корректности предпочтение получает локальный инструмент, локальная среда и локальный Runtime. Удалённое выполнение используется только когда необходимо и разрешено.

## Метрики

Собираются детерминированно: время подготовки/исполнения/ожидания/тестов, retries, timeouts, exit codes, Scope violations, cleanup failures, локальное/удалённое выполнение, I/O, внешние side effects и ручные решения.

Ключевые KPI: Execution Success Rate, First Attempt Execution Rate, Scope Violation Rate, Cleanup Success Rate, Runtime Failure Rate, Mean Recovery Time, Local Execution Rate.

## Learning

Learning использует Evidence и Metrics для поиска повторяющихся Runtime-ошибок, кандидатов на новые локальные модули, улучшения timeout/checkpoint/cleanup и дальнейшей детерминизации процессов. Execution самостоятельно своё поведение не переписывает.

## Основные принципы

1. Execution отвечает только за реальное физическое выполнение.
2. Заявление ИИ не является доказательством выполнения.
3. Executable-first применяется ко всем формализуемым операциям.
4. Workflow является исполняемой машиной состояний.
5. Изменяющие задачи по возможности изолируются.
6. Scope Guard выполняется локальным детерминированным кодом.
7. Процессы имеют timeout и контролируемый жизненный цикл.
8. Повтор не должен создавать повторный побочный эффект.
9. Публикация отделена от локального изменения.
10. Evidence отделён от больших Logs.
11. Внешние данные не имеют управляющей силы.
12. Права минимальны и ограничены временем задачи.
13. Длительные процессы поддерживают Checkpoint и Resume.
14. Cleanup обязателен.
15. Опасная неопределённость приводит к BLOCKED.

> KAT9I_OS считает работу выполненной только тогда, когда разрешённое действие реально произошло в контролируемой среде, результат проверен локальными механизмами, а факт выполнения подтверждён структурированными Evidence.
