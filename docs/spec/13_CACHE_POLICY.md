# 13. Cache Policy — политика кэширования KAT9I_OS

## Назначение

Кэширование используется для экономии времени, токенов, сетевого трафика, вычислений и повторной работы. Кэш не применяется автоматически ко всем данным.

Главный принцип:

> Кэшировать только то, что разрешено, безопасно и имеет достаточную вероятность повторного использования.

## Классы кэширования

- `CACHE_ALLOWED` — обычное разрешённое кэширование;
- `CACHE_LIMITED` — только с ограничениями по времени, месту, шифрованию или Scope;
- `CACHE_SESSION_ONLY` — только в рамках текущей задачи/сессии;
- `NO_CACHE` — сохранение запрещено.

Запрет кэширования имеет приоритет над разрешением.

## Размещение и spill

Класс кэширования определяет не только возможность повторного использования, но и допустимое физическое размещение записи. Memory pressure не может ослаблять эти ограничения.

- `NO_CACHE` не принимается в CacheEngine;
- `CACHE_SESSION_ONLY` в первой реализации хранится только в допустимой оперативной памяти и полностью удаляется при завершении задачи/сессии;
- `CACHE_LIMITED` может попасть на диск только при явном разрешении политики и выполнении всех требований по Scope, месту хранения, TTL/retention и шифрованию;
- `CACHE_ALLOWED` может использовать RAM и разрешённый spill, если Security не задаёт более строгих ограничений.

Если запись нельзя безопасно spill'ить, CacheEngine удаляет её и при необходимости пересчитывает позже. Производительность не имеет приоритета над Security.

## Явная очистка

KAT9I_OS должна поддерживать команду пользователя/администратора «очистить кэш» с указанным Scope: весь кэш, проект, Context, Resource, модель, текущая задача и т. п. Очистка выполняется локальным детерминированным кодом.

Команда очистки кэша не удаляет канонические KnowledgeRecord, Rules, Metrics history, Task state, документы и другие источники истины. Удаляются только восстанавливаемые производные данные.

## Реестр кэша (Cache Registry)

Для записи кэша хранятся как минимум: cache_id, source_ref, source_revision, type, scope, created_at, last_access, size, TTL, Security classification, invalidation policy, recompute cost, hit count, confidence и dependencies.

## Срок жизни (TTL)

`TTL (срок жизни)` различается по типу данных. Он является самообучаемым параметром, но Learning не может превышать максимальные сроки, установленные Security/Policy.

TTL — только один сигнал. Кэш может устареть раньше, если существенно изменился контекст или зависимые версии.

## Смещение контекста (Context Drift)

KAT9I_OS оценивает `Context Drift (смещение контекста)` и `Context Similarity Score (сходство контекста)`. Глобальный фиксированный порог вроде 50% не используется для всех типов данных.

Изменение половины контекста может означать разную полезность для разных типов кэша. Для QA изменение даже одного критичного файла может полностью инвалидировать результат.

## Результаты проверки кэша

Перед использованием запись получает один из статусов:

- `FULL_HIT` — можно использовать полностью;
- `PARTIAL_HIT` — часть результата применима;
- `MISS` — требуется пересчёт;
- `STALE` — запись устарела;
- `FORBIDDEN` — использование/хранение запрещено.

## Частичное попадание и инкрементальный пересчёт (Partial Hit и Incremental Recompute)

Если изменилась только часть входов, KAT9I_OS должна по возможности повторно использовать неизменившуюся часть и пересчитывать только изменившуюся.

Это применяется к индексам, анализу репозитория, embeddings, summaries, dependency graph, Research registry и большим документам.

## Зависимости записи

Кэш привязывается к значимым входам: source revision, RulesRef digest, Skill version, Workflow version, ContextRefs, параметрам запуска и версии инструмента.

Изменение критичного Rule/Skill/Workflow может автоматически инвалидировать зависимый кэш.

## Семантический кэш (Semantic Cache)

Допускается смысловой кэш для поиска похожих предыдущих задач/результатов. Такой результат считается подсказкой, а не актуальным доказательством. Для критичных действий требуется повторная проверка.

Semantic Cache по возможности реализуется локальным индексом, локальными embeddings и локальным ИИ.

## Кэш результатов (Result Cache)

Ответы моделей могут повторно использоваться только если совпадают существенные входы, Rules, версии Skill/Workflow, политика безопасности и требования актуальности.

Не допускается слепое повторное использование Security Decision, USER/ADMIN approval, текущего GitHub status, QA для изменившегося head, прав, секретов и одноразовых токенов.

## Кэш проверок качества (QA Cache)

QA привязан к точной revision. Изменение head SHA инвалидирует действующий QA. Старый QA может использоваться только как вспомогательный источник.

## Прогрев и вытеснение кэша (Cache Warming и Eviction)

Часто используемые разрешённые данные могут предварительно кэшироваться, если выгода доказана. Удаление учитывает TTL, размер, частоту использования, стоимость пересчёта, чувствительность, устаревание, Context Drift и лимиты диска.

## Экономика

Кэширование оценивается не только по Hit Rate, но и по чистой выгоде. Дорогие для пересчёта результаты могут храниться дольше, если Security разрешает.

## Обучение (Learning)

Learning может изменять TTL, пороги сходства, стратегию Partial Hit, Cache Warming, приоритет удаления и перечень выгодных типов кэша. Learning не может отменять `NO_CACHE`, ослаблять Security, кэшировать секреты или превышать максимальные сроки политики.

## Метрики

Минимально измеряются:

- Cache Hit Rate;
- Partial Hit Rate;
- Cache Miss Rate;
- Stale Hit Rate;
- Cache Savings — сэкономленные токены, время, API cost, CPU/GPU и network I/O;
- Cache Waste — стоимость хранения, обновления и бесполезных проверок;
- `Net Cache Gain (чистая выгода кэша)`.

## Объяснимость

Решение об использовании или отклонении кэша должно быть кратко объяснимо через проверяемые признаки: revision, RulesRef, Context Similarity, TTL, зависимости и риск.

## Границы модулей

- Context использует кэш retrieval, summaries, rankings, Context Packs и индексов;
- Resources владеет ResourceRef, source revision и правилами разрешения источника; физическим размещением runtime cache и spill владеет CacheEngine;
- KnowledgeRecord не является кэшем, но его индексы/embeddings/summaries могут кэшироваться;
- Inference может кэшировать capability matrix, availability и routing statistics с отдельной Freshness Policy;
- Execution может использовать build/test/dependency cache, если это разрешено Domain/QA Policy, и отражает использование кэша в Evidence.

## Основной алгоритм

Перед использованием кэша проверяются:

1. разрешено ли кэширование;
2. identity/revision;
3. Rule/Skill/Workflow version;
4. TTL;
5. Context Drift;
6. возможность частичного повторного использования;
7. стоимость пересчёта против стоимости проверки/хранения;
8. риск устаревшего результата.

> Кэш в KAT9I_OS — управляемый экономический механизм повторного использования вычислений. Система хранит только разрешённые данные, учитывает степень изменения контекста, повторно использует неизменившиеся части и самообучается оптимальным срокам и условиям кэширования.
