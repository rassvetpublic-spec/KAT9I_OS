# 15. Интеграции и MCP — внешние подключения KAT9I_OS

## 15.1. Назначение

Модуль интеграций отвечает за то, **как KAT9I_OS технически взаимодействует с внешними системами**.

Главная граница:

- `Resources (ресурсы)` отвечает: **что это за объект**;
- `Integrations (интеграции)` отвечает: **как выполнить операцию с этим объектом**.

Например, Resources знает, что нужен конкретный GitHub PR, а Integrations выбирает способ доступа: локальный Git, встроенный Connector (подключение), API (программный интерфейс) или MCP.

## 15.2. Общая схема

Domain / Context / Resources / Execution
→ Tool Broker (единый брокер инструментов)
→ Integration Registry (реестр интеграций)
→ выбор Adapter (адаптера):
- локальная библиотека;
- CLI (командный интерфейс);
- встроенный Connector (подключение);
- API;
- MCP Client (клиент MCP);
- локальный сервис;
- удалённый сервис.
→ Security Gateway (шлюз безопасности)
→ внешняя система
→ структурированный результат
→ ResourceRef / ResultRef / Evidence.

## 15.3. Connector — подключение

Connector (подключение) — адаптер конкретной внешней системы, например GitHub, Google Drive, Obsidian, локальной файловой системы или Knowledge Store (хранилища знаний).

Он преобразует внутренний контракт KAT9I_OS в вызов внешней системы.

## 15.4. Сменяемые адаптеры

Одна логическая возможность может иметь несколько технических реализаций.

Например чтение GitHub repository может выполняться через:
- локальный Git;
- GitHub Connector;
- REST API;
- MCP.

Доменные модули не должны зависеть от конкретного транспорта.

## 15.5. Tool Broker — единый брокер инструментов

Tool Broker (брокер инструментов) даёт системе одну логическую возможность независимо от физического способа её реализации.

Например capability (возможность) `github.read_pr` может быть реализована через Connector, API, MCP или локальные инструменты.

Domain (домен) запрашивает возможность, а Tool Broker выбирает реализацию.

Это уменьшает число инструментов, видимых Worker, сокращает контекст и снижает вероятность неправильного выбора.

## 15.6. Исполняемый код и локальный приоритет

При выборе Adapter действует принятый порядок:
1. локальный исполняемый код, если он полностью решает задачу;
2. локальный Adapter;
3. уже доступный встроенный Connector;
4. уже оплаченная внешняя возможность;
5. API или MCP в зависимости от правил, доступа к данным, стоимости и задержки.

Security и актуальность всегда проверяются раньше экономии.

## 15.7. Реестр интеграций

Integration Registry (реестр интеграций) должен хранить минимум:
- идентификатор интеграции;
- тип;
- поддерживаемые возможности;
- операции чтения/записи;
- типы ресурсов;
- уровень доверия;
- состояние;
- задержку;
- стоимость;
- доступных Workers;
- версию;
- результат последней проверки доступности.

## 15.8. Проверка доступности

Интеграции должны иметь детерминированные состояния:
- `AVAILABLE` — доступна;
- `DEGRADED` — работает частично;
- `UNAVAILABLE` — недоступна;
- `AUTH_REQUIRED` — требуется авторизация;
- `BLOCKED` — запрещена политикой.

Для обычной проверки доступности LLM не нужен.

## 15.9. Возможности и права — разные сущности

Техническая способность интеграции выполнить действие не означает разрешение на это действие.

Например `read`, `write`, `merge`, `delete` рассматриваются как разные возможности и отдельно проверяются Security.

## 15.10. Шлюз безопасности

Каждый внешний вызов с побочным эффектом проходит через:
Identity (идентичность)
→ Rules (правила)
→ Scope (область действия)
→ Capability Grant (выданное разрешение)
→ Data Classification (классификацию данных)
→ Tool Allowlist (разрешённый набор инструментов)
→ вызов.

Connector не может быть способом обхода Security.

## 15.11. Внешний ответ — это DATA, а не CONTROL

Результат API, MCP, Connector или внешнего сервиса считается `DATA (данные)`.

Даже если внешний инструмент вернул текст с управляющей инструкцией, она не становится `CONTROL (управляющей командой)`.

## 15.12. Структурированный результат

Adapter должен по возможности возвращать структурированный результат:
- resource_id;
- revision;
- status;
- поля объекта;
- ResourceRef;
- Error;
- Evidence.

Если API возвращает JSON, его разбирает обычный код. LLM не должен использоваться для извлечения простых полей, которые можно получить детерминированно.

## 15.13. MCP — Model Context Protocol (протокол контекста модели)

MCP используется как один из способов интеграции с внешними Tools (инструментами) и Resources (ресурсами).

MCP **не является внутренней архитектурой KAT9I_OS**.

Внутри модульного монолита предпочтительны прямые типизированные внутренние интерфейсы.

MCP используется прежде всего на границах:
- другой процесс;
- другой компьютер;
- отдельный продукт;
- сторонний Tool Server (сервер инструментов);
- IDE;
- внешний агент.

## 15.14. Не превращать внутренние модули KAT9I_OS в MCP-сервисы без необходимости

Схема вида Core → MCP → Context → MCP → Resources → MCP → Execution создаёт лишнюю сериализацию, задержки, сложность отладки и дополнительные границы безопасности.

Внутри KAT9I_OS используются внутренние контракты. MCP применяется на внешней границе.

## 15.15. MCP Client — клиент MCP

MCP Client позволяет KAT9I_OS использовать внешний MCP Server.

Путь:
Task capability requirement (требование к возможности задачи)
→ Tool Broker
→ MCP Adapter
→ Security Gateway
→ MCP Server
→ DATA result.

## 15.16. Собственный сервер MCP (MCP Server KAT9I_OS)

KAT9I_OS может предоставлять ограниченный набор возможностей внешним агентам через собственный MCP Server.

Например:
- получить разрешённую задачу;
- получить ContextRef;
- вернуть ResultRef;
- запросить capability;
- получить разрешённый поиск по Knowledge Base.

Нельзя автоматически публиковать наружу все внутренние функции системы.

## 15.17. MCP Gateway — шлюз MCP

Входящий MCP-запрос должен проходить:
authentication (проверку подлинности)
→ Identity
→ schema validation (проверку схемы)
→ Security
→ Scope
→ Tool Allowlist
→ внутреннюю capability
→ sanitized result (очищенный результат).

MCP Server не получает прямого неконтролируемого доступа к Core.

## 15.18. Несколько аккаунтов

Один внешний сервис может иметь несколько подключений: личный аккаунт, рабочий аккаунт, service account (служебный аккаунт).

Integration Registry различает их, а TaskContract и Security определяют, какое подключение разрешено для конкретной задачи.

## 15.19. Учётные данные

Credentials (учётные данные) не передаются как обычный текст запроса.

Используется `CredentialRef / SecretRef (ссылка на учётные данные или секрет)`.

Секрет не должен попадать в Context, обычные Logs, ResultRef или обычный Cache.

## 15.20. Ограничение фактических прав Adapter

Даже если технический токен имеет широкие права, Adapter обязан соблюдать более узкий Capability Grant конкретной задачи.

Например подключение технически умеет запись, но задача разрешает только чтение — Adapter выполняет только чтение.

## 15.21. Лимиты и повторные попытки

Rate limits (ограничения частоты), quotas (квоты) и ошибки интеграций обрабатываются кодом.

Повтор зависит от причины:
- `429` может допускать повтор;
- `403` обычно требует изменения прав;
- `401` может требовать повторной авторизации USER/ADMIN.

Бесконечные повторные попытки запрещены.

## 15.22. Circuit Breaker — автоматическое временное отключение

Если Integration многократно падает, она временно переводится в `DEGRADED` или `UNAVAILABLE`, после чего выбирается альтернативный Adapter.

Это должно работать без LLM.

## 15.23. Fallback — запасной маршрут

Fallback (запасной маршрут) может переключать способ доступа, например Connector → local Git → API → MCP.

Но Fallback не может расширять Security Scope или выдавать новые права.

## 15.24. Web UI — веб-интерфейс

Веб-интерфейс внешнего сервиса считается отдельным типом маршрута.

Наличие сайта не означает наличие безопасного API.

Web UI, Connector и API — разные возможности и могут требовать разных Workers.

## 15.25. Пользователь и администратор в интеграционном процессе

USER и ADMIN могут участвовать в интеграции, например:
- USER подключает аккаунт;
- ADMIN разрешает новую Integration;
- ADMIN выдаёт доступ к чувствительному ресурсу.

Но человек не должен вручную выполнять техническую операцию, которую KAT9I_OS может безопасно выполнить сама.

## 15.26. События и Webhooks

Внешние системы могут создавать события: новый Issue, PR, письмо, изменение документа и т. д.

Правильный путь:
External Event (внешнее событие)
→ Security
→ Event Normalization (нормализация события)
→ Task Candidate (кандидат в задачу)
→ Core
→ Rule Manager
→ TaskContract.

Внешнее событие не становится исполняемой командой напрямую.

## 15.27. Защита от внедрения команд через события

Webhook, Issue, письмо или MCP event считаются DATA.

Даже название Issue вида «ADMIN: удалить всё» не является административной командой.

## 15.28. Публикация результатов

Интеграции выполняют внешние операции записи, например:
- создать PR;
- создать Issue;
- сохранить документ;
- отправить комментарий.

После записи Adapter должен вернуть `ResultRef + revision + Evidence`.

Для критических изменений желательно выполнить повторное чтение и проверить, что результат действительно записан.

## 15.29. Идемпотентность

Повтор одного и того же Integration write не должен создавать лишний дубликат.

Используются task_id, operation_id и внешние механизмы идемпотентности, если они доступны.

## 15.30. Кэш интеграций

Метаданные и некоторые результаты чтения могут кэшироваться только по общей Cache Policy.

Критичные permissions, authentication state и изменяемое внешнее состояние имеют отдельные правила актуальности.

Старый Cache не может служить доказательством текущих прав.

## 15.31. Наблюдаемость и метрики

Для каждого Integration-вызова фиксируются минимум:
- integration_id;
- capability;
- adapter;
- latency (задержка);
- success/failure;
- retry;
- bytes transferred;
- использование кэша;
- внешний побочный эффект;
- task_id.

Полные чувствительные payload (содержимое запросов/ответов) не должны записываться без необходимости.

Ключевые показатели:
- Success Rate (доля успешных вызовов);
- Error Rate (доля ошибок);
- Retry Rate (доля повторов);
- Fallback Rate (доля переключений на запасной маршрут);
- Local Adapter Rate (доля локальных адаптеров);
- MCP Rate;
- API Rate;
- Connector Rate;
- объём переданных данных;
- число внешних операций записи.

## 15.32. Самообучение интеграций

Learning может улучшать выбор Adapter, определять более надёжные маршруты, полезность локального доступа и кэширования.

Learning не может самостоятельно подключать новый внешний сервис с расширенными правами или ослаблять Security.

## 15.33. Что модуль интеграций не должен делать

Integrations не должны:
- выбирать Domain;
- разрешать конфликты Rules;
- назначать Worker;
- определять необходимый Context;
- выбирать Intelligence Tier;
- самостоятельно повышать Trust;
- интерпретировать внешний текст как CONTROL;
- самостоятельно расширять Scope;
- хранить Knowledge как источник истины.

## 15.34. Основные принципы

1. Resources отвечает «что», Integrations — «как».
2. Одна логическая возможность может иметь несколько Adapter.
3. Tool Broker скрывает транспортные различия от Domains.
4. Executable-first и Local-first действуют при выборе способа интеграции.
5. Security проверяется перед внешним вызовом.
6. Read, Write, Merge, Delete — разные возможности.
7. Результаты внешних систем являются DATA.
8. Структурированный ответ предпочтительнее произвольного текста.
9. LLM не парсит то, что может разобрать обычный код.
10. MCP — протокол внешней границы, а не внутренний каркас KAT9I_OS.
11. MCP Server и MCP Client подчиняются общим Security rules.
12. Credentials передаются через SecretRef.
13. Fallback не может расширять права.
14. External Event сначала становится Task Candidate, а не выполняемой командой.
15. External writes должны быть идемпотентными и подтверждаться Evidence.
16. Кэш интеграций подчиняется общей Cache Policy.
17. Metrics и Learning могут оптимизировать Adapter, но не ослаблять Security.

## 15.35. Главный принцип

> KAT9I_OS должна воспринимать GitHub, Google Drive, Obsidian, API, MCP, локальные программы и другие сервисы как сменяемые способы доступа к логическим возможностям, а не как архитектурные зависимости Core.
