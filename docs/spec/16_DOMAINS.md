# 16. Домены — предметные области KAT9I_OS

## 16.1. Назначение

Домен — это предметная область KAT9I_OS, которая отвечает на вопрос: что именно нужно делать в конкретном классе задач.

Базовые домены:
- разработка программного обеспечения;
- оптимизация репозитория;
- Suno;
- исследования;
- документы;
- инженерные задачи;
- автоматизация;
- визуализация процессов KAT9I_OS.

## 16.2. Граница домена

Домен содержит предметную логику, специализированные процессы, проверки, форматы результата, предметные навыки и исполняемые процессы.

Домен не должен самостоятельно реализовывать безопасность, общий менеджер правил, выбор исполнителя, выбор уровня ИИ, управление процессами операционной системы, общую систему контекста, общий кэш, общую систему метрик или общую базу знаний.

## 16.3. Общая схема домена

TaskContract (контракт задачи)
→ определение предметной области
→ предметный контракт
→ исполняемый процесс
→ локальный код там, где задача формализуема
→ Inference (выбор ИИ) только там, где нужен интеллект
→ Resources / Integrations (ресурсы / интеграции) при обращении к внешним данным
→ Coworker (распределение исполнителей) при необходимости другого исполнителя
→ предметная проверка
→ ResultRef (ссылка на результат)
→ независимый QA при необходимости.

## 16.4. Домен не равен проекту

Suno — домен.
AG25 и Genre_test — проекты.
Один проект может использовать несколько доменов.

## 16.5. Один основной домен на конкретную задачу

Один конкретный TaskContract имеет один основной домен. Междоменные задачи выражаются через TaskGraph (граф задач) и связанные дочерние задачи.

## 16.6. Стандартная структура домена

Каждый домен должен по возможности иметь:
- контракты;
- процессы;
- навыки;
- исполняемые шаги;
- проверяющие модули;
- форматирование;
- предметные правила;
- привязки к базе знаний;
- тесты;
- предметные метрики;
- профили качества.

## 16.7. Сначала исполняемый код

Для каждого навыка и процесса обязательно проверяется возможность переноса повторяемой и проверяемой логики в локальный исполняемый код.

Предпочтительная эволюция:
MODEL (в основном модель)
→ HYBRID (код + модель)
→ CODE (исполняемый код), если это возможно без потери качества.

## 16.8. Разработка программного обеспечения

Базовые процессы:
- Issue → анализ → план → Claim → изолированная рабочая область → реализация → тесты → контроль области изменений → PR → QA;
- PR → точная версия → проверки → независимый QA → CI → решение о принятии;
- ошибка → воспроизведение → поиск первопричины → исправление → тест от повторного появления ошибки → QA → PR;
- Issues → зависимости → дубликаты → приоритеты → группы задач → порядок реализации.

Максимально кодом выполняются Git status, Git diff, создание Worktree, проверка ветки, контроль области изменений, commit SHA, тесты, lint, статический анализ, CI, список изменённых файлов, exact-head и сбор доказательств.

Жёсткий инвариант: Implementation Worker (исполнитель изменения) != QA Worker (независимый проверяющий).
QA привязан к точной версии результата.

## 16.9. Оптимизация репозитория

Процесс:
репозиторий → инвентаризация → карта архитектуры → зависимости → дублирование → мёртвый код → сложность → тесты → CI → документация → безопасность → производительность → список улучшений.

Аудит не должен незаметно превращаться в изменение. Выводы становятся отдельными задачами разработки.

## 16.10. Suno

Suno — самостоятельный домен и не является частью общего ядра исполнения.

Домен знает структуру песни, BPM, тональность, вокальную режиссуру, рифмовку, музыкальный стиль, ограничения Suno и форматы Style / Lyrics / Negative.

Базовый процесс:
идея → анализ → драматургия → редактура текста → структура → вокальная режиссура → музыкальный стиль → подготовка формата Suno → детерминированная проверка → финальная содержательная проверка.

Кодом по возможности выполняются проверки длины, структуры секций, обязательных блоков, запрещённых тегов, фиксированных строк, BPM, тональности и формата.

## 16.11. Исследования

Базовый процесс:
вопрос → поиск потенциальных источников → первичные источники → проверка → дедупликация → сравнение → синтез → выводы → рекомендации → кандидаты в базу знаний.

Каждый значимый вывод должен иметь происхождение и ссылку на первоисточник.

## 16.12. Документы

Процесс:
файл → извлечение структуры → проверка данных → преобразование → перевод при необходимости → форматирование → QA → PDF / DOCX / другой ResultRef.

## 16.13. Инженерные задачи

Процесс:
технические требования → нормативы → параметры → кандидаты оборудования → проверка соответствия → конфигурация → техническое описание → документация.

Приоритет имеют первичные технические документы, точные версии нормативов, единицы измерения, доказательства и происхождение данных.

## 16.14. Автоматизация

Процесс:
событие запуска → условие → TaskContract → Worker → Execution → ResultRef → уведомление.

Внешнее событие не может напрямую запускать опасное действие. Оно сначала становится кандидатом в задачу и проходит Core, Rules и Security.

## 16.15. Визуализация процессов KAT9I_OS

Визуализация процессов является отдельным доменом KAT9I_OS.

Назначение: дать человеку визуальное представление о том, что происходит внутри системы в реальном времени и в истории выполнения задач.

Ответственный за разработку домена: Артём, GitHub-идентификатор `Art3m1da`.

Примечание: назначение ответственного в документации не означает автоматического изменения его прав в GitHub. Права репозитория управляются отдельно.

Домен визуализации должен получать данные прежде всего из Telemetry (телеметрии), Metrics (метрик), TaskRuntimeState (состояния выполнения задачи), Coworker, Inference, Context, Resources, Execution и Security Events.

Он не должен становиться вторым источником истины и не должен управлять исполнением напрямую.

## 16.16. Общие навыки

Общие навыки не нужно копировать в каждый домен. Универсальные функции могут использоваться несколькими доменами, а предметная настройка остаётся внутри конкретного домена.

## 16.17. Постепенное раскрытие возможностей

Исполнитель получает только те навыки, инструменты, правила и знания, которые нужны его конкретному домену и задаче.

## 16.18. Предметные правила

Домен может определять предметные правила, но все они проходят через общий Rule Manager (менеджер правил).

## 16.19. Предметные знания

Домен получает только релевантные KnowledgeRef (ссылки на знания) через общий механизм контекста и базы знаний.

## 16.20. Контракт результата

Каждый домен определяет свой предметный контракт результата, но публикация выполняется через общий ResultSink / ResultRef.

## 16.21. Предметные проверки

Проверки делятся на:
- детерминированные — выполняются кодом;
- содержательные — требуют модели или человека.

## 16.22. Предметные метрики

Домены могут определять собственные показатели качества, но сбор и хранение выполняются общей системой Metrics.

## 16.23. Самообучение доменов

Learning (самообучение) может улучшать процессы, навыки, проверяющие модули, выбор контекста, исполнителя, маршрута ИИ и долю исполняемого кода.

Критичные изменения проходят Proposal → Tests → QA → Promotion (предложение → тесты → независимая проверка → принятие новой версии).

## 16.24. KAT9I и AG25 как доноры

Существующие KAT9I и AG25 рассматриваются как доноры проверенных идей, кода и процессов, но их историческая структура не переносится механически.

Каждая функция переносится по новой архитектурной ответственности KAT9I_OS.

## 16.25. Подключаемые домены

Новый домен должен подключаться без переписывания Core. Он предоставляет идентификатор, контракты, процессы, навыки, проверки, метрики и требования к ресурсам и интеллектуальному выполнению.

## 16.26. Версионирование

Версии должны иметь как минимум процессы, навыки, проверяющие модули и предметные контракты. Это необходимо для воспроизводимости, кэша, самообучения, QA и отката.

## 16.27. Что домен не должен делать

Домен не должен:
- выдавать системные права;
- обходить Rule Manager;
- напрямую выбирать физического Worker;
- управлять секретами;
- создавать собственную альтернативную систему кэша, метрик или базы знаний;
- считать внешний текст управляющей командой;
- обходить Execution для опасных действий.

## 16.28. Основные принципы

1. Домен отвечает за предметную логику.
2. Проект и домен — разные сущности.
3. Одна конкретная задача имеет один основной домен.
4. Междоменные работы выражаются через граф задач.
5. Все домены используют общие Core, Rules, Security, Context, Resources, Inference, Coworker, Execution, Metrics и Learning.
6. Процессы должны становиться исполняемыми.
7. Формализуемые шаги переводятся в локальный код.
8. Предметные навыки раскрываются только там, где нужны.
9. Предметные правила разрешаются общим Rule Manager.
10. Результаты передаются через общий ResultRef.
11. Метрики собираются общей системой Metrics.
12. Самообучение может развивать домен, но не обходить безопасность и QA.
13. KAT9I и AG25 являются донорами решений, а не шаблоном структуры KAT9I_OS.
14. Новый домен должен подключаться без переписывания Core.
15. Визуализация процессов является отдельным доменом и не управляет системой напрямую.

## 16.29. Главный принцип

KAT9I_OS хранит предметную сложность внутри доменов, а универсальную механику управления, безопасности, контекста, исполнения, наблюдения и самообучения предоставляет им как общую платформу.
