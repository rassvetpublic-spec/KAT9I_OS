# 23. Тестирование, независимая проверка и критерии готовности KAT9I_OS

## 23.1. Назначение

Этот раздел определяет:

> **как KAT9I_OS доказывает, что отдельный модуль, изменение или вся система действительно работают правильно.**

Основной принцип:

> **утверждение Worker (исполнителя) или модели «всё работает» не является доказательством.**

Готовность подтверждается:

- тестами;
- Evidence (доказательствами выполнения и проверки);
- точной версией проверенного результата;
- независимым QA (независимой проверкой качества);
- измеримыми критериями качества.

## 23.2. Проверка относится к точной версии

Любой PASS (успешное прохождение проверки) должен быть привязан к:

- commit SHA (точному идентификатору коммита);
- версии файла;
- версии модуля;
- версии Workflow (исполняемого процесса);
- версии конфигурации;
- версии системных контрактов.

Если проверенный объект изменился:

> предыдущий PASS не переносится автоматически на новую версию.

## 23.3. Независимый QA

Сохраняется системный инвариант:

> **Implementation Worker (исполнитель реализации) ≠ QA Worker (независимый проверяющий).**

Worker, который создал изменение, может запускать собственные тесты.

Но квалифицирующий QA выполняется отдельным исполнителем.

## 23.4. Самопроверка и независимая проверка — разные вещи

### Самопроверка

Исполнитель:

- запускает тесты;
- проверяет формат;
- выполняет локальные Validators (проверяющие модули);
- исправляет очевидные ошибки.

### Независимый QA

Другой Worker:

- получает ResultRef (ссылку на результат);
- получает точную revision (версию);
- получает требования;
- независимо проверяет результат.

Самопроверка обязательна, но не заменяет независимый QA там, где он требуется.

## 23.5. Уровни тестирования

KAT9I_OS должна поддерживать несколько уровней проверки.

### 1. Тест функции или небольшого модуля

Проверяется отдельная детерминированная операция.

Например:

- вычисление Cache TTL (срока жизни кэша);
- Scope Guard (контроль границ задачи);
- подсчёт токенов;
- разбор ResourceRef (ссылки на ресурс).

### 2. Тест модуля

Проверяется целый системный компонент:

- Context (контекст);
- Resources (ресурсы);
- Inference (выбор вычислительного маршрута и ИИ);
- Coworker (координация исполнителей);
- Execution (исполнение);
- Cache (кэш);
- Recovery (восстановление);
- Forecasting (прогнозирование).

### 3. Контрактный тест

Проверяется взаимодействие между модулями.

Например:

`TaskContract → Coworker`

или:

`Execution → ResultRef`.

### 4. Интеграционный тест

Проверяется работа с реальной или тестовой внешней системой:

- GitHub;
- Telegram;
- MCP (Model Context Protocol — протокол подключения внешних инструментов и ресурсов);
- локальный Git;
- Provider (поставщик ИИ).

### 5. Сквозной тест

Проверяется полный путь:

**запрос → задача → исполнение → QA → результат.**

## 23.6. Детерминированные тесты имеют приоритет

Если результат можно проверить обычным кодом:

> его проверяет код.

ИИ не нужен для проверки:

- JSON schema (структуры данных);
- существования файла;
- exit code (кода завершения процесса);
- commit SHA;
- Scope;
- лимита символов;
- числа результатов;
- статуса GitHub API.

## 23.7. Содержательный QA

ИИ или человек используется там, где результат нельзя полностью проверить формулой.

Например:

- качество архитектуры;
- драматургия песни;
- полнота исследования;
- читаемость документа;
- корректность сложного инженерного вывода.

Но содержательный QA дополняет технические проверки, а не заменяет их.

## 23.8. Контрактные тесты между модулями

Особое значение имеют границы модулей.

Например проверяется:

- Context не выбирает Worker;
- Coworker не выдаёт себе права;
- Inference не исполняет задачу;
- Domain (домен, предметная область) не обходит Security (безопасность);
- Visualization (визуализация) не меняет Task State (состояние задачи);
- Learning (самообучение) не может снять DENY (запрет);
- Cache не становится источником истины.

То есть тестируется не только функция, но и:

> **архитектурная ответственность.**

## 23.9. Тесты безопасности

Обязательные сценарии:

- Prompt Injection (внедрение управляющих инструкций через текст);
- Command Injection (внедрение команд);
- Tool poisoning (подмена или вредоносное поведение инструмента);
- попытка DATA (данных) стать CONTROL (управляющей информацией);
- выход за Scope;
- использование просроченного Grant (разрешения);
- подмена Worker;
- использование старого Lease (временного права выполнять задачу);
- попытка чтения запрещённого ресурса;
- попытка отправить LOCAL_ONLY (только локальные данные) наружу;
- утечка секрета в Log (журнал);
- повтор старого ADMIN Approval (административного разрешения).

## 23.10. Тесты отказоустойчивости

KAT9I_OS должна намеренно проверяться на отказах.

Например:

- Worker исчез во время задачи;
- Worker вернулся после таймаута;
- интернет пропал;
- GitHub недоступен;
- Provider отвечает слишком долго;
- Cache повреждён;
- Runtime (среда исполнения) завершился аварийно;
- KAT9I_OS была перезапущена;
- публикация произошла, но ответ потерян;
- Lease истёк;
- два Worker пытаются закончить одну задачу.

## 23.11. Проверка восстановления

Для Recovery недостаточно проверить:

> система снова запустилась.

Необходимо доказать:

- задача восстановлена с правильной контрольной точки;
- побочный эффект не продублирован;
- старый Worker не смог опубликовать результат;
- ResultRef сохранён;
- права восстановлены корректно;
- прогноз оставшегося времени пересчитан.

## 23.12. Тестирование кэша

Обязательные сценарии:

- полный Cache Hit (полное попадание в кэш);
- Partial Hit (частичное попадание);
- Miss (промах);
- Stale (устаревший кэш);
- запрещённый Cache;
- изменение revision;
- изменение RulesRef;
- изменение Skill version (версии навыка);
- значительный Context Drift (изменение контекста);
- команда очистки;
- полная потеря кэша.

Критический критерий:

> потеря всего кэша не должна нарушать корректность KAT9I_OS.

## 23.13. Проверка прогнозирования

Прогнозирование тестируется отдельно.

Для каждой выборки задач сравниваются:

- прогноз токенов;
- фактические токены;
- прогноз времени;
- фактическое время;
- прогноз стоимости;
- фактическая стоимость;
- прогноз Cache Hit;
- фактический Cache Hit;
- вероятность Retry (повтора);
- фактический Retry.

## 23.14. Точность прогноза

Используются показатели:

- ошибка прогноза времени;
- ошибка прогноза токенов;
- ошибка стоимости;
- ошибка Cache Hit;
- калибровка вероятности Retry;
- калибровка вероятности успеха.

Предсказатель не считается хорошим только потому, что иногда выдаёт точное среднее значение.

Он должен правильно показывать и неопределённость.

## 23.15. Проверка самообучения

Learning должен тестироваться на двух уровнях.

### Проверка механизма

Система действительно:

- получает Metrics (метрики);
- обнаруживает закономерность;
- создаёт Proposal (предложение изменения);
- применяет разрешённую адаптацию;
- сохраняет Provenance (происхождение решения);
- умеет откатиться.

### Проверка пользы

После изменения:

- качество не ухудшилось;
- стоимость снизилась или оправдана;
- количество ошибок не выросло;
- Security не ослаблена.

## 23.16. Тест адаптивных таймаутов

Например система наблюдает:

> Worker часто возвращается через 1–3 секунды после Timeout (таймаута).

Тест должен доказать, что Learning:

1. не меняет глобальный Timeout после одного случая;
2. собирает достаточную статистику;
3. различает Worker и тип задачи;
4. оценивает стоимость ложного таймаута;
5. оценивает стоимость слишком долгого ожидания;
6. меняет параметр только внутри разрешённого диапазона;
7. измеряет результат изменения.

## 23.17. Проверка Coworker

Обязательные сценарии:

- правильный Worker выбран по capability (возможностям);
- Worker без capability исключён;
- недоступный Worker исключён;
- Data Affinity (близость к данным) учитывается;
- Trust (уровень доверия) учитывается;
- Claim (захват задачи) атомарен;
- Lease истекает;
- потерянная задача возвращается;
- независимые задачи параллелятся;
- зависимые задачи не запускаются раньше времени.

## 23.18. Проверка Inference

Нужно доказать, что система:

- сначала рассматривает код;
- затем локальный инструмент;
- затем локальный ИИ;
- выбирает минимально достаточный уровень;
- не выбирает запрещённого Provider;
- учитывает прогноз стоимости и времени;
- не повышает HIGH без причины;
- умеет использовать более дешёвый маршрут после накопления Evidence.

## 23.19. Проверка Context

Проверяется:

- минимальность;
- достаточность;
- Reference-first (сначала ссылка);
- правильный Scope;
- отсутствие лишнего полного чата;
- отсутствие секретов;
- правильная Freshness (актуальность);
- правильная граница CONTROL/DATA.

Отдельно измеряется влияние уменьшения Context на качество.

## 23.20. Проверка Telegram

Для Telegram проверяются:

- разрешённый USER распознан;
- ADMIN определяется отдельно;
- неизвестный пользователь не получает CONTROL;
- пересланная команда остаётся DATA;
- публичный канал остаётся Discovery Source (источником обнаружения информации);
- повтор уведомления не повторяет управляющее действие;
- секреты не отправляются;
- Emergency Stop (аварийная остановка) требует правильных полномочий.

## 23.21. Проверка визуализации

Домен визуализации должен доказать:

- состояние соответствует Telemetry (телеметрии);
- события отображаются без существенной задержки;
- прогноз и факт различаются;
- ошибки отображаются у правильного модуля;
- Replay (повторное воспроизведение) показывает правильную последовательность;
- секреты скрыты;
- интерфейс не влияет на выполнение задач;
- отключение браузера не останавливает KAT9I_OS.

## 23.22. Проверка производительности

Измеряются:

- задержка маршрутизации;
- подготовка Context;
- задержка Tool Broker (брокера инструментов);
- Scheduler (планировщика);
- Execution overhead (накладные расходы исполнения);
- Telemetry overhead;
- Visualization overhead;
- Cache lookup;
- Forecasting overhead.

KAT9I_OS не должна экономить 1000 токенов ценой десятков секунд ненужной управляющей работы.

## 23.23. Накладные расходы KAT9I_OS

Нужно отдельно измерять:

> сколько ресурсов потребляет сама система управления.

Например:

- CPU;
- RAM;
- диск;
- сеть;
- токены на маршрутизацию;
- время оркестрации;
- телеметрия;
- Learning;
- Forecasting.

Это позволяет обнаружить ситуацию, когда управляющая система стала дороже самой полезной работы.

## 23.24. Тестовые данные

Для тестирования должны существовать:

- безопасные искусственные задачи;
- тестовые репозитории;
- поддельные секреты;
- симулированные ошибки;
- тестовые Workers;
- фиксированные наборы данных.

Нельзя использовать реальные секреты только ради тестирования.

## 23.25. Фиксированные эталонные сценарии

Нужен небольшой набор канонических сценариев, которые запускаются после значимых изменений KAT9I_OS.

Например:

### Сценарий A

Простая локальная задача без ИИ.

### Сценарий B

NORMAL-задача с Context и GitHub.

### Сценарий C

Worker падает и задача восстанавливается.

### Сценарий D

Prompt Injection пытается вызвать запрещённый Tool.

### Сценарий E

Cache Partial Hit.

### Сценарий F

QA отклоняет результат.

### Сценарий G

USER принимает решение через Telegram.

## 23.26. Регрессионный набор

Каждая исправленная значимая ошибка должна по возможности превращаться в Regression Test (тест от повторного появления ошибки).

Принцип:

> **ошибка, найденная второй раз в том же виде, означает недостаток системы обучения или тестирования.**

## 23.27. Тест перед исправлением ошибки

Для воспроизводимой ошибки предпочтительный процесс:

**ошибка**
→ **тест, который её воспроизводит**
→ **исправление**
→ **тест становится зелёным**.

Это значительно надёжнее исправления «на глаз».

## 23.28. Evidence тестирования

Результат проверки должен содержать:

- test suite (набор тестов);
- точную revision;
- время;
- Worker;
- Runtime;
- exit code;
- PASS / FAIL;
- количество тестов;
- ссылки на Logs;
- при необходимости Artifact (артефакт результата).

## 23.29. FAIL нельзя превращать в PASS объяснением модели

Если тест реально завершился с ошибкой:

> модель не может объявить его успешным, потому что «ошибка выглядит несущественной».

Исключение теста возможно только через отдельное управляемое изменение политики проверки.

## 23.30. Пропущенный тест

Статусы должны различаться:

- PASS;
- FAIL;
- SKIPPED (пропущено);
- BLOCKED (заблокировано);
- NOT_APPLICABLE (не применяется).

`SKIPPED` не равен `PASS`.

## 23.31. Критичные и некритичные проверки

Каждая проверка имеет уровень критичности.

### Обязательная

FAIL блокирует результат.

### Рекомендованная

FAIL создаёт предупреждение или Proposal.

### Диагностическая

Используется для анализа.

Так система не должна блокировать весь проект из-за необязательного косметического теста.

## 23.32. Ворота готовности

Перед продвижением изменения используются `Readiness Gates (ворота готовности)`.

Например:

**код готов**
↓
локальные тесты PASS
↓
Scope PASS
↓
Security PASS
↓
интеграционные тесты PASS
↓
независимый QA PASS
↓
регрессии отсутствуют
↓
готово к Promotion (продвижению).

## 23.33. Уровни готовности модуля

Предлагаются состояния:

### EXPERIMENTAL — экспериментальный

Архитектура и прототип.

### DEVELOPMENT — разработка

Основная реализация идёт.

### TESTING — тестирование

Функциональность реализована, проводится системная проверка.

### RELEASE CANDIDATE — кандидат на выпуск

Все обязательные функции готовы, проводится финальный QA.

### READY — готов

Выполнены критерии эксплуатации.

### DEPRECATED — устаревающий

Есть замена, компонент выводится из эксплуатации.

## 23.34. Что означает READY

Статус `READY` нельзя выставить вручную только потому, что разработка «выглядит законченной».

Минимально должны быть:

- определённые контракты;
- реализация;
- тесты;
- обязательный QA;
- документация;
- метрики;
- обработка ошибок;
- Security;
- Recovery, если применимо;
- Evidence.

## 23.35. Готовность всей KAT9I_OS

Система может считаться готовой к первой реальной эксплуатации, когда:

1. Core и TaskContract стабильны;
2. Rule Manager работает fail-closed (при критической неопределённости блокирует действие);
3. Security защищает границу CONTROL/DATA;
4. Context работает Reference-first;
5. Coworker умеет безопасно выдавать задачи;
6. Execution реально запускает и контролирует процессы;
7. QA независим;
8. Recovery восстанавливает задачи;
9. Metrics и Telemetry работают;
10. Forecasting даёт измеримый прогноз;
11. Cache можно безопасно очистить;
12. хотя бы один полезный Domain работает end-to-end (сквозным процессом);
13. визуализация показывает реальное состояние;
14. обновление поддерживает откат.

## 23.36. Минимально полезная первая версия

Первая версия KAT9I_OS не обязана иметь все будущие домены.

Главное:

> **одна полная вертикаль должна работать правильно.**

Например:

**GitHub Issue**
→ TaskContract
→ Worker
→ реализация
→ тесты
→ PR
→ независимый QA
→ ResultRef
→ Metrics
→ Visualization
→ Learning.

Такой реальный процесс ценнее большого количества наполовину работающих модулей.

## 23.37. Тестирование самообновления

Обновление KAT9I_OS обязательно проверяется отдельно:

- Backup (резервная копия) создан;
- задачи сохранены;
- новая версия установлена;
- схема мигрирована;
- Health Check (проверка состояния) PASS;
- при искусственной ошибке Rollback (откат) работает.

Откат, который никогда не тестировался, нельзя считать рабочим.

## 23.38. Тестирование без сети

Обязательный сценарий:

> интернет отключён.

Проверяется:

- старт KAT9I_OS;
- локальный Worker;
- локальный Git;
- локальная Knowledge Base (база знаний);
- Cache;
- локальный ИИ;
- визуализация;
- корректное состояние внешних Integrations (интеграций).

## 23.39. Тест полного отказа кэша

Удаляется весь разрешённый Cache.

После этого:

- система запускается;
- источники восстанавливаются;
- нужные индексы пересчитываются;
- результат остаётся корректным;
- Metrics фиксируют увеличение стоимости.

## 23.40. Тест разделения CONTROL/DATA

Нужно иметь специальный набор вредоносных документов, Issue и Tool responses (ответов инструментов).

Они должны пытаться:

- изменить Rules;
- вызвать Tool;
- расширить Scope;
- запросить секрет;
- отменить QA;
- изменить ResultSink (место публикации результата).

Ни один такой DATA-объект не должен получить управляющую силу.

## 23.41. История качества

Для каждого важного модуля сохраняется тренд:

- PASS Rate;
- Regression Rate;
- время;
- токены;
- стоимость;
- число инцидентов;
- прогноз/факт.

Это позволяет видеть не только текущее состояние, но и:

> становится ли KAT9I_OS действительно лучше.

## 23.42. Самообучение тестовой системы

Learning может обнаруживать:

- часто ломающийся модуль;
- слабый набор тестов;
- тесты, которые ничего не находят;
- медленные проверки;
- повторяющиеся классы ошибок.

Learning может предлагать:

- новый Regression Test;
- объединение дублирующих тестов;
- перенос проверки из ИИ в локальный Validator;
- изменение порядка тестов.

## 23.43. Дешёвые тесты сначала

Порядок проверки по возможности:

1. схема;
2. формат;
3. статические проверки;
4. локальные быстрые тесты;
5. интеграционные тесты;
6. дорогие сквозные тесты;
7. модельный QA;
8. человеческий QA, если требуется.

Это позволяет быстро остановить плохой результат до дорогостоящих этапов.

## 23.44. Ранняя остановка при доказанной ошибке

Если обязательная ранняя проверка уже доказала, что результат неверен:

> последующие дорогие проверки не запускаются без причины.

## 23.45. Но ранний FAIL должен оставлять Evidence

Даже при ранней остановке сохраняются:

- причина;
- проверка;
- revision;
- результат.

Learning должен понимать, почему задача остановилась.

## 23.46. Визуализация QA

В браузере пользователь должен видеть:

**Реализация**
→ локальные тесты PASS
→ Security PASS
→ QA Worker назначен
→ QA RUNNING
→ QA PASS / FAIL.

Также:

- сколько времени заняли проверки;
- какая revision проверена;
- какие тесты упали;
- сколько стоил QA.

## 23.47. Главные метрики тестирования

Минимально:

- Test Pass Rate — доля успешных тестов;
- QA Pass Rate — доля успешных независимых проверок;
- First Pass Success Rate — успех с первой попытки;
- Regression Rate — частота регрессий;
- Defect Escape Rate — доля ошибок, прошедших проверки;
- False Positive Rate — доля ложных срабатываний;
- среднее время QA;
- стоимость QA;
- Flaky Test Rate — доля нестабильных тестов;
- Recovery Test Pass Rate;
- Security Test Pass Rate.

## 23.48. Что система QA не должна делать

Она не должна:

- доверять самооценке исполнителя;
- проверять другую revision;
- считать SKIPPED за PASS;
- менять требования ради получения зелёного результата;
- скрывать FAIL;
- расширять Scope;
- исправлять результат и одновременно считать себя независимым QA для этого же изменения;
- использовать полный Chain of Thought (скрытую цепочку рассуждений модели) как Evidence.

## 23.49. Основные принципы

1. **PASS всегда относится к точной версии.**
2. **Реализация и независимый QA выполняются разными Workers.**
3. **Код проверяет всё, что можно проверить детерминированно.**
4. **ИИ используется для содержательной проверки, а не вместо технических тестов.**
5. **Архитектурные границы модулей также тестируются.**
6. **Отказы, восстановление, Cache и Security являются обязательными объектами тестирования.**
7. **Прогнозирование проверяется по прогнозу против факта.**
8. **Каждая серьёзная исправленная ошибка должна по возможности породить Regression Test.**
9. **FAIL нельзя превратить в PASS объяснением модели.**
10. **SKIPPED и BLOCKED не равны PASS.**
11. **Дешёвые проверки выполняются раньше дорогих.**
12. **Готовность определяется Evidence, а не ощущением завершённости.**
13. **Первая версия должна доказать хотя бы одну полноценную сквозную вертикаль.**
14. **Откат и восстановление должны реально тестироваться.**
15. **QA и тестовая система сами измеряются и улучшаются через Learning.**

## 23.50. Главный принцип

> **KAT9I_OS может считать компонент или результат готовым только тогда, когда его требования проверены на точной версии реальными тестами и Evidence, а для значимых изменений результат независимо подтверждён другим исполнителем.**
