# 24. GitHub — ведение проекта и совместная разработка KAT9I_OS

## 24.1. Назначение

GitHub используется не только как хранилище файлов, а как рабочая система совместной разработки KAT9I_OS.

Главный принцип:

> Для каждой сущности существует одно каноническое место. Остальные представления либо ссылаются на него, либо автоматически строятся из него.

## 24.2. Один источник истины

Канонические роли GitHub:

| Механизм | Для чего используется | Является источником истины |
|---|---|---|
| `docs/` | принятая архитектура, правила и спецификации | да, для документации |
| Issue (задача) | работа, которую нужно выполнить, её состояние и обсуждение выполнения | да, для состояния работы |
| Pull Request / PR (запрос изменений) | конкретное предложение изменить проект | только для предлагаемого изменения |
| GitHub Actions | доказательства автоматических проверок | да, для факта проверки конкретной версии |
| Project (доска проекта) | удобное визуальное представление задач | нет |
| Milestone (этап выпуска) | группировка задач по цели версии | нет |
| Release (официальный выпуск) | зафиксированная выпущенная версия | да, для факта выпуска |
| Discussion (обсуждение) | вопросы, обучение и идеи до превращения в работу | нет |
| GitHub Pages | удобное HTML-представление документации | нет, только производное представление |
| Wiki | не используется | нет |

## 24.3. Документация и HTML

Markdown-документы в `docs/` являются каноническими.

HTML-версия не должна вручную копировать текст спецификации. Она должна автоматически строиться из канонических документов и добавлять только представление:

- навигацию;
- поиск;
- уровни подробности;
- сворачивание примеров;
- подсказки терминов;
- режим «Я здесь впервые»;
- визуальные схемы.

При расхождении HTML и Markdown правильным считается Markdown.

## 24.4. Уровни объяснения

HTML должен поддерживать глобальный выбор уровня подробности:

1. **Очень просто** — объяснение, понятное ребёнку примерно 10 лет.
2. **Просто** — что это такое и зачем нужно.
3. **Рабочий** — достаточно коворкеру для безопасной работы.
4. **Технический** — контракты, состояния, границы модулей и точные требования.
5. **Максимум** — крайние случаи, безопасность, доказательства, отказоустойчивость и подробности реализации.

Уровни не должны быть пятью независимыми копиями документации. Они являются представлениями одного канонического содержания.

## 24.5. Примеры

Примеры должны быть сворачиваемыми.

В HTML требуется глобальный переключатель:

> **Показывать примеры**

При выключении примеры сворачиваются, но остаются доступными для ручного раскрытия.

Дополнительно могут существовать переключатели для схем, технических деталей и крайних случаев.

## 24.6. Единый словарь терминов

Для ключевых терминов существует единый словарь.

Одна запись может содержать:

- русское название;
- английский технический синоним;
- очень простое объяснение;
- рабочее объяснение;
- точное техническое определение;
- ссылку на канонический архитектурный раздел.

Словарь объясняет термин, но не должен копировать весь контракт соответствующего модуля.

## 24.7. Вход нового коворкера

Порог входа должен быть минимальным.

Новый участник должен сразу видеть четыре понятных маршрута:

- **Понять, что такое KAT9I_OS**;
- **Научиться работать с GitHub на примере проекта**;
- **Задать вопрос или предложить идею**;
- **Найти задачу и помочь**.

Новый участник не обязан заранее знать Git, GitHub, Issue, PR, QA, Domain, Scope или внутреннюю архитектуру KAT9I_OS.

## 24.8. Форма обратной связи

Для вопросов, пожеланий и сообщений о проблемах используется русская GitHub Issue Form (форма создания задачи).

Она спрашивает простыми словами:

- что человек хотел сделать;
- что произошло;
- чего он ожидал;
- относится ли обращение к вопросу, идее, ошибке или непонятной документации;
- есть ли ссылка, файл или скриншот;
- хочет ли человек помочь с исправлением.

Пользователь не обязан самостоятельно назначать приоритет, область, компонент, этап выпуска или технические метки. Это задача разбора входящей заявки.

## 24.9. Issues и Discussions

Issue используется, когда существует конкретная работа, которую нужно выполнить.

Discussion используется для вопроса, обучения или предварительной идеи.

Пример:

- «Почему Context отделён от Knowledge?» → Discussion.
- «Добавить диаграмму Context и Knowledge» → Issue.

Принятое решение из Discussion должно быть перенесено в каноническую документацию или оформлено как Issue. Само обсуждение источником истины не становится.

## 24.10. Доска проекта

Основная доска:

> **KAT9I_OS — разработка**

Видимые поля и их значения должны быть русскими везде, где GitHub это позволяет.

Главные поля:

- `Статус`;
- `Этап`;
- `Приоритет`;
- `Тип`;
- `Область`;
- `Размер`;
- `Итерация`;
- `Исполнитель`;
- `Проверяющий`;
- `Исполнение`;
- `Цель`;
- `Риск`;
- `Доказательство`.

Базовые состояния задачи:

`Входящие → Нужно разобрать → Готово к работе → В работе → Проверка качества → Заблокировано → Готово`

Поле `Исполнение` отдельно показывает состояние захвата работы исполнителем:

`Свободно → В очереди → Активно → На проверке → Заблокировано → Освобождено`

Итерация длится **3 дня**.

Доска отображает задачи, но не создаёт параллельное состояние задач.

## 24.11. Pull Request — запрос изменений

Для PR используется единый русский шаблон.

Минимально фиксируются:

- зачем нужно изменение;
- связанная задача;
- что изменено;
- что сознательно не менялось;
- область изменения;
- проверки;
- доказательства;
- риски;
- необходимость независимой проверки качества;
- точная версия, которую проверял проверяющий.

## 24.12. Независимая проверка качества

Для значимых изменений сохраняется инвариант:

> Исполнитель изменения не является единственным независимым проверяющим результата.

Проверка относится к точной версии. После изменения head прежняя проверка не считается действующей для новой версии.

## 24.13. Actions — автоматические проверки

Проверка качества репозитория и публикация Pages являются разными процессами.

**Контроль качества** отвечает за корректность проекта.

**Публикация Pages** отвечает только за представление документации.

Ошибка публикации сайта не должна маскироваться под ошибку архитектуры, а успешная публикация не должна считаться полной проверкой качества проекта.

## 24.14. Исторические красные запуски

Исторические FAIL GitHub Actions не переписываются ради визуально зелёной истории.

Если одна инфраструктурная ошибка сломала много старых запусков, она фиксируется как один инцидент, а исправление подтверждается новой успешной версией.

Переписывание старых коммитов только ради изменения статусов запрещено, потому что меняет SHA и разрушает честную историю доказательств.

## 24.15. Защита main

Пока базовое ТЗ принимается пользователем по разделам, владелец может фиксировать принятые разделы непосредственно в `main`.

После заморозки базовой спецификации для обычных изменений должен действовать более строгий путь:

`Задача → ветка → изменение → PR → автопроверки пройдены → независимая проверка качества → слияние`

Тогда для `main` включается Ruleset (набор правил ветки), соответствующий этому процессу.

## 24.16. CODEOWNERS и ответственность

CODEOWNERS используется для автоматического запроса проверки у подходящего владельца части репозитория.

Но:

> CODEOWNERS не является каноническим источником архитектурной ответственности и не выдаёт административные права.

Назначение ответственного за модуль и конкретное назначение исполнителя на задачу — разные действия.

## 24.17. Этапы и выпуски

Milestones рекомендуется использовать для крупных целей, например:

- `v0.1` — первая полноценная сквозная версия;
- `v0.2` — распределённые исполнители, восстановление и расширенная визуализация;
- `v1.0` — эксплуатационно готовая KAT9I_OS.

Release создаётся только для реально выпущенной версии и ссылается на канонические изменения.

## 24.18. Безопасность GitHub-функций

После появления исполняемого кода и зависимостей следует использовать подходящие возможности GitHub:

- Dependabot — предложения обновлений зависимостей;
- Dependency Review — проверка новых зависимостей;
- Secret Scanning — обнаружение случайно опубликованных секретов, если доступно;
- CodeQL или эквивалентный анализ — когда в проекте появится код, который такой анализ реально способен проверять.

Тяжёлые проверки не включаются только ради количества функций.

## 24.19. Главный принцип

> GitHub должен делать совместную работу KAT9I_OS понятной даже новичку, но не создавать параллельные источники истины: архитектура живёт в канонических документах, работа — в задачах, проверки — в Actions и доказательствах, выпуск — в Releases, а Projects, HTML и другие интерфейсы лишь показывают эти данные удобным способом.
