# 25. Полный реестр ТЗ и ABC/XYZ-приоритизация

## 25.1. Назначение

Этот раздел задаёт обязательный инженерный процесс перехода от набора канонических документов KAT9I_OS к управляемому полному ТЗ, приоритетной архитектурной проработке и только затем к реализации.

Каноническая последовательность:

`T0 Requirements Inventory → T1 ABC → T2 XYZ → T3 ABC×XYZ + Coverage/Contradiction → T4 Architecture Convergence → T5 Architecture Baseline → G2/G3 implementation`.

Процесс относится к engineering/control plane разработки KAT9I_OS и не является runtime-модулем операционной системы.

Главная цель:

> **Сначала понять полный набор требований и их риск, затем тратить архитектурное время и только потом кодировать.**

## 25.2. Почему нужен отдельный Requirements Registry

Фактическое ТЗ KAT9I_OS распределено между `docs/tz`, `docs/architecture`, `docs/spec`, ADR/OQ, machine schemas и связанными Issues/PR.

Само наличие большого количества качественных документов не гарантирует, что:

- все требования вообще учтены;
- у каждого требования есть один canonical owner;
- существует однозначный SSoT;
- machine contract соответствует текстовой архитектуре;
- нет противоречащего описания в соседнем разделе;
- приоритет анализа определяется архитектурным риском, а не порядком появления Issue.

Поэтому вводится Requirements Registry как слой traceability и классификации.

Requirements Registry не становится вторым SSoT содержания требований.

Он хранит ссылку на канонический источник и метаданные анализа.

## 25.3. Инвариант Registry

Для каждого требования действует модель:

`Requirement ID → canonical SSoT → canonical owner → status → dependencies → evidence/contract refs → ABC → XYZ → coverage state → implementation trace`.

Registry может сообщить, где находится требование и в каком оно состоянии.

Registry не должен самостоятельно изменять смысл требования.

Если содержимое Registry расходится с профильным SSoT, исправляется Registry либо явно открывается архитектурный конфликт.

## 25.4. Минимальная запись Requirement

Каждая запись должна позволять определить минимум:

- `requirement_id` — стабильный идентификатор;
- короткое название;
- область/тип требования;
- canonical SSoT;
- canonical owner;
- целевой Gate или версия;
- статус: `ACCEPTED`, `OPEN`, `DEFERRED`, `GAP` или `BLOCKED`;
- зависимости;
- machine contract refs, если они требуются;
- Evidence / traceability refs;
- связанный Issue/PR;
- ABC-класс;
- XYZ-класс;
- Coverage/Contradiction status.

Дополнительные поля могут вводиться позже, если они не превращают Registry в копию самих спецификаций.

## 25.5. T0 — Полная инвентаризация требований (Full Requirements Inventory)

T0 отвечает на вопрос:

> **Что вообще входит в ТЗ KAT9I_OS и где находится каноническая истина по каждому требованию?**

Источники T0:

- `docs/tz`;
- `docs/architecture`;
- `docs/spec`;
- ADR и OQ;
- `schemas/v1` и последующие версии schemas;
- Module Registry и responsibility maps;
- связанные Issues и PR;
- действующие Gate/roadmap документы.

Graveyard допускается только как DATA для поиска потерянной истории и не становится источником CONTROL автоматически.

### 25.5.1. Что T0 делает

T0:

- выделяет требования;
- нормализует их идентификаторы;
- связывает требование с SSoT;
- определяет текущего canonical owner;
- фиксирует status и Gate;
- связывает machine contracts и Evidence;
- выявляет дублирование;
- выявляет отсутствующий SSoT;
- выявляет отсутствующего owner;
- выявляет противоречащие тексты;
- выявляет потерянные связи между ТЗ и реализационными Issues.

### 25.5.2. Что T0 не делает

T0 не должен незаметно принимать новое архитектурное решение.

Если во время inventory обнаружена неопределённость, она фиксируется как `GAP` в Requirement status, как `CONTRADICTION` в Coverage/Contradiction status либо как отдельный OQ/Issue.

То есть:

**Inventory ≠ Architecture Decision.**

### 25.5.3. Выход T0

T0 считается завершённым, когда существует полный Requirements Registry с traceability и нет требований без явно указанного состояния.

Неизвестность разрешена только как явно зарегистрированный `GAP`, `OPEN`, `BLOCKED` или `DEFERRED`.

## 25.6. T1 — ABC-анализ

ABC классифицирует критичность требования для текущей архитектуры и целевого Gate.

### A — Критичные требования (Critical)

Класс `A` используется, если отсутствие или неверная реализация требования приводит хотя бы к одному из последствий:

- нарушается обязательная корректность;
- нарушается Security;
- нарушается Recovery;
- становится недостижим ключевой пользовательский результат текущего Gate;
- нарушается canonical ownership или создаётся второй SSoT;
- ломается обязательный системный контракт;
- возникает неприемлемый риск потери/искажения канонического состояния.

`A` означает высокий архитектурный приоритет.

`A` не означает автоматическую немедленную реализацию вне текущего Gate.

### B — Важные требования (Important)

Класс `B` используется для важной функциональности, отсутствие которой заметно ухудшает продукт, но не разрушает фундаментальные инварианты текущего Gate.

### C — Опциональные требования и оптимизация (Optional / Optimization)

Класс `C` используется для:

- удобства;
- косметики;
- оптимизации без обязательного benchmark Evidence;
- расширений будущих версий;
- возможностей, которые можно безопасно добавить позже без нарушения текущего Gate.

ABC должен оцениваться относительно текущего Gate/версии, а не как вечная характеристика требования.

## 25.7. T2 — XYZ-анализ

XYZ классифицирует не важность, а степень архитектурной определённости и риск переделки.

### X — Стабильные требования (Stable)

`X` означает, что:

- canonical SSoT известен;
- canonical owner известен;
- основные границы стабильны;
- обязательные зависимости понятны;
- необходимый machine contract определён либо явно не требуется;
- вероятность крупной архитектурной переделки низкая.

### Y — Умеренная неопределённость (Moderate uncertainty)

`Y` означает умеренную неопределённость:

- часть деталей ещё открыта;
- есть значимые зависимости;
- возможны локальные изменения контрактов;
- требуется дополнительный convergence или Evidence;
- фундаментальная роль модуля при этом уже понятна.

### Z — Высокая неопределённость (High uncertainty)

`Z` означает высокий риск архитектурной переделки или отсутствие критически важной определённости.

Типовые признаки:

- неизвестен canonical owner;
- нет SSoT;
- конкурируют несколько SSoT;
- отсутствует обязательный machine contract;
- существует серьёзный открытый OQ;
- решение зависит от непроверенного внешнего ограничения;
- нет достаточного Evidence для фундаментального выбора;
- изменение может затронуть Core, Security, Recovery, ownership или несколько системных контрактов.

`Z` не означает низкое качество требования.

Это означает высокую неопределённость, которую нужно управляемо снять.

## 25.8. T3 — матрица ABC×XYZ

ABC и XYZ анализируются независимо.

Критичность не должна автоматически повышать или понижать оценку неопределённости.

Приоритет архитектурной проработки:

1. `AZ`;
2. `AY`;
3. `AX`;
4. `BZ`;
5. `BY`;
6. `BX`;
7. `CZ`;
8. `CY`;
9. `CX`.

Главная группа риска — `AZ`:

> критично для системы и одновременно архитектурно плохо определено.

Такие требования анализируются до массовой реализации зависимых компонентов.

`AX` обычно не требует повторного максимального исследования только из-за высокого класса A: если границы действительно стабильны, его можно быстрее переводить в контракт, тест и реализацию.

## 25.9. Проверка покрытия и противоречий (Coverage / Contradiction Pass)

После ABC/XYZ каждое требование проходит отдельную проверку покрытия и непротиворечивости.

Минимальные вопросы:

1. Есть ли один canonical SSoT?
2. Есть ли один canonical owner?
3. Есть ли machine contract, если архитектура его требует?
4. Есть ли достаточная traceability/Evidence?
5. Нет ли конкурирующего SSoT?
6. Нет ли соседнего канонического документа с противоположной семантикой?
7. Совпадает ли status в подробном SSoT и сводных реестрах?
8. Не используется ли `DEFERRED` для маскировки обязательного GAP текущего Gate?
9. Не используется ли DATA как CONTROL?
10. Не объявляется ли Capability как Permission или Result как Evidence?

Типовые результаты проверки:

- `COVERED`;
- `GAP`;
- `CONTRADICTION`;
- `TRACEABILITY_GAP`;
- `CONTRACT_GAP`;
- `OWNER_GAP`;
- `BLOCKED`.

Классификация Coverage не заменяет ABC/XYZ.

Например `AZ + OWNER_GAP` является более срочным архитектурным риском, чем `CX + COVERED`.

## 25.10. T4 — Архитектурная сходимость (Architecture Convergence)

Architecture Convergence выполняется по каноническому §35.

Этот раздел не создаёт второй Convergence Loop.

Он определяет только порядок выбора объектов для §35.

В первую очередь анализируются требования с наиболее высоким риском из T3, особенно `AZ` и `AY`.

Внутри каждого объекта сохраняется полный §35:

`исходные законы → Minimal Baseline → Maximal Brainstorm → классификация идей → Deletion Test → Complexity Guillotine → возврат к законам → blast-radius → independent Critic → финальное решение`.

### 25.10.1. Запрет бессмысленного одинакового анализа

Все разделы не обязаны получать одинаковую глубину Convergence.

Если требование классифицировано как `AX`, полностью покрыто и уже имеет устойчивый контракт, повторное максималистское исследование допускается сократить, если нет нового Evidence риска.

Если требование `AZ`, сокращённый review недостаточен.

## 25.11. T5 — Архитектурная базовая линия (Architecture Baseline)

T5 отвечает на вопрос:

> **Можно ли считать архитектуру достаточно определённой для перехода к следующему реализационному Gate?**

Architecture Baseline допускается только если:

- все требования класса `A` зарегистрированы;
- у всех `A` есть canonical owner;
- у всех `A` есть canonical SSoT;
- нет незакрытых `AZ` для текущего Gate;
- обязательные machine contracts определены либо их отсутствие явно обосновано;
- критические `CONTRADICTION`, `OWNER_GAP` и `CONTRACT_GAP` устранены либо имеют явный `BLOCKED` с владельцем решения;
- `DEFERRED` не скрывает требование, обязательное для текущего Gate;
- blast-radius значимых архитектурных решений синхронизирован;
- независимый Critic/QA выполнен там, где этого требует §35 или release process.

T5 не означает, что реализованы все будущие функции.

T5 означает, что текущий Gate имеет достаточно полную и непротиворечивую архитектурную основу.

## 25.12. Связь T0–T5 с G0/G1/G2/G3

T0–T5 не заменяют существующие project Gates.

Это предварительный и повторяемый engineering pipeline для определения готовности требований.

Типовая связь:

- `T0–T3` — нормализация и приоритизация требований;
- `T4` — архитектурная сходимость;
- `T5` — архитектурный baseline;
- затем соответствующий существующий Gate реализации: G2/G3 или другой, определённый Roadmap/Project.

При изменении крупного требования T0–T5 может быть запущен локально только для затронутого blast radius, а не для всей системы с нуля.

## 25.13. Что не является частью этого процесса

ABC/XYZ не должны превращаться в:

- runtime scheduler;
- приоритет пользовательских Task;
- AI routing policy;
- Security Policy;
- Worker ranking;
- отдельный persistent сервис;
- второй Issue tracker;
- второй Rule Manager.

Это метод управления требованиями и архитектурной неопределённостью при разработке KAT9I_OS.

## 25.14. Архив Graveyard

Graveyard может использоваться во время T0 как источник исторического DATA для восстановления потерянного контекста.

Однако:

`Graveyard DATA ≠ Requirement CONTROL`.

Найденная в Graveyard идея не получает ABC/XYZ как действующее требование, пока не установлена её связь с текущим каноническим SSoT или не проведён отдельный promotion process.

## 25.15. Изменение классификации

ABC и XYZ являются управляемыми метаданными анализа.

Они могут изменяться при появлении нового Evidence, смене Gate или устранении неопределённости.

Типовая эволюция:

`AZ → AY → AX`

означает, что критичное требование постепенно стало архитектурно определённым.

Изменение `AZ → AX` само по себе не изменяет содержание Requirement.

## 25.16. Порядок исполнения первой полной итерации

Для текущего KAT9I_OS первая полная итерация выполняется так:

1. T0 — пройти весь текущий канон и собрать Full Requirements Registry;
2. проверить traceability с открытыми и закрытыми ADR/OQ/Issues;
3. T1 — назначить ABC;
4. T2 — назначить XYZ;
5. T3 — построить матрицу и Coverage/Contradiction report;
6. сформировать ordered worklist `AZ → AY → AX → B* → C*`;
7. T4 — запускать §35 по этому worklist;
8. после каждой архитектурной правки повторять blast-radius и локальный reclassification;
9. T5 — провести Architecture Baseline Gate;
10. только после PASS переводить соответствующий набор требований в реализационный Gate.

## 25.17. Минимальные артефакты первой итерации

Первая полная итерация должна дать минимум три независимых результата:

1. **Requirements Registry** — реестр и traceability;
2. **ABC×XYZ Matrix** — приоритет архитектурной проработки;
3. **Coverage/Contradiction Report** — список GAP/CONTRADICTION и их владельцев.

Архитектурные решения, появившиеся в T4, продолжают храниться у своих профильных SSoT/ADR, а не внутри этих отчётов.

## 25.18. Definition of Done первой итерации

Первая итерация T0–T5 считается завершённой, когда:

- весь актуальный канон охвачен Registry;
- каждый активный Requirement имеет status;
- каждому активному Requirement назначены ABC и XYZ;
- сформирована полная ABC×XYZ Matrix;
- выполнен Coverage/Contradiction pass;
- для всех `AZ` определено действие: исправить, исследовать, BLOCKED или доказанно DEFERRED вне текущего Gate;
- выполнен требуемый Architecture Convergence;
- Architecture Baseline прошёл независимую проверку;
- дальнейшая реализационная очередь строится из Registry/Matrix, а не из случайного порядка появления задач.

## 25.19. Главный принцип

> **Полное ТЗ сначала становится видимым и измеримым. Критичность и неопределённость оцениваются раздельно. Architecture Convergence применяется туда, где риск максимален. Только после этого требования переходят в массовую реализацию.**
