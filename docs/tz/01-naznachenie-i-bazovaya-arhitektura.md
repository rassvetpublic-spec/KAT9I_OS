# Раздел 1. Назначение KAT9I_OS и базовая архитектура

> **Статус:** принято.
>
> **Язык проекта:** русский. Английские технические термины используются только вместе с русским пояснением при первом употреблении.

## Схема системы

**KAT9I_OS — персональная агентная операционная система для управления задачами, правилами, контекстом, ИИ-исполнителями и результатами работы.**

```text
Пользователь
    ↓
Задача
    ↓
Личные + проектные + доменные правила
    ↓
Domain (домен — тип работы)
    ↓
Context + Resources (контекст + источники данных)
    ↓
Inference Router (маршрутизатор ИИ — выбор модели и провайдера)
    ↓
Coworker (распределённая работа агентов)
    ↓
Execution (исполнение задачи)
    ↓
Integrations / MCP (подключения к внешним системам)
    ↓
ResultRef (ссылка на результат)
    ↓
QA (независимая проверка качества)
    ↓
Завершённая задача + Evidence (доказательства выполнения)
```

Внешние источники и исполнители подключаются к системе по ссылкам и через Connector (подключаемый источник):

**GitHub · Google Drive · Obsidian · локальные файлы · ChatGPT · Antigravity · локальные ИИ · другие компьютеры · MCP-серверы**

---

## 1.1. Что такое KAT9I_OS

KAT9I_OS — это не отдельный чат-бот и не просто система запуска агентов.

Это **единая управляющая среда**, которая должна уметь:

- принять задачу пользователя;
- определить её тип;
- применить нужные правила;
- найти необходимые источники контекста;
- выбрать подходящий ИИ;
- выбрать конкретного исполнителя;
- выдать исполнителю только необходимые права и контекст;
- проконтролировать выполнение;
- получить результат;
- провести независимую проверку;
- сохранить доказательства выполнения;
- вернуть пользователю итог.

Главная цель:

> **Управлять полным жизненным циклом задачи — от намерения пользователя до проверенного результата.**

---

## 1.2. Архитектурный подход

KAT9I_OS строится как **Modular Monolith (модульный монолит)**.

### Монолит

Система развивается как один продукт:

- один канонический репозиторий;
- одна основная архитектура;
- единая модель задач;
- единая модель правил;
- единая система проверок;
- единый жизненный цикл выпуска;
- единый набор сквозных тестов.

### Модульный

Внутри продукта сохраняются строгие границы ответственности.

Каждый модуль отвечает только за свою часть системы и взаимодействует с другими через определённые контракты.

Например:

- `Suno` знает, что такое куплет, припев, BPM (темп в ударах в минуту) и вокал;
- `Core` (ядро) не должен знать музыкальные понятия;
- `Coworker` (распределённая работа агентов) знает, кому поручить задачу;
- `Execution` (исполнение) знает, как физически запустить исполнителя;
- `Inference Router` (маршрутизатор ИИ) знает, какой ИИ использовать;
- `Resources` (ресурсы) знает, где находятся исходные данные и результат.

---

## 1.3. Почему выбран модульный монолит

До KAT9I_OS функции системы распределены между KAT9I, AG25 и внешними компонентами.

Это создаёт лишние границы:

- несколько репозиториев;
- отдельные транспортные контракты;
- необходимость синхронизации версий;
- дублирование моделей данных;
- сложные сквозные проверки;
- дополнительные мосты между компонентами;
- сложное определение источника ошибки.

В KAT9I_OS эти функции переходят внутрь одного продукта.

При этом они **не смешиваются**, а распределяются по соответствующим модулям.

| Существующая функция | Место в KAT9I_OS |
|---|---|
| KAT Rule Manager (менеджер правил) | `Core` — ядро управления |
| KAT Skills (навыки) | `Core / Skills` — навыки |
| AG25 Mesh (сетка исполнителей) | `Coworker` — распределённая работа |
| AG25 Worker Runtime (среда исполнения) | `Execution` — исполнение |
| AG25 Sensitive Data (защита чувствительных данных) | `Security` — безопасность |
| AG25 GitHub | `Integrations / GitHub` — подключение GitHub |
| AG25 Suno | `Domains / Suno` — музыкальный домен |
| внешняя Knowledge Base (база знаний) | `Personal / Knowledge` + внешние источники |

AG25 и текущая KAT используются как **доноры проверенных решений**, но KAT9I_OS не должна становиться механическим объединением двух старых структур.

## 1.4. Основные модули

### `Core` — ядро управления

Отвечает за:

- задачи;
- правила;
- навыки;
- маршрутизацию;
- политики;
- системные контракты.

Главный вопрос:

> **Какие правила действуют и что система должна сделать?**

### `Context` — контекст задачи

Отвечает за:

- определение необходимого контекста;
- ограничение объёма передаваемых данных;
- подготовку ссылок на источники;
- сжатие контекста при необходимости;
- подготовку минимального набора информации для исполнителя.

Главный вопрос:

> **Что исполнителю действительно нужно знать?**

### `Resources` — источники и результаты

Отвечает за:

- ссылки на GitHub;
- документы Google Drive;
- локальные файлы;
- личную базу знаний;
- артефакты;
- ссылки на результаты.

Главный вопрос:

> **Где находятся исходные данные и куда должен быть записан результат?**

### `Inference` — выбор ИИ и провайдера

Отвечает за:

- выбор уровня модели: `LOW` (низкий), `NORMAL` (обычный), `HIGH` (высокий);
- выбор локального или удалённого ИИ;
- выбор подписочного Web-интерфейса (веб-интерфейса) или API (программного интерфейса);
- оценку доступных Connector (подключаемых источников);
- выбор оптимального маршрута выполнения.

Главный вопрос:

> **Какой ИИ лучше всего подходит для этого этапа задачи?**

### `Coworker` — распределённая работа агентов

Отвечает за:

- список доступных исполнителей;
- локальных агентов;
- удалённую Катю;
- другие компьютеры;
- распределение задач;
- бронирование задачи исполнителем;
- передачу результата;
- совместную работу нескольких агентов.

Главный вопрос:

> **Кто должен выполнить эту работу?**

### `Execution` — исполнение

Отвечает за:

- запуск процессов;
- запуск Worker (исполнителя);
- Worktree (изолированную рабочую копию Git);
- ветки;
- тайм-ауты;
- контроль области изменений;
- доказательства выполнения;
- очистку после завершения.

Главный вопрос:

> **Как физически выполнить работу?**

### `Security` — безопасность

Отвечает за:

- доступ к данным;
- права исполнителей;
- чувствительные данные;
- разрешённые пути и репозитории;
- временные Capability Grant (разрешения на действия);
- запрет опасных операций.

Главный вопрос:

> **Что этому исполнителю разрешено делать?**

### `Integrations` — подключения

Отвечает за подключение внешних систем:

- GitHub;
- Git;
- Google Drive;
- ChatGPT;
- Antigravity;
- Codex;
- локальные модели;
- MCP (протокол подключения внешних инструментов и источников);
- файловая система;
- другие сервисы.

Главный вопрос:

> **Как технически связаться с внешней системой?**

### `Domains` — прикладные направления работы

Домены содержат предметную логику.

Примеры:

- работа с Issue (задачами GitHub);
- работа с PR / Pull Request (запросами на внесение изменений);
- QA (независимая проверка качества);
- оптимизация репозиториев;
- Suno;
- Research (исследования);
- документы;
- инженерные задачи;
- автоматизация.

Главный вопрос:

> **Что именно мы делаем в этой предметной области?**

### `Personal` — личный слой пользователя

Содержит четыре разных типа персонального контекста:

- **Knowledge (знания)** — факты, история, решения;
- **Rules (правила)** — обязательные требования;
- **Preferences (предпочтения)** — мягкие пожелания;
- **Settings (настройки)** — параметры конкретной установки.

Главный вопрос:

> **Как KAT9I_OS должна работать именно для владельца системы?**

### `Telemetry` — наблюдение за системой

Отвечает за:

- что реально произошло;
- кто выполнял задачу;
- какой ИИ использовался;
- сколько было попыток;
- какой был результат;
- сколько ресурсов потреблено;
- где произошла ошибка;
- насколько качественно выполнена работа.

Главный вопрос:

> **Что произошло на самом деле?**

## 1.5. Reference-first (сначала ссылка)

Один из главных принципов KAT9I_OS:

> **Если исполнитель может сам получить исходные данные через подключённый источник, KAT9I_OS передаёт ссылку на источник, а не копирует всё содержимое в контекст модели.**

Например вместо передачи полного репозитория:

```text
KAT9I_OS
    ↓
GitHub ContextRef (ссылка на источник)
    ↓
ChatGPT с GitHub Connector (подключением GitHub)
    ↓
работа
```

Результат:

```text
ChatGPT
    ↓
PR / Pull Request (запрос на внесение изменений) в GitHub
    ↓
ResultRef (ссылка на результат)
    ↓
KAT9I_OS
```

Это позволяет:

- уменьшить передачу токенов;
- уменьшить исходящий трафик KAT9I_OS;
- использовать уже оплаченные подписки;
- уменьшить дублирование данных;
- упростить передачу результатов между агентами;
- использовать общий внешний источник как рабочее пространство.

---

## 1.6. KAT9I_OS — Control Plane (управляющий слой), а не Data Bus (транспорт данных)

KAT9I_OS должна быть прежде всего **Control Plane (управляющим слоем)**.

Она управляет:

- задачами;
- правилами;
- исполнителями;
- ссылками;
- разрешениями;
- маршрутами;
- состоянием;
- проверками.

Она не должна без необходимости становиться **Data Bus (транспортом больших объёмов данных)**.

Нежелательный путь:

```text
источник
→ KAT9I_OS
→ огромный контекст
→ ИИ
→ огромный ответ
→ KAT9I_OS
→ следующий ИИ
```

Предпочтительный путь:

```text
KAT9I_OS
→ ссылка на источник
→ исполнитель
→ ссылка на результат
→ KAT9I_OS
```

---

## 1.7. Внешние данные не обязаны находиться внутри KAT9I_OS

Модульный монолит относится к **управляющему программному коду**, а не ко всем данным пользователя.

За пределами репозитория KAT9I_OS могут находиться:

- GitHub-репозитории;
- Google Drive;
- Obsidian;
- личная база знаний;
- документы;
- ChatGPT;
- Antigravity;
- локальные модели;
- другие компьютеры;
- MCP-серверы;
- исследовательские базы.

KAT9I_OS подключается к ним через Connector (подключение), Adapter (адаптер) или MCP (протокол подключения внешних инструментов и источников).

## 1.8. Канонический жизненный цикл задачи

```text
Пользователь формулирует задачу
    ↓
Core (ядро) определяет тип задачи и правила
    ↓
Domain (домен) выбирает прикладной сценарий
    ↓
Context (контекст) определяет необходимую информацию
    ↓
Resources (ресурсы) формирует ссылки на источники
    ↓
Inference (выбор ИИ) выбирает ИИ и провайдера
    ↓
Coworker (распределённая работа) выбирает исполнителя
    ↓
Security (безопасность) выдаёт ограниченные права
    ↓
Execution (исполнение) выполняет задачу
    ↓
Результат сохраняется в ResultSink (место хранения результата)
    ↓
KAT9I_OS получает ResultRef (ссылку на результат)
    ↓
QA (независимая проверка качества)
    ↓
Telemetry (наблюдение) сохраняет доказательства
    ↓
Задача завершается
```

## 1.9. Основные архитектурные принципы

1. **KAT9I_OS — единый продукт и единый канонический репозиторий.**
2. **Архитектура строится как Modular Monolith (модульный монолит).**
3. **Каждый модуль имеет одну понятную область ответственности.**
4. **Доменная логика не должна проникать в ядро и общий механизм исполнения.**
5. **KAT9I_OS управляет работой, а не переносит большие данные без необходимости.**
6. **Reference-first (сначала ссылка) используется по умолчанию.**
7. **Контекст материализуется и передаётся текстом только тогда, когда источник невозможно открыть напрямую.**
8. **Один механизм исполнения используется всеми доменами.**
9. **Личные знания физически не обязаны находиться в репозитории KAT9I_OS.**
10. **`LOW` (низкий), `NORMAL` (обычный), `HIGH` (высокий) выбираются для отдельных этапов задачи, а не для всей задачи целиком.**
11. **Локальные модели, подписочные Web-интерфейсы (веб-интерфейсы) и API (программные интерфейсы) являются равноправными маршрутами выполнения.**
12. **Безопасность и обязательные правила имеют приоритет над экономией ресурсов.**
13. **QA (независимая проверка качества) должна быть независимой от исполнителя изменения там, где это требуется политикой.**
14. **Результаты по возможности передаются через ResultRef (ссылку на результат), а не копируются между агентами.**
15. **AG25 и существующая KAT являются источниками проверенных решений, но новая архитектура не обязана сохранять их историческое разделение.**

## 1.10. Цель первого этапа разработки

Первая версия KAT9I_OS должна доказать не наличие большого числа компонентов, а работу одного полного вертикального сценария:

```text
GitHub Issue (задача)
    ↓
правила
    ↓
ContextRef (ссылка на контекст)
    ↓
выбор провайдера
    ↓
Coworker (распределённая работа)
    ↓
Worker (исполнитель)
    ↓
реальное изменение
    ↓
PR / Pull Request (запрос на внесение изменений)
    ↓
ResultRef (ссылка на результат)
    ↓
независимый QA (проверка качества)
    ↓
подтверждённое завершение
```

После того как этот путь работает полностью, архитектура может масштабироваться на другие домены, провайдеры и распределённых исполнителей.
