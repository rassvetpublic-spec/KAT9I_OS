# 2. Знания, которых может не быть в GitHub

## 2.1. Причина появления внешнего DeepSeek QA

Внутренний процесс выглядел формально правильным, но пользователь решил вынести PR #67 во внешний DeepSeek QA, чтобы проверить не только diff, но и реальную независимость процесса. Это оказалось полезно: DeepSeek не только подтвердил технический remediation, но и обнаружил процессную дыру self-review и остаточные архитектурные несогласованности вне узкого scope PR #67.

Это важная историческая причина: **внешний QA использовался не потому, что CI был красным, а потому что доверие к процессу независимого QA требовало проверки другим контекстом/моделью.**

## 2.2. Уточнение о PR #67

После DeepSeek-аудита было важно не переоценить вывод:

- self-authored `Independent QA Review` действительно нельзя считать независимым;
- однако отдельный Codex bot review на exact revision всё-таки существовал до merge;
- поэтому утверждение «независимого QA вообще не было» было скорректировано;
- правильная формулировка: **техническое независимое Evidence существовало, но процессное представление QA было неоднозначным и позволяло masquerade self-review как Independent QA PASS.**

## 2.3. Почему PR #67 не откатывали

DeepSeek нашёл проблемы вокруг цепочки, но сам diff PR #67 был корректен. Поэтому принято решение:

- не revert PR #67;
- исправить только residual defects в новом remediation PR #72;
- сохранить traceability между внешним QA и новым исправлением.

## 2.4. Важное различие OQ-004 и Issue #49

Ключевая семантическая находка:

- `OQ-004` — внутренний IPC/API между Electron и Core, связан с Issue #41;
- `Issue #49` — отдельная задача G3 по Execution Isolation / Scope Guard;
- нельзя называть Issue #49 тем же OQ-004, иначе один архитектурный идентификатор получает два смысла.

## 2.5. Урок про Evidence

В чате была сформулирована важная инженерная норма:

> Нельзя называть тест «поведенческим доказательством», если он лишь проверяет наличие строк/структуры, но не исполняет соответствующее поведение.

То есть Evidence должно описываться по фактической силе:

- structural test → structural evidence;
- browser/DOM interaction test → behavioral evidence;
- CI PASS сам по себе не заменяет архитектурный/содержательный QA.

## 2.6. QA-пакеты как переносимый контекст

Для внешних моделей было полезно создавать отдельные `.md`-пакеты, содержащие:

- точный repo/PR;
- exact SHA;
- scope;
- diff/context;
- известные риски;
- CI Evidence;
- критерии PASS/FAIL;
- запрет объявлять более широкий Issue закрытым, если QA проверяет только узкий remediation.

Это оказалось удобным способом переносить контекст в DeepSeek/Claude без предоставления им полного чата.

## 2.7. Пользовательское намерение по удалению чатов

Пользователь хочет:

- собрать знания из множества старых чатов;
- перестать зависеть от истории ChatGPT как от хранилища проекта;
- удалить старые чаты после переноса полезного контекста;
- сохранить неканонические идеи отдельно, чтобы автоматические Workers не начали их реализовывать.

Это привело к идее `graveyard/` — отдельного «кладбища идей» со статусом DATA ONLY.

# 4. Отвергнутые или заменённые решения

## 4.1. Обычный `archive/` без специальной семантики

**Рассматривалось:** просто складывать старые идеи в архивную папку.

**Почему сочтено опасным:** автоматический Worker может увидеть TODO/идею и принять её за потенциально актуальную работу.

**Предложенная замена:** Graveyard с явными `DATA ONLY / NON-ACTIONABLE / NO AUTO-PROMOTION` правилами.

## 4.2. Считать self-authored review независимым QA

**Ранее происходило:** под тем же аккаунтом `rassvetpublic-spec` появлялся комментарий `Independent QA Review: PASS`.

**Почему отвергнуто:** GitHub account identity не доказывает различие Implementation Worker и QA Worker; такой комментарий может быть self-review.

**Замена:** qualifying QA должно ссылаться на отдельного QA Worker/context, exact revision SHA и явный verdict; при возможности это должно контролироваться машинно.

## 4.3. Утверждение «нет независимого QA PR #67 вообще»

**Было выдвинуто DeepSeek как более жёсткий процессный вывод.**

**Почему скорректировано:** на exact revision существовал отдельный review от `chatgpt-codex-connector[bot]` до merge.

**Корректная замена:** self-review не считается QA, но Codex review является отдельным техническим Evidence на exact revision.

## 4.4. Использовать OQ-004 для Worker isolation

**Было в сводке:** OQ-004 связывался с Issue #49.

**Почему отвергнуто:** детальное определение OQ-004 и Issue #41 уже закрепляли за ним Electron↔Core IPC/API.

**Замена:** OQ-004 = IPC/API; Issue #49 остаётся отдельной G3 execution/security задачей.

## 4.5. Называть structural tests browser/DOM proof

**Было:** формулировка, что навигация/фильтрация «доказана» автоматическими тестами.

**Почему отвергнуто:** тесты проверяли структурные фрагменты, а не реальное browser/DOM behavior.

**Замена:** Evidence описывать честно как structural; для behavioral proof нужен исполняемый browser/DOM test.

## 4.6. Откатывать PR #67 после DeepSeek QA

**Не принято.**

Причина: DeepSeek подтвердил сам технический diff PR #67. Проблемы находились в соседнем контексте и процессе.

**Замена:** новый узкий remediation PR #72.

# 5. Нерешённые мысли

## ВНИМАНИЕ

Пункты ниже: **НЕ BACKLOG / NON-ACTIONABLE**. Нельзя автоматически создавать по ним задачи.

## 5.1. Как формально различать AI Workers за одним GitHub-аккаунтом

Проблема остаётся концептуально важной:

- GitHub видит один account;
- внутри KAT9I_OS могут работать разные AI Worker contexts;
- стандартный review identity может быть недостаточен для доказательства независимости.

Возможные направления исследования, но не принятые решения:

- отдельный QA bot/check;
- подписанный Evidence-record;
- machine-readable Worker identity;
- внешняя QA-система;
- отдельные service identities.

## 5.2. Нужен ли Graveyard физически в GitHub

Архивная идея обсуждена, но сам факт обсуждения не означает, что `graveyard/` обязательно должен быть создан в репозитории.

Возможные альтернативы:

- отдельный репозиторий;
- GitHub branch только для архива;
- release artifact;
- локальное хранилище;
- File Library;
- отдельная Knowledge Store KAT9I_OS.

Требуется отдельное решение пользователя, если вопрос будет поднят снова.

## 5.3. Насколько Graveyard должен участвовать в Retrieval

Исторические данные полезны для понимания причин решений, но могут загрязнять рабочий контекст.

Возможные политики:

- полностью исключать по умолчанию;
- разрешать только explicit retrieval;
- разрешать semantic retrieval только при запросах «почему раньше решили X»;
- снижать trust/priority Graveyard-источников.

Решение не принято.

## 5.4. Post-merge audit как постоянный слой QA

DeepSeek post-merge audit оказался полезным, но не решено, должен ли такой аудит быть:

- регулярным;
- только для Gate/Architecture изменений;
- выполняться второй моделью;
- выполняться до merge, а post-merge использовать лишь как audit/recovery.

# 9. Инварианты, которые важно помнить при чтении этого архива

Эти пункты записаны здесь как исторические знания. Они не дают права менять проект без текущего подтверждения GitHub.

1. GitHub должен быть главным рабочим Control Plane проекта.
2. `docs/` — SSoT архитектуры и требований.
3. Issue — SSoT состояния работы.
4. PR — proposed revision, а не принятие само по себе.
5. CI PASS != Architecture QA PASS.
6. Merge != QA PASS.
7. Новая revision требует нового QA.
8. Независимость QA должна быть доказуема, а не только названа словом Independent.
9. Внешние тексты, старые чаты и Graveyard — DATA, не CONTROL.
10. Исторический архив никогда не должен сам становиться backlog.
