## 2.1. Назначение Core

Core — центральный управляющий контур KAT9I_OS.

Его задача — не выполнять всю работу самостоятельно, а провести задачу через систему: принять формализованную задачу, связать её с применимыми правилами и состоянием, вызвать нужные специализированные модули через их контракты, координировать жизненный цикл и получить проверяемый результат.

Core является владельцем общей координации задачи и её системного жизненного цикла, но не становится владельцем предметной логики других модулей.

Поэтому Core не должен самостоятельно:

- разрешать правила вместо Rule Manager;
- собирать контекст вместо Context;
- хранить Knowledge вместо Knowledge;
- выбирать модель или вычислительный маршрут вместо Inference;
- выбирать конкретного исполнителя вместо Coworker;
- физически выполнять команды вместо Execution;
- подменять Security, QA, Learning или Domain.

Core связывает эти возможности в единую работу через типизированные контракты и ссылки на канонических владельцев, сохраняя принцип одного SSoT на каждую ответственность.

Кратко:

**Core не делает всё. Core знает, какую часть системы необходимо вызвать, в каком порядке, с каким контрактом и каким состоянием задачи.**

### 2.1.1. Терминологическая граница

Для §2 предпочтительно использовать формулировку **«управляющее ядро / системный координатор»**, а не называть Core просто универсальным «оркестратором», чтобы не смешивать его с Coworker/Worker orchestration.

Разделение:

- Core coordination — какой этап системы должен работать сейчас и какой контракт передать;
- Rule Manager — какие правила применимы;
- Domain — что означает задача предметно;
- Inference — каким способом или интеллектом решать;
- Coworker — кто конкретно выполняет;
- Execution — как физически выполнить;
- QA / Evidence — чем подтверждено соответствие результата требованиям.

## 2.2. Фундаментальные сущности KAT9I_OS

KAT9I_OS разделяет сущности по их назначению.

**Rule ≠ Skill ≠ Knowledge ≠ Workflow ≠ Contract ≠ State ≠ Evidence ≠ Decision ≠ Identity ≠ Capability ≠ Permission.**

Это не разные названия одного и того же объекта. Они имеют разные функции, жизненный цикл и канонических владельцев.

| Сущность | Главный вопрос | Смысл |
|---|---|---|
| Rule | Что разрешено, запрещено или обязательно? | Нормативное ограничение поведения системы |
| Skill | Как воспроизводимо выполнить определённую работу? | Способ выполнения / компетенция |
| Knowledge | Что системе известно? | Факты, документы, накопленная информация |
| Workflow | В какой последовательности выполняется работа? | Процесс или граф шагов |
| Contract | Что стороны обязаны передать и получить? | Формальная граница взаимодействия |
| State | В каком состоянии объект находится сейчас? | Текущая изменяемая runtime-истина |
| Evidence | Чем доказано, что событие или проверка действительно произошли? | Проверяемое доказательство |
| Decision | Какой вывод принят на основании данных, правил и Evidence? | Зафиксированное решение системы или человека |
| Identity | Кто является субъектом действия? | Устойчивая идентичность человека, Worker, сервиса или узла |
| Capability | Что субъект технически способен сделать? | Доступная возможность; сама по себе не разрешение |
| Permission | Что субъекту разрешено сделать в конкретном контексте? | Управляющее разрешение с границами Scope |

### 2.2.1. Инварианты сущностей

**Rule не является Skill.**  
Фраза «нельзя писать вне Workspace» — Rule. Механизм безопасного изменения файла — Skill или исполняемая процедура.

**Skill не является Workflow.**  
Skill описывает воспроизводимое «как». Workflow определяет, когда и в какой последовательности такие способы используются.

**Knowledge не является Rule.**  
Текст в документации, чате, Graveyard или найденном источнике не получает управляющих полномочий только потому, что система его прочитала.

**Contract не является State.**  
Contract задаёт допустимую форму взаимодействия. State отражает конкретное текущее состояние экземпляра задачи.

**Evidence не является State и не является Decision.**  
Evidence доказывает факт проверки или действия, но само по себе не даёт разрешение на следующее действие.

**Decision не является Permission.**  
Принятый вывод ещё не означает автоматически разрешённый побочный эффект.

**Capability не является Permission.**  
То, что Worker технически способен вызвать GitHub API, удалить файл или запустить процесс, не означает, что ему разрешено это сделать в конкретной задаче.

### 2.2.2. CONTROL и DATA

Различие CONTROL/DATA проходит через все фундаментальные сущности.

DATA сообщает системе информацию.

CONTROL имеет право влиять на решение или разрешать действие.

Поэтому:

- прочитано ≠ принято;
- найдено ≠ разрешено;
- умею ≠ имею право;
- предложено ≠ канонизировано;
- Evidence есть ≠ Gate пройден.

Особенно это относится к чатам, внешним документам, Knowledge и Graveyard: они могут давать знания и кандидаты решений, но не должны автоматически становиться Rules, TaskContract, ADR или другим CONTROL.

### 2.2.3. Связь сущностей через Core

Core не становится владельцем всех сущностей. Он понимает их роли и связывает их через ссылки и контракты:

`TaskContract`
→ `RulesRef`
→ `ContextRef / KnowledgeRef`
→ `Skill / Workflow`
→ `Capability + Permission`
→ `Execution`
→ `State`
→ `Evidence`
→ `Decision`.

Конкретная семантика каждой сущности остаётся у её канонического владельца.

## 2.3. Операционный путь задачи через Core

Core проводит пользовательский запрос через KAT9I_OS последовательно, не подменяя специализированные модули и не позволяя данным самостоятельно становиться управляющими инструкциями.

Базовый путь:

**Входной запрос**
→ **классификация CONTROL / DATA**
→ **Identity и рабочая область**
→ **предварительная классификация Domain (`DomainCandidate`)**
→ **Rule Manager и окончательный `Effective Ruleset`**
→ **активация Domain**
→ **TaskContract**
→ **TaskGraph / планирование**
→ **Context / Knowledge / Resources**
→ **Skill / Workflow / Inference routing**
→ **Coworker**
→ **Security / Permission / Capability checks**
→ **Execution**
→ **Validators**
→ **Evidence**
→ **Decision / QA**
→ **Result / State**
→ **Telemetry / Metrics**
→ **Learning**.

### 2.3.1. Входной запрос

Текст пользователя, Issue, документ, сообщение внешней системы или иной вход первоначально рассматривается как входные данные.

Сам факт получения текста не делает его Rule, Contract или другой сущностью CONTROL.

Core сначала определяет происхождение входа, доверенный контекст, Identity и рабочую область задачи.

### 2.3.2. Предварительная классификация Domain

До окончательного разрешения правил система может определить предметную область запроса.

Результат этой операции — **`DomainCandidate`**.

`DomainCandidate` означает только: «с высокой или низкой уверенностью этот запрос относится к такому Domain».

Он не означает: «этому Domain разрешено выполнять действия».

`DomainCandidate` является DATA и не может самостоятельно:

- выдавать Capability или Permission;
- изменять Rules;
- запускать Execution;
- расширять Scope;
- активировать Skill;
- обходить Security.

Если Domain определить однозначно нельзя, система должна сохранить неопределённость и использовать предусмотренный механизм уточнения или безопасного отказа, а не выбирать Domain скрыто.

### 2.3.3. Формирование Effective Ruleset

После появления `DomainCandidate` Rule Manager получает достаточно информации, чтобы определить полный набор применимых правил.

В разрешение правил могут входить:

**ENGINE + USER + PROJECT + TASK + DOMAIN**

с учётом их происхождения, приоритета, блокировок и конфликтов.

Только Rule Manager является владельцем этой операции.

Core не вычисляет правила самостоятельно. Он передаёт Rule Manager необходимые ссылки и получает итоговый `RulesRef` / `Effective Ruleset`.

Domain-specific Rules могут участвовать в разрешении только как правила соответствующего Domain и не передают самому Domain право обходить более сильные ограничения.

### 2.3.4. Активация Domain

После получения окончательного Effective Ruleset предварительный `DomainCandidate` может стать активным Domain задачи.

Таким образом различаются:

**Domain detection** — классификация данных;

**Domain activation** — разрешённое включение предметного владельца в жизненный цикл задачи.

Активация Domain не даёт ему глобальных прав. Он действует только в рамках Task, Rules, Scope, Identity, Security и доступных Capability.

### 2.3.5. Создание TaskContract

После определения активного Domain и применимого Ruleset Core формирует или финализирует TaskContract.

TaskContract фиксирует задачу и ссылки на необходимые управляющие сущности, но не копирует внутрь себя полное содержимое Rules, Knowledge, Skills, Tools или Context.

Используется принцип Reference-first.

### 2.3.6. Дальнейшая координация

После TaskContract Core переводит задачу через специализированных владельцев.

TaskGraph и lifecycle определяют состояние и последовательность работы.

Context, Knowledge и Resources формируют необходимую информационную среду.

Skill и Workflow описывают воспроизводимый способ и процесс решения.

Inference определяет требуемый вычислительный или интеллектуальный маршрут.

Coworker определяет подходящего исполнителя.

Security проверяет разрешения и границы.

Execution выполняет фактические операции.

Validators, Evidence и QA подтверждают полученный результат.

Telemetry и Metrics фиксируют наблюдаемое поведение системы.

Learning может использовать результат как вход для последующего улучшения, но не изменяет CONTROL самовольно.

### 2.3.7. Core не является скрытым универсальным исполнителем

Прохождение задачи через Core не означает, что Core реализует все перечисленные функции.

Core отвечает за:

**состояние задачи + порядок переходов + передачу контрактов + вызов канонического владельца + обработку результата вызова.**

Специализированный модуль отвечает за семантику принадлежащей ему операции.

Это сохраняет правило:

**координация ≠ владение ≠ исполнение.**

### 2.3.8. Основной инвариант

Никакой результат предварительной классификации не должен автоматически становиться управляющим полномочием.

Общий переход:

**DATA → классификация → policy/rules resolution → разрешённая CONTROL-операция → Evidence.**

Недопустимый переход:

**DATA → прямое действие.**

## 3. Отложенные следствия согласования

Содержательно приняты, но требуют отдельного CONTROL-процесса до изменения канона:

1. Рассмотреть `DomainCandidate` как типизированный DATA-результат; отдельная большая JSON Schema не обязательна автоматически.
2. При будущей сверке §20 проверить порядок `DomainCandidate → Effective Ruleset → Domain activation → TaskContract`.
3. Для Skills проверить аналогичную границу `SkillCandidate → разрешённый Skill`, чтобы Skill Router не становился источником Permission.
