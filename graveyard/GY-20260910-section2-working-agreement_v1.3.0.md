## 2.7. Системные инварианты операционной модели KAT9I_OS

Инварианты — это свойства архитектуры, которые должны сохраняться независимо от конкретного Domain, Worker, Provider, Skill, Workflow или способа физического развёртывания системы.

§2 фиксирует их как архитектурную карту.

Подробная семантика каждого инварианта остаётся у его канонического владельца.

### 2.7.1. Один смысл — один канонический владелец

Для каждой архитектурной ответственности существует один канонический владелец.

**ONE RESPONSIBILITY → ONE CANONICAL OWNER → MANY REFERENCES / CLIENTS.**

Допускается множество пользователей одной функции, но не несколько независимых источников истины одного смысла.

Если одна ответственность обнаружена одновременно в двух модулях, это архитектурный конфликт, а не допустимое дублирование.

### 2.7.2. Один объект — один основной тип

Системная сущность должна иметь определённый основной тип.

**Rule ≠ Skill ≠ Knowledge ≠ Workflow ≠ Contract ≠ State ≠ Evidence ≠ Decision ≠ Identity ≠ Capability ≠ Permission.**

Один объект может ссылаться на другие сущности, но не должен менять свой тип только из-за того, как его решил использовать конкретный Worker.

Например KnowledgeRecord со словами «всегда делай X» остаётся Knowledge, пока не прошёл отдельную процедуру превращения в Rule.

### 2.7.3. CONTROL ≠ DATA

KAT9I_OS должна всегда сохранять границу между управляющей информацией и данными.

DATA может информировать Decision.

DATA не может самостоятельно выдавать Permission, расширять Scope, изменять Rules или запускать side effect.

Поэтому:

**прочитано ≠ принято**
**найдено ≠ разрешено**
**сгенерировано ≠ утверждено**
**предложено ≠ канонизировано**.

Передача DATA через доверенный внутренний модуль не превращает его автоматически в CONTROL.

### 2.7.4. Candidate ≠ Selection ≠ Permission

Предварительная классификация всегда отделяется от управляющего решения.

Например:

`DomainCandidate ≠ Active Domain`

`SkillCandidate ≠ SkillSelection`

`WorkflowCandidate ≠ WorkflowSelection`

Candidate является DATA.

Selection является Decision.

Decision не является Permission.

Таким образом обнаружение подходящего объекта не может само запускать действие.

### 2.7.5. Capability ≠ Permission

Capability означает:

**«субъект технически способен выполнить действие».**

Permission означает:

**«субъекту разрешено выполнить это действие сейчас, над этим объектом и в этом Scope».**

Фактическое выполнение требует обеих сторон.

**Capability ∧ Permission → потенциально допустимое Execution.**

Наличие инструмента, API, токена доступа или технической возможности не является разрешением.

### 2.7.6. Coordination ≠ Ownership ≠ Execution

Core координирует.

Канонический модуль владеет семантикой своего решения.

Execution выполняет side effect.

Эти роли не должны сливаться.

То, что Core инициирует Security check, не делает Core владельцем Security Decision.

То, что Domain требует GitHub operation, не делает Domain владельцем GitHub transport.

То, что Execution технически может выполнить действие, не даёт Execution права решать, нужно ли это действие.

### 2.7.7. Contract ≠ State

Contract описывает допустимую форму и обязательства взаимодействия.

State описывает фактическое текущее состояние экземпляра системы.

TaskContract не должен использоваться как mutable runtime storage.

TaskRuntimeState не должен скрыто изменять требования TaskContract.

Изменение требования и изменение состояния являются разными операциями.

### 2.7.8. Command ≠ Event

Command означает намерение выполнить действие.

Event означает факт уже произошедшего события.

Event не является скрытой командой.

Command не является доказательством выполнения.

Это позволяет системе безопасно восстанавливаться, повторять доставку сообщений и проводить аудит.

### 2.7.9. Result ≠ Evidence ≠ Decision

Result показывает, что было получено.

Evidence доказывает наблюдаемый факт.

Decision определяет, какой вывод принят.

Например:

`Artifact exists`
→ Result;

`Artifact hash + successful tests`
→ Evidence;

`QA PASS`
→ Decision.

Нельзя считать наличие результата доказательством его корректности.

### 2.7.10. Нет Evidence — нет доказанного успеха

Для действий, где архитектура требует Evidence, отсутствие Evidence означает отсутствие доказательства выполнения.

Система не должна преобразовывать:

**«ошибок не видно»**

в:

**«операция доказанно успешна».**

Особенно это относится к внешним side effects, публикации, QA, Security-sensitive операциям и изменениям канонического состояния.

### 2.7.11. Exact revision для проверяемых объектов

Evidence и QA должны быть связаны с конкретной версией проверенного объекта, когда объект имеет revision.

Изменение объекта после проверки может сделать прежнее Evidence или QA неприменимым.

Нельзя автоматически переносить verdict с одной revision на другую.

### 2.7.12. Fail-closed для критичных переходов

Если система не может доказать обязательное условие критичного действия, действие не выполняется.

Неизвестность не должна автоматически трактоваться как разрешение.

Особенно это относится к:

- Security;
- Scope;
- обязательным Rules;
- Identity;
- Permission;
- contract version;
- critical Gate.

Fail-closed применяется к безопасности и корректности, а не как универсальный способ останавливать любую некритичную работу.

### 2.7.13. DENY нельзя обходить маршрутизацией

Если действие запрещено применимыми Rules или Security, нельзя сделать его разрешённым путём смены:

Worker, Provider, Skill, Workflow, Tool, Integration или способа исполнения.

Маршрутизация выбирает допустимый способ.

Она не изменяет границу допустимого.

### 2.7.14. Scope нельзя расширять скрыто

Scope является частью управляющего контекста задачи.

Worker, Skill, Domain, Context, Integration или Execution не должны расширять Scope самостоятельно.

Если работа требует большего Scope, система должна получить новое официальное решение предусмотренного владельца.

### 2.7.15. Executable-first

Повторяемая, формализуемая и проверяемая часть работы должна по возможности выполняться детерминированным кодом или обычным инструментом.

ИИ используется для остаточной части, действительно требующей интерпретации, генерации или сложного reasoning.

Skill не равен prompt.

Workflow не равен длинной инструкции модели.

### 2.7.16. Local-first

После проверки Executable-first для интеллектуальной части предпочтителен минимально достаточный разрешённый локальный маршрут, если он обеспечивает необходимое качество и безопасность.

Экономия не может отменять Security, Rules или минимальное требуемое качество.

### 2.7.17. Reference-first

Большие объекты не должны копироваться между модулями без необходимости.

По возможности используются versioned References:

`RulesRef`, `ContextRef`, `KnowledgeRef`, `ResourceRef`, `ResultRef`, `EvidenceRef` и другие.

Reference должен вести к каноническому объекту или точно определённой revision.

Ссылка сама по себе не является Permission.

### 2.7.18. Progressive Disclosure

Worker, Provider или другой исполнитель получает только минимально достаточный набор:

Rules, Skills, Tools, Context, Knowledge и Resources.

Полные системные каталоги не должны автоматически попадать в рабочий контекст каждого исполнителя.

Дополнительный контекст раскрывается только при доказанной необходимости.

### 2.7.19. Minimal sufficient intelligence

Для каждого этапа используется минимально достаточный уровень вычислительного интеллекта.

Большая задача не должна автоматически целиком передаваться наиболее мощной модели.

Разные узлы TaskGraph могут использовать разные механизмы:

- обычный код;
- Tool;
- локальный AI;
- внешний AI;
- Human Decision.

### 2.7.20. Skill ≠ Worker ≠ Provider

Skill определяет способ работы.

Worker определяет конкретного исполнителя.

Provider определяет вычислительный или интеллектуальный ресурс.

Эти сущности маршрутизируются независимо.

Выбор Skill не должен автоматически фиксировать конкретного Worker или Provider, если это не является обязательной частью Contract.

### 2.7.21. Workflow ≠ TaskGraph

Workflow является повторно используемым определением процесса.

TaskGraph является конкретной структурой конкретной Task.

Workflow может быть материализован в часть TaskGraph.

TaskGraph может содержать runtime-ветви, которых нет в исходном Workflow: Retry, Recovery, Context Request, Human Decision, дополнительный QA и другие.

### 2.7.22. Cache ≠ Knowledge ≠ Evidence ≠ SSoT

Cache существует для ускорения повторного вычисления.

Knowledge существует для управляемого хранения подтверждённого знания.

Evidence существует для доказательства факта.

SSoT является каноническим источником определённой истины.

Переиспользование результата из Cache не делает Cache источником истины.

Удаление Cache не должно менять корректный логический результат системы.

### 2.7.23. Graveyard всегда DATA

Graveyard является архивом исторических идей, восстановленных материалов, отклонённых вариантов и контекста расследований.

Содержимое Graveyard не является CONTROL и не получает автоматического права влиять на Runtime.

Переход:

**Graveyard DATA → Canonical CONTROL**

возможен только через отдельный явный promotion process с владельцем решения.

### 2.7.24. Learning Proposal ≠ Change

Learning может обнаружить улучшение и сформировать Proposal.

Proposal остаётся кандидатом.

Он не должен автоматически изменять:

- Rules;
- Security;
- Contracts;
- архитектурный ownership;
- Skills высокого риска;
- канонические документы;
- системные разрешения.

Уровень автоматизации изменения определяется отдельной Learning/Promotion policy.

### 2.7.25. Prompt не является системной архитектурой

Prompt является входом для модели, а не заменой Rule Manager, Security, State Store, Contract system или Workflow Engine.

Критичная системная семантика должна существовать вне prompt в типизированной форме.

Замена Provider или Worker не должна разрушать понимание Task, Rules, State, Scope и Permission.

### 2.7.26. LLM output по умолчанию DATA

Вывод модели является результатом вычисления и первоначально рассматривается как DATA.

Он может стать основанием для Decision после предусмотренной проверки.

Модель не может сама повысить собственный output до обязательного Rule, Security Decision, Permission или Evidence выполнения внешнего side effect.

### 2.7.27. Human Decision является типизированным CONTROL

Когда архитектура требует USER или ADMIN Decision, решение должно быть зафиксировано как определённый системный объект.

Историческая фраза из чата, отсутствие ответа или предположение модели о намерении человека не должны автоматически заменять новое требуемое Approval.

### 2.7.28. Identity сохраняется через жизненный цикл

Значимые действия должны позволять определить, кто был субъектом действия или решения:

USER, ADMIN, Worker, Service или другой предусмотренный Identity.

Передача действия между модулями не должна терять Identity и Provenance.

### 2.7.29. Provenance сохраняется

Для значимых Rules, Knowledge, Decisions, Results, Evidence и других системных объектов должно быть возможно определить их происхождение.

Transformation, summary или materialization не должны уничтожать ссылку на первичный источник.

### 2.7.30. Нельзя бесконечно пересказывать пересказы

Derived Context и Summary должны сохранять References на первичные источники.

Для критичных решений используется первичный или канонический источник, когда он доступен.

Это ограничивает накопление ошибок в длинных цепочках AI-generated summaries.

### 2.7.31. Versioned contracts

Устойчивые межмодульные контракты имеют версию.

Неизвестная обязательная версия не должна интерпретироваться «примерно».

Совместимость обеспечивается официальной схемой, адаптером или контролируемым отказом.

### 2.7.32. Physical deployment ≠ logical ownership

Архитектурный модуль определяет ответственность.

Физический process, executable, service, Rust module, Electron process или внешний Worker определяет deployment.

Один логический владелец может иметь несколько физических компонентов.

Несколько физических компонентов не должны создавать несколько независимых архитектурных владельцев одной ответственности.

### 2.7.33. Telemetry ≠ Metrics ≠ Learning

Telemetry отвечает:

**«что произошло?»**

Metrics отвечает:

**«насколько хорошо это произошло?»**

Learning отвечает:

**«что стоит изменить в будущем?»**

Наблюдение не является оценкой.

Оценка не является автоматическим изменением системы.

### 2.7.34. Recovery опирается на факты

После сбоя система восстанавливает состояние из структурированного State, Event Journal, Lease, generation, Checkpoints, Evidence и фактического состояния ресурсов.

LLM может помогать анализировать сложный инцидент, но не является источником истины о том, произошёл ли внешний side effect.

### 2.7.35. False success запрещён

Система не должна сообщать успешное завершение, если обязательная часть результата не доказана.

Если внешнее действие неизвестно, система должна сохранить состояние неопределённости или перейти в Recovery, а не объявлять успех.

Если обязательный QA не выполнен, задача не становится `COMPLETED` как проверенная.

Если публикация не подтверждена, наличие локального Artifact не является опубликованным Result.

### 2.7.36. Главная формула операционной модели

KAT9I_OS должна стремиться к следующей цепочке:

**Intent**
→ **typed Task**
→ **applicable Rules**
→ **authorized Scope**
→ **selected Domain / Workflow / Skill**
→ **minimal Context**
→ **required Capability**
→ **appropriate Inference**
→ **selected Worker**
→ **Permission**
→ **Execution**
→ **Result**
→ **Evidence**
→ **Decision / QA**
→ **State transition**
→ **Telemetry / Metrics**
→ **Learning Proposal**.

Ни один переход в этой цепочке не должен получать дополнительные полномочия только из-за того, что предыдущий этап выдал удобный результат.

### 2.7.37. Итоговый мета-инвариант

Архитектура KAT9I_OS должна оставаться объяснимой.

Для значимого действия система должна уметь ответить:

**что выполнялось;
почему это было выбрано;
какие Rules действовали;
кто был субъектом;
какой Scope был разрешён;
какой Skill/Workflow использовался;
какой Worker и Provider участвовали;
какое Permission позволило действие;
что получилось;
чем это доказано;
какое Decision было принято;
какое состояние стало следующим.**

Если на критичный вопрос нельзя дать структурированный ответ, архитектурная цепочка считается неполной.
