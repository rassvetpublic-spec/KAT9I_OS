## 2.8. Архитектурная карта KAT9I_OS

Этот подраздел показывает KAT9I_OS сверху как единую операционную систему.

Он не является вторым источником истины для устройства отдельных модулей.

Подробная семантика остаётся в профильных архитектурных разделах, а каноническая карта владения ответственностями — в §27.

Если краткая карта §2 расходится с профильным SSoT, исправляется карта §2, а не создаётся второй вариант истины.

### 2.8.1. Общая модель

KAT9I_OS можно представить как последовательность специализированных слоёв:

**Intent / Input**
↓
**Core** — организовать работу системы
↓
**Rule Manager** — определить применимые обязательные Rules
↓
**Domain** — определить предметный смысл задачи
↓
**TaskContract / TaskGraph** — формализовать конкретную работу
↓
**Context + Knowledge + Resources** — дать минимально необходимую информацию и ссылки
↓
**Workflow + Skills** — определить воспроизводимый способ работы
↓
**Inference** — определить необходимый вычислительный или интеллектуальный маршрут
↓
**Coworker** — выбрать конкретного Worker
↓
**Security** — разрешить или запретить конкретное действие
↓
**Execution + Integrations** — физически выполнить разрешённую операцию
↓
**Result + Evidence**
↓
**Validators / QA / Human Decision** — определить, принят ли результат
↓
**State transition**
↓
**Telemetry + Metrics**
↓
**Learning Proposal**.

Core связывает эти этапы, но не подменяет их владельцев.

### 2.8.2. Core — системный координатор

Core отвечает:

**«Что системе необходимо организовать дальше?»**

Его основными объектами являются:

- Task;
- TaskContract;
- TaskGraph;
- TaskRuntimeState;
- Contracts;
- References;
- Decisions;
- Gates;
- переходы жизненного цикла;
- общесистемный Skill Registry;
- generic Skill Routing.

Core не должен содержать внутри себя полную реализацию остальных архитектурных областей.

### 2.8.3. Rule Manager — нормативный слой

Rule Manager отвечает:

**«Какие обязательные ограничения применимы?»**

Он формирует единый Effective Ruleset и RulesRef.

Остальные модули используют этот результат и не собирают собственную альтернативную систему приоритетов Rules.

Подробный владелец этой семантики — §4.

### 2.8.4. Domain — предметный смысл

Domain отвечает:

**«Что означает правильное выполнение задачи этого типа?»**

Domain владеет предметной семантикой, в том числе своими:

- Skills;
- Workflows;
- Validators;
- Domain Rules;
- форматами результата;
- связями с предметным Knowledge.

Domain не становится владельцем общесистемной маршрутизации, Security или Execution.

### 2.8.5. TaskContract — формализация конкретной задачи

TaskContract связывает намерение пользователя с исполняемой системой.

Он определяет:

**что должно быть сделано и в каких границах.**

Он использует ссылки на Rules, Context, Resources и другие системные объекты вместо копирования полных каталогов.

Подробная модель TaskContract принадлежит §3.

### 2.8.6. Context, Knowledge и Resources — информационная плоскость

Эти модули решают разные вопросы.

**Resources:**
«где находится объект?»

**Knowledge:**
«что система уже знает?»

**Context:**
«что из доступного необходимо знать конкретному исполнителю сейчас?»

Они не должны сливаться в одну универсальную базу.

Context использует Reference-first и Progressive Disclosure.

Подробная модель Context принадлежит §7.

### 2.8.7. Skills и Workflows — способы работы

Skill отвечает:

**«Как воспроизводимо выполнить работу?»**

Workflow отвечает:

**«В какой последовательности связать несколько действий?»**

Содержание предметного Skill/Workflow принадлежит соответствующему Domain или системному модулю.

Core поддерживает общесистемную регистрацию и generic routing, но не становится владельцем предметного содержания.

### 2.8.8. Inference — вычислительная маршрутизация

Inference отвечает:

**«Какой минимально достаточный вычислительный или интеллектуальный маршрут нужен?»**

Он различает:

- детерминированный код;
- обычные Tools;
- локальный AI;
- внешний Provider;
- Human Decision.

Inference не является Skill Router и не выбирает конкретного Worker.

Подробная модель маршрутизации принадлежит §10.

### 2.8.9. Coworker — выбор исполнителя

Coworker отвечает:

**«Кто конкретно выполнит работу?»**

Он сопоставляет требования задачи с Worker Registry, Capability, availability, Trust и другими характеристиками исполнителя.

Skill описывает способ работы.

Coworker выбирает исполнителя этого способа.

Это разные решения.

### 2.8.10. Security — граница полномочий

Security отвечает:

**«Разрешено ли этому субъекту выполнить это действие над этим объектом в данном Scope?»**

Ни Core, ни Domain, ни Worker, ни Skill, ни Integration не имеют права самостоятельно заменять Security Decision.

Capability не является Permission.

### 2.8.11. Execution — физическое выполнение

Execution отвечает:

**«Как физически выполнить уже определённое и разрешённое действие?»**

Здесь происходят реальные side effects:

- процессы;
- файлы;
- Git;
- Worktree;
- внешние изменения;
- Runtime operations.

Execution не выбирает цель задачи и не выдаёт себе Permission.

### 2.8.12. Integrations — технический доступ наружу

Integrations предоставляют технический способ работы с внешними системами:

- GitHub;
- API;
- CLI;
- MCP;
- Drive;
- другие Connectors и Adapters.

Integration отвечает:

**«Как технически вызвать внешнюю возможность?»**

но не:

**«Разрешено ли это делать?»**

### 2.8.13. Result, Evidence и QA

После выполнения система должна различать:

**Result**
— что получилось;

**Evidence**
— чем подтверждено произошедшее;

**QA Decision**
— соответствует ли проверенный результат требованиям.

Наличие Artifact не означает QA PASS.

Наличие QA PASS для одной revision не означает PASS для изменённой revision.

### 2.8.14. Telemetry, Metrics и Learning

После выполнения:

**Telemetry**
фиксирует факты;

**Metrics**
оценивает качество, эффективность и стоимость;

**Learning**
ищет возможность улучшения.

Learning формирует Proposal.

Proposal не становится изменением CONTROL автоматически.

### 2.8.15. Recovery

Recovery используется, когда текущий State или фактический результат операции нельзя безопасно определить обычным продолжением lifecycle.

Он восстанавливает состояние из структурированных фактов, а не из предположения модели.

После определения подтверждённого состояния управление снова возвращается в нормальный lifecycle Core.

### 2.8.16. Personal Layer

Personal Layer хранит и предоставляет системно разрешённый пользовательский контекст:

- Preferences;
- профиль;
- устойчивые пользовательские параметры;
- допустимые персональные настройки.

Personal Layer не должен превращать Preference в обязательный Rule без соответствующей типизации и процедуры.

### 2.8.17. Physical Runtime

Логическая архитектурная карта не определяет обязательное физическое размещение модулей.

Части KAT9I_OS могут исполняться:

- в Core Runtime;
- локальном executable;
- Electron process;
- Worker;
- отдельном сервисе;
- внешнем Provider.

Физическое размещение не меняет каноническое архитектурное владение.

### 2.8.18. Основные плоскости системы

Для понимания архитектуры KAT9I_OS удобно рассматривать несколько логических плоскостей.

**Control Plane**

Core
Rule Manager
Security
TaskContract / State / Gates.

Определяет управляемое и разрешённое движение задачи.

**Domain / Capability Plane**

Domain
Skills
Workflows
Validators.

Определяет предметную работу и воспроизводимые способы её выполнения.

**Knowledge / Context Plane**

Knowledge
Resources
Context
Cache.

Обеспечивает необходимую информацию и эффективный доступ к ней.

**Intelligence Plane**

Inference
Providers
Human Decision routes.

Определяет требуемый интеллектуальный или вычислительный маршрут.

**Execution Plane**

Coworker
Worker Registry
Execution
Integrations.

Назначает исполнителя и выполняет фактические действия.

**Assurance Plane**

Evidence
Validators
QA
Recovery.

Доказывает результат и обеспечивает корректное продолжение после проблем.

**Observation / Improvement Plane**

Telemetry
Metrics
Learning.

Наблюдает работу и формирует предложения улучшения.

Плоскости являются способом объяснения архитектуры, а не новыми владельцами функций.

### 2.8.19. Сквозной путь одной задачи

В упрощённом виде:

**Запрос пользователя**

→ Core принимает Task

→ определяется `DomainCandidate`

→ Rule Manager формирует Effective Ruleset

→ активируется Domain

→ формируется TaskContract и TaskGraph

→ выбирается Workflow

→ Skill Registry предоставляет подходящие `SkillCandidate`

→ выбирается Skill

→ Context собирает минимально достаточный Context

→ Inference определяет вычислительный маршрут

→ Coworker выбирает Worker

→ Security проверяет конкретное действие

→ Execution выполняет его через необходимую Integration

→ создаются Result и Evidence

→ Validators / QA / Human Decision принимают предусмотренное решение

→ Core переводит Task в следующее State

→ Telemetry и Metrics фиксируют факт и качество

→ Learning может создать Proposal.

### 2.8.20. Что §2 не должен дублировать

§2 не является:

- полным описанием TaskContract;
- вторым Rule SSoT;
- полной моделью Context;
- каталогом Skills;
- спецификацией Inference;
- Worker Registry;
- Security Policy;
- Execution Protocol;
- схемой всех внутренних Contracts;
- второй картой владения вместо §27;
- полной state machine вместо §20.

§2 объясняет:

**как эти части составляют одну систему.**

### 2.8.21. Навигация к каноническим владельцам

При необходимости детализации §2 направляет читателя к профильным SSoT.

Ключевые переходы:

- Task / TaskContract → §3;
- Rules / Effective Ruleset → §4;
- Learning → профильный раздел Learning;
- Context → §7;
- Inference → §10;
- полный lifecycle → §20;
- внутренние Contracts → §26;
- окончательная ownership map → §27.

По остальным подсистемам используется соответствующий профильный архитектурный раздел и актуальная карта §27.

### 2.8.22. Итоговая формула

KAT9I_OS не является одной большой моделью, одним Prompt или одним универсальным агентом.

Это система специализированных владельцев, связанных через Core:

**ONE TASK
→ MANY SPECIALIZED OWNERS
→ TYPED CONTRACTS
→ EXPLICIT DECISIONS
→ MINIMAL CONTEXT
→ AUTHORIZED EXECUTION
→ VERIFIABLE EVIDENCE
→ CONTROLLED STATE TRANSITIONS.**

Core превращает набор специализированных модулей в одну операционную систему, не забирая их ответственность себе.
