## 2.9. Статус раздела и отношения с каноническими SSoT

Раздел §2 определяет верхнеуровневую архитектурную карту и операционную модель KAT9I_OS.

Он отвечает на вопросы:

- как система в целом устроена;
- какую роль выполняет Core;
- как различаются основные типы системных сущностей;
- как задача проходит между специализированными владельцами;
- какие системные инварианты должны сохраняться;
- как читать остальные архитектурные разделы как части единой системы.

§2 не должен становиться вторым подробным SSoT для функций, уже имеющих канонического владельца.

### 2.9.1. Роль §2

Основная роль §2:

**ARCHITECTURAL MAP + OPERATING MODEL.**

То есть:

**§2 объясняет связи и границы. Профильные разделы определяют подробную семантику.**

Если читателю необходимо понять систему сверху — он начинает с §2.

Если необходимо реализовать или изменить конкретную подсистему — используется её профильный SSoT.

### 2.9.2. §2 и §3

§2 показывает место TaskContract в общей операционной модели.

§3 остаётся каноническим владельцем подробной модели TaskContract.

§2 не должен повторять полную схему TaskContract, все его поля, правила versioning, полный OutputContract и подробные зависимости TaskGraph.

### 2.9.3. §2 и §4

§2 показывает место Rules и Effective Ruleset в общей системе.

§4 остаётся каноническим владельцем Rule Manager, Rule resolution, Effective Ruleset, RulesRef, конфликтов и Scope правил, Executable-first и связанных принципов, определённых этим разделом.

Если формулировка §2 о правилах расходится с §4, должна быть исправлена §2.

### 2.9.4. §2 и Domain

§2 определяет общую границу: **Domain владеет предметным смыслом.**

Подробная архитектура конкретных Domains остаётся в их профильных спецификациях.

§2 не должен содержать предметные правила музыкального, инженерного, GitHub или другого Domain.

### 2.9.5. §2 и Context / Knowledge / Resources

§2 показывает различие между Context, Knowledge и Resources.

Профильные разделы остаются владельцами их подробной модели.

Особенно §2 не должен становиться хранилищем Context schemas, Knowledge lifecycle, Resource Resolver rules, Context Budget algorithms или Cache implementation.

### 2.9.6. §2 и Skills

§2 определяет архитектурную границу:

**Skill semantic ownership** принадлежит Domain или соответствующему системному модулю;

**общесистемный Skill Registry и generic Skill Routing** относятся к Core coordination.

Подробная структура Skill, его код, тесты, Validators и предметная семантика не должны храниться в §2.

Если для Skill Registry будет создан отдельный профильный SSoT, §2 должен ссылаться на него и перестать содержать подробности его реализации.

### 2.9.7. §2 и Inference

§2 показывает место Inference между способом работы и конкретным исполнителем.

§10 остаётся каноническим владельцем вычислительной и интеллектуальной маршрутизации.

§2 не выбирает конкретные Provider, модели, уровни интеллекта или экономические алгоритмы.

### 2.9.8. §2 и Coworker / Execution

§2 фиксирует фундаментальную границу:

**Core организует; Coworker выбирает исполнителя; Execution физически выполняет действие.**

Профильные разделы Coworker и Execution остаются владельцами Worker Registry, scheduling, Claim / Lease, Runtime, Worktree, side effects, Cleanup и execution-specific Evidence.

### 2.9.9. §2 и Security

§2 фиксирует **Capability ≠ Permission** и обязанность обращаться к Security перед защищённым side effect.

Security остаётся единственным владельцем подробной модели Permission, Security Decision, Grants, Approval и security boundaries.

§2 не должен создавать альтернативную Security Policy.

### 2.9.10. §2 и §20

§2 содержит упрощённый путь задачи для объяснения архитектуры.

§20 остаётся каноническим владельцем полного lifecycle и orchestration sequence.

При изменении жизненного цикла сначала изменяется канонический §20, затем синхронизируется обзорная схема §2.

### 2.9.11. §2 и §26

§2 устанавливает принцип: **межмодульное управление осуществляется типизированными Contracts, States, Decisions, Events и References.**

§26 остаётся каноническим владельцем конкретных типов сообщений, schemas, versioning, protocol semantics, TaskRuntimeState, Security Decision, Capability Grant, ResultRef, EvidenceRef, QA Result и Human Decision.

§2 не должен копировать полный каталог внутренних контрактов.

### 2.9.12. §2 и §27

§27 является канонической картой владения архитектурными ответственностями.

§2 использует эту карту для объяснения взаимодействия владельцев.

**§2 = как система работает вместе.**

**§27 = кто является владельцем каждой ответственности.**

Если возникает спор о владельце функции, решающим архитектурным документом является §27 после согласования с профильным SSoT.

§2 затем синхронизируется с этим решением.

### 2.9.13. Запрет на второй SSoT

В §2 не следует переносить подробную спецификацию функции только ради удобства чтения.

Вместо дублирования используется краткое определение, архитектурная граница и ссылка на канонического владельца.

Принцип:

**SUMMARY + BOUNDARY + REFERENCE, NOT DUPLICATE SPECIFICATION.**

### 2.9.14. Правило конфликта документов

Если §2 противоречит профильному каноническому SSoT, §2 считается устаревшей картой в этой точке.

Конфликт должен быть явно исправлен.

Нельзя молча выбирать более удобную формулировку, поддерживать две версии истины или считать §2 автоматически сильнее профильного владельца.

Если конфликт показывает реальную неопределённость ownership, она сначала разрешается архитектурно и фиксируется в канонических владельцах.

### 2.9.15. Эволюция архитектуры

§2 должен быть относительно стабильным.

Добавление каждой новой реализации, Provider, Tool или Worker не требует изменения §2.

§2 изменяется, когда меняется фундаментальная роль Core, граница между архитектурными владельцами, тип фундаментальной сущности, общая operating model, системный инвариант или верхнеуровневая структура KAT9I_OS.

Детальные изменения подсистем происходят в профильных SSoT.

### 2.9.16. Историческая функция раздела

§2 сохраняет исходный смысл Core как общего control plane, но отражает последующую декомпозицию KAT9I_OS.

Исторически многие функции описывались как части Core.

В современной архитектуре значительная часть этих функций получила самостоятельных канонических владельцев.

Поэтому §2 не должен искусственно возвращать их внутрь Core.

Он должен показывать, какая ответственность исторически рассматривалась через Core и какой специализированный владелец отвечает за неё сейчас.

### 2.9.17. Современное определение Core

После архитектурной декомпозиции Core определяется как:

**канонический системный координатор жизненного цикла задачи, состояния, контрактов, переходов и общесистемной маршрутизации capability/Skill, который вызывает специализированных владельцев и не подменяет их семантику.**

Это определение является развитием, а не буквальным возвратом к первоначальному широкому Core.

### 2.9.18. Критерий корректности §2

§2 считается корректным, если после его чтения можно понять:

- из каких крупных частей состоит KAT9I_OS;
- какую роль играет Core;
- чем отличаются фундаментальные сущности;
- как задача перемещается через систему;
- где проходит граница CONTROL/DATA;
- кто принимает различные классы Decisions;
- почему Capability не является Permission;
- почему Result не является Evidence;
- почему Skill не является Worker;
- почему Workflow не является TaskGraph;
- почему один модуль не должен дублировать другого;
- где искать подробный канонический SSoT.

При этом читатель не должен получить впечатление, что §2 сам является подробной спецификацией всех этих подсистем.

### 2.9.19. Итог

§2 является входной архитектурной картой KAT9I_OS.

Его задача:

**сделать целое понятным, не создавая второй источник истины для его частей.**

Финальная формула раздела:

**CORE COORDINATES.  
SPECIALIZED OWNERS DECIDE.  
SECURITY AUTHORIZES.  
EXECUTION ACTS.  
EVIDENCE PROVES.  
STATE RECORDS.  
SSoT REMAINS SINGLE.**
