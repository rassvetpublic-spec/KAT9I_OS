## 2. Отложенный вариант A — собственный полный контур исполнения Kat9I

### Историческая идея

Собрать внутри Kat9I отдельный контур исполнения AI-запросов:

`CredentialBroker → ExecutionSessionRegistry → AccountHealth → Scheduler → CircuitBreaker → Gateway`

Здесь `CredentialBroker` — посредник учётных данных, `ExecutionSessionRegistry` — реестр сессий исполнения, `AccountHealth` — состояние аккаунтов, `Scheduler` — планировщик, `CircuitBreaker` — автоматическая блокировка неисправного маршрута, `Gateway` — шлюз исполнения.

### Почему отложено

Исследование Antigravity Manager показало существенное совпадение: пул аккаунтов, обновление учётных данных, квоты и состояние, закрепление сессий, планирование, повторные попытки и переключение при сбоях, circuit breaker, маршрутизация моделей, прокси и управление сессиями уже существуют в upstream — внешнем исходном проекте.

Немедленная собственная реализация создаёт:

- второй источник состояния контура исполнения;
- больше кода и тестов;
- новую границу безопасности для учётных данных;
- риск несовместимой логики планировщика и квот;
- лишнюю стоимость поддержки и расход токенов;
- преждевременную зависимость архитектуры от предположения, что upstream недостаточен.

### Условие для «раскопки»

Вернуться к идее только после `Capability Matrix` — матрицы покрытия требований возможностями — и воспроизводимого функционального или безопасностного пробела, который нельзя закрыть тонким адаптером, конфигурацией или изоляцией Manager за интерфейсом.

## 3. Отложенный вариант B — собственные AccountPool / QuotaManager / RefreshTokenStore Kat9I

### Историческая идея

Kat9I самостоятельно хранит AI-аккаунты и refresh token — долгоживущие токены обновления, считает квоты и состояние, выбирает аккаунт и выполняет обновление/ротацию credentials — учётных данных.

### Почему отложено

Это дублирует роль Antigravity Manager как владельца жизненного цикла учётных данных и пула ресурсов. Особенно опасно собственное хранилище refresh token: оно расширяет секретную границу Kat9I без доказанной пользы.

### Более дешёвая текущая гипотеза

Kat9I хранит только несекретные метаданные исполнения и получает нормализованные квитанции и статусы от адаптера/Manager.

### Условие для «раскопки»

Только если Manager не обеспечивает необходимую изоляцию, аудит, жизненный цикл учётных данных или требуемую политику и это подтверждено тестом, а не предположением.

## 4. Отложенный вариант C — полная перепись Antigravity Manager на Rust

### Историческая идея

Разобрать upstream-модули Manager и переписать их на Rust внутри Kat9I, чтобы полностью владеть контуром исполнения.

### Почему отложено

- большой объём работ до доказанной необходимости;
- риск повторить уже работающие механизмы хуже;
- усложнение обновлений upstream;
- собственная ответственность за OAuth, обновление токенов и особенности протоколов;
- лицензионные ограничения требуют отдельной проверки и не допускают слепого копирования;
- архитектурная ценность Kat9I находится прежде всего в `control-plane` — управляющем контуре, а не в повторной реализации транспортного шлюза исполнения.

### Условие для «раскопки»

Только отдельные модули после измеримого пробела и Architecture Tournament — архитектурного сравнения кандидатов. Предпочтительна поэтапная миграция через адаптер, а не fork/big-bang — форк и одномоментная полная замена.

## 5. Заменённый вариант D — постоянное соответствие `Worker → один account`

### Историческая идея

Каждому Worker или процессу проверки качества назначить собственный фиксированный AI-аккаунт.

### Почему заменено

Идентичность исполнителя и ресурс исполнения — разные сущности. Фиксированная привязка ухудшает балансировку квот, переключение при сбоях и масштабирование.

Более сильная гипотеза:

`execution_id → account_id → session_id → generation/lease`

То есть конкретное исполнение связывается с аккаунтом, сессией и поколением аренды. Antigravity Manager Account Pool — пул аккаунтов Manager — отвечает за выбор ресурса, а очередь Worker Kat9I — за порядок и правила работы.

### Условие для «раскопки»

Только если конкретный провайдер или аккаунт имеет доказанную обязанность идентичности/безопасности, несовместимую с динамическим планированием.

## 6. Заменённый вариант E — глобальный `current account` как главная сущность исполнения

### Историческая идея

Строить поток исполнения вокруг одного глобального «текущего аккаунта Antigravity».

### Почему заменено

Глобальный слот аккаунта — деталь интеграции, а не подходящий единый источник истины архитектуры исполнения. Он плохо моделирует несколько параллельных задач, повторные попытки, закрепление сессии и журналирование решений.

Если устаревшая версия Antigravity реально имеет один слот credentials — учётных данных, его лучше представлять как **ресурс с одним местом** под `lease/fencing generation` — аренду с поколением защиты от устаревшего владельца, сохраняя выше модель, ориентированную на конкретное исполнение.

### Условие для «раскопки»

Только как адаптер совместимости для старого поведения с одним слотом, не как общая архитектура Kat9I.

## 7. Отклонённый вариант F — глобальный system prompt Manager как второй SSoT

### Историческая идея

Помещать системные правила Kat9I непосредственно в `global system prompt` — глобальную системную инструкцию Manager — и считать её главным загрузочным контекстом для AI.

### Почему отклонено

Это создаёт скрытый второй SSoT — единый источник истины, плохо связываемый с точной ревизией задачи, контекста и Evidence — доказательствами. Изменение инструкции может менять поведение без прозрачной связи с GitHub-политикой и контекстом.

### Допустимый будущий вариант

Инъекция инструкции на транспортном уровне возможна только как производная от доверенных Context/Policy — контекста и политики — с fingerprint/provenance, то есть отпечатком и происхождением, и без самостоятельных полномочий.

## 8. Отложенный вариант G — копировать весь AG25 bootstrap как основу Kat9I

### Историческая идея

Перенести большую часть загрузчика AG25 целиком.

### Почему отложено

AG25 полезен как донор паттернов, но содержит много несвязанного объёма. Полное копирование создаёт лишнюю связанность и ненужные модули.

Полезные донорские идеи уже вынесены в исследовательский контур: единая точка входа, проверки-ворота, `Install/Status/Repair` — установка/статус/восстановление, повторяемость запуска, fail-closed — безопасная остановка при неопределённости, проверка контрольных сумм, переносимое состояние и машиночитаемые квитанции.

### Условие для «раскопки»

Конкретный модуль AG25 переносится только если Kat9I имеет совпадающее требование и перенос дешевле независимой минимальной реализации.

## 9. Заменённый вариант H — junction/copy hacks для состояния Antigravity Manager

### Историческая идея

Переносить состояние Manager через junction/symlink — перенаправление каталогов файловой системы — или повторное копирование каталогов при запуске.

### Почему заменено

Upstream поддерживает собственный каталог данных через `ABV_DATA_DIR`. Штатная точка расширения проще и меньше зависит от внутренней структуры каталогов.

### Условие для «раскопки»

Только если конкретная версия Manager перестаёт поддерживать требуемый пользовательский каталог данных или обнаруживается состояние, которое не следует этому контракту.

## 10. Отложенный вариант I — собственные model router / proxy orchestration / context compression в Kat9I v0

### Историческая идея

Встроить в ранний Kat9I `model router` — маршрутизатор моделей, `proxy orchestration` — управление прокси, собственную политику повторных попыток и `context compression` — сжатие контекста.

### Почему отложено

Эти механизмы уже частично или существенно доступны в Manager. Для Kat9I v0 они не определяют основную ценность управляющего контура и увеличивают объём загрузчика и среды исполнения.

### Условие для «раскопки»

Только по отдельным пробелам возможностей и с измеримыми требованиями: задержка, надёжность, переносимость между провайдерами, стоимость токенов или безопасность.

## 11. Ошибки интерпретации, которые не являются кандидатами на возврат

Следующие пункты не следует «раскапывать» как идеи:

- считать `AGY`, `Antigravity` и `Antigravity IDE` отдельными продуктами в архитектуре Kat9I; принята терминология `AGY = Antigravity`;

Они сохранены здесь только как обоснование, чтобы не повторять ту же ошибку при будущем анализе старых обсуждений.

## 12. Критерий возвращения любой идеи из этого архива

Ни один пункт выше не получает приоритет только потому, что он подробно описан.

Для возвращения требуется обычный жизненный цикл Graveyard:

`Graveyard DATA → ContextRef → GraveyardCandidate → сверка с текущим каноном → ActivationTicket → Human Approval → обычный workflow`

Здесь `ContextRef` — ссылка на источник контекста, `GraveyardCandidate` — кандидат на возврат идеи, `ActivationTicket` — точный билет предлагаемой активации, `Human Approval` — подтверждение человека, `workflow` — обычный рабочий процесс проекта.

Минимальная причина для повторного рассмотрения должна содержать новые Evidence — доказательства: функциональный пробел, пробел безопасности, регрессию upstream, измерение производительности, новое требование переносимости либо изменившийся архитектурный инвариант.

Без таких доказательств действует более простая текущая стратегия: **Kat9I владеет управляющим контуром; механизмы исполнения переиспользуются через минимальный адаптер там, где это безопасно и достаточно.**
