1. Назначение KAT9I_OS и базовая архитектура

Статус: принято.

Схема системы

KAT9I_OS — персональная агентная операционная система для управления задачами, правилами, контекстом, ИИ-исполнителями и результатами работы.

Пользователь
    ↓
Задача
    ↓
Личные + проектные + доменные правила
    ↓
Domain (домен — тип работы)
    ↓
Context + Resources (контекст + источники данных)
    ↓
Inference Router (маршрутизатор ИИ — выбор модели и провайдера)
    ↓
Coworker (распределённая работа агентов)
    ↓
Execution (исполнение задачи)
    ↓
Integrations / MCP (подключения к внешним системам)
    ↓
ResultRef (ссылка на результат)
    ↓
QA (независимая проверка качества)
    ↓
Завершённая задача + Evidence (доказательства выполнения)

Внешние источники и исполнители: GitHub, Google Drive, Obsidian, локальные файлы, ChatGPT, Antigravity, локальные ИИ, другие компьютеры, MCP-серверы.

1.1. Что такое KAT9I_OS

KAT9I_OS — не отдельный чат-бот и не просто система запуска агентов. Это единая управляющая среда, которая принимает задачу, определяет её тип, применяет правила, находит источники контекста, выбирает ИИ и исполнителя, выдаёт ограниченные права, контролирует выполнение, получает результат, организует независимую проверку и сохраняет доказательства выполнения.

Главная цель: управлять полным жизненным циклом задачи — от намерения пользователя до проверенного результата.

1.2. Архитектурный подход

KAT9I_OS строится как Modular Monolith (модульный монолит): один продукт, один канонический репозиторий, единые модели задач и правил, единая система проверок и строгие внутренние границы модулей.

Каждый модуль отвечает только за свою область: Suno знает музыкальную предметную область; Core (ядро) — системные правила; Coworker (распределённая работа) — кому поручить задачу; Execution (исполнение) — как физически её выполнить; Inference Router (маршрутизатор ИИ) — какой ИИ использовать; Resources (ресурсы) — где находятся исходные данные и результат.

1.3. Почему выбран модульный монолит

Текущие функции KAT и AG25 распределены между несколькими компонентами и репозиториями, что создаёт транспортные контракты, синхронизацию версий, дублирование моделей данных и сложные сквозные проверки. В KAT9I_OS полезные функции переносятся внутрь одного продукта, но распределяются по правильным модулям.

Существующая функцияМесто в KAT9I_OS
KAT Rule Manager (менеджер правил)Core — ядро управления
KAT Skills (навыки)Core / Skills — навыки
AG25 Mesh (сетка исполнителей)Coworker — распределённая работа
AG25 Worker Runtime (среда исполнения)Execution — исполнение
AG25 Sensitive Data (защита чувствительных данных)Security — безопасность
AG25 GitHubIntegrations / GitHub — подключение GitHub
AG25 SunoDomains / Suno — музыкальный домен
внешняя Knowledge Base (база знаний)Personal / Knowledge + внешние источники

AG25 и текущая KAT используются как доноры проверенных решений, но KAT9I_OS не должна быть механическим объединением двух старых структур.

1.4. Основные модули

МодульНазначениеГлавный вопрос
Core (ядро)Задачи, правила, навыки, политики, системные контракты.Какие правила действуют и что система должна сделать?
Context (контекст)Минимально необходимая информация и ссылки на источники.Что исполнителю действительно нужно знать?
Resources (ресурсы)Источники, документы, файлы, артефакты и ссылки на результаты.Где взять данные и куда записать результат?
Inference (выбор ИИ)LOW (низкий), NORMAL (обычный), HIGH (высокий), локальный/удалённый ИИ, подписка или API.Какой ИИ подходит этому этапу?
Coworker (распределённая работа)Локальные и удалённые исполнители, распределение, бронирование и передача задач.Кто должен выполнить работу?
Execution (исполнение)Процессы, Worker (исполнитель), Worktree (изолированная Git-копия), ветки, тайм-ауты, доказательства и очистка.Как физически выполнить работу?
Security (безопасность)Права, чувствительные данные, разрешённые области и временные разрешения.Что исполнителю разрешено делать?
Integrations (подключения)GitHub, Git, Google Drive, ChatGPT, Antigravity, Codex, локальные модели, MCP и другие сервисы.Как связаться с внешней системой?
Domains (домены)Issue, PR, QA, оптимизация репозитория, Suno, исследования, документы, инженерия, автоматизация.Что именно мы делаем?
Personal (личный слой)Knowledge (знания), Rules (правила), Preferences (предпочтения), Settings (настройки).Как система должна работать для владельца?
Telemetry (наблюдение)Фактическое выполнение, модели, попытки, ошибки, ресурсы и качество.Что произошло на самом деле?

1.5. Reference-first (сначала ссылка)

Если исполнитель может сам получить исходные данные через подключённый источник, KAT9I_OS передаёт ссылку на источник, а не копирует всё содержимое в контекст модели.
KAT9I_OS
    ↓
GitHub ContextRef (ссылка на источник)
    ↓
ChatGPT с GitHub Connector (подключением GitHub)
    ↓
работа
    ↓
PR / Pull Request (запрос на внесение изменений)
    ↓
ResultRef (ссылка на результат)
    ↓
KAT9I_OS

Это уменьшает передачу токенов и исходящий трафик, позволяет использовать уже оплаченные подписки, уменьшает дублирование данных и упрощает передачу результатов между агентами.

1.6. KAT9I_OS — Control Plane (управляющий слой), а не Data Bus (транспорт данных)

KAT9I_OS управляет задачами, правилами, исполнителями, ссылками, разрешениями, маршрутами, состоянием и проверками. Она не должна без необходимости транспортировать большие объёмы данных между ИИ.

Предпочтительно:
KAT9I_OS → ссылка на источник → исполнитель → ссылка на результат → KAT9I_OS

1.7. Внешние данные

Модульный монолит относится к управляющему программному коду, а не ко всем данным пользователя. GitHub-репозитории, Google Drive, Obsidian, личная база знаний, документы, ChatGPT, Antigravity, локальные модели, другие компьютеры и MCP-серверы могут оставаться внешними. KAT9I_OS подключается к ним через Connector (подключение), Adapter (адаптер) или MCP.

1.9. Основные архитектурные принципы

  1. KAT9I_OS — единый продукт и единый канонический репозиторий.
  2. Архитектура строится как Modular Monolith (модульный монолит).
  3. Каждый модуль имеет одну понятную область ответственности.
  4. Доменная логика не проникает в ядро и общий механизм исполнения.
  5. KAT9I_OS управляет работой, а не переносит большие данные без необходимости.
  6. Reference-first (сначала ссылка) используется по умолчанию.
  7. Контекст передаётся текстом только когда источник невозможно открыть напрямую.
  8. Один механизм исполнения используется всеми доменами.
  9. Личные знания не обязаны находиться в репозитории KAT9I_OS.
  10. LOW (низкий), NORMAL (обычный), HIGH (высокий) выбираются для отдельных этапов задачи.
  11. Локальные модели, подписочные веб-интерфейсы и API (программные интерфейсы) — равноправные маршруты выполнения.
  12. Безопасность и обязательные правила имеют приоритет над экономией ресурсов.
  13. QA (независимая проверка качества) отделяется от исполнителя там, где это требует политика.
  14. Результаты по возможности передаются через ResultRef (ссылку на результат).
  15. AG25 и существующая KAT — доноры проверенных решений, но новая архитектура не обязана сохранять их историческое разделение.

1.10. Цель первого этапа разработки

Первая версия KAT9I_OS должна доказать работу одного полного вертикального сценария:

GitHub Issue (задача)
    ↓
правила
    ↓
ContextRef (ссылка на контекст)
    ↓
выбор провайдера
    ↓
Coworker
    ↓
Worker (исполнитель)
    ↓
реальное изменение
    ↓
PR / Pull Request (запрос на внесение изменений)
    ↓
ResultRef (ссылка на результат)
    ↓
независимый QA (проверка качества)
    ↓
подтверждённое завершение

После доказательства этого пути архитектура масштабируется на другие домены, провайдеры и распределённых исполнителей.
